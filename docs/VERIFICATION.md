## 2026-10-14 rich 连续四条失败：busy 退避与清理期不碰界面

rich 任务 `jmv824y2468t6`（客户端 2026101404）连续四条失败，第 1、3 条各失败两次；失败条目全部是「每条视频的第一个片段」，紧随其后的第二条片段全部发布成功。失败原因一致：`上一条相册素材未清净：复查仍有 1 条相册记录；类型=video；恢复=3次；删除异常=rm:busy`。

两个独立缺陷叠加：

1. **busy 恢复只有约 5 秒。** 旧恢复循环固定 `[500,1500,3000]` 三次退避，之后直接判「未清净」。上一条已发布视频仍被持有句柄时 `rm -f` 报 `Text file busy`，句柄释放晚于这 5 秒，整条就被判失败。现场设备侧每条清理只花 21.9~23.8s，离 90s 总预算还远。
2. **清理期间点了界面。** 1403 起「清理相册」与「我→个人主页」导航并行；上一条视频可能正在个人主页/播放器里被解码，清理时点界面会把它继续拉住，句柄释放被推迟，`rm` 一直 busy。

修复：

- `clearAlbum` 的 busy 恢复改为**总预算内有界退避**：默认从 500ms 起、每次加 600ms、封顶 5s，只要预算没走完、未取消就继续，每轮以当前真实残留重试；预算走完仍清不掉就如实带回 busy 原因。判据不变——物理文件与媒体库四表复查都干净才放行，不假成功、不强停得物。
- 清理阶段**不发任何界面动作**：导航改到清理收敛后启动，与推送/索引重叠，进入发布入口前统一等待（`startNavigation` / `awaitNavigation`）。省时效果保留，清理期不再触碰 App。
- 云端摘要把**阶段成功**的瞬时异常标为「已恢复=」，不再与「失败=」混写——用户反复看到的 139 里有相当一部分是已恢复的回执。
- 回归可注入 `busyRetryDelays` / `busyRetryBudgetMs` 收紧恢复预算；生产不传，吃满 90 秒。

本机模拟器（MuMu / Android 12 / 127.0.0.1:16384）自有探针复现与验收：

| 场景 | 结果 |
|---|---|
| 进程持句柄期间 `rm -f`（`tools/busy-probe.js`） | `rm: ...: Text file busy`（rc=1） |
| 同一文件句柄释放后 `rm -f` | rc=0，文件消失 |
| 新逻辑面对 9 秒占用（`tools/busy-recovery-verify.js`） | 15.3s 收敛，恢复 3 次，物理文件与库记录均清净（8/8） |
| 旧逻辑面对 45 秒占用（临时反向对照，跑完已还原） | **复现 rich 原文**：`复查仍有 1 条相册记录；类型=video；恢复=3次；删除异常=rm:busy` |

反向对照确认改动是必需的：同样的占用现场，旧逻辑失败、新逻辑收敛。探针只用自带测试文件，跑完即清，未触碰用户素材，未强停得物。

**边界**：本机模拟器不等于 rich 实机。rich 上的验收仍需用该设备实跑未发布条目，核对清理阶段不再出现 `rm:busy`、跨条目是否继续。在 rich 验证完成前，不宣称远端 P0 已关闭。

## 2026-10-15 相册清理真因修复 / 2026101503（本轮）

rich 连续多条失败的**真因**不是「等得不够久」，而是删不掉时**跳过了删记录**：`clearAlbum` 的 `removeOne` 里 `rm` 报 `Text file busy` 就当场 `return`，后面的 `content delete` 从未执行 ⇒ 库记录留在 MediaStore、文件留在磁盘，下一轮再忙、再 return。1405 只是把这个死循环多跑了几遍，所以「5 秒和 90 秒没有区别」。1307 那版连发成功不是因为处理了占用，而是那几天**没撞上占用**。

本机 MuMu（127.0.0.1:16384 / Android 12）对照实验（全部可复算）：

- 文件被句柄占住：`rm -f` ❌ `Text file busy`；`mv <目录> <.目录>` ❌ `Operation not permitted`；`touch <目录>/.nomedia` ✅ 成功；`content delete` ✅ 成功。
- 无 `.nomedia` 时 `scan_volume` 必复活（`_id` 变号）；有 `.nomedia` 时重复扫不复活；把 `.nomedia` 删掉再扫立刻复活。
- 因此「相册里有没有它」的判据是**索引为空且重扫不复活**，不是「磁盘文件删掉了没有」。

修复内容：

- `removeOne`：`rm` 失败不再 `return`，改为记录原因 + 给**文件所在目录**写 `.nomedia`（写入后 `[ -f ]` 回读确认）+ 记待回收清单，然后**无论如何**执行 `content delete`；删索引的边界是 `physical.ok || iso.ok`。隔离没确认时保留记录并如实报 `ALBUM_ISOLATION_FAILED`。
- 防误伤：素材落地区及其上层（`Movies/BlueV`、`Movies`、`DCIM`、`/storage/emulated/0`）**禁止**写 `.nomedia` —— 实测写根目录会把本条新素材一起隐藏（`scan_file` 只回 `file/993`）。命中时如实停批。
- 跨条回收：进程内存登记隔离目录（不再发设备遍历命令，rich 的目录命令本身就是历史故障点）；回收**只删清单里记着的路径**，绝不遍历目录删；顺序固定「先删文件、再撤标记」，撤不掉就继续隔离。
- **139 + 占用同时出现**（rich 的长期现象）：删记录回 139 空输出、文件又被占住时，旧收尾只看「物理文件在不在」⇒ 隔离明明已确认也停批。现在先看隔离：**已确认隔离且该文件确属我们观测到占用而进入待回收**时放行（物理文件如实记待回收）；隔离没确认、或 `rm` 回执谎报成功导致文件其实还在时，照旧拦住 —— 不放宽「不以空库伪装清理成功」。
