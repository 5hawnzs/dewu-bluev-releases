# 得物蓝V素材发布工具 — 双通道自动更新方案

> **要的效果**：推代码 → 测试版自动出新版；测试版验收通过后，在测试版里点一下 → 正式版才出新版。
> **本文只做方案，不改任何一行代码。** 标注 `[实测]` 的是我在这台机器上跑出来的，`[官方]` 是 electron-builder 文档原文，`[待确认]` 是我没法在当前环境验证、需要你或后续实测补上的。

---

## 0. 结论先行

**能实现。** 但它不是打开一个开关，是补齐 4 个部件 —— 其中 2 个是当前项目完全没有的**基础设施**：一个**更新源**、一台**打包机**。

同时有 3 个必须提前接受的代价：

| # | 代价 | 依据 |
|---|---|---|
| 1 | **便携版这条路走不通** —— 自动更新只能给**安装版（NSIS）**做 | `[官方]` Windows 上支持自动更新的 target **只有 NSIS**，`portable` 不在列表里 |
| 2 | **需要一台 Windows 打包机常驻** | 打包必须在 Windows 上（项目依赖 `sharp` 原生模块 + `addon:win` 脚本），且要"推了代码就自动跑" |
| 3 | **需要能匿名下载的更新源** | 当前仓库在 **Gitee 私有仓库**，私有仓库的发行版附件默认需要凭据才能下载 ⇒ token 会被打进客户端 `[待确认]` |

## 1. 先回答：为啥有便携版？

**诚实说：仓库里没有留下理由。** 我查了四处：

- `package.json` 的 `win.target` 同时配了 `nsis` + `portable` —— 便携版是 **2026-09-30 15:33 首次提交（`4622e1a`）就带的**，不是后来补的；
- `README.md` 只有一句「`…-1.0.0-x64-便携版.exe` — 免安装版」；
- `docs/HANDOFF.md` / `docs/WINDOWS-E2E.md` 都没有说明为什么要它；
- 历史对话检索也没有相关记录。

所以只能从"它解决什么问题"来倒推它当初的价值：

| 对比项 | 便携版 portable | 安装版 nsis（当前**也已产出**） |
|---|---|---|
| 安装方式 | 免安装，双击即用 | 走安装向导 |
| 程序释放位置 | **每次启动自解压到临时目录** `[实测]`：`%LOCALAPPDATA%\Temp\3K4mTr4OUHvjAjVRgBjQQYk2FPO` | 固定装在 `%LOCALAPPDATA%\Programs\...` |
| 卸载 | 删文件即可、不留痕 | 走卸载程序 |
| 体积 | 88,672,906 B | 88,807,540 B `[实测]` |
| 增量更新包 | 无 `.blockmap` | **有** `.blockmap`（93,420 B）`[实测]` |
| **自动更新** | **不支持** `[官方]` | **支持** `[官方]` |
| 更适合 | 不想装软件的机器、U 盘带走 | 长期使用、要自动更新 |

⇒ 便携版的价值就是「免安装」。代价是**每次启动都自解压一遍**（启动更慢），而且**升级只能手动换文件**。
你现在双击在用的那个（12:46 打开的）就是便携版。

**它与本次需求的冲突**：自动更新 ≈ 安装版专属能力。要做双通道自动更新，主用版本就得从便携版**换成 nsis 安装版**。便携版可以继续留着，但它永远得手动换包。

## 2. 目标流程

```
        ┌─────────────────────────────────────────────────────────┐
        │  你：把代码推到 beta 分支                                  │
        └───────────────────────┬─────────────────────────────────┘
                                ↓  （自动：打包机检测到新提交）
                     [ git pull → 回归 294 项 → npm run dist:win ]
                                ↓  上传 exe + latest.yml + blockmap
        ┌─────────────────────────────────────────────────────────┐
        │  beta 源（更新服务器上的 beta 目录）                        │
        └───────────────────────┬─────────────────────────────────┘
                                ↓  测试版应用启动 / 定时自检
        ┌─────────────────────────────────────────────────────────┐
        │  测试版应用自动更新到新版本 → 你验收                        │
        └───────────────────────┬─────────────────────────────────┘
                                ↓  你点测试版里的「发布正式版」按钮
                     [ promote：同一 commit 打 stable 包 → 上传 ]
                                ↓
        ┌─────────────────────────────────────────────────────────┐
        │  stable 源（更新服务器上的正式目录）                        │
        └───────────────────────┬─────────────────────────────────┘
                                ↓
        ┌─────────────────────────────────────────────────────────┐
        │  正式版应用自动更新到新版本                                 │
        └─────────────────────────────────────────────────────────┘
```

关键点：**测试版和正式版是两条完全隔离的更新通道**，靠**不同的更新源地址**区分 —— 不是靠一个开关。

## 3. 三个必须先做的决策

### 决策 1 ｜更新源放哪

electron-builder 的 `generic` 提供者就是「一个能放文件的 HTTP(S) 静态目录」 `[官方：generic 需要你手动上传，builder 不会代传]`。

| 选项 | 匿名可下载 | 成本 | 说明 |
|---|---|---|---|
| **A. 对象存储**（腾讯云 COS / 阿里云 OSS） | 可设「公有读、私有写」 | 存储 + 流量，88 MB × N 个版本，**几块钱量级** | **推荐**。国内快、支持 HTTPS、可挂自有域名、密钥只放打包机（**七牛不要选** —— 免费额度绑的测试域名**明文禁止下载 exe**，理由见 §8） |
| **B. 自建静态目录**（nginx / `python -m http.server`，挂在一台有公网或内网可达的机器） | 可以 | 需要一台常驻机器 | 最简单，适合"大家本来就在同一内网" |
| **C. Gitee 发行版** | **私有仓库要凭据** `[待确认]` | 免费 | 客户端必须带 token 才能拉更新 ⇒ 不推荐 |
| D. GitHub Releases（公开仓库） | 可以 | 免费 | 国内下载慢，且仓库在 Gitee |

**generic 源上需要放的文件**（`[官方]` 需要手动上传）：

```
<源根>/
├── latest.yml                     ← 正式通道的版本清单
├── 得物蓝V素材发布工具-1.0.1-x64-win.exe
├── 得物蓝V素材发布工具-1.0.1-x64-win.exe.blockmap   ← 增量更新用，能大幅省流量
├── beta.yml                       ← 测试通道的版本清单
├── 得物蓝V素材发布工具-1.0.1-beta-x64-win.exe
└── 得物蓝V素材发布工具-1.0.1-beta-x64-win.exe.blockmap
```

> `.blockmap` 是现成的 —— 当前 `dist/` 里已经产出了 `[实测]`，意味着**增量更新开箱可用**：88 MB 的包，升级时通常只需下几 MB 的差异块。

---

### 决策 2 ｜打包在哪跑

**硬约束**：打 Windows 包的机器必须是 Windows。项目还依赖 `sharp` 的原生二进制（`npm run addon:win` 专门装 win32-x64 版），跨平台构建基本不用考虑。

| 选项 | 怎么做 | 成本 | 备注 |
|---|---|---|---|
| **A. 本机 watcher（推荐起步）** | 在现在这台 Windows 上跑一个常驻小服务：轮询 beta 分支（或接 Gitee Webhook），有新提交就 `git pull && npm ci && 回归 && dist:win && 上传` | 0 元，**机器要常开** | 最容易落地，出问题也好查 |
| B. Gitee Go 自建 Windows 执行器 | 把这台机器注册成 Gitee Go 的 Windows runner，由平台编排 | 0 元 | 配置更复杂，收益是流水线可视化 |
| C. Gitee Go 托管 Windows runner | 直接用平台提供的 | **`[待确认]`** | Gitee Go 免费额度有限；Windows 环境通常需要**自建执行器**（我搜到的资料自相矛盾，没有权威确认） |
| D. 手动 + 一条命令 | `npm run release:beta` 一把梭（拉代码 / 打包 / 上传） | **最省事** | 没有"推了就跑"，但见 §7 我的建议 |

---

### 决策 3 ｜测试版 / 正式版怎么区分

**官方机制** `[官方]`：打包时会自动生成 `resources/app-update.yml`（**编译进包**，不需要也不能自己 `setFeedURL`），里面写死 publish 配置；electron-updater 用 `channel` 决定读哪个清单 —— 默认读 `latest.yml`，把 channel 设成 `beta` 就读 `beta.yml`。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **甲：同 commit 打两次包（推荐）** | beta 包 `publish.url` 指 beta 源；stable 包指 stable 源 | 两条通道彻底隔离、行为可预测 | promote 时要重新打包（几分钟） |
| 乙：一个包、运行时切通道 | 包里同时写两个源地址，按 `autoUpdater.channel` 运行时选 | promote 秒级完成 | 官方不推荐 `setFeedURL`；通道逻辑在客户端，容易被改 |

**★ 关于「测的」和「发的」是不是同一个二进制**：甲方案下正式版是**重新打的包**（代码完全一样，只有 `app-update.yml` 里的源地址不同）。如果你希望严格"测的就是发的"，有一个更优做法：`app-update.yml` 位于 asar **外面**（`resources/` 目录），理论上可以**不重新编译、只换这个 yml + 重算 sha512、重生成 latest.yml**。
⚠️ 但 nsis 安装包本身是自解压可执行文件，直接改包内文件需要解包重压 —— **`[待确认]`：需要实现时实测这条路走不走得通**。走不通就退回"重新打包"（代码相同，风险很低）。

## 4. 「点一下发正式版」怎么落地

| 选项 | 机制 | 凭据放哪 | 风险 |
|---|---|---|---|
| **a. 客户端调本机/内网小服务（推荐）** | 测试版按钮 → HTTP 调打包机上的小服务 → 服务执行 promote | **客户端零凭据** | 小服务要暴露端口，需加一个简单口令 |
| b. 客户端直调 Gitee API | 按钮 → Gitee OpenAPI 建 tag / 传附件 | **token 打进客户端** | token 泄漏；且仍然需要打包机干活 |
| c. 客户端写"发布请求"、打包机轮询 | 按钮 → 在更新源写一个 `PROMOTE` 标记 → 打包机轮询到就 promote | **客户端零凭据** | 有轮询延迟（几十秒） |

⇒ **推荐 a**。如果测试版应用和打包机就是同一台机器，这个服务可以只监听 `127.0.0.1`，连鉴权都省了。

## 5. 分阶段落地（每阶段都有验收标准）

| 阶段 | 内容 | 验收标准（可复算） |
|---|---|---|
| **0. 确认资源（0.5h）** | 确定更新源、确定打包机 | 能往源上传一个文件、并用 `curl` 匿名下载回来 |
| **1. 正式通道打通自动更新（0.5～1 天）** | 加 `build.publish`（generic）、加 `electron-updater`、启动时自检；打 nsis 包上传 | 装 1.0.0 → 把源上换成 1.0.1 → 应用重启后**实测变成 1.0.1** |
| **2. 加 beta 通道（0.5 天）** | 增 `beta` 通道包（源地址不同、`channel=beta`）；加 `release:beta` / `release:stable` 脚本 | beta 包**只**跟随 beta 源；stable 包**只**跟随 stable 源（互相串不到） |
| **3. promote 按钮（1 天）** | 测试版 UI 加按钮 + 打包机小服务 | 点按钮 → stable 源出现新版本 → 正式版应用收到更新 |
| **4.（可选）"推代码自动触发"** | Webhook / 轮询 / CI | 推 beta 分支后无人值守产出新版 |

## 6. 风险与代价清单

1. **现有便携版用户收不到更新** —— 你（以及任何用便携版的人）必须**手动装一次 nsis 包**，之后才进入自动更新通道。
2. **没有代码签名** —— 首次安装会有 SmartScreen 警告（"更多信息 → 仍要运行"）。`[待确认]`：electron-updater 在 Windows 上会对未签名包做何处理（内部工具通常可过，但需要在阶段 1 实测确认）。
3. **自动重启会打断正在跑的发布任务** —— 这个工具可能在跑批量发布，**被静默重启会很糟**。必须定策略：默认「下载好、等退出时安装」（`autoInstallEvent="onQuit"`，v27 才有；当前 electron-builder 是 24.x，行为是"下载后提示，用户点才装"）。**建议保持"用户手动点安装"**，不要静默重启。
4. **88 MB × 每个版本** —— 有 `.blockmap` 能省绝大部分流量（只下差异块）。
5. **打包机独占冲突** —— 这台机器上**现在就有另一条会话在改同一个仓库**。"推了就自动打包"可能打到**半成品**。必须约定：只有特定分支/带 tag 的提交才触发；且打包前**必须过回归 294 项**。
6. **凭据管理** —— 对象存储密钥只放在打包机上，**不进仓库、不进客户端**。
7. **版本号必须手动涨** —— `artifactName` 含 `${version}`，不涨版本号会**同名覆盖**，还会让客户端误判"没有新版本"（electron-updater 按版本号比较）。

## 7. 我的建议

**如果只做一件事：先做阶段 1。**

它本身就是全部价值的主体（"改了代码 → 用户自动拿到新版"），做完立刻解决你现在的痛点 —— 每次改完不用手动传 exe。而且阶段 1 不依赖 CI、不依赖按钮、不依赖 promote，风险最小。

**"推代码自动触发"建议放到最后，甚至先不做。** 它的收益是"省一条命令"，成本是一台常驻机器 + 凭据管理 + 并发冲突风险。看 git log，这个项目两天 9 次提交，但不是每次都要发版 —— **每周几次的频率下，一条 `npm run release:beta` 就够了**，比维护一套常驻流水线划算得多。

**顺序应该是**：阶段 1（自动更新能用）→ 阶段 3（promote 按钮，因为它是你明确要的）→ 阶段 2（beta 通道）→ 阶段 4（自动触发，可选）。

> 注：阶段 3 的按钮依赖阶段 2 的 beta 通道，所以实际上是 1 → 2 → 3。这里只是强调**阶段 4 优先级最低**。

## 8. 已确认的前提（2026-10-01 16:33；16:45 更新）

| 问题 | 答复 | 对方案的影响 |
|---|---|---|
| **测试版**给谁用 | 只有你 | 测试通道只服务你自己，做得糙一点无所谓 |
| **正式版**给谁用 | **会装到别的电脑，不止你一台**（16:40 更正） | ⚠️ 我上一版把这条误记成「只有你一个人在用」，已改。正式版要分发出去 ⇒ 后面几条结论跟着改，见「修正」小节 |
| 有没有对象存储账号 | **没有**（16:40） | 不是障碍（现开一个即可），但选哪个差别很大，见「可选方案」 |
| **更新源定案** | **腾讯云 COS**（16:43 你选定） | ⇒ 阶段 1 具体改动清单见 §9 |
| 正式版用的人数 | **约 10 人**（16:43） | ⇒ 见 §9.4 的三条新增注意点 |
| 打包机 | **就用现在这台，能保证常开** | 阶段 1~3 都不需要额外机器；「Gitee Go 托管 runner」那条路可以直接划掉 |
| 后续换机器 | 你问「能否换」 | **能**，见下 |
| **部署范围** | **会装到别的网络**（16:36 确认） | ⇒ **本机更新源不成立**，更新源必须能被公网访问；见下 |

### ★ 一个必须先说清的硬约束：产物里含全部源码

我解包看过 `app.asar`：`src/` 下的 JS **是明文**（asar 是打包格式，**不是加密**）。也就是说，**88 MB 的 exe 里带着整个项目的源码**。

⇒ **更新源绝对不能是「任何人拿到网址就能下载」的地方。** 这直接排除了几个看起来很香的免费方案：Gitee 公开仓库的发行版、GitHub Releases、公开的对象存储 bucket。

⇒ 只剩两类：**私有读 + 客户端带 token**，或 **本机 / 内网**。

### 已确认部署范围：**跨网络**（2026-10-01 16:36）

⇒ **本机方案不成立。** `127.0.0.1` 的含义是「本机自己」，装在**别的网络**里的应用去访问它，只会找到它自己那台机器。更新源必须**能被公网访问**。

⇒ 于是「选更新源」变成一个必须真做的选型。

### 修正一条我先前说重了的话（2026-10-01 16:42）

上一版我把「更新源绝对不能是任何人拿到网址就能下载的地方」写成了硬约束，理由是 exe 里的源码是明文。**但既然正式版会装到别人的电脑上，源码本来就随包发出去了** —— 每个装过的人手里都有一份。所以：

- 「更新源保密」真正能防的，是**「摸到网址但没拿到安装包的人」也能下载安装包**；它管的是**「谁能装」**，不是「保护源码」。
- ⇒ 要不要**真鉴权**，取决于你**介不介意不知道从哪儿摸到网址的人也能装这个工具**。
  不介意 ⇒ 公开读最省事；介意 ⇒ 上 token。

### 可选方案（核过事实后重排）

你说**没有对象存储账号** —— 这不是障碍（现开一个就行），但选哪个差别很大。我核了几条硬事实，先把一个看起来最香的划掉：

| 选项 | 开通门槛 | 成本 | 能匿名下 exe | 鉴权 |
|---|---|---|---|---|
| **1. 腾讯云 COS**（推荐） | 注册 + 实名；**不要域名、不要备案、不用绑卡** | 新用户 50GB 免费 6 个月；之后存储 ≈0.12 元/GB/月、下行流量 ≈0.5 元/GB ⇒ **一年几块钱** | ✅ | 公开读 ⇒ 靠 URL 保密 |
| **2. Cloudflare R2** | 注册 + **必须绑一张卡**（银联也行，免费额度内不扣费） | **0 元**：10GB 存储/月 + **出站流量全免** | ✅ | `r2.dev` 公共域名 = 公开；要鉴权需自有域名 + Access |
| ~~3. 七牛云~~（划掉） | —— | 号称 10GB **永久**免费 | ❌ **明文禁止下 exe** | —— |
| **4. 云服务器 + nginx + 固定 token** | 买服务器 | ~60–100 元/年 | ✅ | **真鉴权**，token 可换 |

> **七牛为什么被划掉** `[官方]`：七牛的免费额度绑的是**测试域名**，而七牛明确写着 ——
> **自 2020-02-14 起，所有测试域名禁止下载应用程序（apk / ipa / exe / dmg 等）**。
> 想用它就得绑**自有域名**；绑国内 CDN 又必须 **ICP 备案**（要域名 + 大陆服务器 + 10~20 天审核）。
> 为省几十块钱走这条路，不划算。

> **1 / 2 / 4 都能被 electron-updater 正常驱动。** 差别只在：花多少钱、谁来运维、要不要真鉴权。
> `[官方]` 文档明确支持为 publish 传入额外配置、**包括自定义请求头** —— 这是选项 4 能成立的基础。

**我的倾向**：**选项 1（腾讯云 COS）** —— 门槛最低（不用域名、不用备案、不用绑卡）、国内速度快、一年几块钱。
一分钱都不想花 ⇒ **选项 2（R2）**，代价是国内速度一般 + 要绑一张卡。
真正需要"能一键换钥匙" ⇒ **选项 4**。

⚠️ 三个选项共同的硬要求：**版本号每次必须手动涨**。`artifactName` 含 `${version}`，不涨会同名覆盖，而且 electron-updater 按版本号比较，客户端会直接判定「没有新版本」。
⚠️ 还有一个共同的坑：**换更新源地址（或是 token）= 已装的客户端全部失联**，因为它们手里的地址是**编译进包**的。所以"换钥匙"这类操作，实质等于**重新发一遍包**，1 / 2 / 4 都一样。

### 换打包机（回答你的第 3 问）

**能换，而且不影响任何已安装的应用** —— 因为应用只认「更新源网址」，不认打包机。

打包机本身是**无状态**的，只干三件事：拉代码 → 打包 → 上传。换机器需要：

1. 新机器装 Node，在仓库里跑一次 `npm ci`；
2. 拷过去**一个配置文件**（更新源地址 + 上传凭据）—— 我会把这些集中成单个 `.env`，换机器就是拷这一个文件；
3. 若用的是 Gitee Go **自建执行器**，token 与机器绑定，需重新注册生成（用本机 watcher 脚本则没有这一步）。

### 9.3 版本号策略（必须定，否则会静默失效）

`artifactName` 含 `${version}` ⇒ **不涨版本号就同名覆盖**；而且 electron-updater **按版本号比较**，不涨会被判定「没有新版本」。

- 正式：`1.0.1`、`1.0.2` …（三段式递增）
- 测试：`1.0.2-beta.1`、`1.0.2-beta.2` …（预发布段，与 `channel=beta` 的 `beta.yml` 配套）

### 9.4 10 个人规模带来的 3 条新增注意点

1. **不要静默重启** —— 10 台机器上都可能挂着批量发布任务，被自动重启会很糟。保持「下载好 → 用户自己点安装」。
2. **正式版推出去 = 10 个人同时收到** ⇒ 你在测试版上按的那个确认键，比人少的时候更值钱，别跳过。
3. **「谁能装」其实不重要，「谁能用」才重要** —— 现在每台机器各自一个本地账号库、出厂口令都是 `admin / BlueV@2026`。
   10 个人共用同一个 admin ⇒ 出了事分不清是谁、按品牌统计也分不清人。
   这和**品牌权限**是同一件事（另一条会话在做），建议在阶段 3 之前一并定下来。

### 9.5 验收标准（可复算）

| 阶段 | 验收 |
|---|---|
| **0** | 桶里放一个 exe，`curl` 匿名拉回来，字节数一致 |
| **1** | 装 1.0.0 → 源上升级到 1.0.1 → 应用重启后**版本号真的变成 1.0.1** |

| **3** | 测试版点确认 → stable 源出现新版本 → 正式版客户端收到更新 |
