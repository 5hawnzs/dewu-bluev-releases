## 四、必须知道的 4 个坑（都会让人误判）

### 坑 1 · 成功率 KPI 被「模拟成功」和探针拖低了
看板的 `成功率 = 发布成功 / 全部行`，而分母里混着 **88 条「模拟成功」+ 1 条探针**：
现在显示 **121/366 ≈ 33%**，**这不是真实成功率**（真实口径应是 121/(121+156) ≈ 44%，且模拟数据本不该算）。
→ 建议改口径：把 `模拟成功`、`探针` 排除出 KPI 分母。

### 坑 2 · 同一台电脑在看板上变成了「两台」
`m_ce61ca24` 和 `m_fb6e1a86` 的**机器名完全一样**（都叫 WIN-6H81015PUR6）。
原因：`machine_id` 只在首次同步时生成并写进 `config.json`；**重装 App / 清掉配置就会换一个新 id**。
→ 看板的「按机器」汇总会把同一台机器拆成两行。建议：让 machineId 与机器名脱钩前先做一次合并/归一。

### 坑 3 · 看板地址是「云沙箱」，不是长期服务器
这是临时沙箱托管，**能活多久没有保证**。好消息是产物就是纯静态两个文件
（`index.html` + `vendor/supabase.js`），**可以整体搬走**到任意静态托管或对象存储。
→ 如果你要长期依赖，建议尽快搬到一个稳态地址。

### 坑 4 · 拿到链接的人都能看
数据库对 anon 只给 `select`（读），且 `using (true)` —— **没有访问控制**。
（写入倒是收口了：只有 `org='bluev'` 能写，且不能改、不能删。）
→ 不想公开就得上登录（Supabase Auth）或服务端代理；静态页上加口令挡不住人。
