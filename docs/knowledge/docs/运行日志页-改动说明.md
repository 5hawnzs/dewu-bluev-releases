# 左侧新增「运行日志」页 —— 改动说明

> 日期：2026-10-02 凌晨 · 仓库 `D:\work\dewu-bluev-publisher`
> 对应你的原话：**「在 app 左侧的执行中，新增运行日志这一模块，同步 app 下端的日志，且这个部分支持导出。」**

## 一句话

左侧「执行」组里多了一页 **运行日志**（第 10 个页签）。它和最下面那条日志栏**是同一份数据**
（不是复制一份、也不会各走各的），多出来的只有两件事：**能筛**、**能导出**。

---

## 1. 你会在哪儿看到它

```
左侧栏
 ├ 生产
 │   ├ 素材整理
 │   ├ 合规检查
 │   ├ 文案生成
 │   ├ 货号颜色校验
 │   └ 发布单
 ├ 执行
 │   ├ 模拟器发布
 │   └ 运行日志        ← 新增（角标：有错误就显示「N 错」，否则显示「N 条」）
 └ 其他
     ├ 设置
     ├ 品牌统计
     └ 品牌与权限
```

打开后是这样：

- 一条**筛选行**：级别下拉（全部 / 信息 / 成功 / 警告 / 错误）+ 关键字输入框 + 清空 + 导出；
- 一块**日志区**：内容和底部日志栏逐行一致（时间 + 分级配色），只是更长（一屏能看 400px 高）；
- 一块**导出区**：导出按钮 + 「打开文件」「打开所在文件夹」（导出过一次之后才出现）。

## 2. 「同步」是怎么保证的（这是需求里最关键的一条）

日志**只有一份数据**：渲染层内存里的 `state.logs`。底部日志栏和这一页读的是**同一个数组**、
走**同一个渲染函数**，而且三个方向都统一走同一个入口：

| 动作 | 函数 | 两处都更新？ |
|---|---|---|
| 新来一条日志（主进程推送） | `pushLog()` | ✅ 底部 + 页内 |
| 重绘（登录后拉历史 / 切页） | `renderLogs()` | ✅ 底部 + 页内 |
| 清空 | `clearLogs()` | ✅ 底部 + 页内 |

★ 内存里留 **500** 条（提到和主进程 `logbus` 的环形缓冲一致；原来渲染层只留 300），
底部日志栏的 DOM 仍限 300 行（行数多了会拖慢整页重排）。

★ **筛选只作用于这一页**，底部日志栏永远是全量 —— 它就是「刚才发生了什么」，不该被筛掉。

## 3. 导出：一次给两个文件，落在**输出目录**

和合规报告、品牌统计同一个地方（设置页里那个「输出目录」）：

| 文件 | 给谁看 | 内容 |
|---|---|---|
| `运行日志_20261002-023145.log` | 给人看 | 每行 **`2026-10-02 02:31:45 [错误] …`** —— 带完整日期时间与中文等级 |
| `运行日志_20261002-023145.jsonl` | 给脚本 / 同事再分析 | 一行一条 JSON，含 `level` / `levelText` / `msg` / `meta`（批次线索在这里） |

`.log` 的开头是一段**文件头**，长这样：

```
运行日志导出
导出时间：2026-10-02 02:31:45
应用版本：1.0.1
筛选条件：级别=错误 · 关键字=ENG-ERR
本次导出：1 条
内存缓冲区：共 137 条（两者不一致 = 上面那条筛选条件筛掉了一部分）
分等级：信息 120 · 成功 9 · 警告 5 · 错误 3
------------------------------------------------------------
2026-10-02 02:31:12 [错误] 第 7 条发布失败：找不到「发布」按钮
```

★ **导出的就是屏幕上那些**：你筛完了再导，导出的就是筛下来的那一批。
所以文件头特意把 **「本次导出 N 条」** 和 **「内存缓冲区共 M 条」** 分开写 ——
只写一个，过几天回头看到「怎么只有 3 条」，会以为日志丢了。两个数不一样就说明是筛过的。

★ 文件名带**秒**（别的导出只到分钟）。日志是排障时会**反复导**的东西 ——
精确到分钟的话，复现完再导一次会**悄悄覆盖**掉上一次，正好把要留的那份弄丢。

## 4. 怎么用（三步）

1. 跑到出问题为止（或复现出来）；
2. 左侧「执行 → 运行日志」→ 级别选「错误」（或关键字里打上货号 / 批次名）；
3. 点「导出日志」→ 点「打开所在文件夹」→ 把 `.log` 发出来。

## 6. 边界（说清楚，不含糊）

- **本轮没有发版**。这些是代码，**下一个版本才会带上**。
- 导出的是**内存里那 500 条**（和底部日志栏同一份），**不是**磁盘上的全部历史。
  要看长期历史有两个现成的：品牌统计页的「执行日志」（落盘在 `输出目录/run-log.jsonl`，任务级流水、
  按品牌可查），以及发布单页的「重导出日志」（逐条发布结果）。
- 「清空」清的是**界面这份缓存**；主进程还留着最近 500 条，重新登录会再拉回来 ——
  所以提示语里写明了，不写就会出现「我明明清过了怎么又回来了」这种误会。
- 日志内容仍是**版本号 / 通道名 / 业务动作 / 报错**这些，**不含**素材与 SKU 的额外信息；
  导出的文件落在你自己的输出目录，**不会上传到任何地方**。

## 7. 顺带发现的两件事（都不是 bug，但值得记住）

1. **「只在底部清、不清页内」这种破坏测不出来。** 我原本准备了这么一条定点破坏，结果测试全绿 ——
   查下来是：清空的处理函数随后会 `renderAll()` 整页重画，页内**自然就变空了**。
   也就是说这种"缺陷"用户根本看不出差别，**不该算缺陷**；真正会露出来的是「角标不刷新」
   （`renderAll` 不碰侧栏角标），改成这个才红。断言不是没在查东西，是我破坏错了地方。
2. **「切页时两边逐行一致」抓不到「推送漏同步」。** 切页会触发整体重绘一次，
   就算 `pushLog` 忘了同步页内，切过去看着也是对的。真正能抓住它的是
   「**页面开着的时候新来的日志两处同时长出来**」那一条 —— 这条才是「同步」的真守门人。
