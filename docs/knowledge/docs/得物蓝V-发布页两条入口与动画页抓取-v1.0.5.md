# 得物发布页：两条入口路线实测 + 动画页备用抓取通道

> 2026-10-02 深夜 · 已发布 **v1.0.5** · 分支 `main` @ `6c3d56a`

你这轮问的是「你给的这条发布路径（我的 → 主页 → 发布新动态）会不会更好用」。我没靠推理答，
**连上模拟器把两条路逐跳走了一遍**，然后按实测结论改的代码。

## 1. 结论：你给的这条确实更好用，已改成默认

两条路**都通向同一个发布页**（`media.publish.activity.TotalPublishProcessActivity`），但稳定性不一样：

| | 路线① 动态流右上角相机 | 路线② **你给的**：「我」→「主页」→「发布新动态」 |
| --- | --- | --- |
| 跳数 | **1 跳** | 3 跳 |
| 入口控件 | `com.shizhuang.duapp:id/ivCamera` | `com.shizhuang.duapp:id/rlPublish`（可点容器） |
| **有没有文字** | ★ **没有** —— `text` 与 `content-desc` 都是空的，只能按 id 点 | ★ **有** —— 文字就是「发布新动态」，**id + 文字双保险** |
| 起点 | 只在「动态」tab 上才出现 | 固定底部导航 `tab_user`，**不依赖内容流** |
| 结论 | 留作备用 | ★ **推荐（已设为默认）** |

**为什么「有文字」这么重要**：得物一改版，`resource-id` 可能变，但按钮上的字通常不变。
按文字点（`tapText`）比按 id 点（`tapId`）更能扛改版。你这条入口两样都有 —— 所以我把它设成首选，
另一条（相机图标）的 id 留在提示里当备胎。

实测链路（每一步都真点过、真读过后台窗口名）：

```
HomeActivity（我 tab）
  → 点 tvGoHomePage「主页」(838,149)
  → PersonalActivity
  → 点 rlPublish「发布新动态」(121,925)
  → TotalPublishProcessActivity ✅ 到发布页了
```

代码落点：`uimap.DEWU.route` 记下这三步；`uimap.suggest()` 改为**优先用这条**；
「抓取页面结构」生成的候选表第一步现在直接是 `{"action":"tapText","value":"发布新动态"}`。

★ 顺手修了一个我自己造成的不一致：**视频那套（`videoSteps`）的第一步还停留在老路线**。
你说过图文和视频的发布位置一样，但代码里只有图文那一侧改成了新路线 ⇒ 等于「视频复用图文」只对了一半。
现在两套首步**强制一致**，并且加了一条断言专门盯着它。

## 2. 更要紧的发现：发布页首屏**根本抓不下来**

这是这轮最有价值的一条 —— 而且**它直接决定你能不能配出定位表**。

按原设计，「抓取页面结构」是靠 `uiautomator dump`。但我在真机上发现：
发布页首屏是**持续动画页**（相册预览在轮播），`uiautomator dump` 要等窗口 idle，
**而它永远等不到**。我用各种办法试过，全部失败：

| 尝试 | 结果 |
| --- | --- |
| 连试十几次（每次间隔 2~3 秒） | ❌ 全部 `ERROR: could not get idle state.` |
| `uiautomator dump --compressed` | ❌ 同样 |
| 临时把系统动画全关（`animator_duration_scale=0`） | ❌ 同样 |
| 静置 15 秒再试 | ❌ 同样 |

**如果不解决，你点「抓取页面结构」只会得到一句「抓不到」——定位表永远配不出来。**

### 解法：换一条**不等 idle** 的通道

`dumpsys activity top` 会把各 App 的 View Hierarchy **直接打印出来，不用等 idle**。
我把它做成了自动兜底：

```
uiautomator 重试 → 关动画重试（无论成败都还原）→ ★ 只有知道包名时才退到 dumpsys
```

处理要点（都是踩过的）：

1. **按包名过滤 `TASK` 段** —— 输出里同时有好几个 App 的层级（实测 5 个 `View Hierarchy:`），
   必须挑出得物那一段，**不能取第一段**（第一段往往是系统设置）；
2. **坐标是相对父节点的** ⇒ 按缩进还原层次后**逐级累加**。
   不做累加会得到一份「看起来像坐标、实际全错」的表 —— 是最阴的一类错；
3. 滤掉不可见节点（`flags` 第一位不是 `V`，真机里这些 bounds 是 `0,0-0,0`）；
4. `app:id/x` 补全成 `com.shizhuang.duapp:id/x`；`clickable` 取 `flags` 第 6 位。

### ★ 但这条通道有一个必须告诉你的代价

**它拿不到文字**。只有控件 id / 坐标 / 能不能点 —— `text` 和 `content-desc` 全是空的。

所以程序在走这条通道时会**主动在界面上说明**这一点（不会闷着不吭声）：
候选表里凡是「按文字找」的步骤，你得手动改成用 id，或者按坐标改。

## 3. 怎么证明它是对的（不是「看起来像」）

| 验证 | 结果 |
| --- | --- |
| **两套独立实现交叉比对** | 我写了一个 Node 版解析器（进程序）和一个 Python 版（独立写的），同一屏各解析一遍 —— **110 个节点、43 个同名控件坐标逐一对上（±2px）**、能不能点的判断也一致 |
| **夹具用真机数据** | 测试用的那棵控件树是**真机抓下来的**（不是手写的假数据），并且**故意在前面垫了两段别的 App**，用来证明「按包名过滤」真的生效 |
| **全量回归** | 16 套 **864 项全绿**（本轮 adbtest 从 83 → **104** 项） |
| **8 条定点破坏** | 把代码逐条改坏，分别报红 **3 / 1 / 1 / 2 / 1 / 2 / 1 / 1** 条，然后逐字节还原（md5 一致） |

★ 其中有一条破坏**第一次一条都没红** —— 这恰恰说明我的断言写得太松：
「不传包名时不许走备用通道」这条，我原本只看返回值形状，而**两条路的失败结果长得一模一样**
（备用通道自己也会拒绝空包名），所以坏版看起来「正常」。改成查「到底有没有真去调那条命令」之后才抓住。
这条已经写进技能，也写进了项目记忆。

## 5. 你现在只需要三步

你已经有的：模拟器在线（`emulator-5554`）。

1. 「设备管理」→ **扫描设备** → 点那一行的「加入并使用」；
2. 模拟器里走到发布页 —— 走**你给的那条**：「我」→ 右上角「主页」→「发布新动态」；
3. 「设置 → 高级设置」→ **抓取页面结构** → 打开生成的 `uiMap-<时间>.json` 核对 `steps` → **导入 UI 定位表**。

第 3 步如果看到「已改用 dumpsys 抓、没有文字」的提示，那是**正常的**（见上面第 2 节）——
这条通道给的 id 和坐标是准的，只是没有文字，把靠文字的那几步改成 id 即可。

## 6. 诚实声明（哪些我没验证）

- 第 2 节的「首屏抓不下来」，是我在**你这台 MuMu 12 + 当前得物版本**上实测的。
  别的机型/版本可能行为不同 —— 但程序会**自己判断**（先试 uiautomator，失败了才退备用通道），
  所以在能抓的环境里不会有任何变化。
- 「两条入口」的坐标（`(838,149)` / `(121,925)`）是**这一次**实测到的；
  得物改版就可能变。所以代码里用的是**文字**（「主页」「发布新动态」）而不是写死坐标。
- 发布页**后续屏**（填标题 / 搜货号）我这轮没有逐屏实测 —— 那些屏本来就要你按实际页面改定位表。
