# 主图顺序：得物相册到底按什么排？怎么让指定的那张当主图

> 2026-10-05 · 真机实测（MuMu 12 / 得物 / 1080×1920 / `127.0.0.1:16384`）· 结论全部有可复算数字，截图在 `_ordertest/` 里
> 议题来源：你的待办「图文主图后面再说」+ 本轮「命名什么能排到最后一位」

---

## 一、结论先说（三句话）

1. **改名字没用**。得物相册的格子顺序**跟文件名一点关系都没有**——我实测过：文件名顺序、推送顺序、文件时间三个键**故意做成互相矛盾**，相册只跟**文件时间**走。
2. **真正的开关是「文件在设备上的修改时间」**（MediaStore 里的 `date_modified`），相册按它**倒序**排：**时间最新 → 第 1 格**。
3. 所以「想要哪张当主图」**完全能做到**，做法不是命名，而是：**把那张图的设备端时间设成最新**。而且这件事**不需要你改命名习惯**——你现在的名字本身带时间戳，顺序天然可推。

## 二、现状：现在是「哪张」当了主图（代码逐环节）

| 环节 | 位置 | 事实 |
|---|---|---|
| ① 读目录 | `util/winpath.js:126 readdirSafe` → `services/flatten.js:155` | `fs.readdir` **原样返回**，没有任何排序；`row.files` 就是磁盘顺序 |
| ② 建扁平副本 | `flatten.js:230` → `winpath.js:144 linkOrCopy` | 同盘走**硬链接**。实测你的叶子链接计数 = **4**（`-rw-r--r-- 4 …微信图片_2026-10-05_031009_152.jpg`）⇒ **mtime 继承原图** |
| ③ 选中要推的图 | `publisher.js:718` | `media = item.files.filter(type === 'image')` ⇒ **顺序 = 目录顺序** |
| ④ 逐个推送 | `publisher.js:849 for (const f of media) adb.push(...)` | **推送顺序 = 目录顺序**；`adb push` **保留源文件时间**（实测：本地 `2020-01-02 03:04:05` 推上去设备端一模一样） |
| ⑤ 写媒体库 | `publisher.js:854` → `adb.js:176 mediaScan` | `content call … scan_file` ⇒ 库里的 `date_modified` **取自文件 mtime** |
| ⑥ 选图那一步 | 定位表 `steps[8]` | `tapId flThumbSelect, count=${imageCount}` ⇒ **点相册最前面 N 格**（dump 顺序 = 屏幕顺序） |
| ⑦ 主图 | 得物行为 | 第一张 = 内容主图（你的口径；§ 六 列为未复验项） |

**推论（与你观察到的「倒序」吻合）**：现在第 1 格 = **mtime 最新**的那张 = 你**最后**导出/保存的那张。

拿你的真实素材对一遍：`Desktop\1005\S26408002+黑色\` 里 4 张 `微信图片_2026-10-05_031044_123.jpg / …031105 / …031109 / …031114`，
设备端 mtime 实测 `03:11:01 / 03:11:06 / 03:11:10 / 03:11:15` ⇒ **现在当主图的是最后那张 `…031114_455.jpg`**。

## 三、三个实验：怎么把「按什么排」钉死的

做法：造 4 张纯色图（红/绿/蓝/黄），把三个键**故意做成互相矛盾**，然后看得物相册第一屏的格子顺序。

- 文件名顺序：`a_red < b_green < c_blue < d_yellow`
- 推送（入库）顺序：**d → c → b → a**（`date_added` 递增）
- 文件时间：**b(最新) > c > a > d(最旧)**

| 实验 | 操作 | 相册实测顺序 | 说明 |
|---|---|---|---|
| **①** | 推 → touch 设时间 → `scan_file` 入库 | **绿 → 蓝 → 红 → 黄** | 与 **mtime 倒序**完全一致；与文件名/推送顺序**都不符** |
| **②** | **只改文件时间、不重扫库** | 绿 → 蓝 → 红 → 黄（**纹丝不动**） | ⇒ 得物**不实时读文件系统**，读的是**库里的缓存值** |
| **③** | 把时间改成 `黄12:40 > 红12:35 > 绿12:30 > 蓝12:05` 后**重扫** | **黄 → 红 → 绿 → 蓝**（顺序跟着变） | ⇒ 结论闭环：**决定相册顺序的是库里的 `date_modified`，倒序** |

关键数字（实验③，库里回读）：

| 文件 | `date_modified` | 相册位置 |
|---|---|---|
| d_yellow | 1791175200（12:40） | 第 1 格 |
| a_red | 1791174900（12:35） | 第 2 格 |
| b_green | 1791174600（12:30） | 第 3 格 |
| c_blue | 1791173100（12:05） | 第 4 格 |

（同一时刻 `date_added` = 1791174351/352/353/354 **没变**，相册顺序照样跟着 `date_modified` 走 ⇒ 彻底排除「按入库时间排」。）

截图：`_ordertest/album.png`（实验①）、`album-fs-mtime.png`（实验②，顺序不变）、`album-db-rescan.png`（实验③，顺序变了）。

**两条实现上的硬约束（都是实测出来的，不是推断）**：
- `touch` 必须发生在 `scan_file` **之前**（实验②：不重扫，库里旧值不更新 ⇒ 改了也不生效）；
- **不要**改本地扁平副本的时间来达到目的——扁平副本是**硬链接**，改它会把你**原图**的时间一起改掉（同一个 inode）。

## 四、命名这条路：走不通，但仍有用

- **走不通**：实验①里 4 个文件的「名字顺序」和「相册顺序」完全不一致。**没有任何命名能让它排到相册第一格**——因为相册根本不看名字。
- **仍有用**：名字可以当**「哪张要当主图」的信号**，由程序读名字去替你排时间。而你的命名**本来就已经是可排序的**（`微信图片_2026-10-05_031114_455.jpg` 自带时间戳）⇒ **你不需要改任何命名习惯**。

---

## 五、方案

### ★ 推荐 A：按文件名顺序排内容，**第一张自动当主图**

- **规则**：叶子里的图片按**自然序**排（`naturalCompare`，数字按数值比，避免 `img10` 排在 `img9` 前）得 1…N；
  App 把**第 1 张的设备端时间设成最新**，往后每张递减（**每档至少隔 1 秒**——`date_modified` 是秒级）。
- **效果**：相册第 1 格 = 文件名第一个 = **主图**；其余按文件名顺序依次排开。
- **你想换主图**：把那张的名字改得**排最前**（例如加 `0_` / `A_` 前缀）即可——**名字排第一的就是主图**。
- **落地位置**：`publisher.js` 的 push 循环之后、`mediaScan` 之前，加一步「按目标顺序 touch 时间」；时间基准取「当前时间 − i 秒」，保证比设备上任何残留素材都新。
- **为什么用设备端 `touch` 而不是改本地文件时间**：见 §三 最后一条（硬链接会改到原图）。

### 备选 B：显式「封面」标记

- 名字里带 `主图` / `封面` / `cover` / `0-` 的那张 → 设成最新时间；其余按文件名顺序。
- 好处：**封面与内容顺序解耦**（封面可以是第 3 张）。坏处：多一条命名约定要记。

### 备选 C：什么都不改

- 现状 = **最新导出的那张当主图**。如果你的导出顺序本来就把想要的那张放最后，那就别动。

> 视频不受影响（一条只有一个视频，没有「第几格」的问题）——按你的要求，视频不在本方案范围内。

## 七、顺带发现（同源风险，建议一起处理）

1. **相册那一屏 `uiautomator dump` 会失败**：我这次连续 4 次没拿到结构（得反复重试才出来）。而选图步现在是 `tapId`（要抓屏）⇒ 这一屏**最容易卡在这里**。视频那套已经用盲点坐标（`166,359`）绕开了。

   建议加一条校验：点完后读「下一步 (N)」按钮上的数字，**等于 imageCount 才继续**（现在只有下一步的 tapId 会如实报错，但报错点偏后）。
