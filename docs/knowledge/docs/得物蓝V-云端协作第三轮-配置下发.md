**安全性怎么收口**（这点值得你花 30 秒看）：

内置的 `sb_publishable_...` 是 **publishable key**，它**本身就是设计成公开的**——拓新系统自己的前端里也明文放着它。
它不代表任何权限，**权限完全由数据库的 RLS 策略决定**，而策略是：

- `anon` 只能 **insert + select**，**绝不给 update / delete**（否则「改失败变成功」只需一行 JS，看板数字就不值钱了）；
- insert 还要过 `org = 'bluev'` 校验（拿着 key 但不知道组织标识的人灌不进数据）；
- **`service_role` / `secret` key** —— App 的导入功能会**主动拦下**带这两个字样的 key，源码里也有断言焊着。

## 四、过程中查出并修掉的两个真问题

这两条都不是我一开始想到的，是**断言跑红之后**顺着查出来的：

**① `org` 漏传 → 整批数据被数据库拒收，而界面只显示「同步失败」**
`toRow()` 原本直接取 `machine.org`。调用方一旦忘了带这个字段，产生的不是「少一列」，
而是**每一行都被 RLS 拒收**——而用户看到的就是四个字「同步失败」，排查成本极高。已加兜底。

**② 界面清空地址后，后台**照样**在往内置地址推数据**
`cloudsync` 读配置时对空值会兜底到内置地址；但归一化只在启动时做了一次。
于是管理员在界面上把地址框清空、**看到的是空白**，而数据**照样在上传**——
这就是「界面骗人」。已把归一化同时接到写入路径上：**存下来的，永远等于真正在用的**。

**另外改写过一条断言，留档说明**：原来是「代码里不许出现 `service_role` 四个字」。
加了导入拦截之后它**必然误报**——代码里必须出现它，那正是**主动拦下它**的那行判断（看着像漏洞，其实是防线）。
所以拆成两条：① 正面断言「真有这条拦截」（防止将来有人删了拦截、只在注释里说已拦下）；② 负面断言「全文件不许有凭据字面量」。
