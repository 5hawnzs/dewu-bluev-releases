## 2. 怎么修的（不是「加一步」那么简单）

如果只是硬加一步「点 fl_publish」，那在**没有草稿**的正常流程里就会瞎点一下相册页的空白处。
所以给步骤引擎加了**第二套条件：屏幕守卫**。

### `whenOn` / `whenNotOn`（新）

| | 判什么 | 写法 |
|---|---|---|
| `when` / `whenNot`（原有） | **数据** —— 这一行填没填货号 | 占位符名，如 `goods2Sku` |
| `whenOn` / `whenNotOn`（新） | **当前这一屏长什么样** | resource-id，如 `com.shizhuang.duapp:id/iv_draft_title` |

四条硬规矩：

1. **只允许写 resource-id**。写文字（如 `whenOn: "草稿箱"`）在**导入时**就报错 ——
   守卫判错的后果比普通步骤更难查（该点的不点 / 不该点的点了），所以逼着写 id。
2. **拿不到界面结构 ⇒ 硬失败**，不许猜「大概不在草稿箱吧」。
   猜了就会漏点一步，然后卡在下一条，报错指向离真正原因很远的地方。
3. 守卫不成立 ⇒ **一个像素都不碰**，并按 `{skipped:true, why}` 返回，由调用方**写进日志**（不静默）。
4. 候选表（「抓取页面结构」）**自带这一步** —— 否则你重抓一次表，修复就丢了。

### 这一轮我自己踩的坑（如实写，都当场改了）

1. **预演脚本忘了传开关** ⇒ 加了 `--dry` 照样落盘，「预演」变成「真执行」。
   17/17 锚点唯一 + 回读全对，结果没坏，但**预演这一步等于没做**。
   改法：`dry_run` 缺省**跟随命令行**，不靠调用点自觉。
2. **反向验证把「套件中断」当成「抓住了」**。
   一开始 2 条破坏被判 GREEN（没抓住），查下来是：拆掉守卫后断言**抛异常直接中断套件**，
   一行 `FAIL` 都不打 —— 正是我记忆里那个「假通过」坑。
   改法：行为级断言一律 `try/catch` 兜住，把「抛异常」本身算成 FAIL。
3. **中断判据不能用退出码**。我第一版写成「退出码非零 = 中断」，
   而有 FAIL 时退出码本来就不是零 ⇒ 把「期望串写错、本该是没抓住」美化成「抓住了」。
   改法：只看有没有 `ADB TEST ERROR` / PASS 数有没有掉。
4. **行为级断言别用测试自己硬编码的常量**。
   原来行为级用的是测试文件里写死的 id，所以「把配置里的 id 改错」它抓不住 ——
   改成读 `uimap.DEWU.draft.*` 之后，配置写错也会红（D7/D8 由「没命中」变成真 FAIL）。
