# 云端同步失败：根因与对策

生成时间：2026-10-08 14:28　|　只做诊断，**未改任何源码**（`cloudsync.js` 当时正被另一路会话修改且未提交）

## 一、结论

**不是云端的问题，是本机代理断了。**

本机所有域名都被解析成假的 `28.0.0.x`（fake-IP + TUN 模式），而 App 的 `fetch` 是**直连那个假 IP**，
出网唯一依赖本机代理进程 `FlClashCore.exe`（PID 10040）。

它一重启 / 切节点 / TUN 掉 / 开机还没起来 → 连 `28.0.0.116` 超时 → `fetch failed` → 日志里一条「云端同步失败」；
它一回来，同步自己就好了。**这就是「时不时」。**

## 二、证据链（全部实测）

| # | 实测项 | 结果 |
|---|---|---|
| 1 | 默认路由 `netstat -r` | `0.0.0.0/0 → 28.0.0.1`，接口 `28.0.0.2` ⇒ 开着 TUN |
| 2 | DNS 解析 5 个域名 | supabase→`28.0.0.116`、baidu→`28.0.0.159`、qq→`28.0.0.160`、github→`28.0.0.161`、npm→`28.0.0.162`（每域名一个假 IP） |
| 3 | 直连 `28.0.0.116:443` 取证书 | `CN=supabase.co`、`SAN *.supabase.co`、签发 `WE1` ⇒ 流量确由 TUN 接管后转发 |
| 4 | `HTTPS_PROXY=127.0.0.1:9`（死端口）下 fetch | **仍 HTTP 200** ⇒ App 的 fetch **不读**代理环境变量，是直连假 IP |
| 5 | 代理进程 | `tasklist` ⇒ `FlClashCore.exe`，PID 10040，`netstat` 显示 `127.0.0.1:7890 LISTENING` |

### 为什么是「时不时」+ 一次故障连冒好几条

- `syncOnce()` 只在**有待上行数据**时才真联网；没新数据那轮直接 `return`，**连都不连** ⇒ 失败总紧跟在一次发布之后。
- 失败后按 `intervalSec × 2^fail` 退避：**60 → 120 → 240 → 300 秒**重试，**每重试一次就再冒一条 `logbus.warn`**。
- 所以「时不时冒一条」其实是**一次代理中断的连发回响**，不是反复独立故障。
- 直到下次推成功（`fail=0`、`lastError=''`）才停。

### 为什么事后完全查不到原因（这才是真麻烦）

1. `logbus` **只进内存**、不落盘；成功后 `lastError` 又被清空 ⇒ 磁盘零痕迹
   （已在 `run-log.jsonl`、`config.json`、工作区全量搜索，0 命中）。
2. `catch` 里记的是 `String(e.message || e)`，而网络层错的 `e.message` 就是 **`fetch failed`** 六个字，
   `e.cause`（`ENOTFOUND` / `ECONNRESET` / `ETIMEDOUT` / `socket hang up`）**被丢掉**。

实测四种故障各自会显示什么：

| 真实故障 | 日志里能看到 |
|---|---|
| DNS 失败 / 连接被重置（同一台机、同一次） | `fetch failed`（cause **被丢**） |
| 15 秒超时 | `The operation was aborted due to timeout` |
| 服务端 500 | `HTTP 500 · …` |

⇒ 下次看到 `fetch failed`，基本就是代理那条链路断了；看到超时那句才是网络慢。
