## 二、为什么会这样：`uiautomator` 那一下没拿到 idle，退到了备用通道

### 2.1 现场复现

我在**那一屏**上手动跑程序的同一条命令：

```
$ adb shell "rm -f /sdcard/_probe.xml; uiautomator dump /sdcard/_probe.xml"
ERROR: could not get idle state.
$ adb shell "ls -la /sdcard/_probe.xml"
ls: /sdcard/_probe.xml: No such file or directory      ← 失败时**不写文件**
```

⇒ `dumpEx` 的第一通道拿不到东西，按设计退到**备用通道 `dumpsys activity top`**（`adb.js` 的 `dumpViaDumpsys`，只在 `uiautomator` 全败时才走）。
你抓出来的那份 XML 里，属性顺序是 `class → resource-id → package → clickable → text → content-desc → bounds` —— 正好就是 `vhToXml()` 拼出来的格式，**确认走的是备用通道**。

### 2.2 备用通道有两个天生缺陷，这次两个都踩上了

| 缺陷 | 这次的后果 |
| --- | --- |
| ① **拿不到 text**（只有 class / id / bounds / clickable） | 整份表 0 文字 ⇒ 按文字找的步骤全部失效 |
| ② **只给 Activity 那个窗口的 View Hierarchy** | 「关联好物」搜索页是**同一个 Activity 的第二个窗口**，备用通道里**根本不在场** |

第 ② 条的实测证据 —— 现在这一刻（搜索页开着）`dumpsys window` 列出来的是：

```
Window #6 Window{9d0b62b u0 com.shizhuang.duapp/...TotalPublishProcessActivity}   ← 发布页
Window #7 Window{e2d1689 u0 com.shizhuang.duapp/...TotalPublishProcessActivity}   ← 关联好物搜索页
```

而 `dumpsys activity top` 里 `com.shizhuang.duapp` 这条 task **只有一段 `View Hierarchy:`**，
`grep etSearch` = **0**、`grep tvTitle` = **0**，`EditText` 只有发布页的 `etTitle` 和 `etTrendContent`。
（那一处 `关联好物` 命中是发布页 Fragment 的 `mArguments=Bundle[{... title=关联好物, isSmartLabel=true}]`，不是搜索页的标题。）

## 五、从这份好 dump 里挖出的**两个真问题**（不是抓取失败，是表怎么配的问题）

### 问题① `input` 动作**不点输入框**，是往「当前有焦点」的框发广播

看 `publisher.js` 的 `runStep`：`case 'input'` 只做一件事 —— `adb.inputText(serial, step.value)`，**没有任何"先点一下这个框"的动作**。
中文又只能走 `ADB_INPUT_TEXT` 广播，广播只送给**当前有焦点**的输入框。

⇒ 所以「点标题输入框」「点正文输入框」这两步是对的（老表里有），但**搜索框那一步缺了**：
刚打开关联好物页时焦点不在搜索框上，直接 `input ${sku}` **打不进去，而且不报错**。
必须补一步 **`tapId etSearch`**。

### 问题② 商品卡片的**根节点既没有 id 也没有文字** ⇒ 现有三种找法都点不到它

现有动作词只有 7 个：`tapText / tapId / tapDesc / input / wait / back / screenshot`（`uimap.STEP_ACTIONS`）。
卡片根是一个可点的 `ViewGroup`，**没有 resource-id、没有 text、没有 content-desc** ⇒ 三种 tap 一个都用不上。

**绕法（已写进新表）：** 卡片根的第 1 个子节点是 `ivProduct`（商品大图，`[30,238][295,503]`），
点它的**中心**（约 `162,370`）落在卡片范围内，Android 会把这次点击交给可点的卡片根。
所以 `tapId ivProduct` = 「点第 1 张商品卡」，而 `tapId` 取的是**第一个**匹配节点 ⇒ **永远是第 1 个搜索结果**。

**⚠️ 还没验证的一件：** 点下去是「立刻关联并退回发布页」还是「还得再点一下」。
搜完那一页**没有任何确定/完成按钮**，所以我**推断**点一下即关联并关闭 —— 但**这是推断，不是实测**。
