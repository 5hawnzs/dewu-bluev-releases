## 二、现场复现：到底谁会白屏

不是推理，是拿 11 个页签逐个 `renderAll()` 跑出来的（`tools/_rv-projectnull.js`，全部在临时 userData 里跑，不碰本机数据）：

| `state.project` / `state.config` 的形状 | 抛异常的页数 / 11 | 抛异常的页 |
|---|---|---|
| **真值（控制组）** | **0** | — |
| `project = null` | 6 | 1 素材整理 · 2 合规检查 · 3 文案生成 · 4 货号颜色校验 · 6 模拟器发布 · 11 高级设置 |
| `config = null` | 5 | 1 · 2 · 3 · 6 · 11 |
| `project = {ok:false,error}` | 2 | 2 合规检查 · 3 文案生成 |
| `config = {ok:false,error}` | 2 | 3 文案生成 · 6 模拟器发布 |

典型异常就是一句 `Cannot read properties of null/undefined (reading 'stats' / 'compliance' / 'rotateStrategy')`
—— **在渲染过程中抛出 = 整页白屏，且不给用户任何解释**。

## 三、哪些是真会发生的，哪些只是我工具的锅（如实分层）

根因在这句话（`src/main/ipc.js`）：

```js
/** 业务通道一律要先登录 */
function guard(fn) {
  return async (e, ...args) => {
    if (!auth.enabled()) return fn(e, ...args);
    if (!auth.current()) return { ok: false, error: '未登录或登录已过期，请重新登录' };  // ★ 不抛异常
    return fn(e, ...args);
  };
}
```

而 `config:get` / `project:get` **都走这个 guard**。渲染层有 12 处是这样裸赋值的：

```js
state.config = await appApi.configGet();   // 拿到的是 {ok:false,error}，却当成配置存了下来
```

于是 `state.config / state.project` 里躺着一个「长得像、其实缺了 `compliance` / `copy` / `items`」的对象。

| 形状 | 正常安装里会不会出现 | 判断依据 |
|---|---|---|
| `project = null` | **不会** | 主进程 `project.get()` 永远返回 `blank()` 补全的完整对象；且所有 `renderAll()` 调用点都在 `enterApp()` 之后。**只有我这个绕过 `enterApp` 的工具会造出来。** |
| `config = null` | **不会** | 同上（`store.defaults()` 保证键齐全） |
| `{ok:false,error}` | **会**（但是窄路径） | 会话失效 / 账号被停用后，点「模拟器发布 → 连接/使用设备」会走到 `state.project = await appApi.projectGet()`（第 2792、2826 行）——**随后切到「合规检查」或「文案生成」就是白屏**。这就是上面表里 2 页那两行。 |

**所以：这次修的是「窄路径 + 最差表现」的组合**——概率不高，但一旦命中，用户看到的是一片空白，
既不知道「是不是我没数据」，也不知道「我掉线了」，连该做什么都不知道。

## 四、改了什么

改动只有一处，在 `renderAll()` 入口（`src/renderer/app.js`）：

```js
function stateGate() {
  // ① {ok:false} ⇒ kind:'denied'（会话没了）  ② null / 缺关键字段 ⇒ kind:'missing'（还没读到）
}

function renderAll() {
  ...
  const g = stateGate();
  if (g && g.kind === 'denied' && state.auth && state.auth.requireLogin) { showGate(g.why); return; }
  if (g) { /* 只画一句人话：为什么这页没渲染 */ return; }
  // ↓ 值都可信时，照原来的路径渲染（一个字没动）
}
```

- **不是**「补一堆假默认值把页面填满」——那才是造假。缺就是缺，页面上写「还没读到」/「已过期」，如实。
- **不是**「哪儿抛就 catch 哪儿」——那只会把白屏换成半个页面，仍然没人知道为什么。
- 判定放在**唯一入口**，所以 12 处裸赋值、任何未来的新渲染点，都被同一道闸门挡住。

顺带把「拒绝对象」的语义做对了：`{ok:false}` **不是「这页没数据」，是「你已经不在登录状态」**
⇒ 直接回登录页并把原因原样带过去（原来会停在半页白屏上）。

## 六、那 1 条既有 FAIL 的根因（与本次改动无关，但值得你知道）

```
FAIL  统计里「未标品牌」是独立的一桶（不是某个品牌的 0）  → untagged=21 品牌数=2
```

它断言 `untagged.rows === 0`。而这条断言**读的是本机真实台账**：

- 路径：`C:\Users\Administrator\输出\得物\publish-log.jsonl`（`logintest` 没有把 `paths.output` 指到临时目录）
- 实测（我直接数了一遍）：**39 行，其中 18 行没有 `brandId`**，按 brandId 分布 `{brd_muqfsocjcff307: 21, '': 18}`
- 这个数**还在长**：我这一轮里从 12 → 17 → 18 → 21（文件 mtime 12:02，另一路会话正在跑发布测试）

⇒ **它是「测试依赖本机数据」的问题，不是产品缺陷，也不是被我的改动弄红的**（上一轮我拿 HEAD 版代码复跑过，同一条照样红）。
想让它稳定的话有两条路，都需要你点头我再动：
1. `logintest` 启动时把 `paths.output` 指到临时目录，**并自己造一条无品牌 + 一条有品牌的记录**——
   这样断言的语义反而更强（验证的是「分桶规则」，不是「这台机器上恰好没有未标品牌的记录」）；
2. 或者把断言改成 `untagged.rows >= 0 && untagged.id === ''`（只验分桶存在，不验行数）—— 弱，但不会红。
