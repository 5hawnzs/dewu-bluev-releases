## 一、先说我查到了什么（都是真库实测，不是推理）

用内置的那把 key 直接读真库（`rywurhpkovyjpjyvfjdz.supabase.co` / `public.publish_log`）：

| 项 | 实测 |
|---|---|
| 总行数 | **369 行**（还在涨，App 每次跑都推） |
| 按「时间＋篇号＋批次＋款」去重后 | **189 项** |
| 其中被**两个机器标识**重复上报的 | **178 项** ← 几乎全中 |
| 两个标识 | `m_ce61ca24`（178 行）与 `m_fb6e1a86`（184 行），**机器名一模一样**（WIN-6H81015PUR6） |
| 非真实发布的行 | 88 条「模拟成功」＋ 4 条探针（其中 3 条的 result 写的就是「发布成功」） |

### 根因（三件事撞在一起）

1. `cloud.machineId` 原来是**随机** UUID，存在 `config.json` 里；
2. 而 `tools/config-portable.js`（配置搬运工具）**按设计**会把 `cloud.machineId` 置空 ——
   目的是防止两台机器共用一个标识。可**同一台机器**重新导入时，App 就生成了一个**新的**随机 id；
3. 新 id 一来，`(machine_id, ts, seq)` 这个唯一键就拦不住旧数据了 ⇒ **整本台账以新 id 重推一遍**。

⇒ 结果：同一台电脑在云上变成两台，**同一份工作被算了两次**。

**这个洞对看板的杀伤力（实测）：**

| 指标 | 旧看板显示 | 真实值 |
|---|---|---|
| 已发布 | 367 | **137**（真实发布结果，去重后） |
| 成功率 | 33% | **43%** |
| 机器数 | 3 | **1** |
| 最多那款的完成度 | 89/150 = **59%** | 29/150 = **19%** |

> 最后一行才是真正危险的：**款进度虚高 3 倍**。报 59% 会让人以为快发完了，实际只发了 19%。

## 二、改了什么

### App 侧（根因）

| 文件 | 改动 |
|---|---|
| `src/main/services/cloudsync.js` | 新增 `machineFingerprint()`：读 Windows 注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`（**装系统时生成**，重装 App / 清配置 / 换 Windows 用户都不变）→ 用 `sha1('bluev|'+指纹)` 取前 8 位派生 id。**顺序**：① 配置里已有 id ⇒ 照用（**绝不迁移**，迁移＝再翻一倍）；② 没有 ⇒ 按指纹派生；③ 指纹读不到 ⇒ 退回随机（原行为，不抛） |
| `tools/config-portable.js` | 提示文案改写：置空后 App 会按**这台机器的指纹**算回来（同一台机同一个 id，新机是新机自己的 id）⇒ 「防两台共用 id」的设计目标不变，副作用没了 |

### 看板侧（口径）

| 改动 | 说明 |
|---|---|
| **排除「模拟 / 探针」** | `isReal` 只认真实发布结果；且**不只看 result** —— 建库的 4 条探针里有 3 条 result 就是「发布成功」，只按 result 判会把它们放进来（实测：机器数被从 1 撑成 2）。所以再加一道「是不是探针机器」 |
| **折叠重复行** | 按「机器名＋时间＋篇号＋批次＋款＋结果」去重（两台不同机器不太可能在同一毫秒发同一款的同一篇号，不会误并） |
| **机器按名字归一** | 机器数与筛选都按机器名算；同一台机即使换过标识也只算一台，表格里标注「含 N 个机器标识，已合并」 |
| **成功率分母改对** | 分母 = 真实完成条数（不再拿含模拟/探针的总行数） |
| **不藏数据** | 模拟/探针行**仍留在「最近明细」**里（灰色标签「模拟 / 探针」），并在页脚明示「另有 N 条未计入」。**不是删掉，是不冒充发布** |

## 六、附：回答「不是本机运行的日志，能被抓吗？」

**分两种，答案不一样 —— 这点很重要，别混淆：**

| | 能不能统计到 | 说明 |
|---|---|---|
| **发布结果**（谁、哪台机、哪一款、第几篇、成功/失败、耗时…） | **能** | 但**不是被「抓」的** —— 是**那台机器自己推上来的**：App 每 30 秒轮询本机 `publish-log.jsonl`，把新增行推到云上。没有任何中心去主动连别的机器 |
| **运行日志原文** | **抓不到，也不会上行** | 有意为之：日志里带本机绝对路径、行数会爆。**本机的日志也不上云**。上云的只有 18 个结构化字段 +「失败原因」截断 200 字 |

所以对方那台机器要能被统计到，得同时满足：

1. 装的是 **1.0.5 以上**的包（现在发的是 1.0.15，内置了地址与 key）；
2. **云端开关开着** —— 出厂默认就是开的；
3. 那台机器**能连上 `*.supabase.co`**（公司白名单代理可能挡住）；
4. **真的跑完过发布**（走真机 adb 通道）。
   ★ 这点最容易误会：只「生成任务 / 生成文案」不发布 ⇒ 云上**一条都没有**；
   而走了**模拟通道**的会记成「模拟成功」—— 按新口径**不计入统计**（但会在明细里灰色显示）。
