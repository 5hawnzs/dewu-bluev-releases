# 得物蓝V素材发布工具 · 发版流程 SOP

> 一句话：**改代码 ≠ 发版**。发版有两个必须由人触发的动作 —— 我「打包装并上传」，你「下载并安装」。
> 本文所有结论都来自代码（`src/main/updater.js`、`tools/upload-release.js`、`package.json`），不是推测。

---

## 一、直接回答你的三个问题

### Q1：我让你做好 A 功能，测试版会直接生效吗？

**不会「直接」。中间有三道必须过的关，缺一道你那边就看不到变化。**

| # | 关卡 | 谁做 | 漏了会怎样 |
|---|---|---|---|
| 1 | **打测试版包并上传**（`npm run dist:release:beta`） | 我 | ★ 源上还是旧 `beta.yml`，应用**永远显示「已是最新」而且不报错** —— 这是最坑的一种失败，看不出坏 |
| 2 | 通道已切到测试版 | 你（**只有管理员能切**） | 正式版用户读的是 `latest.yml`，永远看不到测试版的包 |
| 3 | 下载 + 安装 | 你 | 只发现、不自动装 |

第 3 关要拆开说，因为它和我上次的说法有出入（上次我说得不够准）：

| 动作 | 自动还是手动 | 代码依据 |
|---|---|---|
| **发现**有新版本 | **自动** —— 启动后 **20 秒**自检一次 | `STARTUP_DELAY_MS = 20 * 1000`；`scheduleStartupCheck()` |
| **下载**新版本 | **手动** —— 界面上点「下载」 | `AUTO_DOWNLOAD = false`（包 88MB，不偷偷占带宽） |
| **安装/重启** | **手动** —— 界面上点「立即安装」 | `autoInstallOnAppQuit = false`；`quitAndInstall` 只由这一个入口调 |

> 所以准确说法是「**自动发现、手动下载、手动安装**」。
> 为什么不自动装：这工具一跑批量发布就是几十分钟，静默重启会把任务拦腰截断，而且发到一半的批次没有回滚。

---

### Q2：测试版生效的时候，正式版会一起生效吗？

**不会。两条通道互不干扰。**

- 源上有**两个清单文件**：正式版读 `latest.yml`、测试版读 `beta.yml`（`CHANNELS = { stable: 'latest', beta: 'beta' }`）。
- 传测试版**只改 `beta.yml`**，`latest.yml` 一个字节都不动。
  **实测证据**（2026-10-01 推 beta.2 之后从公网拉取）：`beta.yml = 1.0.1-beta.2`，而 `latest.yml` **仍然是 `1.0.0`**。
- 还有一道**硬闸门**：版本号带 `-beta` 的包**不允许**发到正式通道，脚本会直接拒绝（`channelMismatch()` → `pre-to-stable`）。
  ⇒ 就算手滑执行了正式版命令，也没法把没验收的包推给所有人。
- 反过来也拦：正式版本号发到测试通道同样被拒（`release-to-beta`）。

所以「测试版和正式版可以共存」的准确含义是：**源上两条通道并存、每个客户端自己选读哪条**，不是装了两份软件。

---

### Q3：测试版验收没问题后，怎么发布到正式版？

**你只要说一句「推送」，剩下两步是我的事：**

1. **改版本号**：`package.json` 里 `1.0.1-beta.2` → **`1.0.1`**
   ★ 必须去掉 `-beta`，否则被上面那道闸门拦住，一条都传不上去。
2. **打包 + 上传正式通道**：`npm run dist:release`
   （= `dist:win` 打包 + `upload-release.js --channel stable` → 写到 `latest.yml`）

然后正式版用户：下次启动 20 秒后（或手动点检查更新）看到 `1.0.1` → 点下载 → 点立即安装。

**你机器上如果装着 beta.2 想切回正式版**：发布 `1.0.1` 之后，`1.0.1 > 1.0.1-beta.2`，切回正式版通道是**正常升级**，不需要降级。
（如果**还没**发 `1.0.1` 就切回去，源上是 `1.0.0`，那就需要降级 —— 代码专门为「测试版→正式版」这**一次**放行了降级，不然切了也回不去。）

**测试通道不受影响**：`beta.yml` 还是 `beta.2`，装了测试版的人不会因为你发正式版而被改动。
下一轮做 A2 功能就是 `1.0.2-beta.1`，两条线各走各的。

```
你提需求 A
   ↓
我改代码 → 跑回归（当前 447 项断言）
   ↓

   ↓

   ├── 有问题 ──→ 退回「我改代码」，下个包叫 beta.N+2
   └── 没问题
        ↓
★ 你说「推送」→ 我把版本号去掉 -beta → 打正式包 → 上传到 latest.yml
        ↓
正式版用户点检查更新 → 下载 → 安装 → 生效
```

## 四、命令原文（留档）

```bash
# 测试版（打包 + 上传到 beta.yml）
npm run dist:release:beta
#   = npm run dist:win && node tools/upload-release.js --channel beta

# 正式版（打包 + 上传到 latest.yml）★ 执行前先把 package.json 版本号去掉 -beta
npm run dist:release
#   = npm run dist:win && node tools/upload-release.js --channel stable

# 只上传、不打包（包已经打好时用）
npm run release:beta
npm run release:stable

# 清理源上堆积的老包（**默认 dry-run，一个字节都不删**）
npm run release:prune
#   = node tools/prune-release.js
npm run release:prune:apply
#   = node tools/prune-release.js --apply   ← 确认过名单之后再执行
```

### 老包清理：什么时候要跑、跑之前看什么

> 产物名字里带版本号（`build.win.artifactName` 那一行），所以**每次发版天然新增一个约 88 MB 的文件**；
> 上传脚本只有「上传」能力、桶上也**没有生命周期规则** ⇒ 老包只增不减。
> 实测（2026-10-02）：桶里 12 个对象、4 个 exe **合计 343 MB**。

**保留策略**：每条通道各留「**当前版本 + 1 个可回滚的历史版本**」（`--keep-more=N` 可调），
`latest.yml` / `beta.yml` 与认不出名字的对象**永远保留**。

★ **故意不做「同名覆盖」**（最省事、也最容易被想到的那个方案），三条代价：
① **回滚没了** —— 正式通道允许降级（用户从测试版切回正式版靠它、出事回退也靠它），包被覆盖就回不去；
② **审计线索没了** —— 「哪次更新对应哪个包」是事后唯一能对上的凭据；
③ 覆盖同版本号会让客户端按版本号比较后判「没有新版本」（上传脚本的 `versionGate` 拦的就是这个）。

★ 三条**fail-closed 闸门**（源上状态不明时宁可什么都不动）：

| 情况 | 行为 | 为什么 |
|---|---|---|
| 读不到 `latest.yml` 的版本号 | **一个字节都不删**，并打印原因 | 源上状态不明时做破坏性操作，最容易把唯一那份可用包毁掉 |
| 版本比该通道当前版本**还新** | **保留**，并写进 `notes` | 多半是「包传上去了、清单没传成」——那正是马上要用来救场的那一份 |
| 认不出名字的对象（清单 / 0 字节占位 / 别人家的 exe） | **保留** | 宁可留着，也不删看不懂的东西 |

跑完还会逐个 `HEAD` 复核「保留名单里的包一个都没少」——**说删干净了要拿源上的事实说话**，不是靠推断。

**上传前两个易踩的点**（都已遇到过）：

1. **`dist/` 里必须只留本次要发的包**。脚本的防呆闸门会比对「`latest.yml` 里写的文件名」和「`dist/` 里的实际文件」，一旦发现多个版本并存会**拒绝上传**（防止传错版本）。旧包先挪走。
2. **版本号必须比源上高**。同版本号重推，已经装了那个版本的机器会显示「已是最新」，**收不到新包、也不报任何错**。
3. ★ **`dist/` 里上次留下的 `win-unpacked/` 会让打包直接中断**（2026-10-02 实测）：
   `remove …\dist\win-unpacked\chrome_100_percent.pak: Access is denied` —— electron-builder 打包前要先清空这个目录，
   清不掉就退出。**根因已查实，不是文件被占用**：沙箱把删除**重定向到回收站**，
   而这棵目录树（约 220 MB）回收站放不下 ⇒ `SHFileOperationW 失败: 0x78 (ERROR_CANCELLED)` ⇒ 沙箱**宁可拒绝删除**。
   同一个目录里**单个小文件能删、整棵目录删不掉**；`mv` 改名、PowerShell `Remove-Item`、electron-builder 三种写法全失败。
   ⇒ 解法：**换个输出目录打包**，再把三样东西搬回来：
   ```bash
   npx electron-builder --win --x64 --publish never -c.directories.output='D:\work\_release-build\1.0.1'
   # 然后把 新目录\ 里的：安装包 exe、同名的 .blockmap、latest.yml 三样 mv 进 dist/
   # （dist/ 里那个 win-unpacked 留着不管它 —— 上传脚本只数 exe，不数目录）
   ```
4. ★ **`--channel` 两种写法都支持**（`--channel beta` 和 `--channel=beta`）。这一条有断言守着：
   只认空格写法的话，`--channel=beta` 会被**静默**忽略、退回 `stable` ——
   那就等于把**测试版包推给所有正式用户**（`latest.yml` 里会写上带 `-beta` 的版本号）。
   同理 `--channel=`（空值）会直接报错，**不会**落回默认值。
5. **想知道某次更新到底下了多少**（判断差分有没有生效）：让用户去
   **设置 → 应用更新 → 更新日志 → 开启**，然后点「下载更新」。日志落在
   `%APPDATA%\<应用名>\logs\update.log`（超过 2 MB 自动轮转为 `.1`）。
   看这两行：
   - `[progress]` —— 抽稀过的进度（每跨 10% 或每 2 秒一条）
   - `[downloaded] 新版本 X 已下载完成：本次共 N 字节（M MB）` ← **这是唯一能定论的证据**
     （对照：满包约 88 MB；若差分生效，这里应远小于它）
   ★ 默认**关**（避免无谓写盘）；日志里只有版本号、通道名与字节数，**不含**素材/品牌/SKU。

## 五、验收清单（推送后核对，都是从公网拉的真实数据）

- [ ] `beta.yml`（或 `latest.yml`）里的版本号 = 本次发布的版本号
- [ ] `latest.yml` 在发测试版时**保持原样**（发正式版时才变）
- [ ] 安装包 HTTP 200，且 `Content-Length` 与本地文件字节数一致
- [ ] 代码已推送，`git ls-remote origin refs/heads/main` 与本地 commit 一致
