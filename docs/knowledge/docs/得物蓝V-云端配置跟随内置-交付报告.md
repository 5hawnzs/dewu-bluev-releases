## 一、你问的「为什么 A 换了项目要重新导出导入」

**原因**：项目地址在架构里是**每台机器本地的一份配置**，而 App **只上行、不下发配置**——
它从云端读的只有一个探活请求，没有任何「读配置」的逻辑。所以 A 改了，云端不知道，也就没法告诉 B、C、D。

**更硬的一层（这轮才查出来）**：原来连 **重打包都换不动老机器**。我写了个探针实测
（`D:\work\_e2e\_freeze-probe.js`：桩掉 electron、userData 指到临时目录、用一个**不同的**内置值去加载）：

| 场景 | config.json 里的 cloud | 实际用的地址 | 结论 |
|---|---|---|---|
| 新装机器 | 没有这个键 | `NEW.supabase.co` | 跟随内置（新包生效） |
| 已存过盘的机器 | `url = OLD.supabase.co` | `OLD.supabase.co` | **内置顶不动** |

**机制**（三行代码串起来，而且是个隐藏动作）：

1. 出厂配置里直接写的是内置地址 → 内置值**进了缓存**；
2. 存盘时写的是**整个缓存**，而「高级设置」页保存时会把**那一页所有输入框的值整体提交**
   ⇒ **改任何一个选项（哪怕跟云毫无关系）都会把云地址一并固化进 `config.json`**；
3. 归一逻辑只在「为空」时补 ⇒ 固化之后再也顶不动。

而 `config.json` **卸载都不删** ⇒ 重打包发了新版，老机器照样连旧地址，**界面上还看不出区别**。
实测细节：探针里只改了一次主题（`ui.theme`），`config.json` 里就冒出了整块 `cloud`。

### 改完之后的语义

- **两个框留空 = 跟随内置**（正常状态，出厂就是这样）→ 换项目**只要发新包**，各台升级后自动跟随；
- **填了 = 只改这一台**（临时调试、或那台要单独指到别处）；**清空即撤回**，回到跟随内置；
- **导出/导入**只留给「升不了级的机器」——★ 反过来说：对方是「跟随内置」时**不要**发那段配置，
  粘了反而会把地址**写死在那台机器上**，日后换项目它就不跟着走了（导出弹窗里已写明这一点）。

## 三、守「界面骗人」的那条线（这轮最关键的设计点）

删掉 `applyCloudDefaults` 之后，原先靠「把内置值写回配置来对齐界面」的那条防线没了。
替代它的是**更直接的一条**：界面必须**如实显示主进程真正在用的地址和来源**。

- 它**无条件渲染**（未启用、未配置也照显示），因为它是「留空＝跟随内置」唯一的可见出口；
- uicheck 里有一条断言焊死：**界面显示的地址必须 == `status().url`**，且来源词必须和主进程报的一致。

### ★ 本轮我自己踩的一个「假通过」（已写进记忆与技能）

那条 uicheck 断言第一版写成「整段文本里出现『跟随内置』」。可那一行里**本来就同时有**
「跟随内置」和「本机指定」两个词（前面的徽章 + 后面的说明）——于是我把**来源那半句人为改成「本机指定」**，
断言**照样 PASS**。改成「只取 `来源：` 后面那一段，且不许出现反面的词」之后，坏版才真红。

一般规律：**同一段文案里出现两个互斥词时，「包含」型断言必然假通过**——
要么截到唯一片段，要么补一条「不许出现反义词」的负向断言。
