# 得物蓝V 发布工具 —— 提速收口 + 验证闭环（2026-10-03）

> 本轮三件事：① 收口上一轮未完成的验证 ② **加快发布速度（重点：点 App 按钮）** ③ 热词库挪到货号颜色校验下面。
> 所有数字都是**本机实测**（MuMu 12 / 得物 / 1080×1920 / 真机串 `127.0.0.1:16384`），不是估算。

---

## 一、先给结论：慢的不是「点击」，是「点击前那次抓屏」

这是本轮最重要的发现。用户感觉「点 App 上按钮太慢」，但实测下来**点击本身只要 0.14 秒**：

| 动作 | 实测耗时 |
|---|---|
| `input tap x y`（点一下） | **138 – 146 ms** |
| 纯 `adb shell` 往返 | 135 ms |
| `dumpsys activity top` | 160 ms |
| 普通页 `uiautomator dump`（抓屏本体） | **2036 ms** |
| 一次「合并式抓屏」（rm+dump+cat） | ≈ **2240 ms** |
| **相册页 `uiautomator dump`（连打 3 次）** | **11230 / 11136 / 11127 ms，三次全部 `could not get idle state`** |

**抓屏比点击贵 15 倍。** 而相册页更夸张：那一下要白等 **11.1 秒**。
（对照：同一张相册页**关掉三个系统动画**后 → **2036 ms** 就抓到。）

⇒ 所以提速的方向不是「把点击调快」，而是**① 能省掉的抓屏就省掉 ② 省不掉的就合并往返 ③ 同一批里同一个坑只踩一次**。

## 二、已落地的五个提速项

| # | 改动 | 机制 | 实测收益 |
|---|---|---|---|
| 1 | `tapXY` 新动作 | 按固定坐标直点，**完全不抓屏** | 一步省 ~2.2 s（相册那种屏省 13.6 s） |
| 2 | `tapSeq` 多点合并 | N 次点击合成**一条** shell，间隔用设备端 `sleep 0.25` | 3 击 380 ms → **127 ms** |
| 3 | `dumpOnce` 合并 | `rm` + `uiautomator dump` + `cat` 由 3 次往返合成 **1 条** shell | 每次抓屏省 ~2 次往返 |
| 4 | 屏幕守卫复用抓屏 | 守卫抓到的那份结构直接给同一步的点击用 | 每次守卫步省 ~2.3 s |
| 5 | **「不会 idle 的屏」同批只付一次** | 按**步骤名**记住「这一步这一屏不会 idle」，本批第 2 条起直接走关动画 | **每条内容省 11.07 s** |

第 5 项是本轮最大的一块，真机实测：

```
第 1 条内容（默认路径，先白抓一次）: 13462 ms
第 2 条内容（缓存命中，直接关动画）: 2396 ms
动画开关（跑之前）：1 1 1
动画开关（跑之后）：1 1 1        ← 必须还原，不许把用户设备留在改过的状态
```

同一步在**同一次运行里出现两次**的逐步计时（真机端到端）：

```
#5 切到「照片」页签   13824 ms   ← 第 1 次：先白等一次 idle 超时
#6 切到「照片」页签    3085 ms   ← 第 2 次：缓存命中，不再白等
```

日志里会说清这件事（不静默换通道）：
> `页面一直不 idle，已临时关掉系统动画抓到结构（抓完已还原）；本批后面再遇到这一步就直接走关动画，不再白等那 ~11 秒`

## 三、一个**被否掉**的方案（重要，别再试第二次）

用户说「坐标摸清楚了」，所以一度想把大量点击步改成 `tapXY`（盲点，不抓屏）。
**实测后否掉了**——这些屏的坐标会漂：

| 目标 | 观察到的坐标漂移 |
|---|---|
| 相册页页签 | y **276 ↔ 140** |
| 相册页网格 | y **359 ↔ 204 ↔ 240** |
| 编辑页标题框 `etTitle` | y **308（图文）/ 444（视频）** |
| 主页「发布新动态」 | 位置随上方内容变（网络驱动页面） |

盲点坐标一旦点错就是**静默点错**（挂错商品 / 少选一张图），最难查。
⇒ 最终只保留了**一颗**确定稳定的盲点：底部栏 `tab_user`，`[810,1819][1080,1920]` → 中心 **(945,1869)**，
与配置里的 `tapXY 945,1869` 完全对上（这是 App 全局底栏，不随页面变）。
其余全部保留抓屏，宁慢不误杀。

```
✅ smoke 39   ✅ adbtest 196   ✅ pendingtest 9   ✅ compliancetest 26
✅ videotest 43  ✅ batchtest 29   ✅ copytest 190   ✅ reporttest 49
✅ brandtest 82  ✅ uicheck 178   ✅ logintest 96   ✅ gatetest 19
✅ updatertest 50 ✅ releasetest 65 ✅ prunetest 45  ✅ logtest 45  ✅ cloudtest 57
```

**反向验证（定点破坏）：9 条靶断言，9 条被抓住，0 条漏网**

每条破坏都**从干净源码起**（先 `restore`），`try/finally` 兜还原，跑完复核 MD5 与快照一致。
判据是「**那一条断言行变成 FAIL**」，**不拿退出码当判据**（套件中断 ≠ 抓住）。

| 破坏 | 靶断言 | 结果 |
|---|---|---|
| D1 拆掉 `tapSeq` 多点合并 | 3 个点只发一条 shell | 红，实际变成 **3 条** |
| D2 拆掉守卫结构复用 | 带 whenOn 的步只抓 1 次屏 | 红，实际 **dump 次数=2** |
| D3 拆掉 rm/dump/cat 合并 | 同一条 shell 里 rm 先于 dump | 红，「没找到同时含 rm 与 dump 的命令」 |
| D4 拆掉 tapXY 不抓屏 | tapXY 一次 dump 都没抓 | 红，实际抓了一屏才点 |
| D5 拆掉 `preferAnimOff` 快路 | 已知这屏不会 idle 只抓一次 | 红，实际 **dump 次数=2** |
| D6 拆掉「记进缓存」 | 第 1 次跑就把这步记进缓存 | 红，**缓存={}** |

每条都配了**反向对照**，防止「空 == 空」式假通过：
- 数 dump 次数的断言配了「连抓两次就是 2」的对照
- 「第 2 次只抓一次」配了「不给缓存时两次都是 2+2=4 次」的对照
- 还加了一条**负向**：页面本来就会 idle 时**不许**往缓存里塞（否则以后会无端关掉用户设备的动画）

## 五、过程中踩到并修掉的坑（都写进注释了）

1. **`dumpOnce` 合并后 adbtest 一次挂 35 条** —— 夹具 `shellSub` 把 `2>&1` 当成「输出文件名」，还不认 `echo`。
   ⇒ 修夹具：剥掉重定向 + 支持 `echo`（真机上重定向不属于命令本身）。
2. **两条源码级断言被我自己的改动「正当打破」**（写法变了、语义没变）
   ⇒ 改成看语义：正则不锁死参数写法；「rm 先于 dump」改为在**同一条 shell 内**比先后位置。
3. **补断言时踩到「抛异常一条 FAIL 都不打」** —— 点击成功时 `runStep` 返回的是 `undefined`，
   我写成 `!r22.skipped` ⇒ 整段崩掉、一条不打，只看 FAIL 的人会误判成全绿。
   ⇒ 改 `!(r22 && r22.skipped)`。**这是本轮最险的一次假绿。**
4. **脚本是 LF、源码是 CRLF** ⇒ 跨行锚点 `count=0`。
   ⇒ 补丁一律「读入归一成 LF 匹配锚点、写回按该文件原风格转」，并回读复核 `CRLF>0 且 LF=0`。
5. **`screenGuard` 在 publisher.js 里，不在 adb.js** ⇒ 锚点放错文件，`count=0` 被闸门拦下、没落盘。
