# 得物蓝V：转网页版，还是继续做 App？

> 判断日期：2026-10-02
> 依据：本仓库源码实测（`D:\work\dewu-bluev-publisher`）+ `docs/HANDOFF.md` + 工作区记忆 `REFERENCE-得物蓝V.md`
> 口径：能给数字的地方给数字；没实测的地方明确标「未实测」，不拿推断当结论。

---

## 0. 一句话结论

**这不是「网页 vs App」的二选一。**

- 你的**发布核心**（读本地素材 → 本机 adb 驱动模拟器 → 上传/填文案/点发布）**只能跑在本机**，浏览器做不到（不是「难做」，是**做不了**，见 §1）。
- 所以你真正缺的**不是**一个网页版发布器，而是**一个跨机协作层**：谁负责哪几款、各机进度到哪、还剩多少、汇总统计。
- 正确解法 = **本机执行端（保留现有 App，做薄）+ 云端协作台（新增网页 + Supabase）**。执行层留本机，协作层上云。

**纯网页版对你这个业务流程走不通；但「网页 + 本机小助手」是可行的，而且那个「本机小助手」本质上就是你现在这个 App。**

## 1. 先摆事实：这个工具到底靠什么在干活

下面每一条都是从源码里读出来的，不是印象。右边一列是「换到浏览器会怎样」：

| 能力 | 现在靠什么（源码位置） | 换到浏览器会怎样 |
|---|---|---|
| 读本地 50 款素材目录 | Electron `dialog.showOpenDialog` + `fs`（`ipc.js:303`），能读**任意盘符任意路径** | ⚠️ 只能「用户手动授权一个目录」（File System Access API，Chromium 专属）或逐个选文件；拿不到任意路径 |
| 非 mp4 自动转 mp4 | 本机 `vendor/ffmpeg/ffmpeg.exe`（82.8 MB，`video.js`） | ❌ 浏览器不能执行本机 exe（WASM 版 ffmpeg 性能/兼容都差一档，且要重写整条转码逻辑） |
| **驱动模拟器发布** | 本机 `vendor/adb/adb.exe`：`push` 推图 → `mediaScan` 媒体扫描 → `uiautomator dump` 取控件 → `tap`/`inputText` 点击输入（`publisher.js:66~287`） | ❌ **浏览器沙箱里没有任何办法启动或调用本机进程** —— adb 一个字节都调不动。这是死结，没有绕过办法 |
| 中文输入 | 本机装 ADBKeyboard + `ADB_INPUT_TEXT` 广播（`adb.js`） | ❌ 同上，属于「操作本机模拟器」 |
| 发布结果台账 | 本机 `publish-log.jsonl` / `run-log.jsonl`（`stats.js`） | 换到浏览器**不会自动变好**，还得看数据层怎么设计（见 §2.2） |

**结论：发布这一步，浏览器物理上做不到。** 任何「纯网页版发布器」的方案，最后都会在「怎么把图推到模拟器、怎么点得物界面」这一步撞墙。

## 2. 逐条回应你的四个判断

### 2.1 「网页更方便」——一半成立

- **成立的一半**：多用户管理、看板、进度、日志聚合、跨机统计 —— 这些**确实**是网页的强项，App 天生弱。
- **不成立的一半**：**发布本身**。因为发布必须在本机跑 adb，所以「网页里点一下就把 50 款发出去」这件事不存在。
- 结论：**网页做「管理」，本机做「发布」**，不是用一个换掉另一个。

### 2.2 「app 端无法实时收取不同用户的操作日志」——不是 App 的锅，是数据层的锅

这条我特意去查了，你的判断方向对，但归因不对：

- 现在跨机统计**只能靠「把各台机器的输出目录指到同一个共享位置」**——这句话白纸黑字写在 `docs/HANDOFF.md:407-408`：
  > 「品牌统计页也补了一句写明：**这一页统计的是本机这个输出目录**，跨机汇总只能靠把各台指到同一个共享位置。」
- 也就是说：**收不到别人日志，是因为台账是「本机 jsonl」这个设计**，跟「界面是网页还是 App」**没有关系**。
- 反过来说：
  - 把数据层换成云（Supabase）→ **现有 App 一样能实时收**；
  - 你哪怕做了纯网页，如果台账还写在浏览器本地，**照样收不到别人的**。

⇒ **「收不收得到别人的日志」是「数据放本机还是放云」决定的，不是「web 还是 app」决定的。** 这是本次判断里最需要纠正的一条。

### 2.3 「app 端反馈链接 supabase 会有风险」——方向对，但解法不是「改用网页」

- Supabase 的**标准安全模型**就是：客户端只拿 **anon key（本来就设计成公开的）**，真正的门禁是数据库里的 **RLS 行级安全策略**。**浏览器端用 anon key 是它的原生用法**，不是漏洞。
- 真正的红线只有一条：**任何客户端（网页 or App）都不许内置 `service_role` key**（那是绕过 RLS 的万能钥匙）。所以风险点是「**密钥放哪、怎么轮换/吊销**」，不是「web 还是 app」。
- App 形态确实**多一些**麻烦（安装包分发出去、密钥嵌在包里、吊销不干净），但这是**可以设计掉的**：
  - App/执行端**不直连** Supabase 管理面，改用**机器令牌**（一机一令牌，可单独吊销）走一个很薄的网关（Supabase Edge Function 即可）；
  - 业务数据（发布结果/状态）上行用**最小字段集**。
- ⇒ 你现在担心的风险，**不用推翻架构来解决，用「一机一令牌 + 最小字段」就能收口**。

### 2.4 「app 端发布流程、速度都比网页端慢」——需要实测，而且大概率是误判

这条**必须用数据说话**。我从源码里读到的硬事实：

- 发布节奏是**人为间隔 60 秒/条**（`src/main/store.js:60  intervalSec: 60`）。
- 源码注释（`publisher.js` 文件头）写得很直白：
  > 「发布节奏是人为间隔（60–120 秒/条），**不是性能问题**；**2.5 小时里 93% 是在等间隔**」
- 也就是说：**发布耗时的 93% 是在「故意等」，不是在算、不是在渲染、不是在跑代码。**

**速度小账（按 60 秒/条）**：

| 并行设备数 | 7500 条预计耗时 | 说明 |
|---|---|---|
| 1 台 | ≈ **125 小时** | 7500 × 60s |
| 5 台 | ≈ **25 小时** | |
| 10 台 | ≈ **12.5 小时** | |
| 20 台 | ≈ **6.3 小时** | 需要 20 个得物账号，风控风险另算 |

（视频条按 90 秒/条另算；失败重跑另加。）

⇒ **决定速度的是「并行设备数」和「人为间隔」，不是你用什么技术栈做界面。** 换成网页，这 93% 的等待一秒都不会少。

> ★ 但这条**我给的不是实测结论**，是「从代码与设计推断 + 必须实测」的口径：你手里还没有网页版可以对比，所以「App 比网页慢」目前**无从证实**。建议先跑阶段 0（见 §5）把真实数字拿到手，再决定要不要谈提速。

## 3. 推荐架构：本机执行端 + 云端协作台（混合）

**核心思路：把「执行」和「协作」拆开，各放各该在的地方。**

```
        ┌──────────────────────── 云（Supabase）────────────────────────┐
        │  多用户账号 / 任务分配 / 进度看板 / 实时日志 / 跨机统计 / 权限  │
        └───────▲───────────────────────────────────────▲──────────────┘
                │ anon key + RLS                        │ 机器令牌（一机一令牌）
                │ （浏览器原生用法）                     │ （最小字段上行）
        ┌───────┴────────┐                    ┌─────────┴──────────────┐
        │  网页控制台      │  127.0.0.1 本机通道 │  本机执行端（每台一台）  │
        │  （浏览器）      │◄──── WebSocket ───►│  现有 App 做薄 / 或无界面版│
        │  看板·派活·监控  │    （配对码授权）    │  读素材·ffmpeg·adb 发布 │
        └────────────────┘                    └───────────┬────────────┘
                                                          │ adb
                                                   ┌──────▼──────┐
                                                   │ MuMu 模拟器  │
                                                   │ （得物账号） │
                                                   └─────────────┘
```

**两块分工：**

| | 本机执行端（保留现有 App） | 云端协作台（新增网页） |
|---|---|---|
| 干什么 | 读本地素材、ffmpeg 转码、adb 驱动模拟器、真实发布、写本地日志 | 多用户、派活、进度看板、实时日志、跨机统计、品牌权限 |
| 为什么放这 | 浏览器做不到（§1） | App 天生弱、且跨机必须共享（§2.2） |
| 技术栈 | **不换**，继续 Electron + adb | 新增，Supabase + 一个静态前端即可 |

**两条链路：**

1. **浏览器 ↔ 本机执行端**：走 `127.0.0.1` 的 WebSocket/HTTP。网页里点「开始发布」→ 通过本机通道发给执行端 → 执行端调 adb。
   - ★ 必须**配对授权**（执行端显示配对码/一次性令牌，网页输对才连得上），否则「任意网页都能控制你本机的模拟器」= 安全问题。
2. **双方 ↔ Supabase**：数据同步。浏览器用 anon + RLS；执行端用**机器令牌**把「发布结果（结构化）→ 状态」上行、把「当前进行到哪」下行。

**这样你抱怨的三点会同时消失**：
- 多用户实时看日志 → 云端 + Realtime；
- 跨机统计 → 云端聚合（不再依赖共享盘）；
- 发布仍在本机跑 → **速度一点不减**。

## 4. 如果你坚持「纯网页」——唯一路线与代价

唯一可行路线是**服务器模拟器农场**：

```
素材上传到服务器 → 服务器上跑 N 个模拟器 + adb → 纯网页监控
```

**代价（必须先想清楚）：**

1. **得物风控风险升高**：N 个账号集中在一台机器、一个出口 IP。**多人多机各自家宽 IP，反而比这安全。**
2. **要一台能同时跑 N 个模拟器的高配机器/多台机器**（模拟器吃 CPU/内存很厉害）。
3. **素材要上传**（你现在的隐私边界是「素材不出本机」，这条路会打破它）。
4. **得物账号的登录态/验证码**要集中处理，出问题就是全部停摆。

⇒ 只适合「**24 小时无人值守、大规模跑量**」的场景。就你现在的 50 款 × 150 篇、多人分工来说，**不划算**。

## 5. 落地顺序（建议）

> 原则：**先做便宜且见效快的，先拿数据再决定要不要谈提速。** 不要一上来就动发布核心。

**阶段 0（半天）—— 先实测，别猜**
真机跑**一条**发布，秒表计时，拆出「等间隔占了多久 / 真正操作占了多久」。拿到这个数，§2.4 那个争论当场结束。

**阶段 1（半天～1 天）—— 只读看板（性价比最高）**
- 各机把 `publish-log.jsonl` **增量上行**到 Supabase；
- 网页只读展示：**谁 / 哪款 / 发了几篇 / 剩几篇**。
- 立刻解决「看不见别人进度」+「跨机统计靠共享盘」两个真痛点，**不动发布核心一行代码**。

**阶段 2 —— 派活 + 实时日志 + 权限上云**
- 任务分配（哪个人负责哪几款、锁定防重复）；
- 实时日志（Supabase Realtime 推送）；
- 品牌/权限从「本机 auth.json」搬到云，一人一号。

**阶段 3 —— 收口**
- 执行端配对授权、一机一令牌、字段最小化、吊销流程。

**★ 不要做的**：**重写发布核心**（`adb.js` / `uimap.js` / `publisher.js`）。
这套代码是你踩了无数坑才稳下来的，有 **768 项断言**在守（uicheck / logintest / adbtest / videotest…）。重写 = 把那些坑（中文输入法判据、dump 抓不到、多色漏填才拦、扁平副本里转码…）**再踩一遍**。执行端只需要「做薄 + 加一个对外接口」，不需要换血。

## 8. 补充对照：那套「拓新系统」不是反例，恰恰是本方案的原型

> 追记（2026-10-02）：用户追问「我之前做的拓新系统，不是可以调用 MuMu 吗？」——我去看了那套代码
> （`C:\Users\Administrator\WorkBuddy\2026-09-18-19-34-22\dewu-kol`，**另一个工作空间**），结论如下。
> **上一轮的判断不变，而且被它印证了。**

### 8.1 「网页能调 MuMu」是错觉——调 MuMu 的从来不是网页

拓新的真实链路（读代码实证）：

```
网页（Supabase 后台）──只做两件事──► ① 往 run_requests 插一条 pending  ② 读状态
                                        （★ 网页端连 update 权限都没有，
                                          migration_12 只给 select/insert/delete）
                                            │
                                            ▼
本机 Python：watch_requests.py（每 10 秒轮询 run_requests）领任务
                                            │
                                            ▼
本机：app_scan.py → ADB = D:\MUMU\MuMuPlayer\nx_main\adb.exe → 驱动 MuMu
```

- 用户看到的是「**网页点一下，十几秒后模拟器就动了**」，于是记成「网页能调 MuMu」。
- 实际上：**网页只写了数据库里的一行**；**调 adb 的始终是本机那个 Python 进程**。
- 更硬的证据：**页面在权限层就改不了执行状态**（没有 `update` 权限）。一个连状态都改不了的网页，当然也不可能驱动模拟器。

⇒ **和 §1 的结论完全一致：浏览器碰不到 adb。拓新不是反例，是例证。**

### 8.2 两者真正的不同：一个是「读」，一个是「写」

| 维度 | 拓新系统（dewu-kol） | 得物蓝V |
|---|---|---|
| 任务性质 | **采集 / 读**（扫得物社区达人） | **发布 / 写**（发穿搭精选） |
| **得物有没有网页版入口** | **有** —— `www.dewu.com/community` ⇒ **主通道走浏览器自动化，根本不用模拟器** | **没有** —— 发布在 App 内 ⇒ **只能模拟器 + adb** |
| MuMu 的角色 | **可选支路**（只有「App 扫描」才用；`doctor.js` 里那几项「只影响 App 扫描，不影响网页扫描」） | **唯一通道** |
| 协作层 | **Supabase 任务队列** `run_requests` + 设备授权 + 看板 | **无**（本地 jsonl，跨机只能靠共享盘） |
| 谁在调 MuMu | 本机 **Python** | 本机 **Electron** 主进程 |
| 常驻能力 | 靠 agent 会话守候（一次 ≈54 分钟接力）⇒ **不稳** | 真常驻 exe ⇒ **更稳** |

**★ 决定性判据（下次直接套用）**：**看你要做的那个动作，得物有没有网页版入口。**

- 有（比如「浏览社区、看达人主页」）⇒ 浏览器自动化能顶，可以不碰模拟器；
- 没有（比如「发穿搭精选、发蓝V内容」）⇒ **必须模拟器 + adb**。

拓新之所以看起来「网页就能跑起来」，是因为它主要干的是**第一类**（读）；而你要干的是**第二类**（写）。

### 8.3 该抄什么、不该抄什么

**该抄（而且比我上一轮提的 WebSocket 更好）**：

- **云端任务队列 + 本机轮询领取**：网页往队列里写任务，本机执行端每 10 秒拉一次。
  比「浏览器↔本机开端口 + 配对码」**更简单**（不用开端口、不用配对、无暴露面），
  且**天然多机并发安全**（拓新用 `--expected=<状态>` 做原子认领，两个实例不会抢同一条）。
- **网页只给写权限、不给改状态的权限**（拓新 `migration_12` 就是 select/insert/delete，**没有 update**）——
  状态只能由执行端回写，从根上防止「网页乱改执行结果」。
- **设备授权 + 心跳**（一机一名、管理员开启才接单；未授权只写日志不接任务）。
- **台账读不到时放行、只在其明确 `enabled === false` 时才拦**（保守方向 = 宁可跑，不让一次查询失败把整点停摆）。

**不该抄**：

- ★ **别抄它的「会话守候」**：拓新的监听器**靠 agent 会话活着**（一次 `--budget=9` 连跑 6 遍 ≈54 分钟接力），
  因为平台**禁止真常驻进程**（`CREATE_BREAKAWAY_FROM_JOB` / `Register-ScheduledTask` / WMI / `explorer` 代启**四条路全堵**）。
  这会带来「会话一断、任务卡在 running」的老毛病。**蓝V 有真常驻 exe，这条完全不需要。**
- ★ **别把发布搬到服务器**：拓新是「读」，蓝V 是「写 + 账号风控」，风控敏感度不是一回事（见 §4）。

### 8.4 一个值得先核实的前提

**得物的「穿搭精选发布」到底有没有网页版入口？**

- 如果**没有**（当前实现如此）⇒ 本报告 §3 的混合架构成立，执行端必须留本机。
- 如果**有**（像社区那样能网页发布）⇒ 游戏规则会变：发布这一半也可能像拓新一样走浏览器自动化，
  整个架构会轻很多。

★ 这个前提我**没有核实过**（没实测得物的网页端发布能力），所以**不当作结论**——建议你确认后再定方案。
