# 四项故障排查与修复（2026-10-03 晚）

设备：`127.0.0.1:16384`（MuMu 12 / Android 12 / 1080×1920），全程真机实测，数字可复算。

---

## 一、为什么"点开始发布后模拟器毫无动作、30 条全在排队"

### 根因：代码在等一个跟"得物看不看得到素材"**毫无关系**的条件

`publisher.js` 原来在推完视频后会调 `adb.mediaVisible()` 等 **MediaStore 索引到这个文件**，最多等 180 秒；等不到就 `throw`。
于是每条视频都在这里耗满 180 秒然后失败 —— 30 条就是 30 次失败，界面表现就是"全部排队、模拟器没动作"。

### 实测证据链

| 步骤 | 实测结果 |
|---|---|
| 把一个 mp4 放进 `/sdcard/DCIM/Camera`，确认它**不在** MediaStore | `instore = False` ✓ 前提成立 |
| 冷启动得物 → 走发布入口 → 打开相册 | 相册 `flVideo = 6`，设备 mp4 数 = 6 |
| 数相册里的时长标记 | `00:05 ×3、00:15 ×3` —— **不在库里的那个 00:05 也在列表里** |
| 这是不是实时监听？ | 停在相册页不退出，再放一个新文件，`flVideo` 恒为 6，**不会冒出来** |

⇒ **得物是"打开相册那一刻"自己扫文件系统，既不读 MediaStore，也不是实时监听。**

同一台设备上，让文件进 MediaStore 的办法我全试过：

| 办法 | 结果 |
|---|---|
| `am broadcast MEDIA_SCANNER_SCAN_FILE` | `result=0`，但**没有接收者**，不进库 |
| `content call --method scan_file` | 返回空 `Bundle`，不进库 |
| `am broadcast MEDIA_MOUNTED` | 受保护广播，`Permission Denial ... uid=2000(shell)` |
| `content insert` 直写 MediaStore | 没权限（shell 不在 media_rw 组），设备也没有 `su` |
| `force-stop` 媒体提供器 | **约 45 秒后进库**，但期间 `/sdcard` 会变成 `Permission denied` |
| 重启模拟器时的开机扫描 | 有效（`326113200712-1.mp4` 的 `date_added` ≈ 开机时刻） |

### 修复

- 新增 `adb.filesMissing()`：推完当场确认文件真落到设备上（一条 shell，约 150 ms）
- 「等 MediaStore」降为**可选**：`videoIndexTimeoutSec = 0`（默认，不等）；设成正数才退回旧行为
- 同步修正 `adb.js#mediaScan` 上方那段会误导人的注释（它原写着"调用方**必须**等 mediaVisible"）

## 二、为什么"我设的是 1 分钟，日志却按 90 秒"

`store.js` 里有个**界面上根本没有控件**的隐藏默认值 `videoIntervalSec: 90`，而代码里视频一律用它：

```js
const wait = video ? (c.videoIntervalSec || Math.round((c.intervalSec || ...) * 1.5)) : ...
```

你设的 `intervalSec = 60` 对视频**完全不起作用**。预估"75 分钟"就是这么来的：30 × (90 + 60) = 4500 秒 = 75 分钟。

### 修复

- `videoIntervalSec` 默认改成 **0** = 跟随你在界面上设的那个
- 三处引用（`estimate` / `run` / 界面预估）全部去掉 `× 1.5`
- 真需要单独放宽视频间隔时，显式填一个 >0 的秒数仍然生效
- 你现有的 `config.json` 里压着 `90` / `180` 两个旧默认值，**已归一成 0**（原文件已备份）

修完：30 条视频预估从 **75 分钟 → 60 分钟**（30 × (60 + 60)）。

## 三、为什么"只开了一个模拟器，却有两个设备序列号"

`adb devices` 在你这台机器上会列出三行：

```
127.0.0.1:16384   device  product:Nottingham model:NTH_AN00
127.0.0.1:5555    device  product:Nottingham model:NTH_AN00
127.0.0.1:7555    device  product:Nottingham model:NTH_AN00
```

实测三者 `settings get secure android_id` **全是 `927145746ae845d6`**、`/proc/uptime` 也一致 ⇒ **是同一台模拟器，MuMu 12 把它暴露在三个端口上**，不是三台设备。

### 修复

`scanDevices()` 现在按 `android_id` 判同一台，只留一个主串，界面上主串下方标一行：
"这台还出现在 16384 / 7555 —— 同一个模拟器的其它端口，不用管"。
**读不到 android_id 时一律不合并**（宁可多列，也不把两台真设备并成一台 —— 这条有专门的负向断言守着）。

## 四、为什么"货号 / 颜色两列是空的"

`report.js` 构造 `copyRows` 时只给了 `{ id, title, body, topics, status, from }`，**没带 sku/color**；
而文案生成页那两列读的正是 `copyRows`（`app.js`：`rows.length ? rows : …`）。
同一时刻 `items` 里其实早就有值 —— 实测 `3261132007+煤黑色01+1` 能正确解析成 `sku=3261132007 / color=煤黑色01 / how=plus`，只是没带到 `copyRows` 上。

### 修复

- 把 sku/color 提成变量，`items` 与 `copyRows` 共用
- 再加一道兜底：任何 copyRow 缺这两个字段，按 id 从 `items` 补齐（防以后新增构造路径重犯）

| 真机验证 | 落地确认通过；不在 MediaStore 的新视频**出现在相册里**（00:05 从 2 个变 3 个） |

反向验证里两条我的判断错误，已记下来：

1. **D1 我期望写多了** —— 破坏后走旧路径，夹具里没造"索引延迟"，发布照样成功，"真的发出去了"那条本来就不该红。
2. **D5 只拆一处被兜底救回来** —— 我给 `copyRows` 加了兜底，只破坏"构造时不带字段"断言仍是绿的，必须**把兜底一起拆掉**才红。这是"一处缺陷多道防线"的老坑。
3. 另外我自己把破坏写成 `copyRows.push({ id, title: row.title // 破坏`，**行尾注释吃掉了后面的 `});`** ⇒ 源码语法错误 ⇒ 测试一条都没跑（0 PASS 0 FAIL）。已给验证脚本加了健全性检查：**破坏后 PASS 数必须 > 0**，否则报"破坏方式有问题"，不让它被误读成"断言没抓住"。
