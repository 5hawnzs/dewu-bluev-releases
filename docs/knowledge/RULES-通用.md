# 跨项目工作偏好（用户级）

> 由多轮协作归纳出的硬要求，与具体项目无关。**项目专属规则写在各自项目的
> `.workbuddy/memory/MEMORY.md` 里**，不要往这里堆。

## 诚实性（最高优先级）
- **绝不写假值**：取不到数据就说「取不到」/填 `—`；**未知 ≠ 0**。
- 认不出的东西不得当成「已确认不满足」。**不编造、不美化、不把猜测写成事实。**
- 汇报失败/降级要**明说**（例如「未迁移，功能已置灰」），不许让界面骗人、也不许让结论骗人。

## 速度与准确度的取舍
- 要求「最快最准」时：**快 = 减少无效耗时，准 = 不误杀本来有效的东西**。
  宁可多花一次开销也绝不误杀；任何「为了显得快而丢数据」的方案都要拒绝并说明。

## 改动的证据标准
- 说「修好了」之前必须有**可复算的实测数字**（前后对比），不能只有推理。
- 测试要**双向**：喂「改前」的版本必须红，否则证明不了断言在查东西。
  ★ **「反向验证」的「假通过」坑（①~⑭，都实测踩过；全绿 ≠ 断言有效）**：
  ① **备份顺序写反** —— 先 `cp` 再改，备份的是**正确版** ⇒「用改前版跑」也全绿。
     必须**先造坏版**（在正确内容里定点替换掉关键判断）→ 跑到红 → 再删掉坏版。
  ② **环境变量选错** —— 测试读的是 `PERM_HTML` 而你传了 `DEWU_IDX` ⇒ 全绿。
     反向验证前先确认「这个测试到底读哪个变量」。
  ③ **改前版抛异常而不是报失败** —— 测试脚本 `split()` 一个改前不存在的串 → `IndexError`。
     切分前先判 `len(parts) > 1`，并加一条显式断言说明「改前版根本没有这东西」。
     ★ 同一个坑的另一副面孔：**把待测真函数抠出来跑时，坏版会让它 `TypeError`**
     （例：关掉 `if (!rows.length)` 后走到 `rows[0].xxx`）⇒ 测试**直接崩、一条 FAIL 都不打**，
     反向验证时看着像「这段根本没被覆盖」。⇒ 抠函数跑必须 `try/catch` 接住，
     并补一条「**所有用例一个都不许抛异常**」的聚合断言（它往往是唯一抓住这类坏版的断言）。
  ④ **坏版只是「追加」、没「替换掉」关键那句** —— 例如在事件处理器后面加一行无关注释，
     原处理器照样生效 ⇒ 坏版根本没坏，断言仍绿，**看起来像「断言无效」，其实是坏版没造对**。
     （2026-09-22 实测：`var z = t.closest('[data-zoom]')` 后面追加一行 ⇒ 点击仍能打开弹层。）
     ⇒ **造坏版后先自问「我到底改掉了哪一条判断」**；只有把关键那句**替换成不成立的**才算坏版。
     ⇒ 脚本里加两条护栏：替换前断言 `count(旧串) == 1`、替换后断言 `旧串 not in 新文本`。
  ⑤ **定点破坏的锚点不唯一** —— `text.replace(旧, 新)` **只换第一处**。锚点若在文件里出现
     多次（实测 `if (!rows.length) {` 出现 **7 次**），你以为改的是目标那段，其实**等于没改** ⇒
     坏版仍是好的、断言仍绿（同④，也是一种假信号）。⇒ 锚点先过 `count==1`，不唯一就**拒绝执行并报错**
     （把上下几行一起当锚点），别默默替换第一处。
     ★ **跨行锚点遇到 CRLF 文件 ⇒ `count` 会变成 0**（2026-10-01 实测）：源码里是 `\r\n`，
     而锚点字符串里写的是 `\n` ⇒ 永远匹配不上，表现为「锚点找不到」而不是「改错地方」。
     ⇒ 多行锚点要么显式用 `\r\n`，要么**只取其中一行**当锚点（更稳）；`apply()` 里再加一层兜底：
     原文匹配 0 次且锚点含换行时，自动把 `\n` 换成 `\r\n` 再试一次。
  ⑥ **一处缺陷往往有多条防线 ⇒ 只拆一条会全绿**（2026-10-01 实测）。同一个坑常被两处独立代码
     同时兜住：例 `adb.dump()` 的「失败时返回上一屏」被 ① 抓前 `rm -f` 远端文件、
     ② 检查 dump 是否真回了 `dumped to` 两条防线拦住。实测数字：只拆 ① → **只红 1 条**
     （顺序断言），核心那条「返回值必须是 null」**仍是绿的**；只拆 ② 也不红核心那条；
     **①+② 一起拆才红 6 条**。
     ⇒ 判据：**破坏工具明明打印了「已破坏 X」，测试却全绿 ⇒ 先怀疑「还有另一条防线」**，
     而不是「断言没在查东西」。**逐条排除到某条断言变红**，才算证明它有效。
     ⇒ 工具要支持**一次破坏多项**（`break P6 P9`）；坏版注释里写明**哪几项属于同一处缺陷**，
     免得下次又只拆一条。（已落进技能 `bilateral-fix-verification` §3.1。）
  ⑦ **比较型断言：两边都可能取空 ⇒ 空==空 判成「一致」**（2026-10-01 实测）。写
     「本地 X == 远端 Y ⇒ ✅ 一致」时，只要**取值命令本身失败**（路径写错、命令报错），
     两边都会是空串，`[ -n "$X" ]` 又忘了加 ⇒ 打出绿字，其实什么都没比。
     ⇒ 比较型断言**先断言非空**（`[ -n "$X" ] && [ -n "$Y" ]`），且**打印实际值**
     （`本地=$A 远端=$B`）—— 空值一眼就穿帮。
     ⇒ Windows 沙箱里这条尤其容易中：**别把 `/d/...` 传给原生 exe**（`git -C /d/work/x` 会被
     解析成 `<当前盘>:\d\work\x`），拿到空结果再一比就「假一致」。（见技能 `win-sandbox-scripting`）
  ⑧ **破坏脚本自己崩在半路 ⇒ 还原没跑到、坏版被留在源码里**（2026-10-01 实测，这一类比「假绿」更危险）。
     `check` 的流程通常是「逐个 `apply` → 跑测试 → 最后统一 `restore()`」；只要中途任何一步抛异常
     （实测就是 ⑤★ 的 CRLF 锚点，`count==0` 直接 throw），`restore()` 就永远不会执行 ⇒
     **磁盘上留下 B1~B5 的全部坏版**，而人只看到脚本报错退出，很容易直接去改别的。
     ⇒ 三道护栏：(a) `apply()` **先把所有替换全部校验通过，再动磁盘**（改一半是最糟的中间态）；
     (b) 循环体用 `try { ... } finally { restore(); }` 兜住 —— 崩了也必须还原；
     (c) **每次跑完都要独立复核**：`grep -rn "BREAK " src/` 与 `*.bak` 必须为空，
     别信脚本自己打印的「已还原」（它可能根本没跑到那一行）。
  ⑨ **报告里的数字别凭记忆**（2026-10-01 实测）。断言数 / 文件数 / 行数这类数字每次改动都会变：
     嘴上说「291 项全绿」，实测是 **294**（差在 `brandtest` 实际 58 项、不是 55）。
     ⇒ **写进文档或汇报前重新跑一次、取真实输出**；顺手核对文档里已存的旧数字（旧文档还写着 216）。
     ⇒ 同理：**字符数要按字符算、不能按字节**（中文 1 字 = 3 字节，`wc -c` 会吓人一跳）；
     记忆文件的「上限」也不例外（实测 8062 字节 = 3990 字符，后者才是判据）。
  ⑩ **逐条破坏没有先「还原」⇒ 上一条的破坏留在盘上，红里混着上一条的效果（「累计破坏」）**（2026-10-01 实测）。
     `check` 的朴素写法是「`for` 每项：`apply` → 跑测试 → 记录 FAIL 数 …最后统一 `restore`」。
     这样 **B2 的 FAIL 数里就含着 B1 的破坏**——你以为在量 B2，其实量的是「B1+B2」。
     实测：B8 本该只红 **1** 条，因为 B7 的破坏还在，红了 **3** 条 ⇒ 结论完全失真。
     ⇒ 修法：循环体里**每条破坏之前先 `restore(true)`**（静默还原），保证**每条都从干净源码开始**。
     修后逐条数字才可信（实测 B7→2 / B8→1 / B9→1 / B10→3 / B11→1 / B12→1，各自干净）。
     ⇒ 判据：**破坏工具报「已破坏」，却红了「明显不相关」的断言 ⇒ 先怀疑上一条没还原**，
     别急着下「这条断言在查别的东西」的结论。与 ⑧ 是同一件事的两面（⑧ 是崩了没还原，⑩ 是没崩但也没还原）。
  ⑪ **破坏脚本的「备份」只建一次、还原时又把备份删掉 ⇒ 后面每条破坏都无备份可还原，最后一条坏版
     永久留在源码里**（2026-10-02 实测，比 ⑧ 更隐蔽：**脚本全程没崩**，还正常打印「已还原：True」）。
     实测经过：开头 `copyfile(SRC, BAK)` 建一次备份；循环体「apply → 跑测试 → `restore()`」，
     而 `restore()` 写成「`copyfile(BAK, SRC)` + `os.remove(BAK)`」⇒ **第 1 条还原之后 BAK 就没了**，
     第 2~4 条破坏直接写盘、跑完调 `restore()` 时 BAK 不存在 ⇒ **什么都没做**，坏版一路叠加。
     最后那句「已还原」判的是「BAK 不存在」——跟源码干不干净**毫无关系**。
     后果：源码里留下 `st.offset += 0`（把增量游标废掉），症状是**「单独跑测试全绿、进一键回归却红」**，
     极易被误判成环境差异 / 并发干扰（实测真去查了 env 与 tmpdir，白查半天）。
     ⇒ 修法：**还原＝把内存里那份干净副本写回磁盘，再读回来逐字比对**，不一致直接退出并报错。
     别拿「备份文件」当唯一真相源（它的生命周期比循环体长不了多少），**更别拿「备份在不在」当还原成功的判据**。
     ⇒ 判据：**「单独跑绿、批量跑红」⇒ 先 `git diff` 看源码是不是被上一轮的破坏脚本改过**，别先查环境。
     ★ 推论：**上一轮记下来的破坏红数也要重跑重取**——修好还原逻辑后，实测 B2 从 **10** 掉到 **1**、
     B3 从 13 掉到 3、B4 从 9 掉到 2、B6 从 12 掉到 3。**拿旧数当基准 = 拿失真数当基准。**
  ⑫ **同一段文案里本来就同时出现两个互斥词 ⇒ 「文本里包含 X」型断言说反了也照样绿**（2026-10-02 实测）。
     实测经过：界面那行是「`跟随内置` 当前实际在用：https://… · 来源：`跟随内置（换项目＝发新包…）`」——
     徽章 + 说明**都**含这两个词。断言写成「整段 `.includes('跟随内置')`」，
     于是把「来源」那半句**人为改成「本机指定」**（真·说反）后仍然 PASS。
     改成「只取 **`来源：` 后面那一段**，且**不许出现反面的词**」之后，坏版才真变红。
     ⇒ 判据：**断言盯的片段里若存在互斥词（是/否、开/关、A/B），「包含」型断言必然假通过** ——
     要么截到唯一片段再比，要么加一条「不许出现反义词」的负向断言。
     ★ 这条属于 ⑥（一处语义多条防线/串味）的近亲：**不是断言没查东西，是它查的那个词同时属于两种结果**。
  ⑬ **验「被拒绝」只测了负向 ⇒ 假通过**（2026-10-02 实测）。给表打一条**错 org** 的插入，
     返回 `401 + 42501 new row violates row-level security policy` —— 看着像「策略在按 org 卡人」，
     其实「这张表谁都插不进去」（缺 grant / 压根没策略）**给的是同一个错误码**。
     ⇒ 必须补一次**正向对照**（用正确的值插进去返 `201`），才证明策略**按值区分**。
     ★ 旁证技巧：被 RLS 拒的插入**会消耗 identity 序列**（探针行拿到 `id=2` 而不是 1）
     ⇒ 说明它走到了 `with check` 才被拒，不是卡在权限层。
  ⑭ **「幂等 / 防重 / 可重试」只按代码判、没喂重复请求 ⇒ 以为做了、其实没做**（2026-10-02 实测）。
     源码里明明写着 `Prefer: resolution=ignore-duplicates`，实测重复插入照样 `409 + 23505`；
     补一个 `?on_conflict=<唯一索引的列>` 才真的 `201`（响应头这时才出现 `preference-applied`）。
     ⇒ 判据：**「防重」的判据是「重复请求的返回」，不是「源码里写了那个头」**；
     并且顺手问一句「客户端拿到这个失败会怎么办」——本例里它**不推进游标**，
     于是同一批永远重发 ⇒ **同步永久卡死**（网络越差越容易踩：插入成功但响应丢了/超时）。
     ★ 与 ⑦（比较型断言两边取空）同族：**没喂到能区分两种结果的输入，就等于没测。**
  ⑮ ★★★ **「故障现象 / 夹具判据 / 修复代码 / 回归断言」四者互为出处 ⇒ 整套可靠性 = 0**
     （2026-10-04 实测，代价是**真的改坏了发出去的内容**）。
     经过：真机上报 `输入失败：/system/bin/sh: no closing quote`。我判定「设备端 sh 把**行首 `#`** 当注释，
     连带吃掉收尾双引号」—— 而这条判据的**唯一出处是我当时新写的假夹具里、我自己编的那一行**
     （`if (/(^|\n)(#|`)/ && !/(^|\n)\\ /) return fail('no closing quote')`）。
     随后：照这个判据写「转义修法」⇒ 夹具变绿 ⇒ 断言照着修法写 ⇒ 全绿收工。
     四样东西其实是**同一个幻觉的四个副本**，互相"证明"。
     真实后果不是"没修好"，是**把反斜杠写进了发布出去的正文**（真机 dump 读出 `\#TW男装`）。
     真机逐条实验 12 组（MuMu 12 / Android 12）：行首 `#`、`##`、行首反引号、`"a\n$X"`、`"a\n;b"` **一次都不炸**。
     ⇒ 破法三条：
       ① 判据只能来自**被测系统本身的逐条实验**，不许由我发明；夹具里**不许出现我没在真机上见过的判据**。
       ② 修法的证据必须**独立于修法**：本例用「设备端**真正收到的字符串**逐字符 == 源文」这个行为级断言
          （夹具按 sh 双引号语义解码后记账）—— 它当场就能红给我看。
       ③ 遇到「某个现象只有我这个新夹具能复现」时，**先怀疑夹具**，而不是先写修复。
     ★ 与 ③（改前版抛异常⇒一条 FAIL 不打）、⑥（一处缺陷多条防线⇒只拆一条假绿）同族，
       但更狠：那两条是**测不到**，这条是**测反了**。
  ⑯ ★★ **双向验证脚本「跑起来之后」，工作区的被改文件不能当判据**（2026-10-05 实测）。
     破坏脚本 = 「改成坏版 → 跑 → 还原」，所以它运行**期间**目标文件**本来就是坏的**。
     实测踩坑：跑到一半去 `git diff` 看那条修复，看到的是**坏版那行**，差点判成「我的修复没生效」。
     ⇒ 铁律：脚本一启动就把原始字节落成 `*.prebreak` 备份；**中途任何核对（审自己的改动 / 锚点唯一性）
       都读那个备份**；还原也**只认备份**（`cp` 回 + md5 复核），始终**禁 `git checkout`**。
     ⇒ 要「跳过某一轮、只重跑另一轮」，给脚本加 `--only=<标签>`，**别手工去改源码**。
  ⑰ ★★ **跑套件的那次 `execFileSync` 必须带 `timeout`**（2026-10-05 实测）。
     同一份坏版，一次 run 只要 **289s** 正常收敛；另一次 **19 分钟仍未返回**（该次阻塞的**确切原因未查明**，
     不编）。判「在跑」还是「卡住」：采样进程 **CPU 时间 + 内存** —— 都不涨 ⇒ 阻塞。
     ⇒ `timeout: 12*60*1000` 起步；`catch` 里区分「断言失败」与「被超时杀掉」（`e.signal || e.killed`），
       超时那一轮**记为不可用**，不许当通过。处置顺序：**停进程 → 按字节备份还原（md5 复核）→ 补超时 → 只重跑那轮**。
  ⑱ ★ **一个坏版可能同时具备两个方向的缺陷 ⇒ 期望表要把两条都算红**（2026-10-05 实测）。
     把一处正则「改回旧写法」这种破坏，我原以为只该让**正向**断言红；实测**负向**也红 ——
     因为那个旧写法本来**两头都错**（既拒合法值，又放行假格式），而这正是当初那个 bug 的两半。
     现象是脚本报「与预测不符」，**其实是我预测漏了一半**。
     ⇒ 负向用例里**必须**留着「旧版会错误放行的那种值」，否则这条破坏会漏掉一半缺陷。
     ⇒ 边界：破坏面**广**（一次红一片）不叫「分辨力有问题」；判据永远只有一句 —— **我指定的那条，红了没有**。
- 断言盯**语义**，别锁内联写法（重构会连出假红）；负向断言只看**代码行**（注释会一起命中）。
  ★ 这条自己写测试时**最容易忘**：2026-09-22 写「源码里不再出现那个错句」的负向断言时，
  被**我自己写来解释这个坑的注释**弄红了 ⇒ 负向断言一律先 `codeOnly()`（只留代码行）。
  ⇒ 若维护一份「通用测试基座」（抠函数 + 灌桩 + 反向验证），就把 `codeOnly()` / `count==1` 检查
  / `try-catch` + 「不许抛异常」断言**做成基座里的固定件**，别指望每次记得。
- 「源码里有这行字」≠「它真的解决了问题」→ 关键修复做**行为级验证**（把真实代码块抠出来跑）。

## 会话与任务存储（客户端机制）
- **任务（todo）按会话隔离**：`~/.workbuddy/tasks/<sessionId>/*.json`（一个会话一个目录）。

  多半是**在看另一个会话**，不是数据被删。
- **对话消息会丢**（已实测发生）⇒ 用户的重要交办要**落地成工作区文件**（台账/待办），

- ★★ **「越用越卡、一卡消息就没了」的根因是会话记录文件太大**：

  （同机第二大会话仅 22.9 MB）⇒ 客户端每轮读写/渲染巨型文件；**卡住瞬间你的消息写入被中断 ⇒ 没落盘**
  （旁证：消息时间戳出现**乱序**）。**诊断**：按大小排序 `projects/` 下的 `*.jsonl`。
  **对策 = 开新会话**（换工作区不管用），但先写一份**交接单**再走。
- ★ **迁移会话的完整流程**（实战）：
  ① 先查这个会话体量（上一条命令）+ 列清「真正没做的」；
  ② ★ **开工前先 `git status` + 看关键文件 mtime** —— 可能**另一个会话刚改过同一份文件**

  ④ 写交接单：怎么用 + **新会话该选哪个工作区** + 先读哪几份 + 当前真实状态（含**已知失败**）+ 环境速查；
  ⑤ 交付时附上交接单与台账文件（用户可能换端打开）。
- ★★ **记忆有两套，别写错地方**：**工作区级** `<工作区根>/.workbuddy/memory/` 是**自动注入源**，

## 环境
- Windows 沙箱下的命令/路径/编码坑见技能 `win-sandbox-scripting`。
- **每次 Bash 调用都是新 shell** ⇒ PATH 必须在**同一条命令里**重新 `export`（否则 `ls`/`env` 都找不到）。

- ★ **同一文件的多个 Edit 必须串行**（一个消息只发一个，等结果再发下一个）：并行发会**互相覆盖、只有最后一个生效**
  （Edit 仍返回成功，前面的改动被静默吞掉）。改完立刻用测试/读文件验证，别信「Edit 返回成功」。

## `show_widget` 内联片段的结构约束（2026-10-01 实测）

- ★★ **片段必须以非 `<svg>` 元素开头**。若把 `href="#…"` 要用的那张
  `<svg width="0" height="0">`（`<symbol>` 符号表）放在**开头**，会收到
  `"widget_code must contain exactly one <svg> element."` 而**整份被拒**。
  ⇒ 规则：**setup 块一律放末尾**（`body + SETUP`；`<use>` 是渲染期按 id 解析，前向引用合法），
  这样片段以 `<div>` 起头、按 HTML 解析。
  **顺序改了画面变没变必须证**：`<use>` 版 vs 直连版逐像素比对（实测 0 / 4,012,800）。
- ★ **同一片段里 id 不能重**：内联 N 份同一图形 = N 个同名 `id`，
  而 `url(#x)` 取**第一个**匹配项 ⇒ 副本颜色碰巧一致时看着没事，**换变体就上错色**（真 bug，非洁癖）。
  解法：`<symbol>` + `<use>` 去重（实测 19.9KB→11.8KB）。
  写盘前 `assert len(ids) == len(set(ids))` 且 `set(refs) <= set(ids)`。
- ★ **`%` 占位符比参数多不会报错**，`%d`/`%s` 会直接印进产物 ⇒ 拼完立刻
  `assert not re.search(r'%\d?\$?[ds]', HTML)` 与 `assert '%%' not in HTML`。

## JS 模板字符串里写注释：禁带反引号

在 ``...`` 模板串**内部**写 `//` 注释时，注释里出现 **反引号** 会把模板串**当场截断**，
`node --check` 报 `SyntaxError: missing ) after argument list`，而且报的行号指向模板串**开头**，
很容易看错地方（实测：在 `tools/uicheck.js` 里用 `executeJavaScript(`(async () => {...})()`)`
包一大段脚本时踩到）。

- 症状：报错行 = 模板串起始行；真正的原因在**后面**某条注释里。
- 对策：模板串里的注释**一律不要用反引号**引用标识符，改用 `「」` 或直接不引。
- 同理：`python -c "..."` 里的反引号会被 **bash 命令替换**吃掉（见本文件另一条）——
  两类坑的共同点：**外层引号语法 + 内层反引号 = 静默或半静默截断**。
- 自查：改完含模板串的文件，立刻 `node --check <file>`，别等跑测试。
## ★★ 记忆「上限」是**字符**，不是字节（2026-10-03 实测踩过）

- 症状：用 `wc -c` / `ls -l` 的文件大小判「`MEMORY.md` 有没有超 4000 上限」⇒ **虚高近 3 倍**
  （中文在 UTF-8 里占 3 字节），于是把「还剩 25 字符」误报成「已超限、被静默截断」，**给用户报了个假结论**。
- 实测（2026-10-03）：用户级 `~/.workbuddy/MEMORY.md` = **字节 8002 / 字符 3950**（上限 4000，剩 **50**）；
  某工作区 `MEMORY.md` = **字节 5594 / 字符 2975**（上限 3000，剩 **25**）。
- ⇒ 判超限一律用 `len(io.open(p, encoding='utf-8').read())`（Python 字符数）。
  **不要**用 `wc -c`、`os.path.getsize`、`ls -l`（它们给的是字节）。
- ★ 「顶格」≠「已截断」，真正要盯的是**剩余量**；上面两例都已**顶到罚球线**，下一次写入就会从尾部丢规则。

## ★★ 会话「闪退 / 不见了」之后，怎么把内容捞回来（2026-10-03 实测）

**结论先说：闪退 ≠ 数据没了。** 会话记录是**逐条落盘**的，客户端崩了文件还在。
用户说「前个会话也没完成，闪退后就没了」时，**不要重头再问一遍**，直接去磁盘捞。

### 1. 文件在哪 / 谁是谁

- 路径：`~/.workbuddy/projects/<目录名>/<sessionId>.jsonl`（**一行一条 JSON 记录**）。
- ★ `<目录名>` **不可逆推真实路径**（`-` 同时表示 `:` 和 `\`，且真实文件夹名本身也含 `-`）
  ⇒ 要判归属就读每行里的 **`cwd`** 字段。
- **谁是「当前会话」，别看文件大小**：找同目录下 **mtime 最新且在长大**的那个
  （隔 1 分钟两次采样，两次都前进 = 活跃会话）。实测：同目录同时有 **109 MB** 的旧会话
  和 **170 KB** 的新会话，新会话才是用户当前在用的那个。

### 2. 记录长什么样（解析时的三个坑，我全踩过）

| 记录 `type` | 说明 |
|---|---|
| `message` | 真正的对话消息，`role` = `user` / `assistant` |
| `reasoning` | 模型思考（`rawContent[].reasoning_text`）—— **待办/结论常藏在这里** |
| `function_call` / `function_call_result` | 工具调用与结果（结果在 `output.text`） |
| `file-history-snapshot` | 文件改动快照 |

- **坑 1：消息正文块不是 `type:'text'`**，而是 `input_text` / `output_text`，正文在 **`text`** 字段里。
  只判 `b['type']=='text'` 会**打印出一片空**，误以为「没记录」。
- **坑 2：JSON 是紧凑无空格的**（`"type":"message"`）。用 `'"type": "message"'` 当预过滤 ⇒ **0 命中**。
- **坑 3：109 MB 别整体 `json.loads`**。只读尾巴：`f.seek(max(0, size-4_000_000))` → `split('\n')[1:]`
  （**丢掉第一行**，它被 seek 截断了）。

### 3. 最值钱的一条：`conversation_history_summary`

上下文爆掉时客户端会自动塞一条**摘要记录**（`message`，role=`user`，正文包在
`<conversation_history_summary>` 里）。它有固定小节，等于**现成的交接单**：

```
## 1. Primary Request and Intent     用户到底要什么
## 3. Files and Code Sections         改过哪些文件
## 4. Errors and fixes                踩过什么坑、怎么修的
## 6. All user messages               用户说过的原话（引用/追责用）
## 7. Pending Tasks                   ★ 待办
## 8. Current Work                    崩在哪一步
## 9. Optional Next Step              ★ 下一步该干嘛
```

### 4. 标准动作（照做即可）

1. `ls -lat` 该工作区对应的 `projects/<目录名>/` → 认出活跃会话 + 被闪退的那个。
2. 从**闪退那个**文件尾部捞：最后一条 `message`（谁说了什么）+ **最近一条 `conversation_history_summary`**（§7/§8/§9）。
3. ★ **拿它跟当日工作日志 + 磁盘现状（`git status`、配置、产物 mtime）对一遍**再回答 ——
   摘要里的「Pending Tasks」可能已经被后面的动作做掉了，**别把已完成项当待办报给用户**。
4. 把捞回来的摘要**落成工作区里的一个文件**（命名带「内容找回」），并告知用户路径 ——
   他那边界面上的会话是真的没了，这份文件就是他唯一能回看的东西。

### 5. 顺手要做的两件事

- **恢复出的待办，一次全列给他**。用户会问「还有什么待确认的，你全部列给我」——
  这说明他已经不信「一条条挤牙膏」了；把日志里的「待用户拍板 / 等用户放话 / pending」字段
  全量交叉核对后合并成**一张清单**（每条写：现状 / 卡在哪 / 需要他做什么 / 建议），再交付文件。
- 之后仍然要按「★ 会话记录文件太大 ⇒ 开新会话 + 先写交接单」处理，**否则下一次还会崩**。

## §实测数字（从 `MEMORY.md` 搬出来存这里，2026-10-03）

> 原则：`MEMORY.md` 只留「不遵守就出事」的祈使句；**理由 / 常量 / 实测数字都放这里**。
> 每条都标了来源，可复算。取不到的一律写「未取到」，**不填 0**。

### A. 整机卡机（CPU/内存/磁盘全宽松时）

- 判据：Windows 事件日志 `ID 1000/1002` 里，**同一程序 24h 崩 N 次且间隔恒定**。
- 实测：向日葵 —— **每 16.2 分钟崩 1 次**（间隔恒定），是它把整机拖到「卡机」。
- 内存吃紧的判据**不是**看「用了百分之多少」，要看 `PagesPerSec` + 页面文件用量：
  实测一次「疑似内存压力」**页面文件 959 MB / 7.4 GB、已用 68%、`PagesPerSec`=7** ⇒
  **判定不是内存压力**（真的内存压力下 `PagesPerSec` 会持续高企）。

### B. 定时任务「合并」的覆盖率陷阱

- 平台语义：`next_run = 本次完成时刻 + 55 分钟`（不是「整点对齐」）。
- 实测：6 条每小时任务合并成 1 条后，**实际间隔 ~2 小时、覆盖率只剩 ~55%**。
  复算证据：**04:29 结束 → 05:24 才跑下一次**。
- ⇒ 合并前必须讲清，并让用户在「拉长单次 / 留 2 条错开 / 改常驻进程」里选一个。

### C. WorkBuddy 崩溃取证实测（2026-10-03）

- 崩溃报告目录 `~/.workbuddy/logs/Crash-Log/crash-report-main-<pid>-<启动时间>.json`。

## §交接给别的代理 / 换机：先分类「git 内 / 外」（2026-10-05 实测）

用户问「要让 Codex 接你的班，我得给他什么？」—— 正确回答的骨架**不是「给他源码」**，而是先**分类**：

| 类别 | 结论 |
| --- | --- |
| **git 里全都有** | clone 完就能开工：源码 + 测试 + 入口文档 + 知识库 |
| **git 外，但本机已就位** | ★ 最常见答案：**同机运行 = 只缺一次 `npm install`**（凭据文件已 gitignore、设备/模拟器/SDK 本机已有、SSH key 已有） |
| **git 外，二进制/原件** | 已发布产物、归档、大 zip、取证件 ⇒ 按需索取，**故意不进 git** |

★★ **知识资产默认在仓库之外、clone 拿不到**：项目规则全文 / 记忆索引 / 技能 / 历史文档 / 工作日志，
都在客户端私有目录（`<工作区>/.workbuddy/memory/`、`~/.workbuddy/skills/`）⇒ 必须**收进仓库**（如 `docs/knowledge/`），
否则交接时「等于不存在」。
★★ **入库前必做三道检查**：① 确认该目录**不在构建白名单**（读 `package.json` 的 `build.files`）——
否则内部规则会随安装包**外发给终端用户**；② 扫凭据字面量（`eyJ…` / `AKID…` / `sb_secret_` / `sk-…`），
命中的**解 JWT 载荷看 `role`** 再逐条判死（`anon` 且本就随公开前端发布过 ⇒ 可接受；`service_role` ⇒ 停手），别一把删；
③ 剔 `__pycache__` / `*.bak`（★ `find -prune -exec rm -rf` **实测没删掉**，直接 `rm -rf <路径>` 才干净）。
★★ **入口写进「那个工具会自动读的文件」**：Codex = 仓库根 **`AGENTS.md`**；Claude Code = `CLAUDE.md`。
入口**只放祈使句 + 指针**（它每轮都进上下文，塞长了会被截断），详细内容放知识库并注明「按需查、别整读」。
★★ **知识库是快照、会过期**：客户端活文档一改，仓库里的那份就错了，接手方会按**旧规则**干活 ⇒
顶部写明「快照 + 导出时间 + 活文档路径」，并留一条「改完活文档要重新导出」的规则 + 导出脚本路径。
★ 必须写进交接单的一项：**「已知遗留（明知未修）」** —— 不写，接手方会把老问题当新 bug 重查一遍。
★ 推送取证只认 `git ls-remote origin refs/heads/main` == `git rev-parse HEAD`；
`git commit -F` 的路径要给 **Windows 形式**（`E:/…`；Git Bash 的 `/e/…` 会被 git 报 `could not read log file`）。

⇒ 完整可复用流程、脚本模式与坑速查表见技能 `repo-handoff-to-external-agent`。
