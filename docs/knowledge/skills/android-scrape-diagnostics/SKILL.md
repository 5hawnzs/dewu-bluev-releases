# Android App 界面采集器：排障与加固闭环

适用场景：Python/Node + `adb shell uiautomator dump` 抓 `resource-id`/`text` 来采集第三方 App。
典型症状：**命中率莫名偏低**（某些类型条目系统性缺失）、**字段偶尔写错值**、App 改版后整片失效。

核心心法：**「写错数据」比「缺数据」严重得多**。
缺数据会被下游校验拦住；写错的数据会静默混进交付结果。所以所有解析都按
「**宁可不填，也不填错**」（prefer null over wrong）设计。

---

## 0. 铁律（踩过的坑，逐条对应下方章节）

1. **不要在没有现场快照的情况下猜原因。** 失败时先把控件树原文留档（§1）。
2. **文本匹配必须「整段匹配」，不要 `search()` 子串。**（§4）
3. **可选字段必须由分隔符引出**，否则 `昨天去露营了呀` 会被解析成「昨天」+ 地区「去露营了呀」。（§4）
4. **同一个文本在不同 `resource-id` 上含义完全不同**——`resource-id` 是「来源可信度」的信号。（§4）
5. **不知道自己在哪个页面时，绝对不要按返回键。** 需要页面判定函数。（§3）
6. **`class` 属性也会骗你**：落到 `android.webkit.WebView` 说明已经跳到别的活动页了。（§3）
7. **故障现场必须冻结成夹具**，否则下次 App 改版又得重来一遍。（§2）
8. **模拟器只有一个时，批处理在用就别做交互实验**——会互相抢界面，两边都废。
9. **已经写进库的数据也要能事后审计**（源字段 vs 派生字段交叉校验）。（§6）
10. **先量化耗时再优化**：拿不到「按原因归因的耗时占比」，就是在凭感觉改。（§7.1）
11. **判「不可采」要双向证明**（页面控件树 + 网络侧全量 key 普查），确认后主动放弃并留逃生开关。（§7.2）
12. **放弃分支必须有唯一出口**，否则迟早漏掉「回到列表页」这种收尾步骤。（§7.3）
13. **展示层不要用无条件 `else` 兜底状态**——它会把所有未知原因都塞进一个错误标签里。（§8）
14. **和主字段同一次 dump 拿到的字段，删了不省时间**，别当成优化来汇报。
15. **测试里按标记抽函数时，起止标记要落在同一个函数体内**。（§10）
16. **dump 前必须先删设备上的旧 xml，并且**检查 `uiautomator dump` 是否真的回了 `dumped to`
    ——`uiautomator dump` 失败时**不写文件**，直接 `cat` 会把**上一屏**当成当前屏。
    这是**两条独立防线**：只做一条，另一条仍拦得住，于是「拆一条 → 测试全绿」会让你误判成断言没在查东西（§12.1）。
17. **详情页是覆盖层时，下层列表节点仍在树里**：解析前必须按容器边界整段剪掉，
    否则会取到邻卡的标题/点赞数（值合理但张冠李戴）。（§12.2）
18. **「读不到」的原因要分「结构性」与「本次」**：前者重试是浪费，后者才值得重试；
    未知一律 `null` + 把原因随记录存下来，展示层显示 `—` 并给出理由。（§12.3）
19. **同一字段多种显示形态时，正则要「特异性高的排前面」**：宽泛的正则「能匹配上」≠
    「匹配对了」，会让值**静默错位**（`2026-08-12` 被 `(\d{1,2})-(\d{1,2})` 咬成 `26-08`）。
20. **只知道「月 / 日」（App 常省略本年度年份）必须补年**，否则字段为 `None` →
    被完整度闸门判「缺字段」→ **整条记录静默丢弃**，日志只留一句「缺 X」。（§12.5）
    判据：某类记录**系统性缺失**且缺的总是**同一项** → 先怀疑「这种显示形态没解析出来」。
21. **改多实例前先复核「到底哪几处必须改」** —— 方案里的待改造项常是推论而非实测，
    照着改会白改、还会把本来正确的逻辑改坏。（§17.1）
22. **「已有扫描进程」这道闸门必须按实例过滤**：它靠解析进程命令行工作，
    不过滤会让实例 1 把实例 0 当成自己 → **永远起不来**。端口必须写进**命令行**（环境变量看不见）。（§17.2）
23. **默认实例的文件名（锁 / pid / 心跳 / 日志）必须一字不改**，只给非默认实例加 `-<port>` 后缀。
    否则改代码瞬间「老进程持旧锁名、新代码查新锁名」→ **互斥直接失效**。（§17.3）
24. **「谁要的数据」和「哪个号去采的」是两件事**：合并成一个字段会弄坏「仅看我的」这类既有过滤。（§17.6）
25. **约束的 NULL 盲区 ≠ 会出事**：先验证「能让 NULL 落库的路径是否存在」，
    上游闸门已堵死就不必补索引（往往要 DDL）。（§17.5）
26. **拆掉「一把全局锁」之前，先回头找它「顺带提供了哪些互斥」** —— 这类隐式副作用不在
    任何注释里，拆掉后**不报错**，只会表现为「同一条任务被跑了两遍、计数翻倍」。多实例改造中
    **请求认领**就是被它顺带保护的（§17.8）。
27. **多实例上线的安全顺序：先把新实例的调度任务全部建好、置为「暂停」，等实例本身就绪
    （创建 + 登录）后再一次性激活**。提前激活会让新实例去抢共享队列的任务，然后在自己的
    adb 端口上连接失败 → 任务白跑。（§17.9）
28. **「入库闸门」的开关绝不能绑在「筛选模式」上。** 写成 `if 模式A:` 时，模式 B 会**整段
    跳过**它 —— 表现为「该类记录全部残缺也照样入库」+「状态下发口径回落到旧分支」，
    一次改动**同时**弄坏「该挡的没挡住」和「该标对的标错了」。（§18.1）
29. **「条件不符」与「数据有缺」是两件事，别用一个闸门处理。** 闸门只丢**数据有缺**的记录；
    「不在用户设定区间内」只**如实标注**（并把「差在哪」原文存下来）。据此推论：
    **日期闸门只能属于「逐级放宽」那套模式**，在「区间筛选」模式下按日期丢记录是错的。（§18.2）
30. **用户要「停止」这类控制指令，且表格没有 update 权限时**：用**控制行**（insert 一行
    `status='stop'` + 目标 id）表达，由持高权限的采集端轮询执行 —— 零 DDL、只用已有权限、
    还顺带留痕。**但必须配一个独立看门狗线程**，因为主循环常被「子进程有输出才推进」卡住。（§18.3）
31. **收尾状态要以「数据层现状」为准，不能只看退出码。** 用户主动停过的任务，其退出码必然非 0；
    若无条件写「失败」就是把用户主动要的结果**写假**。收尾必须带条件更新（CAS）。（§18.3）
32. **别拿「会被常驻进程正常改写」的文件当测试指纹**（轮转日志、心跳、拿锁时建/放锁时删的锁文件）。
    它们的 mtime 变化与被测对象无关，断言只会一直红，还容易掩盖真失败。改断言**隔离是否生效**。（§18.4）
33. **⚠️「编辑成功」的返回完全不可信。** 这类沙箱里出现过「一批编辑全部报成功、实际一处没落位」，
    而且缺的往往是**最关键的接线**（缺 import → 运行即 NameError、缺函数定义、开关仍是旧写法）。
    **改完必须按行为复核**（逐个 grep 新符号 + 跑断言），并且把测试写成
    「少了这处编辑就变红」——让不落位**当场暴露**，而不是等线上报障。（§18.5）
34. **`adb input` 返回 0 ≠ 点中了；「换 9 种注入姿势全失败」也**不能**直接判「这块区域不可点」。**
    先做**阳性对照**（点页签/标题栏）分辨「链路不通 / 坐标错 / 真不可点」，
    再**证明那一格真的有可交互目标**（`clickable` 节点 + `bounds` 覆盖该坐标，或截图看画了什么）。
    ★★ 最常见的错：在**没有目标**的页面上测点击 ⇒ 必然得出「点不动」。
    本项目就因此写了三条**错结论**（「区域性问题」「换姿势没用」「9 种全失败」），
    2026-10 复测**全部推翻**（真因＝相册里没素材 + 用了另一种布局的坐标）。（§12.6 / §21）
35. **`uiautomator dump` 在持续动画页上会彻底失效**（2026-10 实测：连试十几次 / `--compressed` /
    关系统动画 / 静置 15s 全报 `could not get idle state.`，而用户要抓的正是这一屏）⇒
    必须留一条**不等 idle** 的退路：`dumpsys activity top`。要点：按**包名**过滤 `TASK` 段
    （**别取第一段** —— 输出里有多个 App 的层级）、按缩进**逐级累加**坐标（它是相对父节点的；
    不累加会得到一份「像坐标但全错」的表）、滤掉 `flags` 首位不是 `V` 的节点、补全 `app:id/x`。
    ★ 这条通道**拿不到 `text` / `content-desc`** —— 必须**如实标注、不许编**；降级只在「已知包名」时做。
    ★ 自写的解析器要用**真机夹具 + 两套独立实现互比**证明（实测 43 个同名控件 ±2px 对上）。（§12.1b）

## 1. 第一步：让程序在「找不到东西」时自动留档

不要打印「没找到」就完事——**把当时的完整控件树原文存下来**，离线慢慢分析。

```python
DIAG_DIR = os.path.join(BASE, "diag")
DIAG_ON = os.environ.get("SCAN_DIAG", "1") == "1"
DIAG_MAX = int(os.environ.get("SCAN_DIAG_MAX", "40"))       # 必须限量，否则占满磁盘
_diag_count = [0]

def diag_dump(tag):
    """把「某个入口没找到」的现场控件树存一份快照到 diag/"""
    if not DIAG_ON or _diag_count[0] >= DIAG_MAX:
        return None
    try:
        raw = dump_raw()                      # ⚠️ 存**原文**，不要存解析后的结构
        if not raw or "<node" not in raw:
            return None
        _diag_count[0] += 1
        os.makedirs(DIAG_DIR, exist_ok=True)
        safe = re.sub(r"[^0-9A-Za-z_]+", "_", tag)[:40] or "page"
        p = os.path.join(DIAG_DIR,
                         f"{datetime.now().strftime('%H%M%S')}_{_diag_count[0]:02d}_{safe}.xml")
        with open(p, "w", encoding="utf-8") as f:
            f.write(raw)
        log(f"  诊断快照: diag/{os.path.basename(p)}")
        return p
    except Exception as e:
        log(f"  诊断快照失败: {e}")
        return None
```

**要点**
- 文件名带**时分秒 + 序号 + 语义 tag**（`104720_10_date_try_videoContentArea.xml`），事后一眼看出「第 10 次留档、当时在试哪个入口」。
- `dump()` 要拆成 `dump_raw()`（原文）+ `parse_nodes(raw)`，否则留档的会是结构体，丢失了 `class`/`clickable` 等排查所需属性。
- 在**每一个「预期入口没找到」的分支**都调一次：找不到分享按钮、找不到日期、找不到粉丝数……
- 同时给「**点完之后**」也留档：点入口 → dump → 留档。这样能看出「点错入口跳到了哪个页面」。

## 3. 第三步：先加「页面判定」，再谈解析

绝大多数「静默丢数据」的根因是**程序不知道自己站在哪个页面**，于是对错误的页面做操作。

```python
def on_feed(nodes):          # 列表页：有卡片容器 + 顶部频道签
    has_cards = any(n["rid"] == "clGridRoot" for n in nodes)
    chips = [n["text"] for n in nodes if n["text"] in ("灵感", "追番", "关注")]
    return has_cards and bool(chips)

def on_detail(nodes):        # 详情页：**必须排除列表页特征**
    if not nodes: return False
    if find_one(nodes, "clGridRoot"):     # ⚠️ 列表卡片上也有 tvUsername/tvTitle！
        return False
    return any(find_one(nodes, rid) for rid in
               ("tvUsername", "tvUserName", "userName", "avatarView",
                "shareView", "flShare", "contentTime", "tvItemEditTime"))

def is_comment_sheet(nodes):  # 评论面板：有评论控件，且**没有**帖子级日期控件
    if not nodes or not any(n.get("rid") in COMMENT_RIDS for n in nodes):
        return False
    return not any(find_one(nodes, r) for r in POST_DATE_RIDS)

def is_webview_page(nodes):   # 跳到活动页/落地页了
    return bool(nodes) and any((n.get("cls") or "") == "WebView" for n in nodes)
```

**血泪教训**：`back()`（`adb shell input keyevent 4`）在详情页上按会**直接退回列表页**。
一个无条件 `back()` 就能把整条采集流程废掉——现场快照里 `clGridRoot` 出现十几次，而日志写的是
「分享按钮未找到」，**误导性极强**。规则：

> 只有「确认弹层出现了」或「确认已经离开当前页了」才按 `back()`。

为此需要 `is_popup(nodes)`（例如「有 `contentTime` 但没有详情页主体控件」）。

**并且**：如果发现跳到了评论面板 / 活动页，要**立刻退回**——它们不但会给出错误数据，
还会**盖住你要点的按钮**，导致后续字段也一起丢。

## 4. 第四步：解析函数必须是严格整段匹配 + 来源白/黑名单

这是本次最有价值的一条。

### 4.1 反例：宽松子串匹配会写出错误数据

```python
_DATE_RE = re.compile(r"(刚刚|今天|昨天|前天|\d+\s*天前|\d{1,2}-\d{1,2})")   # ❌ 危险

def find_date_text(nodes):
    for n in nodes:
        if len(n["text"]) <= 24 and _DATE_RE.search(n["text"]):
            return n["text"]           # 子串命中就返回 → 灾难
```

实际被它匹配到并当成「发布日期」的两类文本：

| 文本 | 真实含义 | 后果 |
|---|---|---|
| `07-25 · 青海` | 评论面板里**评论者**的时间 + 评论者地区 | 把评论时间当成了帖子发布时间 |
| `(08.24-09.02)` | 活动页的**活动周期** | 把活动周期当成了发布时间 |

### 4.2 正例：严格整段匹配 + 分隔符约束

```python
_STRICT_DATE_RE = re.compile(
    r'^(?:编辑于\s*)?'
    r'(?:\d{4}-\d{1,2}-\d{1,2}|\d{1,2}-\d{1,2}|\d{4}年\d{1,2}月\d{1,2}日|\d{1,2}月\d{1,2}日'
    r'|刚刚|今天|昨天|前天|\d+\s*(?:分钟|小时|天)前)'
    # ⚠️ 可选的地名**必须由分隔符（·/｜/空白）引出**——
    #    否则 `昨天去露营了呀` 会被整段匹配成「昨天」+ 地名「去露营了呀」
    r'(?:\s*[·|｜]\s*[\u4e00-\u9fa5A-Za-z]{1,10}|\s+[\u4e00-\u9fa5A-Za-z]{1,10})?$'
)
```

配套的**来源黑名单**（比黑名单更重要的是「同一个文本换一个 rid 就不可信」）：

```python
# 评论控件上的时间永远是「评论者」的时间，与内容本身无关
COMMENT_SHEET_RIDS = ("tvParentTime", "tvChildTime", "tvParentContent", "tvChildContent",
                      "tvExpandAllReply", "tvParentUsername", "tvChildUsername")
DATE_BAN_RIDS = frozenset(COMMENT_SHEET_RIDS + (
    "tvReply", "tvParentLike", "tvChildLike",
    "tvHotReply", "tvBottomReply", "tvCommentHint",
    "tvUsername", "tvUserName", "userName", "tvTitle", "tvContent",
))

def find_date_text(nodes):
    """两道闸门：① 页面类型不对直接返回 None；② 逐节点严格整段匹配 + rid 黑名单"""
    if not nodes or is_comment_sheet(nodes) or is_webview_page(nodes):
        return None
    ct = find_one(nodes, "contentTime")         # 明确可信的专用 rid → 最高优先级
    if ct and ct[0]["text"]:
        return clean_content_time(ct[0]["text"])
    for n in nodes:
        t = (n["text"] or "").strip()
        if not t or len(t) > 24:                # 长文本里有日期样式 = 巧合
            continue
        if (n.get("rid") or "") in DATE_BAN_RIDS:
            continue
        t2 = clean_content_time(t)
        if _STRICT_DATE_RE.match(t2):
            return t2
    return None
```

## 6. 第五步：入库后审计（源字段 vs 派生字段交叉校验）

代码修复只对**新进程**生效。批处理还在跑、或历史数据已入库时，要能**事后审计**。

思路：**原始字段的「形态」能指认它的来源**。
本例中 `raw.edit_time_raw` 有两种形态，一眼可辨：

| 形态 | 来源 | 是否可信 |
|---|---|---|
| `17小时前  广东` / `2天前 广东` / `编辑于 08-12 湖北` | 帖子自身区域 | ✅ |
| `07-25 · 青海`（**MM-DD + `·` + 地名**） | 评论面板 | ❌ |

```python
SUSPECT_RE = re.compile(r'^\s*\d{1,2}-\d{1,2}\s*·\s*\S+')      # 评论时间指纹
TRUSTED_RE = re.compile(r'^(?:编辑于\s*)?(?:\d{4}-\d{1,2}-\d{1,2}|\d{1,2}-\d{1,2}|刚刚|今天|昨天|'
                        r'前天|\d+\s*(?:分钟|小时|天)前)(?:[\s·|｜]+\S{1,10})?$')

def audit(recs, today):
    """纯函数 → 可单测。返回 (可疑, 无法自证, 正常)"""
    suspect, unknown, fine = [], [], []
    for r in recs:
        e = ((r.get("raw") or {}).get("edit_time_raw") or "").strip()
        if not e:
            unknown.append(...)                       # 缺原始字段 = 无法自证
            continue
        if SUSPECT_RE.match(e) and not TRUSTED_RE.match(e):
            suspect.append(...)                       # 指纹命中
            continue
        exp, _ = parse_publish(e, today)              # 派生值必须能由源字段重算出来
        (fine if exp == r.get("publish_date") else suspect).append(...)
    return suspect, unknown, fine
```

**关键**：把 `audit()` 写成**纯函数**，这样它自己也能被测；并且**用同一个解析函数**去重算派生值
（`parse_publish`），避免审计逻辑与生产逻辑漂移。

## 7. 效率与资源纪律

- **只有一台设备/模拟器时**：批处理在跑就别做交互实验（`adb shell input` 会互相打断页面状态）。
  正确做法是**离线分析快照**；必须实测交互时，等批处理结束再做（或专门写一个 `probe_*.py` 脚本待命）。
- **每多试一个入口就多花 8~10 秒**（tap + dump + back）。入口候选表要有优先级，
  并且**每次点击后都验证结果**，命中就立刻收工。
- **不要上滑试探**：在「上下滑切换条目」的信息流里，上滑会直接切到下一条，把当前目标弄丢。
- 加**限量**（快照份数、重试次数、打开卡片数上限），避免一次异常把时间全烧光。

### 7.1 先量化「时间花在哪」，再动手优化（别凭感觉）

日志里每个阶段都带时间戳，直接算「相邻两次『打开条目』的间隔」就是单条耗时。
真实案例：一轮 31 分钟 / 打开 18 个详情页 / 只入库 1 条 → 单条平均 **102s**。
按占比排序后发现：**44% 的条目属于「结构性不可采」布局**，每张白耗 ~125s（多点几次 63s
+ 取链接 25s + 进主页 12s + 节流等待 25s），产出 0。**这才是第一优先级**，
而不是去优化那 13% 的正经解析耗时。

量化脚本要输出：总耗时、单条平均/中位/最快/最慢、每类丢弃原因计数、**按原因归因的耗时估算**。
拿不到「优化后预计耗时」这一栏，就说明还没找到真正的大头。

### 7.2 「结构性不可采」：确定后要**主动放弃**，且只留一个出口

判定一个布局「不可采」之前，必须**双向证明**，否则会漏采：

1. **页面侧**：把该布局的控件树完整列出来（所有 rid + 所有 text + content-desc），
   确认确实**不存在**目标字段的载体节点。要贴证据（哪份快照、哪些 rid），不是「我试了几次没有」。
2. **网络侧**：如果这是个「前端页面能顺带拿到数据」的场景，去抓它的 SSR/内嵌 JSON，
   **全量 key 普查**（正则扫 `"key":` 再去重）看有没有目标字段。
   真实案例：抓 H5 分享页 3 次，全量 key 里只有 `timestamp`（服务器当前时间）与 `requestCostTime`
   → **确认无发布日期**，堵死了「网络兜底」这条路，也就证明 App 侧确实无解。
3. 确认后 → 写一个语义明确的判定函数（如 `is_immersive_video()`），**识别到就立刻放弃**，
   跳过后面的所有取数步骤，并挂一个逃生开关（`--keep-xxx`）以防对方改版。

**⚠️ 判定函数必须双向保守**：只要看到一个目标字段的载体节点就判否（宁可多试一次，不能误杀）。
另外要排除「浮层状态」——评论面板/WebView 是盖在原页面上的，底层的容器 rid **仍在** dump 里，
不加这个判断会把浮层误判成「干净的原页面」。
用真实快照做双向断言：不可采布局 → 是；标准布局/浮层 → 否。

### 7.3 「放弃」收敛到唯一出口（否则迟早漏一步）

放弃分支会长到 4~5 条（字段不达标 / 字段缺失 / 命中黑名单 / 布局不可采 / 完整度不足），
每条都复制一份「打日志 + 记名单 + 返回 + 校验页面 + 节流等待」→ **改一处漏一处**。
真实事故：某条分支漏了「校验是否回到列表页」，导致后续所有条目都在错误页面上空转。

正确做法：一个 `leave_card(reason, mark_pairs=(), interval=...)`：

```python
def leave_card(reason, mark_pairs=(), interval=20):
    log(f"  {reason} → 不入库，继续下一条")
    for nick, title in mark_pairs:          # 例如记入「无目标字段」名单，后续轮次不再重复打开
        if nick and title:
            mark_nodate(date.today(), nick, title)
    back(3)
    if not on_feed(dump()):                 # 校验一次
        back(3)                             # 兜底再退一层（可能被弹层挡住）
    time.sleep(max(2.0, interval * 0.5 + random.uniform(-2, 2)))   # 抖动，避免固定节奏
```

用**桩**测它的调用契约：`back` 次数、`dump` 次数、休眠区间、`mark_pairs` 里缺字段的那组是否被跳过。
另外加一条「接线断言」：源码里 `leave_card(` 的出现次数 ≥ 分支数 —— 防止有人日后又把分支写成复制粘贴。

### 7.4 优化顺序：先砍「注定失败」的路径，再谈并发与节流

按收益从大到小：

1. **砍掉注定失败的整条路径**（不可采布局）—— 收益最大且不影响产出（本来也采不到）。
2. **把判定前移**：某个字段一旦读到就能判断成败，就**当场判**，
   不要等到后面把链接/主页/截图都干完才判。真实案例：发布日期一读到就不达标，
   却还先把「取分享链接 + 进主页截图」走完 → 每条白花 ~37s。
3. **把黑名单判定前移到「拿到可靠标识」之后**：真实 UID 一到手就能判，命中就直接走，
   省掉后面的主页访问与文件上传。
4. 删掉「只为凑字段」的二次采样（补评/藏而多一次 dump + sleep ≈ 7s/条）。
5. 最后才动节流间隔（占比通常只有 ~25%，而且调快会抬高风控风险，属配置而非代码）。

**注意**：字段如果和主字段来自**同一次 dump**，删掉它**不省任何时间**。
这时要如实告诉用户：「已删掉费时的二次采样，但字段保留（零成本）；要不要连字段一起去掉，你定。」
别把「零成本字段」当成效率优化来汇报。

## 8. 展示层的「无条件 else 兜底」是隐形误标重灾区

采集端写进库的状态字段（如 `valid` / `is_excluded`）是**扫描期的快照**；
展示层如果写成：

```js
var status = r.valid ? '有效' : (r.is_ai ? 'AI剔除' : (r.is_fake ? '刷量剔除' : '清单排除'));
```

最后一个 `else` **无条件兜底**，于是此后任何「`valid=false` 且不是 AI/刷量」的记录
——包括将来新增的每一种失败原因——都会被贴上「清单排除」。

真实案例：用户报「某达人**不在**排除清单里，检索页却显示状态『清单排除』」。
根因链：扫描时命中过清单 → 记录 `is_excluded=true` → 清单条目后来被移除 →
状态仍显示「清单排除」；又因为**实时清单里查不到**，该行不会被「隐藏已处理」的过滤条件藏起来 → 现象成立。

正确做法：

1. **展示层按「当前数据」实时重算**，不要直接信任快照字段（快照只作补充信息）。
2. 每个状态都带一个 `why`（悬停可见），让用户能自己核对。
3. 给「历史上命中过、现在已不在清单」单独一个状态（如「曾排除(已移出)」），
   而不是塞进「清单排除」——**状态语义必须可被用户用一次搜索验证**。
4. 给这个 bug 写测试时，**用真实报障场景当输入**（`valid=false, is_excluded=false` →
   断言结果**不包含**「清单排除」字样）；并补一条「已移出」场景。

## 10. 维护测试的抽取标记（易被自己改坏）

用「从 HTML/源码里按起止标记抽函数再 eval」的测试框架时，**抽取边界是脆弱的**：

- 真实案例：`grab('function exclAllVisible() {', '      return true;\n    });\n  }')` ——
  第一个标记是 `exclAllVisible`，但结束标记其实是**紧随其后的 `exclFiltered` 的结尾**
  （一个 grab 顺带把两个函数都抽进去了）。给 `exclFiltered` 加了排序后，
  结束标记消失 → 测试直接抛 `end not found`。
- 规则：**每个函数一段 grab，起止标记都落在同一个函数体内**；
  改了函数体（尤其是结尾语句）时，回头检查抽取标记。
- 测试报 `end not found` 时，先怀疑自己刚改的源码，而不是测试框架。

## 11. 反面故障：**该被挡住的没挡住**（过滤静默失效 / 字段假值）

§8 讲的是「展示层误标」，这一节讲另一半：**采集器把本该排除的内容采了进来**，
而且日志一路正常、没有任何报错 —— 用户看到的却是「我明明拉黑了，怎么还被采了 3 条」。

### 11.1 过滤器「按属主生效」→ 生产调用方属主不同 → 静默全失效

典型形态：
```python
def build_excl_index(exclusions, owner=None):
    for e in exclusions or []:
        kind = e.get("kind") or "coop"
        if kind == "block" and owner and e.get("added_by") != owner:
            continue          # ← 「拉黑只对创建者生效」
```
而生产入口固定 `--owner system`（或 `owner=None`、`"admin"` 之类），于是
**任何用户在前端做的「拉黑」对采集器全部无效果**，一条都拦不住。
日志里那句汇总（`排除清单跳过 0 条`）看起来完全正常，不会有人怀疑。

**诊断三步（顺序别换）**
1. **先看数据库里那些条目的字段值**，而不是先读代码：
   `select id,nickname,uid,kind,added_by from exclusion_list where nickname ilike '%X%'`
   → 看到 `kind='block'`、`added_by='someone@x.com'` 是第一个信号。
2. **再用生产实际参数跑一遍过滤函数**，断言命中：
   ```python
   for owner in ("system", "user1@x.com", "user2@y.com"):
       idx = build_excl_index(EXCLUSIONS, owner)
       hit, by = excl_match(idx, uid=None, nickname="被拉黑的人")
       assert hit is not None, f"owner={owner} 时没命中"
   ```
   **这一步必须进回归测试**（见 §11.4），否则下次改回去也没人知道。
3. **对时间线**：把「排除项创建时间」与「记录入库时间」并排看 ——
   如果有多条记录的时间**晚于**排除项创建时间，就是硬证据（实现比推理有力）。

**修复时要想清语义，别只删条件**：「拉黑只对创建者生效」在产品上可能是有意设计
（A 拉黑不该影响 B）。删掉它就意味着变成「全团队共识」。正确做法是：
- 明确选定一种语义，并**在执行端与展示端都写清各自的口径**（两边可以**刻意不同**：
  执行端全局不采（省时间），展示端仍只对本人隐藏（历史记录不凭空消失））；
- 同步改所有面向用户的文案（否则「不影响他人」的旧提示会变成谎言）；
- 在代码注释里写清「为什么两边不一样」，防止后来者「顺手统一」把它改回去。

### 11.2 字段读不到时写成 0 / 空串 / 默认值 → 污染下游一切判断

```js
title: r.title || null, likes: r.likes ?? 0, collects: r.collects ?? null
//                                     ^^^^^^^ 读不到就写 0
```
后果链：**「0 赞」看起来像真实数据** → 用户以为这条内容真的没人点赞 →
下游的区间筛选/排序/门槛判断全部基于假值 → 更糟的是，它让「多张卡片看起来一模一样」
（同一达人、同一天、同为 0 赞）→ 用户合理地怀疑「是不是重复采了」。

**原则：字段未知就写 null，绝不写一个「看起来合理的假值」。**
与「日期宁可不填也不填错」同一条心法 —— 缺数据会被下游的空值检查拦住，假数据会一路穿透。

**排查入口**：在采集日志里统计各字段的值分布，而不是只看有没有报错。
```bash
grep -o "赞=[^ ]*" 采集日志.log | sort | uniq -c
#   7 赞=None        ← 全部读不到！读取链路坏了，但没有任何异常输出
```
**看到某字段大面积 None/空，就该怀疑读取链路，而不是当成「这些内容恰好没数据」。**

### 11.3 「看起来重复」≠「重复入库」：先核业务主键

用户说「显示了三条相同的内容」时，**先取四条身份字段做对照，再决定是不是去重 bug**：

| 对照项 | 相同 → | 不同 → |
|---|---|---|
| 业务主键（内容 ID / trend_id） | 真重复，查去重键与 upsert | 是不同内容 |
| 详情页短链 / 永久链接 | 同上 | 是不同内容 |
| 标题 | 同上 | 是不同内容 |
| 封面图 URL | 同上 | 是不同内容 |

本例中三项全不同 → **不是重复入库，而是「缺按人去重」**：
采集器只有「同一条内容」去重（`uid|标题`），没有「同一个人」去重，
于是同一达人在信息流里连出多条就被逐条采下。
用户说「相同」的真实原因是**除标题外其余字段全一样**（达人/日期/粉丝/点赞/形式），
而点赞还全是假的 0（§11.2 叠加放大）。

**修复要顺着用户的真实意图**：「达人拓新」类需求里，业务单位是**人**不是**内容** ——
按人加日限额（如 `MAX_PER_KOL_DAY=1`），在**列表卡片层**就跳过，
省下的是整条详情页链路（本例约 100s/条），而不是等到入库再去重。

### 11.4 这两类 bug 的回归测试怎么写

它们都属于「静默失效」，所以测试要**反向断言**，而不只是正向断言：
```python
# ① 用生产真实参数覆盖（别只测那个恰好能通过的 owner）
for owner in ("system", "user1@x.com", "user2@y.com"):
    assert excl_match(build_excl_index(LIST, owner), None, "被拉黑的人")[0] is not None

# ② 反向断言「旧的错误写法已从源码里消失」
src = open("app_scan.py", encoding="utf-8").read()
assert 'if kind == "block" and owner and e.get("added_by") != owner:' not in src

# ③ 接线自检：防止「函数写了但没被调用」
assert 'kol_quota_blocked(' in src and 'kol_dup_skip += 1' in src

# ④ 字段口径：未知必须写 null
assert "likes: r.likes ?? null" in push_src and "likes: r.likes ?? 0" not in push_src
```
**「抽出纯函数再测」是让这种事可测的关键**：把「该不该跳过这个人」从主循环里抽成
`kol_quota_blocked(nick_count, nickname, limit)`，边界（限额 0 / 负数 / 空昵称 / 多达人）
就能被穷举断言，而不必启动模拟器。

## 12. 静默「读错」：dump 拿到上一屏、叠层污染解析

§8 是展示层误标，§11 是「该挡住的没挡住」，这一节是第三种静默故障：
**程序不报错、日志正常、值也「有」——但值是错的**。
它比「读不到」危险得多，因为下游的空值检查**完全拦不住它**：「上一个真实状态」和「邻卡的数」
都是格式合法、量级合理的值。

### 12.1 `uiautomator dump` 失败时不写文件 → `cat` 回上一屏

**现象**
- 连续 dump N 次返回**字节级相同**的 XML（页面明明在滚动/有动画）；
- 按返回键/点按「没反应」，误判成手势没生效；
- 日志里没有任何异常。

**根因**：`uiautomator dump /sdcard/ui.xml` 在界面无法进入 idle 时会失败，只往 **stderr** 打
`ERROR: could not get idle state.`，**此时它不创建也不覆盖目标文件**（软键盘挂着、有循环动画时极易触发）。
旧实现把「dump」和「cat」当成原子操作：
```python
adb("shell", "uiautomator", "dump", "/sdcard/ui.xml")
return adb("exec-out", "cat", "/sdcard/ui.xml")     # ← 文件是上一次的
```
于是「当前页面」实际是**若干秒前的页面**，所有基于它的判定（在不在列表页、卡片有几张、
点赞多少、有没有进详情）全部错位。

**修复：先删后写，失败即重试，绝不返回陈旧内容**
```python
adb("shell", "rm", "-f", "/sdcard/ui.xml")
adb("shell", "uiautomator", "dump", "/sdcard/ui.xml", timeout=20)
out = adb("exec-out", "cat", "/sdcard/ui.xml", timeout=20)
if "<node" not in out and retry:          # 空 ⇒ 重连重试；返回空也好过返回旧的
    connect(); sleep(3)
    adb("shell", "rm", "-f", "/sdcard/ui.xml")
    adb("shell", "uiautomator", "dump", "/sdcard/ui.xml", timeout=20)
    out = adb("exec-out", "cat", "/sdcard/ui.xml", timeout=20)
```

**识别信号（按可信度排序）**
1. 多次 dump **内容完全相同**，而页面显然在动 → 几乎可确诊；
2. 「按键后 dump 不变」——不是手势失效，是 dump 没刷新；
3. **`uiautomator dump` 的 stderr 有 `could not get idle state`**。
   ⚠️ 必须**单独收集 stderr**：混进 stdout 后会被 `if "<node" in out` 这种判断吞掉，永远看不见。

**最快的自证手段**（不读日志）：dump 前先 `adb shell rm -f <path>`，再 dump，
若 `cat` 输出为空 ⇒ dump 确实失败了。一条命令就能定位。

**顺带两条经验**
- **软键盘是头号元凶**。连续 dump 失败时先 `adb shell am force-stop <pkg>` + `monkey` 重启 App
  把键盘收掉，再继续排查；否则你会在一个「假的故障现场」上耗很久（键永远按不动）。
- 采集主循环里要防止「误点进输入框 → 键盘挂起 → dump 全失败 → 页面判定永远为假 →
  每轮都走『恢复：重启 App』」这种**自我循环**（表现是日志里反复重启 App）。

### 12.1a 补：第二条防线、「长期不 idle」的量化、以及「关动画」到底算不算解法

> 来源：2026-10 在一个「得物」发布页上实测。**先删文件**这条已经写在 §12.1 里了，但它**只是两条防线之一**。

**① 两道防线要都做，且都要有各自的断言**

| 防线 | 做什么 | 只做另一条时会怎样 |
| --- | --- | --- |
| A 删旧文件 | dump 前 `rm -f <path>` | 失败时 `cat` 回上一屏（§12.1 的现象） |
| B 验 dump 成功 | 检查 stdout 是否含 `dumped to`；不含就走失败通道并**带回原因** | 同上（只要文件还在） |

实测（定点破坏）：单独拆 A，测试只红 1 条（顺序断言）；单独拆 B 也不红。
**两条一起拆**才红 6 条，其中包括「返回值是上一屏的残留 XML」。
⇒ 教训：**造坏版后先自问「我到底改掉了哪一条判断」**；一处缺陷有多条防线时，
只拆一条的「全绿」是假绿。别据此删掉断言。

**② 「长期不 idle」是真事，不要当成瞬时抖动**

实测数字：进入目标页后 `ERROR: could not get idle state.`，
**连续 60 次尝试（约 10 分钟）全失败**；同一台设备、同一页面，过一段时间又能成功。
所以：
- **不要用「重试 2~3 次」当解决方案**（预算差两个数量级）；
- 也不要写成「这个页面**永远** dump 不了」——它会自己稳定下来。**两种说法都是错的**。

诊断顺序（都做过，可复用）：
1. `dumpsys window | grep mCurrentFocus` 确认人在目标页；
2. `dumpsys power | grep mWakefulness=` 排除息屏（实测 `Awake`）；
3. `ps -A | grep uiautomator` 排除残留进程；
4. 再量化：**每秒试一次、记录第几秒成功**，拿到「等了多久」的真实分布。

**③ 「关动画」是兜底手段，不是根因 —— 别把它写成「标准解法」**

单变量 A/B（**同一页面、同一秒**，只改一个 `settings` 值）：

| 条件 | 结果 |
| --- | --- |
| `animator_duration_scale=1`（卡住中） | ❌ `could not get idle state.`，**0 字节** |
| **只**把它改成 `0` | ✅ **立即成功**（24263 字节） |
| 页面不离开、还原为 `1` | ✅ **仍然成功** |

但**另一次实测在 `=1` 时同一页面也能抓到**（页面自己稳定后就不受它影响）。
⇒ 结论：置 0 只是**打断当前正在跑的那个循环动画**，不是「因为动画开着所以永远不 idle」。
写结论时必须带上这个反例，否则会误导后来者去做「无脑关动画」。

**用它的正确姿势**（三件都要）：
```js
// 只在 dump 报 idle 时才动手；读完原值再改
const before = await animGet(serial);        // settings get global <三个 key>；读不齐就【不要动它】
if (!before) return last;                    // 宁可重试失败，也不猜着改回去
await animSet(serial, 0);
try {
  return await dumpOnce(serial);
} finally {
  await animRestore(serial, before);         // ★ 无论成败都还原，绝不把用户设备留在改过的状态
}
```
- **还原要保真**：原值若是「没设过」（`settings get` 回字符串 `null`），要用
  `settings delete` 而不是 `put ... null`，否则会把字面量 `"null"` 写进设备。
- **一定会有人忘记还原**（实测：命令跑到一半 adb 断开 → `put 0` 生效、`put 1` 没执行
  → 设备动画停在 0）。所以收尾必须**回读确认**，别信「我发过还原命令」。

**④ 行为级断言用「哨兵法」**（比看代码行可靠）

```
① 先正常 dump 一次（此时设备上留着一份 XML）
② 在目标文件位置放一个哨兵 / 或让 dump 失败
③ 断言「解析函数的返回值 === null」——而不是「看起来像 XML」
```
哨兵内容可用一行假 XML（如 `<hierarchy>SENTINEL_FROM_HOME_PAGE</hierarchy>`）：
它**含 `<`**，能骗过 `if ("<" in out)` 这类简陋校验 —— 正好用来测「你有没有真的检查成功」。
  加固方式：dump 返回空时**不要**继续按「页面判定为假」的逻辑走，
  而是走「重连 + 重试」；重试仍空才视为异常页。

### 12.1b 彻底抓不到时的**最后退路**：`dumpsys activity top`（含解析要点）

> 2026-10-02 实测。§12.1a 那条「等它自己稳定」在这台机器 / 这个页面上**没等到**：
> 连续十几次（间隔 2~3s）+ `--compressed` + 关系统动画 + 静置 15s —— **全报 `could not get idle state.`**。
> 而用户要抓的偏偏就是这一屏 ⇒ 必须有**不依赖 idle** 的抓法，否则「抓取」这个功能对他等于不存在。

**为什么可行**：`uiautomator dump` 要先等窗口 idle；`dumpsys activity top` **不等**，
它把各 task 的 `View Hierarchy` 直接打印出来（输出很长，落盘再解析）。

**能拿到什么 / 拿不到什么 —— 必须如实标注**：

| 有 | 没有 |
| --- | --- |
| `class` / `resource-id` / 逐级累加后的 **bounds** / **clickable** | ★ **`text` 与 `content-desc`（全空）** |

⇒ 靠文字定位的步骤要改成按 id / 坐标；**绝不许编一个 text 出来**；
交给用户时也要**明确说**这条通道少了文字（别让他以为抓到的和平时一样全）。

**解析要点（每一条都踩过）**：

1. **先按包名过滤 `TASK` 段** —— 输出里同时有多个 App 的层级（实测 5 个 `View Hierarchy:`）。
   **不要「取第一段」**：第一段通常不是目标 App。判据是 `TASK ... :<包名>` 行。
2. **坐标是相对父节点的** ⇒ 按**缩进**还原层次后**逐级累加**：维护栈 `[indent, 绝对x, 绝对y]`，
   遇 `indent <= 栈顶` 弹栈；当前绝对坐标 = 父的绝对 + 自己的相对。
   ★ 不做累加、直接当绝对坐标用，会得到一份**看起来像坐标、实际全错**的表（最阴的一类错）。
3. **`flags` 第一位不是 `V` 的节点要滤掉**（不可见 / 没布局；真机里这类 bounds 常是 `0,0-0,0`），
   否则后续点击落到屏幕外。`x2<=x1 || y2<=y1` 的也丢。
4. `#7f091395 app:id/flThumbSelect` 要**补全成 `com.xxx:id/flThumbSelect`**；
   `clickable` 取 `flags` 第 6 位（`C`）——这是 `View.toString` 的固定位次。
5. `DuImageLoaderView{holder=DraweeHolder{...}}` 这类**没有 bounds 的行直接跳过**（正则不匹配即可）。

**必做的交叉验证**：找一个**两种方式都能抓**的页面，把同一批控件的坐标对齐
（实测 **43 个同名控件逐一对上，±2px**、clickable 一致）。
自己写的解析器**必须**用「真机夹具 + 两套独立实现互比」证明一遍 —— 不能只看「输出看起来像 XML」。
夹具就取**真机输出**（别手写假数据），并**故意在里面垫两段别的 App**，用来证明过滤确实按包名做。

**降级链的正确写法**（只在前面全败时才走）：

```
uiautomator 重试 → 关动画重试（必还原）→ ★ 仅当知道目标包名时才退到 dumpsys
```

- **不给包名就不降级**（否则会抠到别的 App 的树，产出假数据）；
- 断言要查**「有没有真去调那一步」**（指令日志里该有则有、不该有不许有），
  **不能只看返回值形状** —— 两条路的失败结果常常长得一模一样（详见技能 `bilateral-fix-verification` §4.3）。

### 12.2 两层界面同时在树里 → 解析函数取到「邻卡」的值

「从列表点进详情」的场景里，详情页往往是**覆盖层（overlay）**，
下层列表的卡片节点**仍然留在 XML 树里**（实测详情页树上残留 12 个卡片点赞节点、
15 个点赞容器；`count(rid=...)` 这类聚合会被直接放大）。

后果：`find_one("tvTitle")` / `count(rid="tvLikeNumber")` 这类按 rid 取值的解析，
会取到**同一屏下层邻卡**的标题与点赞数。值合理、格式正确、无报错，但**张冠李戴**。

**修复：解析前按容器边界把「非本层」节点整段剔除**
```python
def drop_other_layer(nodes):
    gb = [n["bounds"] for n in nodes if n["rid"] == "clGridRoot" and n["bounds"]]
    if not gb:
        return nodes                      # 纯详情页 → 无副作用（关键）
    return [n for n in nodes
            if not (n["bounds"] and any(inside(n["bounds"], g) for g in gb))]
```
**要点是「有则剪、无则不动」**：同一个解析函数必须同时服务「纯详情页」与「详情叠在列表上」，
不能要求调用方先判断自己在哪一层。

**验证方式（两条都要，缺一不算修好）**
- **真机夹具**：留一份「详情叠在列表上」的过渡态 XML，断言剪枝后节点数骤降
  （本例 246 → 46），并断言**取到的是详情页的值而非邻卡的值**（断言取 31、不取 999）；
- **no-op 证明**：纯详情页样本剪枝前后结果**完全一致**。

### 12.3 反模式：在展示层把「读不到」兜底成默认值

```js
title: r.title || '',
likes: r.likes ?? 0          // ← 读不到就写 0
```
叠加 §12.1/§12.2，就会产出「**看起来合理但是错**」的交付。三条规则：

1. **未知一律 `null`**，展示层显示 `—`，不要用 `0`/`''`/`'未知'` 之类的「占位真值」；
2. **把「为什么读不到」随记录一起存下来**（例：`raw.likes_note`），展示层 hover 显示原因 ——
   否则用户只会看到一行 `—`，无法判断是「内容本来没有」还是「采集坏了」；
3. **原因要分「结构性拿不到」与「本次没拿到」**：
   用状态字段在采集端就分开（例 `likes_state = number | icon_only | absent`），
   比在展示层猜要可靠。结构性拿不到的**重试是纯浪费**（本例重试 5 秒后再 dump，
   两层依然一个数字都没有），应当直接放弃并留痕。

**测试必须加反向断言** —— 静默错误只能靠反向断言守住：
```python
assert 'icon_only": 0' not in src          # 证明没有把 icon_only 猜成 0 的地方
assert '"likes": 0' not in default_fill_src
```
正向断言只能证明「新的对了」，反向断言才能证明「旧的错法不会回来」。

### 12.4 判定「结构性拿不到」的标准动作

遇到「某字段大面积读不到」，**不要先改代码放宽条件**，按这个顺序取证：

1. **日志层**：确认重试已经发生过且仍为空（排除「只是这次没抓到」）；
2. **快照层**：找一份该场景的控件树夹具，**直方图统计**整个树里有没有这类节点
   （本例：整棵树 115 个节点，一个数字都没有；底部互动栏三个控件文本是
   `点赞`/`收藏`/`评论` 而不是 `31`/`7`/`8`）→ 证明不是解析 bug；
3. **对照实验层**：同屏取「能读到的」和「读不到的」各一个，走同一条链路，
   在 **0s / 6s / 15s** 三个时点各 dump 一次 → **若都无变化，排除懒加载**；
   若「能读到的」读到、「读不到的」读不到，则是**按内容类型差异化的展示**；
4. **旁路层**：换一条获取路径验证（改用 H5/分享页/接口），确认那里**也没有**这个字段
   （本例 H5 分享页的 key 只有 `contentId/cover/media/userInfo/videoShareUrl`）。

四层一致后再下结论，并把结论**写进代码注释与交付报告**，同时给出用户可选项
（换数据源 / 接受 `null` / 接受记 `0`）—— 这是产品决策，不要替用户拍板。

### 12.5 同一字段多种显示形态：**正则顺序错会静默改值 + 静默丢记录**（双重陷阱）

App 里同一个字段常有多种显示形态，靠一组正则依次试。**顺序写错会同时踩两个坑**：

**坑 A：宽泛正则「能匹配上」≠「匹配对了」→ 值被静默改掉**

实测（得物发布时间）：本年度只显示 `8月12日` / `08-12`（**无年份**），往年才显示 `2025-08-12`。
若把宽泛的 `(\d{1,2})-(\d{1,2})` 排在前面：

```
'2026-08-12'  →  `(\d{1,2})-(\d{1,2})` 命中 '26-08'   ← 取到 26 月 08 日！
              →  补年逻辑把 26 月当非法值/换年 →  最终成了 '08-26'
```

**日期整体错位**，格式合法、无异常、日志里还显示得挺正常。
> 铁律：**多个正则匹配同一段文本时，特异性高的必须排在前面**。
> 先认「带年份的完整形态」，再认「只有月日」，最后才是相对时间（`3天前`）。
> 每加一个形态，都要回头检查它有没有**抢先吃掉**已有形态。

**坑 B：补不出年份 → 整条被完整度闸门丢掉（静默丢记录）**

只知道「月 / 日」时必须补年，且要处理「补出来落在未来」：

```python
def fill_year(mm, dd, today):
    for year in (today.year, today.year - 1):     # 本年度优先，落未来则回退上一年
        try:
            d = date(year, mm, dd)
        except ValueError:
            continue                              # 2月30日 这类非法 → 继续试
        if d <= today:
            return d.isoformat()
    return None                                   # 都试不出 → None，绝不猜
```

不补的后果**极其隐蔽**：字段为 `None` → 被完整度闸门判「缺发布日期」→ **整条记录被丢弃**，
日志里只留一句「缺 发布日期」，看上去像「这条内容本来就没日期」。

**判据（什么时候怀疑这里）**：某类记录**系统性缺失**、且日志里缺的字段是**同一项**
→ 先怀疑「这种显示形态没解析出来」，而不是「这类内容本来就没有」。

**测试要三条一起写**：
1. 每种形态各一个正例（含**本年度无年份**的那个）；
2. **顺序守卫**：断言 `'2026-08-12'` 解析结果是 `2026-08-12`（若顺序被改回宽泛在前，这条会红）；
3. 非法日期（`2月30日`）返回 `None` —— 证明**没有瞎猜**。

### 12.6 注入点击「没报错但没生效」：先分清「链路不通 / 坐标错 / **那里根本没东西可点**」

`adb shell input tap x y` **永远返回 0**，点没点中它不管。

> ★★★ **本节原版结论「相册缩略图块是区域性问题、换 9 种注入姿势全没用」已于 2026-10-01 复测推翻。**
> 真因是**当时相册里一条素材都没有**（点在空白背景上）+ 用的坐标属于**另一种布局**。
> 把素材弄进相册后重测同一格 → 页面**确实跳转**了（md5 变化 + 出现新页面节点）。详见 §21。
> **留着这段是为了记住这个坑**：在**没有目标**的页面上测点击，必然得出「点不动」。

**第一步永远是阳性对照**（证明注入链路本身是通的）；
**第二步必须证明「那一格真的有东西可点」** —— 这一步最容易被跳过，也最容易造成错结论：

| 顺序 | 操作 | 说明 |
|---|---|---|
| 1 | 点页签 / 标题栏（同页） | ✅ 生效 ⇒ 注入通道没问题，排除「链路不通」 |
| 2 | **确认目标位置有可交互目标** | `uiautomator dump` 找 `clickable="true"`（或带 `content-desc`）的节点，**`bounds` 必须覆盖你要点的坐标**；或看截图里那一格**画了什么** |
| 3 | 点目标控件 | 到这一步才谈「坐标对不对 / 能不能点」 |

★ **跳过了第 2 步，第 3 步的结论一定是错的。**

**判据用「选中态 / 节点数 / 截图哈希」，不要靠肉眼**；每步都留指纹，别只看命令有没有报错：

```bash
adb -s $DEV exec-out screencap -p > step.png && md5sum step.png   # 与上一步相同 = 没生效
# 更稳的是比结构：选中态 selected、某 id 的节点个数、有没有出现新页面的标志节点
adb -s $DEV shell "rm -f /sdcard/s.xml; uiautomator dump /sdcard/s.xml"
adb -s $DEV exec-out cat /sdcard/s.xml > s.xml
```

★ **md5 变了也要看清是「谁」变的**：异步加载、下拉回弹、状态栏跳秒都会让 md5 变 ——
必须配上**页面结构变化**才算证据。

**两个必须先排除的干扰变量**：
1. **系统动画缩放**：dump 要它=0（§12.1a），但**点击不一定** —— 在 0 和 1 下各测一次，
   别把「关动画」和「点不动」混成一个原因。
2. **页面是否已僵死**：长时间反复操作后页面会整体不响应 —— **退出重进**再测，否则你测的是假现场。

**坐标漂移也要防**：同一页面可能有「工具栏展开 / 折叠」等**多套布局**，同一控件 y 相差 **102 px**。
写死坐标必翻车 —— **抓完 dump 立刻点**，并按 `resource-id` 取 `bounds` 现算中心点，
或在缩放图上用**像素级定位**（§21.2）而不是肉眼估。

**结论要怎么写**：只写「在当前设备、当前状态下这一步没生效」，并**附上当时那一格有什么** +
**阳性对照是什么** + **试过哪些姿势**。★ **不要**在「没有目标」的状态下判「这块区域不可点」——
那会把「没素材」误判成「产品缺陷」，还白耗掉 9 种注入方式的测试时间。

## 13. 字段下线与口径反转：四层清单摘除 + 留痕标记

### 13.1 「不要再抓 X」= 全链路摘除，不是只改解析
只改解析器，会留下**永远为空的列 / 永远筛不到结果的筛选项** —— 比不改更糟（用户以为坏了）。
按这四层逐项过一遍，每层都要能被反向断言证明：

| 层 | 要改什么 | 容易漏的 |
|---|---|---|
| 采集 | 解析分支、兜底 hint 列表、重采合并、日志字段 | 兜底/重采里的**次要**赋值路径 |
| 落库 | 写入前显式 `null`；检查有没有 `?? 0` 这类**假值默认** | `?? 0` 就是「宁可不填也不填错」的反例 |
| 展示 | 列表列、详情弹窗行、CSV 表头+行、**筛选条件档位** | CSV 与筛选条件是独立代码路径 |
| 测试 | 受影响的断言逐条改，并**新增反向断言**「旧写法已搜不到」 | 旧断言会在下次跑测试时替你发现漏改 |

- **保留键名**（写 `null`）通常比删键更安全：旧记录 / 旧前端 / 导出脚本都不会 KeyError；
- 删掉因下线而**彻底无用**的函数与 import（死代码会误导下一个排查的人）；
- 前端改动前先**备份当前文件**（`_backup_<file>_<version>.html`），口径再来一次反转时能一键恢复。

### 13.2 口径反转：把「判定依据」留痕，而不是只留结论
本例的教训：先得出「得物不公开点赞数 → 不许猜 0」，用户看了两张截图后直接推翻
（**0 赞时得物不画数字，只显示文字标签** → 标签就是 0）。这是**合法的口径反转** ——
用户是领域真相源，代码里的推理再自洽也要让路。

所以：**判定结论必须带机器可读的留痕**，否则反转时无法回填历史数据。
```python
d["likes"] = 0
d["likes_zero_label"] = True      # 为什么是 0：标签态，而不是「读到数字 0」
raw["likes_source"] = "detail"    # 值从哪来：详情页 / 卡片兜底 / 未知
raw["likes_note"] = "……"           # 给人看的一句话（前端原样展示）
```
- 有了留痕，口径反转后可以按 `likes_zero_label/state` 精准筛选受影响记录，
  **而不是全表回填**（本例 id=63 因当时无留痕 → 保持 `null`，宁可不动也不写错）；
- 留痕字段要**同时**出现在：数据侧 `raw`、（若有）展示侧 tooltip、以及测试的正/反断言里；
- 「标签=0」这类 UI 语义**只对确实如此的位置生效**（本例只对点赞/收藏位，
  评论位是固定文案 → 不能顺手也判 0）—— 按位置区分，别按「看起来一样」推广。

### 13.3 反转的代价最小化：把变更做成可回滚的单点
- 口径常量集中定义（如 `_INTERACT_LABELS = ("点赞",)`），改口径 = 改一行；
- 卡片层与详情层**各自判定、各自留痕**：卡片层用来早筛（0 赞直接不点进去，省 ≈70s/条），
  详情层用来定案。两层口径必须来自同一个常量/注释，避免只改一处；
- 上线后**用一轮小样本端到端验证**（`--limit 3` 不带 push）看日志与落盘 JSON，
  再交给定时任务跑全量。

## 14. 触发链路要「队列 + 看护」：点一下就没人管，= 用户体感「点了没反应」

### 14.1 典型故障链（本项目实测，用户反复投诉「点了筛选一直没跑」）
```
网页点按钮 → 往 run_requests 插一条 pending → 等每 10 分钟一次的定时任务来消费
```
三层叠加，缺一层都不会这么难受：
1. **没有常驻消费者**：延迟 0~10 分钟不可控；
2. **撞上资源占用就静默跳过**：定时任务发现锁被另一个长任务持有 → 直接跳过，
   请求留在 pending，**既不重试也不告警**；
3. **长任务挂在会话上**：会话结束子进程被回收 → 状态卡在 `running`，
   要等「45 分钟超时」才自愈 → 这 45 分钟里后面全部干等。

### 14.2 修法：独立队列监听器 + 状态自愈
- **监听器只做三件事**：拉队列 / 抢同一把资源锁 / 起子进程并回写状态。
  每 10 秒一轮，空闲即开跑（本项目 `watch_requests.py`）。
- **僵尸状态要回收，而且优先「重跑」而不是「判失败」**：
  `status=running` 但机器上既无锁也无进程（并已超过 90 秒）→ 说明执行它的进程没了。
  这时**重跑它**比标记 failed 更对：用户要的是这批数据，不是让他重新点一次。
  90 秒的宽限窗口是留给「刚 start-run、子进程还没起来」的正常瞬间。
- **判活要两个信号**：锁文件里的 pid 存活 + 进程表里真的有扫描命令行。
  只看锁会被陈旧锁骗，只看进程会被包装链（shell/node 包装）骗。
- **排队必须可见**：前端把「前面还有 N 个任务」「已运行 N 分钟」算出来实时展示，
  并**在提交后自动轮询刷新 1 分钟**。旧版提交后页面毫无变化，用户以为没跑就反复点，
  队列越堆越长 —— **可见性和吞吐同等重要**。

### 14.3 判据速查
| 现象 | 该怀疑什么 |
|---|---|
| 点了没反应，队列里 pending 一直不动 | 没有常驻消费者 / 消费者被资源锁挡住没重试 |
| 状态卡 running 很久，后面全排队 | 长任务随会话被回收；自愈阈值（45 分钟）太钝 |
| 「明明跑完了但状态没变」 | `finish-run` 在异常路径上没执行 —— 收尾要放 `finally` |
| 同一请求被跑了两遍 | 自愈和正常消费撞车；需要单实例守卫 + 锁 + 状态前置校验 |

### 14.4 如果平台**不允许常驻进程**：把「会话时长」当唯一杠杆（本项目实测结论）

上一节的「独立监听器」在托管沙箱里可能根本活不下来。**别急着写，先花 10 分钟确认能不能常驻**
—— 否则会得到一个「看起来对、实际每小时漏 40 分钟」的方案（我们踩过）。

**第一步：确认真常驻是否可行（五条路，本项目全部实测堵死）**

| 逃逸手法 | 结果 |
|---|---|
| `Popen(creationflags=CREATE_BREAKAWAY_FROM_JOB \| DETACHED_PROCESS \| ...)` | `[WinError 5] 拒绝访问`（Job 未授予 BREAKAWAY_OK） |
| `Register-ScheduledTask`（ScheduledTasks 模块） | cmdlet 存在，4 种身份注册**全部拒绝访问** |
| WMI `Invoke-CimMethod Win32_Process Create` | 沙箱拦 |
| `explorer.exe <bat>` 代启（经典手法） | 进程**能跑**，但仍在会话 Job 内 |
| `Shell.Application` / `WScript.Shell` COM | 沙箱拦 |

**判定工具（务必用，别靠肉眼）**：`IsProcessInJob(hProc, NULL, &res)` —— hJob 传 NULL 时问的是
「目标进程是否和**我**在同一个 Job 里」。**先拿自身 pid 做对照组**（必须为 True，否则测试无效）。
`explorer` 那条路就是靠它判死的：父进程链已断、进程还在跑，看着像逃逸成功，实则 `InCurrentJob=True`。
（完整可运行脚本见本技能配套的 `_jobcheck.py` 思路：`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)`
→ `IsProcessInJob` → `CloseHandle`。）

**第二步：查清调度器**next_run**的真实算法（别相信 rrule 的字段名）**

实测某平台：`next_run_at - last_run_at` **一律 55 分钟**，`FREQ=HOURLY;BYMINUTE=7/17/27...`
里的 `BYMINUTE` **被完全忽略**。后果是 N 个任务被挤到**同一个 ~16 分钟窗口**扎堆触发，
之后 45 分钟无人唤醒 —— 这就是「点了没反应」的元凶。

> 排查动作：把每个相关任务的 `last_run_at` / `next_run_at` 都换算成本地时间打出来，
> 看差值是不是常数、看触发时刻是不是扎堆。**这一步比读 rrule 有用得多。**

**第三步：设计（三条铁律）**
1. **单次会话尽量长，但宁短勿长**。让定时任务在**一个会话里把同一条短命令连跑 N 遍**
   （受 shell 工具前台 timeout 上限约束，本项目是 9 分钟 × 6 遍 ≈ 54 分钟）。
   关键：**周期 ≈ 下轮触发间隔，且不要超过它** —— 一旦超过，下一轮窗口的触发会全部撞在
   「现任还活着」上被挡掉，等现任退出后要再等一个完整周期，覆盖率**掉到 50%**。
2. **抢不到实例锁的会话不要「秒退」，要「待命接替」**：每 N 秒盯一下现任，
   现任一退出立刻接管（连同心跳状态一起打出来）。这样被调度器挤掉的会话从**浪费**变成**冗余**。
   锁文件必须 `O_CREAT|O_EXCL` **原子抢占**（多个待命者会在同一瞬间醒过来）。
3. **提示词只写「跑什么、跑几遍、不要做什么」**。让 agent 顺便「读日志、做分析、写汇报」会把
   会话拉长好几倍、加重调度拥挤 —— 守候类任务的提示词越"傻"越可靠。

**给用户的诚实口径**：这条路做不到 100% 覆盖（稳态 94%~97%，每次空窗几分钟）。
不要用「覆盖约 90%，空窗 ≤1 分钟」这种没验证过的估算去汇报 —— 我们报过一次，被打脸了。


## 15. 「整站时间差 8 小时」：先证伪机器时钟，再查存储与展示

用户报「系统时间和实际时间对不上」时，**别一上来就怀疑机器**。按这个顺序查，
三层各自独立，通常问题在**第三层**：

1. **机器时钟**：`date`（Bash）/ `node -e "new Date().toString()"` / Python `datetime.now()`
   三处交叉验证。三者一致且为本地时区 → **机器没问题**，立刻往下走，别浪费时间校准系统时间。
2. **存储**：PostgreSQL `timestamptz` 经 PostgREST 返回的字符串**一律是 UTC 且带 `+00:00`**
   （`created_at`、`updated_at` 全如此）。**存储本身是对的**。
3. **展示**：`String(r.created_at).slice(0, 16)` 这类「截字符串当格式化」的写法会把
   **时区后缀和 8 小时时差一起丢掉** → 页面**恒早 8 小时**。

**同源的第二颗雷**：`new Date().toISOString().slice(0, 10)` 被当作「今天」。
`toISOString()` 是 UTC，于是**本地 00:00 ~ 08:00 期间算出来的「今天」是前一天** ——
日活计数、按日文件名、按日去重 key、日报分桶全部受影响，而且**只在凌晨复现**，极难查。

**修法要点**：
- 收敛到**唯一的时间解析/格式化入口**（`tsDate` / `fmtLocal` / `localDay` / `todayLocal`），
  全站禁止再出现 `.slice()` 截时间串。
- **裸串（无时区后缀）按 ISO 8601 一律当 UTC**，不要「按本地猜」：库里 99% 是带 `+00:00`
  的 UTC 串，两种语义混用比统一偏移更危险。
- **排序用的 `localeCompare` 不用改**：比较的两边是同格式 ISO 串，字典序 = 时刻序。
  「见到时间就改」会引入新 bug。
- **回归要真的换时区跑**：`TZ=Asia/Shanghai node test.js`（子进程真跑函数），
  覆盖跨日 / 裸串 / `Z` 后缀 / `+08:00` 后缀 / 空值非法值；再加「旧写法已从源码里消失」
  的反向断言（**断言前先把注释剥掉**，注释里留旧名有价值）。

### 15.1 顺手一条：修复会暴露「历史数据本来就没存」

同一轮里给列表加「筛选条件」列时发现：老记录**从来没有存过**当时的筛选条件
（请求表里没有快照字段，配置表也没有指向记录的外键）。此时只有三种做法：

- 加列/加表补 → 老数据照样补不回来，还欠一次手工 DDL；
- **编一个「大概是这样」** → 污染数据，坚决不做；
- **快照内嵌 + 可就近推断 + 明说缺口** ← 正解。

具体：新记录把生效配置原文写进记录的 JSON 字段（**零 DDL**），展示为**精确**；
老记录按「记录时刻之前最近一条配置」推断，**弹窗里必须标「仅供参考」**；
连一条历史配置都够不着，就显示**「未留存」**而不是空白或占位值。

**这条要写进测试**：三态（exact / inferred / none）各断言一次，并且**反向断言
「精确态不会被打上仅供参考的标」**。区分不了来源的数据，比没有数据更危险。

**同类推论**：图片类的「取不到」也一样 —— 取不到就显示 `—` 并写明原因，
**绝不用占位图 URL 顶上**（下游会把它当成真实首图去比对、去算相似度）。


## 16. 用户给了「目标条数」却只跑了几条：**目标必须落进数据层**

### 16.1 症状与真因（三层叠加，缺一层都解释不通）

用户说「我要 20 条，实际只跑了 5 条」。现场证据齐全、可复核：
请求记录（`run_requests`）提交时刻、耗时（31 分 15 秒）、目标 20、实际入库 5、
状态**正常 `done`** —— 一切「看起来正常」，所以用户只能反复投诉而查不出原因。

三层原因：

1. **请求表里没有 target 列** → 后端**根本不知道**用户要几条，提交时只写了
   属主 / 配置 id / 状态。
2. **监听器只跑一轮**，且那一轮的单轮条数**写死**。
3. **一轮之内刷到底就判 `done`** —— 这是**正常收尾**，不产生任何未达标提示。

> **教训**：**「跑完了」≠「跑够了」**。凡带目标数的任务，目标必须落进数据层，
> 否则执行端只能取默认值，而「取默认值」的结果一定是静默少跑。

### 16.2 修法一：目标落数据层（能加列就加列）

最正统：`run_requests` 加 `target_count`。取不到时**按「无目标」处理并只跑一轮**，
**绝不猜**（这条要写成断言）。

### 16.3 修法二：**零 DDL 侧取**（不能改表结构时的通用招）

若环境约束是「**DDL 只能手工执行**」，就别为了加一列去等人工窗口。利用一条时序事实：

> 前端提交流程本来就是「**先 insert 配置表、再 insert 请求表**」，两次写入**间隔毫秒级**。

于是执行端只要查「**最近一条配置记录**」，那条就是本次请求的目标。

- 取数封装成一个 CLI 子命令（如 `latest-config`）：
  `GET filter_configs?order=created_at.desc&limit=1` → 返回配置原文 + 时间戳。
- 执行端不直接连库，**统一走这条子命令**（保持「执行端不懂表结构」的分层）。
- ⚠️ **并发前提**：这套依赖「同一个属主不会毫秒级连提两次」。多人并发下要用
  「最近一条且 `owner` 等于本次请求的 `owner`」来收窄；**做不到就退回 16.2 加列**。
- 这是一个**通用模式**：凡是「前端已有一份提交内容、后端却读不到」的字段，
  先看**是不是有一条时间上紧邻的、后端可见的记录**可以侧取。比等 DDL 快得多。

### 16.4 修法三：目标驱动多轮（收尾必须有三态）

执行循环：每轮条数 = `min(剩余, ROUND_CAP)`，其中 `ROUND_CAP` 是**单轮上限**
（本项目 30，防止一轮把时间全吃掉导致后面饿死）。

收尾**三态**（每一态都要有测试）：

| 态 | 触发条件 | 动作 |
|---|---|---|
| 达标 | 累计 ≥ 目标 | `done` + 正常摘要 |
| 干涸 | **连续 2 轮零产出** | `done` + **写明未达标原因** |
| 预算将尽 | 会话剩余 < 预留值 | **保持 running，交下一时段接力** |

再加两个边界：**无目标 → 只跑一轮**；**轮数 > `MAX_ROUNDS` → 停**。

**摘要文案是产品的一部分**，必须写成
「**目标 N 条 → 实际 M 条（K 轮），未达标：原因**」。
只写「已完成」，用户下次还是只能看到那三个字，等于没修。

### 16.5 ⚠️「预算将尽 → 保持 running」这条为什么必须有

托管沙箱的会话会被硬杀（见 §14.4）。若在会话还剩 1 分钟时启动一轮 30 条，
进程被杀 → 请求卡在 `running` 永久僵尸，用户看到的是「永远在跑」。
**预留值 = 单轮最坏耗时的上界**（本项目 120 秒），低于它就干净退出、让下一时段接力；
同时监听器要能把**僵尸 running 回收重跑**（超时才自愈）。

### 16.6 测试怎么写（本轮实测有效，31 条断言）

**不要**只测「函数返回对不对」，要**真跑编排层**：

- 把 PID、心跳、日志路径**隔离到临时目录**（否则测试会抢到真实实例的锁）；
- **monkeypatch** 两个外部依赖：取目标（`latest_config`）与单轮执行（`run_scan`）；
- 逐个覆盖：达标 / 连续零产出 / 无目标 / 预算将尽 / 单轮上限 / 执行异常退出 / **不猜目标**；
- 另加**静态接线断言**：常量真的存在、`tick()` 真的调了 `run_goal`、
  摘要模板真的含「目标 … 实际 …」——防止「函数写了但没接上」。

### 16.7 顺带一条：本轮 `test_*` 抓出的**真 bug**，值得当模式记

**「＋ 新增一条」一次冒出 11 行**：原实现是「先把**自动生成**的整组条件灌进去，再加一条」，
于是在「自动生成」模式下点一下 = 10 条 + 1 条。
**教训：「自动生成的结果」和「用户手写的输入」是两个语义**，
用一个「是否被用户碰过」的闸门字段区分；新增时必须
`if (!手工结果) 手工结果 = [];` ——**从空开始加一条，而不是继承生成结果**。

> 这类 bug 只有**真跑浏览器交互**才抓得到（静态断言全绿）。参考 `headless-ui-selftest` 技能，
> 以及其中第 7 条「自检页表格必须补齐真实列数」这个**假 FAIL** 陷阱。

## 17. 单实例采集器改造成多实例（模拟器多开）

前提：一台机器上跑多个模拟器实例，每个实例挂**不同的 App 账号**（同账号并发必被踢下线）。
MuMu 的规则是**每个实例一个固定 adb 端口**（实例 0=16384，每多开一个 +32）。

### 17.1 ⚠️ 先复核「必须改哪几处」，别照着旧清单改

我们踩过的坑：上一轮列的「4 处改造」里，**只有 2 处真的必须改**，另 2 处本来就已具备：

| 项 | 常见错觉 | 复核方法 |
|---|---|---|
| 端口参数化 | 必须改 | `grep -n "16384\|SERIAL"` —— 写死的必然要改 |
| 每实例一把锁 | 必须改，但**重点不在锁文件**（见 17.2） | 顺着「谁能拦住并发」列全部闸门 |
| 跨实例结果去重 | 以为要新写 | `grep` 查入库去重键的查询**有没有带 owner/实例过滤** |
| 每日配额口径 | 以为要改 | 看配额计数是从哪个集合派生的 |

> **教训**：方案里的「待改造项」往往是推论而不是实测结论。动手前逐条复核，
> 否则会白改两处、还会把本来正确的逻辑改坏。

### 17.2 真坑：进程表闸门会把**别的实例**误判成「已有扫描在跑」

大多数采集器都有「机器上已有扫描进程就不许再起一个」的保护，判据通常是
**遍历进程命令行**找自己的脚本名 + 关键参数：

```
if "app_scan.py" not in cmd or "--limit" not in cmd and "--push" not in cmd: continue
```

→ 实例 1 想跑时，会看到实例 0 的 `app_scan.py --limit 8 --push`，
判定「已有扫描进程」→ **实例 1 永远起不来**。

**所以「每实例一把锁」只改锁文件名是不够的** —— 锁各一把 ≠ 能同时跑。
必须给这道闸门也加实例过滤：

```python
def cmd_instance(cmd):
    """从命令行认出实例；认不出（没写 --adb-port）→ 默认实例（保证旧调用行为不变）"""
    m = re.search(r"--adb-port[=\s]+(\d+)", cmd or "")
    return m.group(1) if m else DEFAULT_INSTANCE

def scanners_running(exclude_pids=(), instance=None):
    want = str(instance) if instance is not None else instance_id()
    ...
    if cmd_instance(cmd) != want:
        continue
```

**连带的一条硬要求**：`--adb-port` **必须写进子进程的命令行**，不能只靠环境变量 ——
进程表里只看得到命令行。所有拉起 `app_scan.py` 的地方（监听器、跑批脚本）都要带上。

### 17.3 向后兼容的三条设计（决定能不能安全上线）

必须做到「不开多开时行为**一字不变**」，否则改代码的瞬间线上就出事故：

1. **默认实例沿用原来的文件名**：
   `lock_name_for("16384") == "rounds.lock"`（而不是 `rounds-16384.lock`）。
   > 为什么关键：改代码的瞬间，**老进程还持着 `rounds.lock`**，新代码若去查
   > `rounds-16384.lock` 会认为「没人持锁」→ **互斥直接失效** → 两个扫描抢同一个模拟器。
   > 同理 `watch.pid` / 心跳 / 日志：默认实例名字一字不改，只给非默认实例加 `-<port>` 后缀。
2. **认不出的归默认实例**：命令行没写 `--adb-port` 的旧写法、旧定时任务、旧测试
   → 一律算默认实例，行为与改造前一致。
3. **允许显式覆盖**：`ROUNDS_LOCK` / `WATCH_PID` 等环境变量优先于实例推导
   （测试与人工隔离要靠它）。

### 17.4 一个极容易漏的联动：端口必须**同时**打通「实例标识」的消费方

只设采集器自己的 `ADB_PORT` 不够 —— 锁模块的实例判定与锁路径都靠实例标识，
而它的 `LOCK_PATH` 往往是 **import 时算一次**的。漏掉的症状很隐蔽：
**端口变了、锁却还是默认实例那把** → 两个实例看上去互斥，实际在等一把根本不该等的锁。

```python
def set_adb_port(port):
    if not str(port).isdigit():
        return False                       # 绝不猜、绝不错开
    ADB_PORT = str(port); SERIAL = f"{HOST}:{port}"
    os.environ["DEWU_ADB_PORT"] = str(port)     # ① 子进程能继承
    mod = sys.modules.get("scan_lock")          # ② 已加载的锁模块也要同步
    if mod is not None and not os.environ.get("ROUNDS_LOCK"):
        mod.LOCK_PATH = os.path.join(BASE, mod.lock_name_for(port))
    return True
```

调用位置也必须在「并发闸门」**之前**（否则闸门按错实例判断），这条值得写成断言。

### 17.5 「唯一的 NULL 盲区」不等于「这个盲区会出事」

多开最容易担心的重复问题：入库唯一约束若是 `(日期, uid, url)`，而 **url 可空** ——
关系库把 NULL 视为互不相等 → 约束对 `url IS NULL` 的行不生效。

**先别急着加索引（往往要 DDL），先顺着数据流验证「NULL 能不能落库」**：

```python
if not short_url:
    miss.append("发布链接")     # ← 完整性闸门把它列为必需项
...
"url": short_url,               # ← 记录里的 url 就是同一个值
```

→ **url 缺失的记录根本进不了库** → 唯一约束的盲区**结构上碰不到**。
（实测复核：当日 12 条记录里 `url` 为空 0 条、`uid+title` 重复组 0、`uid+url` 重复组 0。）

> 通用判据：约束有盲区 → 问「**能让盲区值落库的路径存在吗**」。
> 若上游闸门已堵死，补索引纯属浪费（还可能触发一次不必要的 DDL）。

### 17.6 「谁要的数据」和「哪个号去采的」是两件事，别合并成一个字段

用户往往会说「数据按实例账号归属」。直接照做会**弄坏一个既有功能**：

- 记录里的 `owner` 通常 = **谁要的数据**（例如「点立即筛选按钮的人」）；
  列表页的「筛选人」列 + 「仅看我的筛选」全靠它。
- 请求被**另一个实例**接走时，若把 `owner` 改写成那个实例的登录账号
  → **点按钮的人在自己的「仅看我的筛选」里看不到结果**。

正确做法是拆成两个字段，各回答一个问题：

| 字段 | 回答 | 取值 |
|---|---|---|
| `owner` | 谁要的数据 | 立即筛选 = 请求人；定时跑批 = 该实例账号（配置） |
| 新增留痕（塞进 JSON 字段，**零 DDL**） | 哪台机器/哪个号采的 | 实例端口 `16416` |

这样「出问题能定位到具体哪个号被风控」的诉求满足了，而权限/过滤语义没被破坏。

### 17.7 回归测试怎么写（84 条断言的结构，可直接照搬）

分 11 组，**A 组最重要**：

| 组 | 测什么 |
|---|---|
| **A 向后兼容** | 默认实例的锁名/pid/心跳/日志**一字不变**；不带端口 → 归默认实例 |
| B 实例隔离 | 非默认实例的文件名都带 `-<port>`；显式覆盖优先 |
| C 命令行解析 | `--adb-port N` / `--adb-port=N` / 缺省 / 空 / None / 多空格 |
| **D 按实例过滤** | 造一份「两个实例都在跑」的进程表，断言**互相看不见**；反证「不过滤会互相挡死」 |
| E 真实互斥 | 真跑锁文件：同实例重复获取必失败；**另一实例仍能拿到**（多开并行的证明） |
| F 端口打通 | 非法端口返回 False 且不改状态；`import` 时就能定好端口；打通到锁路径 |
| G 接线 | 源码断言：所有拉起子进程的地方都带 `--adb-port`；锁名只有一处真源 |
| H 产线未被污染 | 临时目录隔离；产线锁/pid 文件 mtime+size **逐字节复核未变** |
| I/J | 去重与归属的口径断言（含「完整性闸门堵死 NULL 盲区」的证明） |
| **K 原子认领（CAS）** | 源码断言 + **打桩行为验证**：抢到→True、没抢到→False、拿不到返回值→False |

> 写这类测试的第一原则：**它本身绝不能碰产线文件**。
> 把锁路径重定向到临时目录，并在结尾**复核产线文件指纹**（`st_mtime_ns + st_size`）。
> 还要在子进程里做环境相关的用例，避免污染本进程的环境变量与模块状态。
>
> 行为类用例**不要只做源码字符串断言**：把要验证的函数在子进程里 `import` 进来、
> 给它依赖的「打桩」（`mod.node_json = lambda *a: {...}`），再断言返回值与调用参数。
> 源码断言只保证「没被改坏」，行为断言才能证明「逻辑是对的」。两者都要有。

### 17.8 ⚠️ 多开真正最危险的一处：拆锁会**静默**废掉「请求认领互斥」

这一条是本类改造里最容易漏、后果又不报错的坑，单独成节。

**现象**：单实例 → 多实例的改造完成后，一切「看起来」都对：两个实例各有各的锁、
各自能起扫描、进程闸门也不再互相误判。但真实的运行结果是 —— **同一个待处理请求
被两个实例各跑了一遍**：重复采集、日志里同一请求出现两次、计数翻倍。

**原因**：原来那把**全局**锁，除了「模拟器互斥」这个本职，还**顺带**提供了
「同一个任务不会被两个消费者同时拿走」这个副作用：

| | 单实例（改造前） | 多实例（改造后） |
|---|---|---|
| 消费者数量 | 同时只有 1 个（pid 文件全局单实例） | 每个实例 1 个 |
| 各自看到的待办 | 1 份 | **两个人同时看到同一条** |
| 抢锁 | 全局一把 → 第二个抢不到，跳过 | **各自一把，互不冲突** → 都拿到 |
| 结果 | 同一条只被处理 1 次 | **并发处理同一条** |

**关键认知**：这种「原来靠锁的副作用实现的保证」既不写在注释里，也没有任何测试守着。
拆锁的人很容易只想着「锁要按实例分开」而忘掉它附带保护的别的东西。
**改造动作是「拆锁」时，必须额外问一句：这把锁原来还保护了什么？**

**修法：把「置为进行中」升级为数据库条件更新（CAS）**，让数据层裁决归属：

```js
// 后端：<id> 与 <观察到的当前状态> 一起作为条件；命中 0 行 = 已被别人抢走
const q = expected ? `id=eq.${id}&status=eq.${expected}` : `id=eq.${id}`;
const r = await api('PATCH', table, q, { status: 'running', started_at: nowISO },
                    expected ? 'return=representation' : 'return=minimal');
const claimed = Array.isArray(r.data) && r.data.length === 1;
```

```python
# 前端消费者：抢到才跑；抢不到立刻换下一条（别白跑）
if not start_run(rid, expected):     # expected = "running" if 回收僵尸 else "pending"
    log(f"#{rid} 已被另一实例认领 → 换下一条")
    return True                      # 算干了活 → 主循环 1 秒后立刻重挑，不干等轮询间隔
```

四条必须同时满足，否则 CAS 会变成新 bug：

1. **必须 `return=representation`**。用 `return=minimal` 只回 204，拿不到「改了几行」，
   而条件 `PATCH` 命中 0 行**不会报错** → 你会把「没抢到」当成「抢到了」。
2. **失败关闭**：网络抖动拿不到返回值时，按「**没抢到**」处理（返回 `False`）。
   宁可少跑一次，也不要两个实例都以为自己是赢家。漏掉的请求交给下面的僵尸回收兜底。
3. **僵尸回收也要 CAS**，只是 `expected` 换成「观察到它当时是 `running`」。
   否则两个实例会同时回收同一条卡死任务，又并发跑一遍 —— 等于把坑从「新请求」搬到「回收」。
4. **顺序：先抢实例锁 → 再 CAS 认领 → 才启动真正的工作**。
   反过来（先认领再抢锁）会在抢不到锁时留下一条「状态是进行中但没人在跑」的记录。

**兜底为什么成立**：CAS 失败但实际已被写成「进行中」而没人跑的情况，会被已有的
「僵尸回收」（状态是 running、机器上无进程、且已运行超过 N 秒）在下一轮重新捞起来。
所以「失败关闭」不会丢任务 —— 但前提是**僵尸回收这条路存在且也被 CAS 保护**。

**回归怎么锁死**（K 组 13 条，可直接照搬）：源码断言（条件拼接、`return=representation`、
`claimed` 判定、认领在启动之前）＋ **打桩行为验证**（三种返回值各跑一次）＋
**主循环行为验证**（认领失败时：不启动工作、释放锁、返回「干了活」）。

### 17.9 上线顺序：新实例的任务**先建好但暂停**，实例就绪后再激活

多实例的调度侧通常要给新实例复制一套定时任务。**不要建完就直接启用。**

原因：待办队列（本例是 `run_requests`）是**各实例共享**的。新实例此刻还没被创建/登录时，
它的消费者会正常认领到任务，然后在自己那个还不存在的 adb 端口上连接失败 →
任务白跑一轮（虽然僵尸回收能兜底，但纯属浪费配额与时间）。

安全顺序：

1. 先把新实例的全部调度任务建好，状态设为 **暂停**（提示词里带好实例标识参数）。
2. 用户完成「创建实例 + 登录账号」。
3. **一次性批量激活**，再做一次双实例的真机端到端。

顺带：趁着这次改造，把定时任务列表里**已过期但仍是启用态**的一次性任务清掉，
并复核那些「按小时跑」的批量任务在多开之后会不会和守候任务抢实例——多开后抢锁的
影响会被放大（两个实例都在守候，批量任务撞上任何一个都会把它挤掉一段）。

## 18. 「该被挡住/标对的静默失效」第三类：**入库闸门绑错了模式** + 给用户一个「停止」

本节来自一次真实报障，三句话同时到：
> 「某达人显示未达标，但数据好像都是全的，看看是不是 bug」
> 「某条为什么抓不到图片、链接」
> 「筛选任务需要支持停止，本次筛选全部不达标，我想让他直接停止筛选」

### 18.1 症状：①「数据齐全却判未达标」与 ②「残缺记录照样入库」是**同一处**根因

采集器有两套筛选模式（本例：`targeted` 逐级放宽 / `multi` 区间筛选），前端默认走 `multi`。
门控装配写成：

```python
if mode == "targeted" or (mode == "auto" and cfg_mode == "targeted"):
    tcfg = cfg
    steps = ...            # 依赖 tcfg 的初始化
# 其它模式 → tcfg 保持 None
...
if tcfg:                                  # ← 祸根一：完整度闸门写在「模式」里
    miss = completeness_missing(...)
    if miss: 丢弃并 continue
...
"valid": (not is_excluded) and (True if tcfg else bool(tier)),   # ← 祸根二
```

于是 `multi` 模式下两件事一起坏：

* **闸门整段被跳过** → 无图 / 无链接 / 无发布日期 / `uid == 昵称` 的残缺记录照样入库。
  用户体感就是「**为什么这条抓不到图片、链接**」。（本例实测：该记录本该被拦下 **7 项**。）
* `valid` 落到**旧的 `bool(tier)`**（`tier` 只在点赞 ≥ 某档时才有值）→ 点赞不高的记录
  **一律被标「未达标」**，且标签**一个字都不解释差在哪** → 用户只能猜是数据 bug。
  （本例实测：那条记录 8 项完整度**全齐**，赞 38 / 粉 83，只是不在「50~100 赞 / 近 24 小时」区间内。）

**诊断入口（照抄这两步就能定位）**：

```bash
# ① 把「同一批、不同模式」的记录拉出来对比 valid —— 模式是唯一变量
#    实测：run_id=10 (mode=multi) 的记录 valid 全 false；
#          run_id=11 (mode=targeted) 的记录 valid 全 true；两者 tier 都是 None。
# ② 直接数「两条报障记录缺几项完整度」
```

```python
# ② 拿真实字段回放闸门：把报障记录的字段原样喂进去，数缺项
miss = completeness_missing(is_video=True, video_url=None, image_urls=[], publish_date=None,
                            short_url=None, avatar_url="https://x/a.jpg", followers=None,
                            uid="175的小咸穿搭版", nickname="175的小咸穿搭版",
                            trend_id=None, profile_shot_url=None)
# → 7 项；其中含「发布链接 / 发布日期」= 用户问的「抓不到图片、链接」
```

### 18.2 修法：闸门与「哪套模式」**解耦**；把「条件不符」降级为**标注**

```python
tcfg = None     # 逐级放宽那套（None = 未启用）
mcfg = None     # 区间那套（None = 未启用）
if mode == "targeted" or (mode == "auto" and cfg_mode == "targeted"):
    tcfg = ...
elif mode == "multi" or (mode == "auto" and cfg_mode == "multi"):
    mcfg = cfg if cfg_mode == "multi" else {}

# ⚠️ 入库闸门（完整度）在两种模式下**都**适用 —— 它管的是「数据有没有缺」，与筛选模式无关
gating = (tcfg is not None) or (mcfg is not None)
...
if gating:                                  # ← 不再是 if tcfg
    miss = completeness_missing(...)
    if miss:
        skip_incomplete += 1
        continue

# valid 三分支：明确「当时生效的口径」，别让它悄悄回落到旧分支
if tcfg is not None:
    valid, vreason = True, []               # 逐级放宽：入库前已过闸，故有效
elif mcfg is not None:
    vreason = multi_conditions_miss(mcfg, likes, followers, publish_date)
    valid = not vreason
else:
    valid = bool(tier)                      # 两者都没配 → 保留旧口径，并**注明是旧口径**
```

**关键推论（这条线最容易改错）**：

> 闸门丢的是「**数据有缺**」；「**条件不符**」只标注、不丢记录。
> 所以 **日期闸门只能属于「逐级放宽」那套** —— 在区间筛选模式下因为「日期不在区间内」就丢掉
> 记录是错的（那正是用户想人工复核的东西）。

```python
if tcfg and not date_pass(publish_date, steps[step_i]):   # ← 必须保留 tcfg 这个限定
```

**「未达标原因」要落库、要能展示**（否则用户永远只能看到一句「未达标」）：

```python
# 区间判定：不设限 → 放行；取不到值 → 如实说「无法确认」，既不放过也不写假值
def _range_miss(label, val, rng):
    lo, hi = (rng or {}).get("min"), (rng or {}).get("max")
    if lo is None and hi is None: return None
    if val is None: return f"{label}未取到，无法确认是否在设定区间内"
    if lo is not None and val < int(lo): return f"{label} {val} 低于下限 {int(lo)}"
    if hi is not None and val > int(hi): return f"{label} {val} 高于上限 {int(hi)}"
    return None

rec["raw"]["valid_reason"] = vreason        # 零 DDL：塞进既有 jsonb 字段
```

展示层（前端）据此把话**说透**，直接回答「是不是 bug」：

```js
var rs = ((r.raw || {}).valid_reason) || [];
var why = rs.length
  ? '未满足当时的筛选条件：' + rs.join('；') +
    '。（该条数据本身是完整的，只是不在你设定的条件范围内）'
  : '扫描时未通过筛选条件（点赞量 / 发布时间 / 完整度任一不满足），或缺少发布日期。' +
    '该记录早于「未达标原因」上线，未留存具体原因。';   // ← 旧记录**不许编一个原因**
```

### 18.3 给用户一个「⏹ 停止」：控制行 + 看门狗线程 + CAS 收尾

**前提约束**：前端用的匿名/受限角色**没有该表的 update 权限**（RLS 只给了 select/insert/delete），
而加一条 update 策略需要**手跑 DDL**（很多环境里这是禁区）。于是把「停止」表达为**一行数据**：

```
表格: run_requests
insert { status: 'stop', summary: 'stop #<目标id>', requested_by: <谁点的> }
```

采集端（持高权限 key）每次轮询把它读出来执行，并消费掉（`stop → stopped`，带条件更新 →
多实例下只会成功一次）。好处：**零 DDL、只用前端本来就有的权限，还顺带留下「谁在什么时候
要求停止」的痕迹**。

**⚠️ 必须配独立看门狗线程**：主循环通常写成 `for line in proc.stdout:`，
而采一条内容要 ≈100 秒（长间隔 + 风控节流）→ 把检查塞进主循环 = 「用户点了停止，
要等 1 分半才生效」。线程是 daemon，每轮先看子进程是否已退出，不会残留。

```python
def _start_cancel_watchdog(proc, rid):
    """后台轮询停止信号，命中就 kill 掉采集子进程。返回 (thread, state)。"""
    state = {"cancelled": False, "stop": False}

    def loop():
        while not state["stop"]:
            time.sleep(CANCEL_POLL)                       # 10~15s：手感够快、又不至于刷爆 node 进程
            if state["stop"] or proc.poll() is not None:
                return
            try:
                if stop_asking(rid):                      # 读信号 + **顺手执行掉**
                    state["cancelled"] = True
                    try: proc.kill()
                    except Exception: pass
                    return
            except Exception:
                pass

    th = threading.Thread(target=loop, name="cancel-watchdog", daemon=True)
    th.start()
    return th, state
```

**「顺手执行掉」是必须的**：本实例正在跑这一轮时，主循环阻塞在 `run_scan` 里，
根本轮不到空闲逻辑去处理信号 —— 若只在那里处理，**单实例部署下这个功能等于不存在**。

**收尾三态 + CAS**（这一步决定了「用户主动停的」会不会被写成「失败」）：

```python
st = "cancelled" if run_status(rid) == "cancelled" else ("done" if rc == 0 else "failed")
finish_run(rid, st, summary, expected="running")     # 带条件更新：已 cancelled 的记录不许被改写
```

收尾文案也要分开 —— **手动停止不是「未达标」**（写那三个字会让用户以为机器又坏了）：

```python
if cancelled:
    head += f"，已按网页端要求停止（已入库的 {produced} 条全部保留）"
elif produced < target:
    head += "，未达标：" + "；".join(reasons)
```

前端两处**必须**同步（否则点几次停止就把自己的每日额度刷掉）：

```js
function isRunTask(x){ return !!x && x.status !== 'stop' && x.status !== 'stopped'; }
function runTasks(){ return (state.runs || []).filter(isRunTask); }
// 「任务列表 / 今日配额 / 成员筛选次数 / 历史记录」四处口径一律改用 runTasks()
```

按钮侧：只给**未结束**的任务渲染；已发信号还没被处理的显示「停止中…」（防连点堆信号）。

**回到「停止本次正在跑的」这类运维请求，顺序不可颠倒**：

1. **先取消排在后面的 pending**（不拦住它，停掉当前这条它会立刻开跑下一轮）；
2. 再把正在跑的那条置 `cancelled`；
3. **最后**才 kill 采集子进程。
   （先 kill 会有竞态：那一刻库里还是 running，监听器收尾可能先写成 failed。）

### 18.4 ⚠️ 别拿「会被常驻进程正常改写」的文件当测试指纹

本节的隔离测试原本这样收尾：比对 `rounds.lock` / `watch.pid` / `watch_heartbeat.json`
的 `mtime+size` 未变。结果**一直红** —— 因为：

* 锁文件被常驻监听器反复 **创建 / 删除**（拿到锁就写、放锁就删）；
* 心跳文件每 10 秒被刷一次。

这些都是**正常的运行时行为**，与被测对象无关。**改成断言「隔离是否真的生效」**才有意义：

```python
ok(str(SL.LOCK_PATH).startswith(_TMP),   "锁被重定向到临时目录 —— 不会抢产线的模拟器")
ok(str(W.PID_PATH).startswith(_TMP),     "pid 文件被重定向 —— 不会把产线监听器挤下线")
ok(str(W.HB_PATH).startswith(_TMP),      "心跳被重定向 —— 不污染巡检")
ok(os.path.abspath(W.BASE) == os.path.abspath(HERE), "被测模块确实来自产线目录（不是测了副本）")
ok(not SL.owns(),                        "测试结束时没有残留持有中的锁")
```

### 18.5 ⚠️「编辑报成功」不等于落位 —— 这类沙箱里必须**按行为复核**

本轮最贵的一课：一批改动**全部报成功**，实际 grep 发现 **6 处没落位**，而且缺的都是**接线**：

| 漏掉的东西 | 后果 |
|---|---|
| 常量定义（`ANY_INSTANCE = "*"`） | 调用时 `NameError` |
| `import threading` | 看门狗线程启动即 `NameError` |
| 被主循环调用的新函数（`run_status`） | **每轮轮询都抛异常**，收尾状态全错 |
| 返回值新增的键（`cancelled`） | 上游判断永远为假，「已停止」被写成「异常退出」 |
| 前端函数体（`recStatus` 的分支） | 用户看到的还是旧文案 |
| 行模板里的按钮 | 功能「写了但不存在」 |

**纪律**：

1. **改完逐个 grep 新符号**（不是 grep 文件、是 grep 每个新名字），核对**真实源码**而不是记忆；
2. **测试要写成「少了这处编辑就变红」** —— 本轮正是 15 条 FAIL 把 6 处漏改一次性抓了出来；
3. 断言串要与**实现措辞**对齐（`"if gating and stats_now:"` 里的 `if` 也要算），
   否则 FAIL 会误导你以为是实现错了；
4. 子进程里 `print(json.dumps(...))` **必须 `ensure_ascii=False`**，
   否则中文变 `\uXXXX`，含中文的断言永远匹配不上（**这是测试自己的坑，不是实现的**）。

### 18.6 顺带修掉的一个多开隐性坑：僵尸回收会抢别人的活

「僵尸任务」判据通常是「状态是 running，但**本实例**既没锁也没采集进程」。
多开之后这个判据**只看得见自己** → 实例 0 看到实例 1 正常在跑的请求时，
会把它当僵尸**抢过来重跑**（CAS 也会通过，因为它确实是 running）→ 两个实例同抢一个模拟器。

```python
# scan_lock：加哨兵，表示「不按实例过滤」
ANY_INSTANCE = "*"
def any_scanners_running(exclude_pids=()):
    return scanners_running(exclude_pids=exclude_pids, instance=ANY_INSTANCE)

# 消费端：回收僵尸前先问一句「全机到底有没有实例在采」
if zombie and SL.any_scanners_running():
    log("本机有扫描进程在运行（可能是另一个实例）→ 不回收僵尸任务")
    zombie = []
```

**验证要两条路都覆盖**：`any_scanners_running()` 为假 → 正常回收（期望状态 `running`）；
为真 → **一条都不回收**（`start_run` 不被调用）。

## 19. 「出有效内容太慢」怎么查：先把一轮**按阶段记账**，再改「早退顺序」

来自一次真实报障：「点击筛选后，出有效的内容速度还是太慢，有解决的方法吗，
模拟器多开能不能解决？」—— 这是**最容易答错**的一类问题：直觉会把人带到「加机器」，
而实测瓶颈几乎全在「注定要丢弃的详情页」上。

### 19.1 第一步永远是记账，不是优化

别猜。把**一轮**的日志按时间戳拆开（每条都有 `[HH:MM:SS]`）：

```
[01:58:24] 打开卡片: 减肥的虾皮 | ...
[01:58:44]   图片: 采到 3/7 张          ← +20s
[01:59:07]   短链: https://dw4.co/...   ← +23s
[01:59:19]   主页: 粉丝=357 关注=23     ← +11s
[01:59:19]   主页截图: ✓                ← +0s
[01:59:27]   发布日期 2026-09-07 不满足「10天内」 → 不入库，继续下一条   ← +8s
```

**日期是最后一步才拿到的** → 前面 55 秒对一条注定被丢弃的记录**全部白做**。

再算整轮（对照收尾那几行统计）：

| 去向 | 次数 | 单次 | 小计 |
|---|---|---|---|
| 真正产出 | 10 | 106s | 18 min |
| 日期不达标丢弃 | 12 | 63s | 13 min |
| `dump` 失败放弃 | 16 | 62s | 17 min |
| 完整度不足丢弃 | 2 | 70s | 2 min |
| 其它 | 4 | 45s | 3 min |

一轮 68 分 9 秒，**只有 18 分钟花在有产出的内容上**；命中率 23%，**52% 砸在注定丢弃的页面上**。
**这张表才是优化清单**；「多开」只是把这张表乘 2，成本却高得多。

### 19.2 根因一：预筛被写进了「模式分支」里 → 另一种模式**静默不筛**

```python
def card_gate(card, tcfg, step, excl_idx):
    if tcfg:                        # ← 祸根：整段只在「定向」模式执行
        ...内容形式 + 点赞预筛...
    hit, _by = excl_match(...)       # 只剩排除清单
```

而前端默认走的是**另一种模式** → `tcfg is None` → **点赞预筛从未执行**；另一套默认参数
还是「不限时间 · 不限点赞」，等于完全没有门槛。用户设「50~100 赞」，**0 赞卡片照样点进
详情页**，花 90 秒采完才发现不符合 → 既「慢」，又「全部显示未达标」——**两个体感同一个 bug**。

**修法**：把两种条件归一成同一套「区间」语义，让预筛函数**与模式无关**。

```python
def card_gate(card, tcfg, step, excl_idx, mcfg=None):
    content = None
    lk_min = lk_max = None
    if tcfg is not None:             # 逐级放宽：只有下限
        content = tcfg.get("content") or "both"
        lk_min = int((step or {}).get("likes") or 0)
    elif mcfg is not None:           # 区间筛选：闭区间，**上限也要判**
        _rng = (mcfg.get("likes") or {})
        lk_min, lk_max = _rng.get("min"), _rng.get("max")
    ...
    lk = card.get("likes")
    if lk is not None:               # ⚠️ 读不到就放行，交给详情页那道闸
        if lk_min is not None and lk < int(lk_min):
            return False, "点赞不足"
        if lk_max is not None and lk > int(lk_max):
            return False, "点赞超上限"
```

**上限那一档别漏**：设「50~100 赞」时，5000 赞的爆款同样不该被点进去（省 90 秒）。

调用处必须跟着传：`card_gate(c, tcfg, steps[step_i], excl_idx, mcfg=mcfg)` —— **不传等于没修**。

**自检问句**（模式有几个就问几遍）：**「另一个模式下，这个预筛还在吗？」**
⚠️ 尤其当预筛的**日志**已经改对、而**逻辑**没改时，日志会「看起来在工作」。

### 19.3 根因二：「早知道」分支的**前提**错了 —— 它要的值，恰恰要操作后才有

代码里往往已有一个「早退」分支，注释还写着「实测命中 N 张」。但要看它的**前置条件**：

```python
# 旧：只在「首屏已经读到日期」时才判
if tcfg and detail["edit_time_raw"]:
    if not date_pass(...):
        leave_card(...)
```

注释还解释「日期读不到仍要走完整流程，因为日期可能上滑后才渲染出来」。
**问题恰恰在这里：这类帖子（图文帖）的日期几乎必然要上滑才渲染** → 条件恒假 →
**早退分支形同虚设**，所有卡片都溜到流程末尾才判日期。

**修法**：把「拿值」主动做掉，并把判定挪到**昂贵操作之前**。

```python
# 先主动上滑去拿日期（视频页不滑 —— 上滑会切走视频）
if not detail["edit_time_raw"] and not detail["is_video"]:
    for _ in range(2):
        swipe_up(2.0)
        _ns = dump()
        _et = find_one(_ns, "tvItemEditTime")
        if _et:
            detail["edit_time_raw"] = _et[0]["text"]
            break
# 再判：不达标立刻走，后面的「分享链路 + 主页」全省（省 36~52s/条）
```

**两条配套纪律**：

1. **移动而不是复制**：原来排在末尾的那次「上滑找日期」必须**删掉**，否则等于上滑两轮。
2. **别破坏采集顺序的依赖**：截图/图集采集**必须趁页面在首屏**，所以「上滑」不能挪到它
   前面 —— 只能挪到它**之后、分享之前**。想再快就要「先滑再翻回顶部重新打开」，
   那是拿达标卡片（真正的产出）去冒险，**不划算**。

### 19.4 根因三：失败重试链没有熔断

```
dump 为空 → 重连 → sleep 3 → 再 dump → 再重连 → 放弃      （实测 62 秒/条）
```

而在详情页流程里这条路会被**调用 2~3 次**（首屏 / 点击重试 / 数字补齐）→ 一次失败 ≈60 秒起。
一轮里 16/44 次栽在这里。

**修法**（三条常数级改动一起上）：

```python
DUMP_TIMEOUT = int(os.environ.get("DUMP_TIMEOUT", "12"))         # 20 → 12
DUMP_RETRY_WAIT = float(os.environ.get("DUMP_RETRY_WAIT", "1"))  # 3 → 1
...
time.sleep(2)        # 「数字补齐」那次的等待：6 → 2
```

**判据**：同一条失败路径上各处等待时间**相加**才是真实成本。单看每一处都不大，
叠起来就是一条 60 秒的死路。

### 19.5 根因四：「保护性中止」把状态写成了**不可逆**

风控触发时写一个 `aborted: true`，然后**整天不再跑** —— 实测当天 04:34~10:42 五次调度
**全部空转**（≈8 小时零采集），用户只会觉得「今天特别慢」。

**修法**：把「中止」改成**带截止时间的冷却**，并且能自动恢复：

```python
ABORT_COOLDOWN_H = float(os.environ.get("ABORT_COOLDOWN_H", "2"))
st["aborted"] = True
st["abort_until"] = (datetime.now() + timedelta(hours=ABORT_COOLDOWN_H)).isoformat(timespec="seconds")
```
```python
if st.get("aborted"):
    until = str(st.get("abort_until") or "")
    if until and datetime.now().isoformat(timespec="seconds") < until:
        w(f"冷却中（至 {until}）→ 跳过"); return
    w("冷却已结束 → 自动恢复")
    st["aborted"] = False; st["abort_until"] = ""
```

⚠️ **老状态文件没有 `abort_until` 字段** → 必须落到「恢复」而不是「永久锁死」
（`setdefault("abort_until", "")`），否则升级后老文件会把任务锁到第二天。

### 19.6 ⚠️ 早退最容易犯的错：把「未知」当成「不达标」

这是本轮**自己引入、靠实现复核才抓到**的 bug，务必当模式记住。

区间判定函数通常长这样（它同时服务「标注原因」和「决定丢不丢」两种用途）：

```python
def _range_miss(label, val, rng):
    if lo is None and hi is None: return None
    if val is None: return f"{label}未取到，无法确认是否在设定区间内"   # ← 话术，不是判据
    ...
```

**「标注」时**这句话是对的（要如实告诉用户「无法确认」）；
**「丢弃」时**拿它当判据就是**误杀** —— 一条只是没读到点赞的记录会被丢掉。

```python
# ✗ 错：未取到 → 也走 leave_card
_lmiss = _range_miss("点赞", detail["likes"], _lk_rng)

# ✓ 对：只在确实读到值时才早退
_lmiss = (None if detail["likes"] is None
          else _range_miss("点赞", detail["likes"], _lk_rng))
```

**纪律**：凡是要「丢记录」的地方，先问一句 —— **这个判断在「值缺失」时返回什么？**
若返回的是「非空说明文字」，就必须自己加 `is not None` 守卫。
（同理：**未知不得当作 0**，也别把「0 赞」和「没读到」混成一件事。）

### 19.7 测试怎么写（105 条断言里，真正值钱的是这三类）

1. **行为断言优先于源码断言** —— 把纯函数抠进子进程、打桩依赖，喂 8 个用例：

```python
C = lambda **kw: dict({'username':'a','title':'t','likes':None,'video':False}, **kw)
g(C(likes=10),   mcfg={'likes':{'min':50,'max':100}})   # → 拦（修前：放行）
g(C(likes=200),  mcfg={'likes':{'min':50,'max':100}})   # → 拦（上限）
g(C(likes=80),   mcfg={'likes':{'min':50,'max':100}})   # → 放行
g(C(likes=None), mcfg={'likes':{'min':50,'max':100}})   # → 放行（交给下一道闸）
```

   **修 bug 之前先跑一遍这些用例**：「三条 multi 用例全都放行」这个现象本身，
   就是最有说服力的证据。

2. **状态机要真跑**：验收「冷却恢复」不要只 grep 源码，用临时状态文件 + 一个安全阀
   真跑一次 —— `TARGET_ROUNDS=0` 能让它在**抢锁之前**返回，绝不会真开扫：

```python
env = dict(os.environ, TARGET_ROUNDS="0", ROUNDS_STATE=tmp_state, ROUNDS_LOG=tmp_log)
subprocess.run([sys.executable, "run_rounds.py"], env=env, cwd=HERE, timeout=120)
```
   三个场景都要覆盖：**未到点 / 已过点 / 老文件缺字段**。

3. **顺序类改动用「位置断言」**，不要只断言「新代码存在」：

```python
ok(SRC.index("_lk_rng = ") < SRC.index("# 0) 图片/头像截图采集"),
   "点赞判定排在图片采集**之前**（否则照样白采 20s 图）")
ok("nodes3 = dump()" not in SRC, "流程末尾那次重复上滑已删除")
```

4. **并发下假红：探针类函数带「保守兜底」时，别拿死值断言**（2026-09-20 实测）
   —— 现象：全量回归 37 个文件一起跑时 `test_rounds_lock.py` 偶发 `FAIL=1`，
   单跑 5/5 全绿。根因不在产线：

```python
# scan_lock.pid_alive —— except 分支是**有意**的保守兜底（宁可不抢锁，不可乱抢）
try:
    r = subprocess.run(["tasklist", "/FI", f"PID eq {pid}", ...], timeout=20, ...)
    return str(pid) in (r.stdout or "")
except Exception:
    return True          # ← 高负载下 tasklist 超时，这里就返回 True
```
   → 断言「死 pid 应判为已死」在机器忙时必然假红。

   **处理原则：改测试，不改产线语义。** 三步：
   - **①探针判断要紧贴调用量，不要用文件开头算好的常量分支。**
     第一版补丁把探针结果存成模块级 `_PID_PROBE_OK`，结果人工强制降级时立刻 `FAIL=2`
     —— 因为探针可能在「算常量」与「真调用」之间恢复，两条路都断言就全错。
   - **②重试计数替代单次探测**：`pid` 探针给 3 次，任一次判为已死即算「探针可用」。
   - **③两条路各自断言真实不变量**，而不是死盯某一个结果：

```python
_probe_now = (R._pid_alive(999999) is False)      # ★ 紧贴调用之前
got, why = R.acquire_lock()
with open(R.LOCK_PATH, encoding="utf-8") as f:
    info = json.load(f)
if _probe_now:                                     # 探针说「已死」→ 必须真接管
    ok(got is True and info.get("pid") == os.getpid(), "3) 接管后锁归属自己")
else:                                              # 探针说「活着」→ 必须拒绝，且不得覆盖原锁
    ok(got is False and "进程存活" in why, "3) 保守拒绝抢锁（产线有意语义）")
    ok(info.get("pid") == 999999, "3b) 拒绝抢锁时不覆盖原锁记录")
```

   **验证方式**：把 `scan_lock.pid_alive` 打桩成 `lambda pid: (False if not pid else True)`
   跑一份临时副本 —— 两条分支都必须 `PASS=19 FAIL=0`。
   ⚠️ 打桩时**保留 `if not pid` 这类前置守卫**，否则会误伤别的断言
   （第一版打桩把 `pid_alive(None)` 也变成 True → `8c) None 视为不存活` 假红，
   那次假红是**测试脚本的错**，不是产线的错）。

### 19.8 什么时候才该上多开

**多开是乘法，先要把被乘数做大。** 判断顺序：

1. **先看瓶颈是不是「串行等待」** —— 本例是（adb dump、截图、`sleep`），所以多开**理论上**
   接近线性；若瓶颈在服务端风控或内容池，多开只会更快撞墙。
2. **必须给每个实例独立账号** —— 同一个号 + 同一个推荐流 → 两个实例采到**同一批内容**，
   重复率翻倍，**等于没多开**。
3. **先量资源余量**：本例 16 逻辑核够，但**内存已占 81%、只剩 5.8 GB** → 再开一个模拟器
   会立刻让 `dump` 超时率上升（当时已经 36%），**反而更慢**。
4. **同出口 IP 多号并发会推高风控**（本例单实例已经 3 次验证码/轮）。

**算给用户听**：直接多开 = 6.8 min/条 ÷ 2 ≈ 3.4（还要赌风控）；
先改完上面四条再开 = 2.5 min/条 ÷ 2 ≈ **1.25**。**同样的机器，差 2.7 倍。**

## 20. 「某页面有没有某字段」——**先用历史快照普查，别急着跑模拟器**

### 20.1 触发场景

用户问：「App 的详情页上有没有显示 X？」「这个字段能不能抓？」——并且**不想为此占用模拟器时间**。
**不要**立刻开工改采集器、也不要「挂到下一轮顺便看」：先问一句
**「这个页面我以前 dump 过没有？」** 多数情况答案是「有，而且很多」。

采集器为了排障留下的现场快照（`diag/`、`*-probe`、`fixtures/`）本身就是**样本库**。
本项目实测：一次普查翻出 **151 个 XML**，其中 **95 个是内容详情页** ——
足够给出结论，**成本 0、模拟器 0 次启动、采集流程一行未改**。

> 顺带：这比用户设想的「挂到下次任务顺手验证」**更快**（不用等任务），
> 也不违反「不额外耗时」的约束。先翻盘再动手，是这里的默认动作。

### 20.2 方法：先**分类页面**，再统计关键词命中

不要把所有 XML 混在一起搜关键词 —— 同一个词在不同页面上含义完全不同（见 20.3）。三步：

**① 按 `resource-id` 指纹给每个 XML 判页面类型**（本项目得物 App 实测可用）：

| 页面类型 | 指纹（任一命中） |
|---|---|
| **内容详情页** | `tvInteract` + (`tvUsername`\|`tvUserName`)；或 `flShare`/`shareView`；或 作者 + `tvItemEditTime`/`contentTime` |
| **达人主页** | `tvFansCount` + `tvLikeCount`（本项目还有 `tvReadCount`） |
| **社区流 / 列表** | `clGridRoot` |
| **话题页** | `tvTopicUseNumber` |
| 其它（活动 WebView 等） | 都不命中 |

**② 对每一类，统计「含关键词的文件数 / 该类文件总数」** —— 这样得到的是**硬数字**
（本项目：「内容详情页 95 个，含『阅读』的 **0** 个」），而不是「我翻了翻没看到」。

**③ 再列「该类页面出现过的全部计数类控件」** —— 这是**最强证据**：
把该页面所有 XML 里 rid 含 `count`/`number`/`num`/`read`/`view`/`like`/`interact` 的控件名去重汇总。
若 95 个详情页快照里只出现 `tvInteract`/`likeView`/`commentView`/`collectView` 而**没有任何 read/view 类**，
那「详情页不显示阅读量」就是可复算的结论，不是观感。

### 20.3 三个必须避开的坑

1. **同名字段在不同页面含义不同**（本项目实测）：
   - `tvTopicUseNumber` = 「532人参与 · **883万次阅读**」→ 这是**话题**的累计阅读量，**不是**单条内容的；
   - 活动 WebView 里搜到的「单条阅读量≥10000」是**规则文案**，不是数据；
   - 只有 `tvReadCount`（数字）+ `tvRead`（标签「阅读」）挂在**达人主页**的 `personalInfoView` 里，
     与 `followLay`/`fansLay`/`saluteLay` 并列 ⇒ 它是**账号累计阅读量**。
   ⇒ **「含关键词」≠「有这个指标」**，必须看 rid 归属 + 它在树里的位置。
2. **快照可能是「分屏态」**：本项目 `p5_04_share.xml` 里**左半边是内容详情页、右半边是达人主页**
   （靠 bounds 宽度就能看出来）。**别把右栏主页的字段当成本条内容的字段**。
   判据：看 `bounds` —— 详情页那一栏会被压到窄宽度（如 `(0,0,216,1920)`）。
3. **快照是历史产物，App 可能已改版**：结论要带上「基于哪天的快照」；
   要给用户拍板用的话，最好提示「如需 100% 确认，可用新快照复核」。

### 20.4 第二个收益：判断「是不是零成本可加」

一旦确认字段**存在于某页**，顺手再做一步：**这一步的 dump 现有流程是不是已经有了？**
本项目就是这种情况 —— 采集器为了拿粉丝数已经 `nodes4 = dump()` 了达人主页那一屏，
`extract_profile()` 只读了 `tvFansCount`/`tvFollowCount`/`tvLikeCount`，
而 `tvReadCount` 就在**同一份 XML 里**。

⇒ 加一行 `find_one(nodes4, "tvReadCount")` 即可，**零额外 dump / 零额外点击 / 零额外导航 / 零额外耗时**。
**这个判断决定了要不要「新增一次导航」——先查「同一屏有没有」，再决定动不动代码。**

### 20.5 交付物长什么样

1. **硬数字表**：页面类型 × 文件数 × 命中数（可复算）；
2. **该页面的完整可见文本**（用户常明确要「不要过滤、不要精简」，按坐标顺序输出全部
   `text` + `content-desc`）；
3. **字段的控件结构**（`rid` / `text` / `bounds` 三列），别只给一个数字；
4. **口径纠偏**：说清该字段是**账号级**还是**内容级**、是**累计值**还是**动态值** ——
   否则用户会按错误口径去用（本项目：账号累计阅读量被误当成单条内容阅读量）；
5. **明确写「本轮一行代码没改、模拟器没启动」** —— 用户对「不额外耗时」很敏感，要让他能核。

## 21. ★★★ 「adb 点了没反应」：先做阳性对照，再谈「点不动」

**最贵的一类误判**：在**没有目标**的位置上测点击，必然得出「点不动」，然后被写成结论。
本项目实测踩过：曾报告「发布页相册缩略图块 adb 注入点不动（9 种注入全失败、截图 md5 一字不差）」
—— **结论是错的**。真因是**相册里当时一条素材都没有**（点在空白背景上），
再加上用的坐标属于**另一种布局**（同一控件两套布局 y 差 102px）。

### 21.1 铁律：测「点不点得动」之前，先证明**那里有东西可点**

1. **先确认该位置有没有可交互目标**：截图 + `uiautomator dump`，找 `clickable="true"`
   （或带 `content-desc`）的节点，**它的 `bounds` 必须真的覆盖你要点的坐标**。
2. **没有目标的页面上测点击 = 测了个寂寞**。此时任何「md5 没变」都**不能**当「点不动」的证据。
   ⇒ 报告里必须写清「当时那一格**有什么**」，而不是只写「点了没反应」。
3. **阳性对照**：同一次会话里，先用一个**已知可点**的元素（页签 / 标题栏 / 返回）
   证明「adb 注入这条链路本身是通的」，再去测可疑元素。
   ★ **链路不通**和**元素不可点**是两回事，必须分开证。
4. **md5 变了也要看清是「谁」变了**：异步加载、下拉回弹、状态栏跳秒都会让 md5 变化。
   ⇒ 变化必须配上**页面结构变化**（dump 里出现新页面的标志节点）才算证据。

### 21.2 ★★ 别在缩放图上肉眼估坐标 —— 用像素找

在 1/2 缩放的截图上「看着差不多」估出来的坐标，误差常 >20px，足以落在隔壁格。
写个**像素级定位器**：按行扫描截图，找**连续亮像素跨度 ≥ 阈值（如 40px）**的行程
（这一步自动滤掉文字/图标这类窄行程），再把相邻行合并成块 —— 块的 `[x0,y0]` 就是缩略图的真实位置。
本项目正是靠它发现缩略图在 `(87,255)`，而写死的 `(88,358)` 属于**另一种布局**。

> ★ 同一屏有**多套布局**时（图片=一行多格、视频=单格大缩略图），
> **一个写死的坐标必然有一半场景点空**：要么按布局分支取坐标，要么**从 dump 的 `bounds` 现算中心点**。

### 21.3 ★★ 推文件进设备后「相册里选不到」——媒体扫描三条路，先判哪条还有接收者

`adb push` 只是把文件放进存储，**相册（MediaStore）要另外收录**才会出现在 App 的选择器里。
在 MuMu 12 / Android 12 上**三条路实测全断**：

| 办法 | 实测结果 | 判据 |
|---|---|---|
| `am broadcast -a android.intent.action.MEDIA_MOUNTED` | `SecurityException` | 已是**受保护广播**，`uid=2000(shell)` 无权发 |
| `... -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file://…` | 返回 `Broadcast completed: result=0`，**等 20 秒 `content query` 仍是 0 行** | ★ 判「**没有接收者**」而不是「慢」——**必须给出等待时长**才算证据 |
| `content insert --uri content://media/external/file` | 静默失败 | shell 不在 `media_rw` 组 |
| **重启模拟器** | ✓ 系统重扫，文件进库 | 唯一有效 |

⇒ 两条纪律：

1. **「发成功了」≠「生效了」**：广播返回 `result=0` 只说明「没人处理」。
   一定要**回头查目标状态**（`content query` 计数），否则会把「无效」写成「成功」。
2. ★★ **别把「调大超时」当解法**：实测永远没用 ⇒ 变成让用户白等的**假建议**。
   要写就写「**这台设备只有重启才收录**」，并给「发布前自动重启一次」这种**能落地**的出路。

### 21.4 ★★ 被推翻的结论要**当场改掉全部副本**

上一条错误结论当时已经写进了三处：交给用户的报告、项目 `docs/HANDOFF.md`、以及**记忆/技能文件**。
复测推翻后**必须一次性全改**，并在原位留「← 日期 + 复测推翻」的标记 ——
否则下次会话读到旧副本，会把已经被推翻的结论当事实继续用。

> ★ 反面模式：只在最新那份文档里更正，旧副本留着自相矛盾。用户会同时看到两套说法，直接失去信任。
