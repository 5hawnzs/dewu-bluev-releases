# 数据源合并可行性审计（「能读到」≠「能替换」）

## 何时用

- 用户问：「同一个接口/同一个响应里就能读到 A 和 B，我还要不要分两次抓？」
- 你要把两个定时脚本 / 两个采集器合成一个，或想把某个字段的数据源换掉。
- 有人拿「抽样几条对得上」当证据说「同源、可以直接替换」——**这时最该用本技能**。

## 三条核心原则

1. **「能读到」≠「能替换」。** 字段出现在同一个响应里，只说明**能省一次请求**，
   不说明**口径一致、可以互相覆盖**。这两件事必须分开回答。
2. **「合并」的正确含义是「合并请求，字段语义各归各位」**，不是「把两个脚本揉成一个」。
   现值 / 基线 / 快照三类值各有各的定义域，合并后仍然必须分家。
3. **先量「现状产出率」，再谈合并。** 如果被替换的那条路本来就在空转，
   合并就不是「用新的换掉能用的」，而是「把一个空转的换掉」——这是最有力的论据，
   也决定了风险讨论的重心完全不同。**这一步最容易被跳过。**

## 六步法

### 第 1 步：把「能力」和「口径」分开取证

- **能力**：翻原始响应样本（抓包文件 / 历史 dump），**把字段名逐字抄下来**，
  不要凭记忆或凭文档转述。样本里没有的字段，就当它不存在。
- **口径**：见第 2 步。

### 第 2 步：全量对账，**不要抽样**

抽样 4 条「几乎完全一致」什么也证明不了。把库里**全部**可比对的主键拿去调一次接口。

**判定表（关键）**：

| 差值形态 | 含义 | 能否合并 |
|---|---|---|
| **单边**（新源 ≥ 旧值 占绝大多数，仅极少数微小负差） | 同一指标、只是**时间更新** | ✅ 可以 |
| **双边散乱**（有正有负、幅度大、无规律） | **不同口径**（如「热度」vs「点赞」） | ❌ 不可以 |
| 大量新源为 0 / 缺失，而旧值非 0 | 新源在该维度**不可用** | ❌ 不可以 |

- 微小负差要**逐条捞出来看**（例：几百分之一的一条 -2 = 用户取消点赞），
  **不要当噪声放过**，也不要因为一条负差就否掉整个方案。
- 一定同时统计：**完全相同 / 新源更大 / 新源更小 / 旧值为空 / 新源没返回 / 新源字段缺失**，
  六个桶都要有数。只报「一致率」是耍流氓。

### 第 3 步：★ 现状产出率体检（决定「值不值」）

查被替换那条路**实际产出**了多少：

- 成功时间戳有值的条数 / 尝试时间戳有值的条数 / **两个都没有（从没跑过）**的条数。
- 定时任务自身提示词里如果写着「整轮成功 0 也属正常」，那就是**自认不可靠**。
- 单次耗时 × 频次 = 每天烧掉多少时间。

**如果产出 ≈ 0，把它写进结论的第一段** —— 这比任何技术论证都有说服力。

### 第 4 步：合并前必查的 4 类风险（逐条给结论，不能只说「有风险」）

1. **语义分家** —— 列出现值 / 基线 / 快照字段各是谁写的、什么时刻的值。
   ★ **基线类字段（「进系统时」的值）绝不能被新源覆盖**，否则所有「涨了多少」的派生显示全废。
2. **★ 写入顺序打架（最容易漏的真陷阱）** —— 如果 A 路径刚写了「现值 + 基线（同值）」，
   B 路径随后只覆盖「现值」，就会出现**「刚入库就显示涨了 N」的假角标**。
   修法：让两条路径**现值与基线取同一个时刻的同一个值**，或让 B 路径干脆不写现值。
   （这类 bug 属于「界面在骗人」，比数据少更严重。）
3. **集体跳变** —— 换源瞬间，历史记录会**一次性**从旧值跳到新值。
   算一下：跳变中位数 / p90 / 最大值。**这不是 bug**，但要**主动告知用户**，否则会被当成故障排查。
4. **单点故障** —— 合并前两条路的**依赖是否独立**（一条要凭证、一条不要 → 合并后凭证失效即双双停更）。
   缓解组合拳：① 数据源整体不可用时**一个字都不写**（列停在旧值，而不是写成错值）；
   ② 探活失败**明确报错因**；③ **保留旧路径但不挂定时**，降级为「主路挂了时的手工兜底」。

### 第 5 步：算「白拿」的收益

同一次响应里顺带返回、当前没用的维度：统计各字段的有值率。
有值率明显低于 100% 的字段（例：`shareNum` 177/213），说明**部分数据形态不给该字段**，
必须按「取不到就显示 `—`」处理，**未知 ≠ 0**。这是把收益写实的必要一步。

### 第 6 步：留**只读**探针 + 明确「未做」

- 探针必须**只读**（不 PATCH / 不 POST 入库），并支持参数复跑；结论要能被第三方重算。
- 交付时**明确写出「代码一行未改 / 定时任务未动」**，并把待拍板项落到台账文件，
  不要只留在聊天里（对话会丢）。

### 第 7 步：★ 结论被否（用户回「不改」）时，一样要收口

很多审计止于「给建议」；**用户选「不改」时，不做收口会留下一个将来必踩的坑** ——
几周后有人看到「点赞数一直是旧的 / 这条链路产出为 0」，会当成 bug 重新排查一遍。

**必须写死的三样东西**（写进台账 + 长期记忆，不只写在日志里）：

1. **决策本身**：原话 + 日期 + 一句话结论（例：「保持现状，两条路不合并」）。
2. **被明确接受的既知后果**，逐条带**实测数字**（例：`likes_updated_at` 仅 1/216；
   回访 ≈30 分钟/天、产出 ≈0；角标覆盖率仅 15/216）。
   ⇒ 并加一句「**这不是缺陷，是选择；不要当 bug 查**」。
3. **把调研章节降级为「留档证据」**，并单列一节「**将来若重新评估，可直接复用的结论**」
   （把第 2~5 步的结论压成几条，省得下次重跑全量对账）。

**同时注意**：把「**只想去掉无效开销**」这类**与合并无关**的小事单独标出来
（例：把每天空转的定时任务降频/暂停），并写明**须用户单独发话，不自行处理** ——
否则「不改」很容易被误读成「什么都不许动」。

**收口检查表**：决策落在 ① 台账（顶部摘要 + 待办行 + 调研章节头，三处）② 长期记忆索引
③ 归档文件（编号连续、不留断档）④ 提交保存。写完**回读校验**（去重数、md5、编号序列），
别凭「我改过了」下结论。

## 实测踩过的坑

- ★★ **传参类型会伪装成「凭证失效」**。同一个接口，`contentIds` 发**数字数组**正常，
  发**字符串数组**被拒成「请求参数不合法」，**全部批次 0 条返回** ——
  现象和「凭证过期 / 被封」几乎一样。
  ⇒ **判断「凭证失效」前，先拿线上真脚本的传参构造方式逐字对齐**（类型、是否 `parseInt`、
  是否包了一层对象），再下结论。自写探针第一件事就是「先用真脚本跑通一次」。
- **抽样验证的误导性**：4 条里「3 条一样、1 条 +1」很容易被解读成「完全同源」；
  全量 212 条才看得出这是**单边单调**（时间差），而不是「有时多有时少」。
- **「几乎完全一致」这种措辞要警惕** —— 它同时掩盖了「也许口径差一点」和
  「也许只是时间差」两件完全不同的事，必须用分布把它拆开。
- **不动已有基线**：给历史记录补基线时，判据是「**从未被回访更新过**」⇒ 现值**就是**当时的基线，
  这是**可证的**，不是猜。但必须先过滤掉「采集时就没读到值」的记录
  （常见标记：`*_source === 'unknown'`），历史项目里往往踩过「假 0」的坑。
- **替换掉某个小节编号后要顺手补平**：把「待拍板」小节改写成「已拍板」时，
  若挪动了编号（`40.8 → 40.9`），归档里会**留下编号断档**，且正文里那句
  「见 40.8」会**指向自己**。⇒ 改完 `grep -n '^### 40\.'` 回读一遍编号序列再提交。

## 只读对账探针骨架

```js
// 只读：不 PATCH、不 POST。★ contentIds 必须发数字
const ids = Array.from(byKey.keys()).map((k) => parseInt(k, 10)).filter((n) => !isNaN(n));
const map = new Map();
let ok = 0, err = 0;
for (const b of chunk(ids, 50)) {
  const r = await fetchList(b, cred);            // 复用线上真脚本的函数，别自己重写
  if (r.err) { err++; console.log('✗ 批失败: ' + r.err); }
  else { ok++; for (const it of r.items) map.set(String(it.id), it); }
  await sleep(400);                              // 节流
}
// 关键：六个桶都要报，负差逐条打印
```

## 反模式（看到就停下来）

- ❌ 用「抽样 3~4 条对得上」论证「同源、可替换」。
- ❌ 把「同一个响应里有这个字段」直接当成「口径一致」。
- ❌ 只报「一致率 xx%」，不报差值分布和方向。
- ❌ 合并方案里把「现值」和「进系统时基线」混成一个写入口径。
- ❌ 论证完就动手改代码 —— **这是咨询题就只出建议**，待拍板项落到台账，等确认再改。
- ❌ 只改代码不查「现状产出率」，导致把一个空转的旧路径当成「能用的东西」保护起来。
- ❌ **用户回「不改」后就不管了** —— 结论被否同样要收口：写死「既知后果 + 这不是 bug」，
  否则同一场排查几周后会被重做一遍（见第 7 步）。
