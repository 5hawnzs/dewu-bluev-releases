# 「自动刷新」真伪审计 + 数据指纹盲区排查

## 何时用

- 用户问「**自动刷新是不是假刷新 / 有没有真的在刷**」
- 「刷新了，但页面上的数字一动不动」「数据明明改了，对方页面没反应」
- 「点了刷新按钮，看不到变化，要 F5 才出来」
- 你接手一个「静默刷新 + 数据指纹（signature / dirty / memo 比较）」的页面，要评估它靠不靠谱

## 〇、先分清「用户说的是哪一个刷新」—— 页面上的「刷新」常常不是一个东西

★ **最容易把整份结论带偏的一步**。实测（2026-09-24 得物）：用户问「自动刷新是不是假刷新」，
而同一条工具条上**并排有三个东西**，职责完全不同：

| 控件 | 职责 | 判据（问自己） |
|---|---|---|
| 「🔄 刷新」/「自动刷新」（定时） | **重读数据库**，把**新采到 / 新入库的内容显示到页面**（不刷 ⇒ 新内容一直不显示） | 它该不该去源头抓？**不该** —— 抓数字是另一个按钮的活 |
| 「📥 刷新数据」（可能仅管理员） | 去**外部源**把**阅读数 / 点赞量**这类指标读回来、写回库 | 它是不是由**本机监听器/另一个进程**执行？前端只投一行请求？ |

⇒ **先向用户确认「你指的是哪一个」，再动手审计**。混为一谈会得到两个都错的结论：
把「只重读库」当成缺陷（其实是设计），或者用「它有没有抓回指标」去判真假（抓数字根本不是它的活）。

⚠️ 但也正因为**两件事分工互补**，它们会在**同一条缝**上咬合：
「刷新数据」在**另一个进程**里写库（如 `raw.read_num`），「自动刷新」必须**看得见这个变化**才会重绘。
⇒ 于是**指纹盲区恰好长在这条缝上**：修之前，刷新数据抓回来的数字**永远不会**出现在表格里
（只有点开详情弹窗才看得到新值）—— 用户必然得出「刷新是假的」。
**报告时的正确措辞**：这两件事不是一回事（分工），但你的修复正好让它们**闭环**。

判别技巧：读按钮的 `title` / 代码注释，通常写着「**不是一回事**」；再看它有没有写库路径
（`insert/update/upsert` / 投一行 request），以及真活是不是在**本机监听器**里。

## 一、先分型：三种「假刷新」混在一起，别一口咬定是假的

用户说的「假刷新」通常是这三件事的**观感叠加**，必须分别取证、分别下结论：

| 型 | 判据 | 取证方式 |
|---|---|---|
| **① 只重读库，不去源头抓**（**多半是设计如此**，别当缺陷 —— 见第〇节） | 刷新只发 `select`，整段零 `insert/update/upsert` | 桩住数据层**数调用**：一次刷新 = N 条查询、全部是 select |
| **② 指纹盲区**（真 bug） | 某字段变了但 `dataSig()` 没变 ⇒ 短路返回 ⇒ 不重绘 | 逐字段探针：**只改这一个字段**，指纹必须变 |
| **③ 条件性不跑** | 页面在后台 / 有弹窗 → `autoPaused()` 直接 return | 行为级：`document.hidden=true` 后连续 tick，数调用次数 |

**结论句子要照这三条写**：「不是假刷新 —— 它真的每 5 分钟发 8 条查询（但那是**重读库**、按设计不去源头抓
指标）；而且『阅读数』这类字段确实变了不重绘（已修）；另外页面在后台就直接暂停，这多半才是你觉得没刷新的原因。」

★ 附带一条常被忽略的**衔接缺口**：若「抓数据」那个按钮跑完只更新自己的状态文案、**不重载列表**
（实测：轮询里只调 `refreshRuns()` → `loadRuns() + updateMsg()`），那用户抓回来的数字要等**下一跳自动刷新**
（或后台被暂停 ⇒ 永远等不到）才显示。这不是指纹问题，但用户观感一样是「刷新没用」——
报告里要点出来，并给出「跑完替用户把那一跳提前执行一次」的最小改法（**只重读库、不额外打外部源**，不改变分工）。

## 二、四步取证（每步都要「可复算数字」，不要读代码猜）

### 步 1：读短路条件，定位「不重绘」的判据

```js
var sig = dataSig();
var changed = (sig !== state.dataSig);
state.dataSig = sig;
if (opts.silent && !changed) return false;   // ★ 自动刷新就是在这里被短路掉的
```

⚠️ 顺带记住一个**反直觉但关键**的事实：**短路只跳过「渲染」，不跳过「取数」** ——
`state.records = r1.data` 已经执行了。所以「弹窗/详情页」是当场从 state 渲染的，会是新值；
**表格里那些不会重绘的格子才是旧值** ⇒ 表格和弹窗对不上，最容易被当成「刷新是假的」。
报告时要把这条点明，否则用户永远查不到「为什么弹窗是新的、列表是旧的」。

### 步 2：列「界面上显示的字段」× 「指纹覆盖」对照表

把表格/列表**真正渲染出来的**每个字段列出来，逐个去指纹里找。
只看指纹函数是不够的 —— 关键是**谁在写这个字段**：

| 字段 | 谁写 | 在指纹里？ |
|---|---|---|
| `likes`（表列） | 采集入库 + 另一个进程刷新 | ✅ |
| `raw.read_num`（阅读数） | **另一个进程**（refresh_readnum / 刷新按钮） | ❌ ← 盲区 |
| `raw.read_num_note`（「—」的原因 tooltip） | 同上 | ❌ ← 盲区 |
| `raw.content_type` / `raw.handheld*` | 另一个进程（分类器） | ✅（历史上踩过，已补） |
| `myModules` / `filterConfigs` | 管理员在别的账号上改 | ✅（历史上踩过，已补） |

**规律**：历史上修过的盲区全是「**另一个进程/另一个角色**写库、指纹里没有」。
所以新加任何「由后台进程回填」的字段，必须同步问一句：**它进指纹了吗？**

### 步 3：逐字段探针（行为级，喂真指纹函数）

```js
const fn = new Function('state', dataSigSrc + '\nreturn dataSig;');   // dataSigSrc = 从产线文件抠出来的真函数
st.records = [{ id: 1, likes: 10, valid: true, raw: { read_num: 100, content_type: '美妆护肤' } }];
const a = fn(st)();  mutate(st.records[0]);  const b = fn(st)();
// 期望：a !== b
```

★ **必须同时有「反向探针」**：那些**与显示无关、每次都变**的字段
（如 `raw.read_num_tried_at`、`raw.likes_updated_at`）**不许**进指纹 ——
否则每轮自动刷新都白重绘 500 行，正是当初做指纹要避免的事。
有正有反，才证明这个指纹是「按需重绘」而不是「要么不动、要么乱动」。

### 步 4：条件性不跑，用行为级数调用次数

```js
A.document.hidden = true; A.state.autoLeft = 5;
for (let i = 0; i < 10; i++) A.api.autoTick();
// 期望：loadAll 调用 0 次、autoLeft 仍是 5（暂停**不扣**倒计时）
```

判据要写成**相对顺序**（`if (why) { … return; }` 排在减法之前），
别写成「这段里不含减法」—— 减法就在同一段里，那样断的是错的东西（本轮假红过一次）。

## 三、修复原则

1. **只加「要显示的」字段**：`raw.read_num` + `raw.read_num_note`（表格列 + 「—」时的 tooltip）。
2. **绝不把整个 `raw` 塞进指纹**：里面有一堆时间戳每次尝试都会变。
3. 补完立刻把「正/反两个探针」都写进测试，并在修好的**同一位置**留一条注释说明
   「为什么只加这两个」（否则下一个人会把整个 raw 塞进来）。
4. 指纹变长是有代价的（500 行 × 每字段十几字符），但比「看起来是假刷新」便宜得多；**不要为此省**。

## 四、反向验证（造坏版，必须变红而不是崩溃）

| 坏版 | 改什么 | 期望红 |
|---|---|---|
| ① 指纹缺口回来 | 删掉 `+ raw.read_num` 那一行 | 逐字段探针那两条 |
| ② 拆掉短路 | `if (opts.silent && !changed) return false;` → `if (false) …` | 「数据没变不动 DOM」 |
| ③ 后台照跑 | `if (document.hidden) return '页面在后台';` → `if (false) …` | 暂停那两条 |
| ④ 暂停也扣倒计时 | 把减法挪到 `if (why)` **之前** | 顺序 + 行为级 |
| ⑤ 把无关时间戳塞进指纹 | 追加 `+ raw.read_num_tried_at` | **反向**探针（「不该变」那条） |
| ⑥ 轮询顺手重绘整表 | 在 `refreshRuns()` 里加 `renderRecordsTable()` | 「轮询不重绘记录表」 |
| ⑦ 刷新顺手写库 | 在 `loadAll` 里加一次 `upsert` | 「整段零写操作」 |

写坏版脚本时：锚点先 `count(old) == 1`，不唯一就**拒绝执行并报错**；
替换后断言 `old not in bad`。⚠️ 若某条坏版本身是「在旧串后面追加」，
`old in bad` 会误判成「替换没生效」⇒ 把新串改写成**真正的替换**（把关键判断包进新结构里），
不要为了省事放宽这条守卫。

## 五、跨框架对照（同一家族的假刷新）

| 框架 | 等价物 | 同样的盲区形态 |
|---|---|---|
| 原生 SPA（本例） | `dataSig()` 字符串指纹 + 短路 | 字段没进指纹 |
| React | `useEffect` 依赖数组 / `memo` 比较 | 依赖数组漏了字段 ⇒ 不重渲染 |
| Vue | `computed` / `watch` 依赖 | 读了非响应式对象属性 ⇒ 不触发 |
| SWR / react-query | `revalidateOnFocus` + 结构比较 | 比较函数只比 `id` ⇒ 内容变了不刷 |
| 任何「后台进程回填」 | 由另一个进程写的字段 | **最容易漏的就是这些** |

## 六、实测记录（可复算，2026-09-24 得物达人拓新）

- 一次自动刷新 = **8 条**并行查询（6 条 `sb.from` + 2 条分页拉取），**零写操作**。
- 数据没变 → 返回 `false`，`renders` 计数 **0 次 DOM 操作**；点赞 10→11 → 重绘 ≥1 次。
- 补前：`raw.read_num` 变的探针 `changed=false`（**盲区坐实**）；
  补后：`raw.read_num` / `raw.read_num_note` 都 `changed=true`，
  而 `raw.read_num_tried_at` 仍 `changed=false`（反向探针守住）。
- 新增 `test_auto_refresh_truth.js` **PASS 31 / FAIL 0**；
  `_verify_auto_refresh_truth.py` **7 个坏版全部按预期变红**。
- 顺手发现的两条「假绿」见技能 `python-name-safety-audit`（切片撑大崩溃 + runner 不计崩溃）。
- ★ 用户当日当面纠正：「**自动刷新和刷新数据不是一个东西** —— 刷新数据是读内容的阅读数和点赞数；
  刷新只是有可能有新的内容进入到该页面，如果不刷新内容不会显示在页面中」。
  ⇒ 我原先汇报里「只重读数据库、不去源头抓」的那个「**但**」已订正为「**分工，不是缺陷**」（见第〇节）；
  代码侧本来就写着「与左边那个『🔄 刷新』**不是一回事**」⇒ **UI 无需改**，要改的是**结论措辞**。
- ★ 两件事的接缝 = 指纹盲区所在：`刷新数据` 在另一个进程写 `raw.read_num`，`自动刷新` 看不见变化就不重绘
  ⇒ 修之前抓回来的阅读数**永远不出现在表格里** ⇒ 用户的「两件事」设计要靠这个修复才闭环。
