# 外部二进制依赖：能不能内置进安装包

## 0. 先问这一句

**「你要它解决哪个具体场景？」** 没有场景就不内置 —— 内置的代价是**永久的**：体积、
许可义务、每次升级都要跟、出错时你还得替它背书。

**★★ 真实案例（同一项目，先判「不内置」、一天后翻案 —— 两版都留着，因为前后两步都有价值）：**

**第 1 版（2026-10-01）：判定「不内置」。** 问「能不能内置 ffmpeg 转码」，而那个应用
「根本不需要转码」—— 视频是原文件推送，平台的硬要求只有「扩展名 `.mp4`」和「<600 秒」，
两条都已经用纯 JS 解析 MP4 头（`moov → mvhd`）实现了。此时内置 ffmpeg 是**花 77 MB 买一个用不到的能力**。

**第 2 版（2026-10-02）：翻案，改判「内置」。** 用户说：「我会传 mp4、m4v、**mov** 等类型的视频」——
⇒ **场景变了，结论必须重算**。平台**只收 mp4**，`.mov`/`.m4v` 不转就发不出去，
原判「不需要转码」的前提（素材天然都是 mp4）**根本不成立**。最终内置 GPL 静态版 ffmpeg（79 MB）。

> ★★ **教训（这条比案例本身重要）**：判「有没有场景」要问**用户实际手里是什么素材**，
> **不能只看「平台校验规则里有几条」**。「平台只查扩展名」≠「素材天然都是那个扩展名」——
> 上游给你的格式不在你控制范围内。第 1 版的推理链每一步都对，错的只是那个**没被验证的隐含前提**。
> ⇒ 复述一遍前提给用户听（「你现在传的都是 mp4 吧？」），比闷头推演更省事。

## 1. 体积：必须实测，不许凭印象

三条路，按场景选：

| 场景 | 命令 | 说明 |
|---|---|---|
| 本机已有该文件 | `stat -c %s <file>` | 最准，直接拿字节数 |
| 远端单文件 | `curl -sIL <url> \| grep -i content-length` | 只发 HEAD，不下整包 |
| GitHub Release 资产 | `curl -s https://api.github.com/repos/<owner>/<repo>/releases/tags/<tag>` | **一次拿全平台** asset 的 `size` 字段，最省事 |

GitHub API 那条特别好用，能把一个 release 里所有平台/所有配套文件（含 `.LICENSE`
和 `ffprobe` 这类第二二进制）的大小一次列全 —— 避免你只算了主程序、漏算了配套 DLL。

实测样例（ffmpeg-static b6.0，win32-x64）：
`ffmpeg-win32-x64` = 77.4 MB、`.gz` = 27.6 MB、`ffprobe-win32-x64` = 77.2 MB、
`win32-x64.LICENSE` = 35,147 B。

★ **别忘了「配套文件」**：一个"单文件"工具往往要旁边两个 DLL，或者要第二个二进制
（`ffmpeg` 常配 `ffprobe`）。只算 exe 会低估一倍。

★★ **量到了体积 ≠ 下得下来**：`api.github.com` 能通**不代表** release 资产能下。
实测（2026-10-02，国内网络）：`api.github.com` / `raw.githubusercontent.com` /
`objects.githubusercontent.com` **都通**，但 **`github.com` 本身 timeout** ⇒
`github.com/<owner>/<repo>/releases/download/...` 这条**重定向到 github.com 的**下不来
（表现为 `curl` 静默失败、只花几十秒返回空文件）。
⇒ **先探连通性再下**：`curl -s -o /dev/null -w "%{http_code} %{time_total}s" --max-time 15 https://<host>/`
⇒ **兜底走国内镜像**：npm 系的二进制基本都镜像在
`https://registry.npmmirror.com/-/binary/<pkg>/`（列目录 → 取版本 → 下载），
★ **下完必须核对字节数**（与 GitHub API 报的 `size` 比）—— 镜像滞后/缺文件时是静默的。
ffmpeg-static 实测：GitHub `.zip` 里 82,797,568 B ↔ 镜像 `.gz` 28.2 MB，解压后字节数一致。

⚠️ 体积结论要标注口径：「解压后 / 未压缩」和「压缩后的安装包增量」不是一回事。
`compression: maximum` 的 NSIS 包，实际增量通常只有未压缩体积的 **1/2 ~ 1/3**
（可压缩内容越少越接近 1:1）。别把未压缩数字直接加到安装包大小上。

实测校准（adb 三件套 8.28 MB + 输入法 apk 17 KB，NSIS/`compression: maximum`）：
安装包 **85.03 → 87.96 MB = +2.92 MB（+3.4%）** ⇒ 这一段和 §1 的「1/2~1/3」吻合。
**结论：先算压缩比再报体积，否则会把 +3 MB 说成 +8 MB 吓退用户。**

## 2. 许可：三分类，先分类再谈做不做

| 类型 | 常见 | 能随包分发吗 |
|---|---|---|
| 宽松（Apache 2.0 / MIT / BSD） | adb（Apache 2.0）、ADBKeyboard（MIT） | ✅ 可以，**保留版权声明 + NOTICE 文件**即可 |
| 传染（GPL / AGPL） | ffmpeg 的 GPL 构建 | ⚠️ 与闭源应用**捆绑分发有传染风险** |
| 有条件（LGPL） | ffmpeg 的 LGPL 构建 | ✅ 动态链接 + 允许用户替换该库 + 声明 |

★★ **必查陷阱：npm 上最省事的那条路，往往是 GPL 构建。**
`npm i ffmpeg-static` 下下来的就是 GPL 版 —— 而且它会把许可证一起下下来，**可以直接验证**：
asset 里那个 `.LICENSE` 文件 35,147 字节，正好是 GPL-3.0 全文的长度。
**「装得上」≠「发得出去」** —— 内部自用和对外分发是两条完全不同的线，要跟用户讲清是哪条。

要绕开就用 LGPL 构建（例如 BtbN 的 `ffmpeg-*-lgpl.zip`），代价是体积更大
（实测完整 LGPL 包 **168 MB**，比单文件 GPL 版大一倍以上，因为带全套共享 DLL）。

## 3. Electron 落地：五条必做

**首选运输方式 = `extraResources`**（不要把二进制塞进 `build.files` / 只靠 `asarUnpack`）：

```jsonc
// package.json
{
  "build": {
    "extraResources": [
      { "from": "vendor/adb", "to": "adb",
        "filter": ["adb.exe", "AdbWinApi.dll", "AdbWinUsbApi.dll", "LICENSE.txt", "NOTICE.txt"] },
      { "from": "vendor/adbkeyboard", "to": "adbkeyboard", "filter": ["ADBKeyboard.apk"] }
    ]
  }
}
```

1. **为什么是 `extraResources` 而不是 `files` + `asarUnpack`**：
   `app.asar` 是归档，**里面的 exe 无法被 `execFile` 执行**；`asarUnpack` 虽然会解到
   `app.asar.unpacked/`，但**文件条目仍留在 asar 里**，源码目录也仍进包。
   `extraResources` 干脆搬到 `resources/<to>/`，**完全不进 asar**，
   路径用 `process.resourcesPath` 拼、开发态用 `app.getAppPath()` 拼：
   ```js
   const vendorDir = (name) => app.isPackaged
     ? path.join(process.resourcesPath, name)
     : path.join(app.getAppPath(), 'vendor', name);
   ```
   ★ 源码目录 **`vendor/` 要故意提交进 git**（否则 CI 打包时文件不在）。
   ★ `filter` 白名单要**逐个列出**，别写 `**/*` —— 否则把仓库里的临时文件也发出去。
2. **解析优先级显式定义 + 显示给用户看**：**用户手填（且文件真实存在）> 内置 > 系统 PATH**。
   ★ 手填的必须能覆盖内置（否则用户「换了版本却没生效」且界面看不出来）；
   ★ 手填的路径**不存在**时，可以回退，但**必须如实报出来**（「你填的那个不存在」是一个独立来源值，
   不能和「你没填」合并成同一个状态）—— 否则等于悄悄替掉了用户的配置。
   做法：把这段写成**纯函数**并让 `exists` 可注入，就能不碰文件系统跑全分支断言：
   ```js
   resolveAdbChoice({ configured, bundled, exists = () => false })
   // → { path, source: 'configured' | 'bundled' | 'path' | 'configured-missing', configuredMissing, bundled }
   ```
3. **保留"覆盖"通道**：内置版本可能因为对方软件升级而对不上（见 §4）。
4. **许可文件随包**：`LICENSE` / `NOTICE` 一起进 `resources/`，并在「关于」里可见。
   ★ 切许可证全文要**从上游原件里切**（例如官方 `NOTICE.txt` 的前 207 行就是 Apache 2.0 全文），
   别从网上随便复制一份 —— 版本/措辞对不上就是合规问题。
5. **md5 与「文件清单文档」互校，做成断言**：`vendor/README.md` 里写死
   `文件 · 字节数 · md5 · 来源 URL`，自检脚本**读文档、算 md5、逐字节比对**。
   ⇒ 这样「换了文件忘了改文档」和「文档写了但文件没进包」两种漂移都会被红掉。

★★ **测试替身（假 adb）必须校验路径存在性**：假 adb 只按 `argv` 记录、对不存在的绝对路径
也照常返回的话，「用户手填了一个不存在的 adb」这条用例会**假绿**。假替身要 `fs.existsSync`
并在缺失时回 `ENOENT`，才能真验出回退逻辑。

★★ **最后一步是「在产物里跑一次」，不是在源码里跑一次**：
打包时**别打回默认 `dist/`**（旧文件被占用/沙箱拒绝删除会中断），改打到独立目录：
`electron-builder … -c.directories.output=dist-verify`。
然后在产物里直接执行内置二进制（如 `dist-verify/win-unpacked/resources/adb/adb.exe version`），
**打印出版本号才算真的能跑** —— 只看「文件在不在」证明不了 exe 可执行。
同时记录**安装包体积前后对比**，这才是 §1 要的数字。

## 3.5 ★★ 「装上了」≠「能用了」：多步安装型依赖要验到最后一步

以 Android 输入法 apk 为例，**三步缺一不可**：
`adb install -r <apk>` → `adb shell ime enable <组件>` → `adb shell ime set <组件>`。
只做第一步时，广播（`ADB_INPUT_TEXT`）**没人接**，脚本看起来"什么都没发生"、且不报错。

- 组件名不要写死：用 `ime list -s` 里含 `adbkeyboard` 的那条；
- **装完必须复核**：`settings get secure default_input_method` 与目标组件比对，
  不一致就按失败上报，并区分卡在哪一步（`step: 'apk' | 'install' | 'ime'`）；
- ★★ **副作用要主动讲清**：把它设成当前输入法后，**在设备上手动点输入框不会弹键盘**
  （这类"给脚本用的输入法"本来就是这么设计的）⇒ **只由用户点按钮触发，绝不自动做**；
  界面上要同时区分「已装」「已装且是当前输入法」两个状态（`installed` vs `active`），
  并给一个一键按钮，别只报"没装"。

## 3.6 ★★ 内置的是「干活型」工具（转码器/转换器）时：四件事必须做到

以 ffmpeg 转 mp4 为例（得物只收 mp4，非 mp4 要自动转）。这类工具和 adb 那种「发指令」的不同：
**它要产出新文件**，所以「有没有产出」和「产出对不对」都得验。

1. **策略：能无损就不重编码**。先 `-c copy` 只换容器（H.264/HEVC 这类目标容器放得下的编码，
   **秒级、画质零损失**），失败了再走重编码兜底（`libx264 + aac`）。
   ⇒ 让绝大多数输入（如 iPhone 的 `.mov`）走第一条路，用户感知是「秒转」。
2. ★★ **不许「有输出文件就算成功」—— 必须解析产物核对**。转完读 `ftyp` 品牌 / `moov` / 视频轨编码，
   不符合目标容器就走下一档或如实报错。实测价值：一个 `.mov`（`ftyp=qt`）转完品牌必须是 mp4 家族，
   **`qt` 不算** —— 这条判据同时用来做**鉴别力自证**（拿没转的 `.mov` 去校验，必须判**不通过**）。
3. ★★ **任何失败先删半成品再抛错**（`try/catch` + `rmQuiet(dst)`），否则下游会把半截文件当成品。
   另外要挡两种「长得像视频但不是」的输入：坏文件、**只有音频轨没有视频轨**的文件
   （后者会产出一个「没画面却叫 .mp4」的东西）。
4. ★★ **取消要两个检查点**：① **入口**——已取消就根本不启动（否则用户刚点完取消，这一条照样转完落盘）；
   ② **跑完后**——ffmpeg 可能抢在轮询（每 500ms）前跑完，这时产物也不能交出去。
   只做「跑的过程中轮询 kill」是不够的：小文件会在第一次轮询前就结束。

★ **转换发生在哪个目录要搞清**：这类应用通常先在**扁平副本目录**（硬链接）里干活，
⇒ 在副本里「写新文件 + 删旧链接 + 改名」，**原素材目录完全不动**。把这点写进交付报告，
否则用户会以为你改了他的原文件。

★ **内置转码器会「引爆」别处的隐藏 bug**：原来「非目标格式根本不处理」的路径是**没被走过**的，
一旦接上，所有为它准备的半成品代码都会开始执行。本例实测：`syncItem()` 把 `type` **写死成 `'image'`**，
图片分支无所谓，但视频转完后复用它会把**视频静默改成图片**、发布时按图文走步骤。
⇒ 引入新能力前，**先扫一遍「这段代码以前从没被走到过」的分支**。

## 4. ★★ 版本冲突：必须实测，不能拍胸脯

`adb` 这类客户端/服务端架构的工具，**内置的 client 版本和机器上已在跑的 server 版本
不一致时**，会打印 `adb server version (X) doesn't match this client (Y); killing...`
然后**自动杀掉并重启 server**。通常无感 —— 但如果模拟器正跑着，**可能出现一次需要重启
模拟器 / 重新握手**的情况。

⇒ 这条**必须真机实测**（装上内置版 → 启动模拟器 → 连一次），
不能因为"官方版一般兼容"就写进交付说明。同类风险还有：厂商定制的 adb 与官方版行为差异。

**实测结论（可直接引用，但仍要在自己的环境复测）**：官方 platform-tools `37.0.1`
与 MuMu 12 自带的 `36.0.0` **先后使用不重启 adb 服务** —— 先用厂商版起 daemon、
再用官方版 `devices`，无 `killing server` 输出，复用同一 daemon、设备仍在线。

判别小技巧：看版本号格式。`Android Debug Bridge version 1.0.41 / Version 36.0.0-13206524`
这种 `主版本.次版本-构建号` 就是官方 platform-tools 的编号规则，说明模拟器厂商用的是官方构建。
★ 选内置哪个版本时**优先取官方构建**（provenance 干净、许可清楚），别直接从厂商目录里拷。

## 5. 决策口径（怎么给用户答复）

按这三档给，**不要把"能不能"和"该不该"混成一个答案**：

1. **能做且该做** —— 体积小（个位数 MB 或更小）、许可干净、且解决的是**用户第一道墙**。
2. **能做但先别做** —— 能力当前**没有使用场景**，或体积/许可代价明显（§0、§2）。
3. **能做但有条件** —— 可随包但要留声明，或需要保留用户覆盖通道（§2、§3）。

同时给出**不内置时的替代方案**，通常比内置便宜得多。例如"素材格式不合规"这件事，
不内置转码器也可以：**在入口就拦下来，明确告诉用户哪一条不合规**（比默默转码更可控）。

★ 折中方案：**首次运行时按需下载**（体积不涨）。但要提醒用户这**打破了「应用除更新器外
不出网」的约束**，且需要发布源上多放一个文件、多一个校验步骤 —— 让用户自己选。

## 6. 顺带：不止问的那一样

用户问「能不能内置 A」，往往**同一类问题还有 B 和 C 没被问到**。
做完调查顺手扫一遍同类外部依赖（界面里的「外部依赖」清单页、所有会被 `execFile` /
`spawn` 调用的东西、所有要 push/安装到设备上的文件），把**整张账**交出去。
