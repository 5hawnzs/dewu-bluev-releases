# 内置二进制/编解码库：能力真伪审计

## 0. 先反查判据（90% 的假绿在这里）

找到决定那枚徽章的那个函数，逐字读它**测了什么**。

最典型的假绿：

```js
function hasHeif() { return engine === 'sharp'; }   // 只证明「库加载成功」
```

「依赖能 require 成功」「exe 文件存在」「路径能解析」—— 这些**都不等于**「这项能力可用」。
审计结论里必须把这两件事分开说：**加载成功** vs **能力可用**。

顺便查一件常被忽略的事：界面上那一列可能**不是同一套词**。
「内置 / 可用 / 已就绪 / 待同步」往往是每行各自写死的徽章，
别以为它们共享一个分类体系（`内置` 常是「随包带了」，`可用` 常是运行时探测）。

## 1. 三级证据（缺一条都不算数）

### ① 包内产物 = 源码产物？（哈希）
必须证明「我测的那份 = 用户实际跑的那份」，否则一轮实测可能白做。

```bash
sha256sum <源码/node_modules/.../x.dll> <dist/.../app.asar.unpacked/.../x.dll>
```

三处（源码 / dist / dist-new 或安装副本）前 16 位一致才算闭环。
**注意**：npm 包里同名 dll 常有**两份**（平台专用包 + 主包内自带），内容可能相同 —— 两处都要比。

### ② 符号扫描 —— **必须配正向对照**
看二进制里有没有目标解码器的符号（如 HEVC 需要 `libde265`；只有 `aom/dav1d` 说明只带 AV1）。

> ★★★ **`strings` 在 Windows 沙箱里可能输出 0 行**（读不出任何东西）。
> 此时「grep 不到 libde265」是**假阴性** —— 空==空 的假通过。

改用 Python 直接扫字节，并**同时**打印必然存在的对照项：

```python
import re
d = open(p, 'rb').read()
S = [s.decode('ascii','ignore').lower() for s in re.findall(rb'[ -~]{4,}', d)]
for k in ['libjpeg','libpng','vips',   # ← 正向对照：必须 >0，否则扫描本身失效
          'de265','x265','hevc','aom']:
    print(k, sum(1 for x in S if k in x))
```

对照项全 0 ⇒ 扫描方法有问题，**不是**「库里没有这个东西」。
库自己常会打出一行能力自述（如 `heic/avif load/save with libheif: true`），那是很好的锚点。

### ③ 真样本行为级解码（决定性证据）
- 拿**真**样本，别用自己造的近似物（能造出编码器就说明有编码器，不代表有解码器）。
  上游仓库的示例文件通常够用；或从真实设备导出。
- 先看容器品牌确认样本是什么：`xxd | head -1`，`ftyp = mif1/heic/hevc` 才是真 HEVC 的 HEIC。
- **分两步测，别只测第一步**：
  - `metadata()/读文件头` 常能过（只解析容器）⇒ **不足以**证明能解码；
  - `resize/jpeg/toBuffer` 这类**真像素转换**才是判据。
- 失败串通常很直白，直接抄进结论：`No decoding plugin installed for this compression format`。
- ★ **正向对照**：同一库对另一种格式（如 AVIF/AV1）跑通，才能说「通路没坏、只是缺这一种」。
- ★ 连**编码**也一起试（`compression:'hevc'` → `heifsave: Unsupported compression`），
  能把「只读不了」和「完全没这个编解码器」区分开。

## 2. 交叉验证官方口径
预编译版**因专利**不内置某个编解码器（HEVC/H.265 最典型）是行业常态，
官方文档里通常会明说「需要 globally-installed libvips compiled with support for …」。
拿到这一条，就能把结论从「这台机器的问题」升级成「**与机器无关的固定事实**」——
这直接决定第 4 步怎么答复。

## 3. 反向验证：让断言能区分「预判」与「撞墙」
老断言往往长这样：

```js
ok('HEIC 降级为人工', rows.some(r => r.file === 'x.heic' && r.status === 'manual'));
```

**「试了一下、失败了」也是 `manual`** ⇒ 在「库加载成功」的机器上这条照样绿，是个假绿。

新断言要同时钉住三件事（互为反向）：

```js
ok('HEIC 预判为人工（人工口径，不是靠转换失败才变人工）',
  row.status === 'manual'
  && /需先转 JPG/.test(row.action)      // 走的是「人工口径」
  && !/处理失败/.test(row.result || '') // 且不是撞墙失败
);
```

然后**把判据改回旧版**跑一次，这条必须变红（并会多出一次无谓失败计数）。
备份 → 破坏 → 跑 → **`cp` 还原**（★ 禁 `git checkout --`，会抹掉未提交的在制品）→ 再跑确认绿。

## 4. 修法：宁可写死事实，不要动态假绿

两条路，按成本选：

- **能做真探测**：内置一张几百字节的探针样本，启动时试解一次、缓存结果。
  换任何机器、任何版本都显示真实状态。
- **做不了 / 不值得**（用户常选这条）：把那一行**写死成固定事实** ——
  `['HEIC 解码', '不可用 · HEIC 需先转 JPG', ['warn','不可用']]`。
  **不要**留着 `info.hasHeif ? '可用' : '不可用'` 这种「可能可用」的余地，
  因为判据本身就不成立。

★ 同时把**下游行为**一起改掉，否则界面和实际行为不一致（这是最讨厌的一种不一致）：
- 合规/校验流程：既然解不了，就**扫到即预判为人工**，别白试一次转换再报「处理失败」；
- 启动日志：恒成立的事**降级成 `info`**，别每次启动都 `warn` 吓人；
- 文案别指向不存在的解法（写「需 sharp/libheif」会让人以为「装个 sharp 就行」，
  而它本来就在包里）。

## 5. 连带面清单（改完按这个过一遍）

```bash
grep -rn "<库名>\|<格式名>\|含 <格式>\|<旧徽章词>" src tools docs README.md AGENTS.md
```

- 界面文案（可能不止一处：说明行、表头、tooltip）
- 文档：README / E2E 手册 / 交接文档里那句「XX 可用」多半也是错的
- 挂在旧文案上的**回归断言**（改了文案会红，或更糟：恒绿）
- 别处用同一判据的函数（`hasXxx()` 可能被 3 处调用）

## 6. 汇报口径

- 说清「**与机器无关**」还是「这台机器的问题」——前者必须给定论，别让人白折腾换机。
- 给出「区分两种不可用」的**可操作判据**（例：如果连同源的另一种能力也降级了 ⇒ 是整体加载失败；
  只有这一项不行 ⇒ 是能力本身缺失）。
- 直接给出**素材侧的正解**（源头不产该格式，如 iPhone 相机设成「兼容性最佳」= JPEG），
  它通常比修软件便宜得多。

## 7. 已核实的事实（2026-10-08，可作参照）

- `sharp@0.33.5` 预编译（含 `libheif 1.18.2`）：**可解 AVIF(AV1)，不可解 HEIC(HEVC)**。
  `libvips-42.dll` 里 `de265` 命中 0、`aom` 41；`format.heif.input.fileSuffix === ['.avif']`。
  真 HEVC 的 `.heic` 解码报 `heif: No decoding plugin installed for this compression format`，
  编码报 `heifsave: Unsupported compression`。原因：HEVC 专利，预编译版不内置。
