# 看板指标口径审计与修正

聚合看板最常见的故障不是"页面打不开"，而是**页面好看、数字系统性错**。
它错得很有规律，且**几乎总会把"进度"报高、把"成功率"报低** —— 前者让人误判能干完，后者让人白查产品。

## 铁律：先量化，别先改

**在动任何代码之前，先拿真库数据算出「错了几倍」。** 一句话结论必须带上前后两个数字，
否则你无法判断该不该改、改完有没有效果，也无法向用户交代。

```js
// 取全量（别抽样！抽样会漏掉"只在某些机器上才重复"的那类）
const rows = await fetchAll();                 // 上限多少就取多少，取不到要明说
const uniq = new Map();                        // 按「业务主键」去重
for (const r of rows) uniq.set(key(r), 1);
console.log('行数', rows.length, '唯一业务项', uniq.size, '虚增', rows.length - uniq.size);
```

**业务主键怎么选**：由产生数据的那一刻决定、与"哪台机器/哪个账号"无关的那些字段。
本项目用的是 `时间 + 篇号 + 批次 + 款 + 结果`（同一个毫秒发同一款的同一篇号，两台不同机器几乎不可能重合）。

## 三类系统性虚增（都真实踩过，按出现频率排）

### ① 分母混入非业务行（最隐蔽）
看板把**测试行 / 模拟行 / 探针行**当业务行算进分母。
- **症状**：成功率明显偏低（本项目实测 33%，真实 43%）；KPI 总数比实际工作项多。
- **判据**：把 `result` 等字段的**取值枚举**打出来（`groupBy(result).count()`），
  你会看到「发布成功 / 失败 / **模拟成功** / **探针（非真实发布）**」这类混在一起的值。
- **修法**：分出"只算真实结果"的集合，其余**另行计数并在界面上明示**（见下文「不藏数据」）。

### ② ★★ 判据不能只看一个字段 —— 非业务行会"长得像业务行"
**这是本项目最值钱的一条。** 建库时留的 4 条探针里，**有 3 条的 `result` 写的就是「发布成功」**，
只看 `result` 会把它们放进统计 ⇒ 「机器数」被从 1 撑成 2。
- **判据**：改口径前，先对"要排除的那批行"做一次**字段画像**：
  `distinct(machine_id, machine_name, result, mode)` —— 看清它们只是"长得像"，不是"等于"。
- **修法**：排除条件写成**多字段合取**（`result ∈ 真实集合 **且** 机器标识/名称不是探针`）。

### ③ 身份漂移 ⇒ 同一件事被算两次（最危险，会虚增 2~3 倍）
`machine_id` / `user_id` 这类标识**在客户端本地生成并存配置**，一旦：
配置被搬运工具的「机器专属值置空」清掉、重装、换操作系统用户 ⇒ **生成新标识**。
而服务端唯一键往往含这个标识（`(machine_id, ts, seq)`）⇒ **旧数据拦不住**，
客户端游标一重置就把**整本台账以新标识重推一遍**。
- **症状**：`n 项工作占了 2n~3n 行`；同一台电脑在"按机器"表里出现两行；**完成度虚高 3 倍**（59% vs 真实 19%）。
- **诊断一句话**：`按业务主键分组 → 每组有几个不同标识`，只要有一组 >1 就中了。
- **修法（两侧都要改）**：
  - **客户端（根因）**：标识改为由**机器稳定指纹**派生（Windows：注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`，
    `reg query` + 超时；其他平台找等价物），**读不到就回退随机，绝不抛**。
    ★★ **顺序必须是「配置里已有标识 ⇒ 照用」**——**迁移已有标识 = 再产生一批重复**，这是明确禁止的。
  - **看板（存量数据）**：按「机器**名**」聚合展示（同一台机换过标识也只算一台），
    并按业务主键**折叠重复行**；表格里标注「含 N 个标识，已合并」，别偷偷合并。
  - ⚠️ 服务端的唯一键**改不动历史数据**（且按设计不给 update/delete）⇒ 前端折叠是唯一出路。

## 「不藏数据」原则（口径修正最容易犯的错）

排除 ≠ 删除。**被排除的行必须仍然可见，只是不冒充业务数据**：
- 明细表照常列出，用**另一种颜色的标签**标出（如灰色的「模拟 / 探针」）；
- 页脚写明「另有 N 条模拟/探针**未计入**上述统计」；
- 折叠掉的重复行数也写出来（「已折叠 N 条重复行」）。
理由：用户一旦发现"数字变少了但看不出为什么"，就会怀疑你在美化。

## 自证四件套（缺一件就等于没修）

1. **行为级断言**：把看板里那段**纯函数抠出来真跑**（判据函数 + 去重函数），
   喂一个**含全部坏形态的夹具**（重复行 / 模拟行 / 探针行 / 探针但 result 正常），断言输出数量。
   —— 比"源码里有这行字"强一个量级（本项目正是这一步逼出了「探针 result 写成发布成功」那个漏判）。
2. **正反两面**：正面断言「用了新公式」，**反面断言「旧公式已不存在」**
   （只写正面 ⇒ 有人把公式改回去也照样绿）。
3. **逐条破坏**：每条防线单独拆掉，确认**对应那条**变红；备份用「跑前 cp 到临时目录」，
   **绝不用 `git checkout --`**（会抹掉未提交的在制品）；逐条破坏前先还原。
4. **真数据回放渲染验收**：真实浏览器打开页面 + **真库取回的数据**原样回放 ⇒ 读回 KPI 文本。
   这一步的价值在于**它看得见"数据长得像真的"这种情况**，源码级断言看不见。
   ★ 沙箱里 Chrome 的坑（漏 `--no-sandbox` ⇒ 导航 `ERR_ABORTED` 停在 about:blank；
   Chrome 走不通系统代理而 curl 能通）见技能 `headless-ui-selftest` 同名章节。

## 汇报口径

对用户要给出**可复算的前后对照表**，别只说"修好了"：

| 指标 | 改前 | 改后 |
|---|---|---|
| 已发布 | 367 | 137 |
| 成功率 | 33% | 43% |
| 机器数 | 3 | 1 |
| 完成度 | 59% | 19% |

并**明说没验证的部分**（如「没有第二台真机的实测数据」「修复只对以后新生成的标识生效」）。
