# 被注入的记忆文件：超限重构 + 零丢失复核

## 什么时候用

- 系统提示出现 `Your MEMORY.md has exceeded the size limit and was truncated during injection`，
  并附带 **ACTION REQUIRED: 先清理 MEMORY.md 再干正事**。
- 用户说「记忆文件太乱了 / 越写越长 / 换个机器怎么没有这些规则」。
- 项目记忆有多份副本（工作区一份、代码仓库里同步一份），需要收口并推送。

**核心判断：这类文件是「注入上下文」，不是归档。** 它越长，被截断得越早 ——
**截断是静默的**（最后一条规则读一半就没了），比「文件太大」本身危险得多。

## 关键量尺：先量，再改（别看肉眼）

被注入的文件要按**字符数**而不是字节数判断风险（中文 1 字符 = 3 字节）：

```bash
PY=/c/Users/<user>/.workbuddy/binaries/python/versions/3.13.12/python.exe
"$PY" -c "
import io
s=io.open(r'<path>/MEMORY.md',encoding='utf-8').read()
print(len(s.encode('utf-8')),'bytes /',len(s),'chars /',s.count(chr(10))+1,'lines')"
```

**判断是否已触雷的经验法**：去看被注入的那份内容**停在哪里**。
若它停在原文件的约 70~75% 处，说明上限大致就在那个字符数附近 ⇒ 新文件必须明显低于它。
（实测：4,541 字符的文件在约 73% 处被截断；重构到 4,529 字符仍不安全，
必须靠**缩小体积 + 分层**双管齐下，不能只压措辞。）

> ★★ **量的是「落盘后的字符数」，不是内存里的 `len()`**（2026-10-03 实测）：
> CRLF 文件**每行多 1 个字符**。把一份用 `\n` 拼好、`len()` = **2950** 的内容写进 CRLF 文件，
> 回读是 **3003**（+53 = 行数）⇒ 白白超限，脚本里那句 `assert len <= 3000` 根本没拦住。
> 对策：① 写盘后**必须回读再量一次**（`len(open(p, encoding='utf-8').read())`）；
> ② 预算先扣掉「行数」这一份：`lf_only + 行数 ≤ 上限 - 15`。

## 分层：索引只留「钩子」，细节进参考资料

**这是唯一能既压体积又不丢规则的办法**（单纯压措辞只能省 10~20%，还会丢掉「为什么」）。

1. **MEMORY.md = 索引**：每节 3~8 条**祈使句**硬约束 + 一个 `§N` 指针。
   保留判据 ——「**不遵守就出事，且从代码/测试里看不出来**」。
   典型保留对象：诚实性铁律、UTC 时间陷阱、服务端闸门语义、「读不到 ≠ 不限」、
   会被静默绕过的权限闸门、派生值编号规则、测试假通过的坑。
2. **REFERENCE-<项目>.md = 完整版**：新增一节
   `## §N 完整硬约束清单（MEMORY.md 的完整版）`，含**理由、常量、路径、§ 指针**。
3. **在索引第一行写明**：`> 完整硬约束清单 = REFERENCE-<项目>.md §N`。
   不写这句，将来就不会有人（包括你自己）去查。
4. **当轮新增的规则必须两头都落**：索引里要有祈使句，参考资料里要有理由。
   ⚠️ 只往索引里加 = 体积继续涨；只往参考资料里加 = 下次记不住。

> ⚠️ 反面教材（实测踩过）：第一版「压缩」只是删掉括号里的解释，
> 结果因为同时**新增了本轮 6 条规则**，字符数几乎没降（4,541 → 4,529），存在意义为零。
> **先分层，再压措辞。**

## 零丢失复核（必须做，否则「整理」等于删规则）

改完逐项核对，而不是凭印象：

```bash
# 1) 体积真的降了（至少 -30% 字节）
# 2) 索引里 §N 指针存在
grep -c "§N" MEMORY.md
# 3) 参考资料里新节真的写进去了
grep -n "^## §N" REFERENCE-<项目>.md
# 4) 逐节标题对得上：索引的每一节都能在完整版里找到
# 5) ★ 指针不能**悬空** —— 第 2 条只查「§N 这个符号在不在」，查不出这个：
for n in $(grep -o "§[0-9]\+" MEMORY.md | sort -u | tr -d '§'); do
  echo "--- §$n"; sed -n "/^## §$n/,/^## §/p" REFERENCE-<项目>.md | head -8
done   # 逐个**人眼**确认：这一节真的在讲索引里说的那件事
```

再加一条**反查**：把重构**前**的 MEMORY.md 存成副本，逐条把「★/★★ 标记的规则关键词」
在重构后的两个文件里各 grep 一次，命中数必须 ≥ 1。**没命中就说明那条规则被删了。**

> ★★ **把这条反查做成固定件：先写「守卫关键词清单」，不满足就整体不写盘**（2026-10-03 实测）。
> 从旧文里抽「不遵守就出事」的每条硬约束，各取 1~2 个**不随措辞变化**的词
> （如 `isBlocked` / `service_role` / `ELECTRON_RUN_AS_NODE` / `concurrent-workspace-safe-release`），
> 在**同一个脚本**里 `assert` 它们全部出现在新文本中**且**长度达标 ——
> **任一不满足就 `assert` 崩掉、一个字都不落盘**（本轮：77 条守卫 + 长度闸门，一次跑过）。
> 比跑完再 grep 强的地方：它把「零丢失」变成**写盘的前置条件**，而不是事后检查。

> ★★ **2026-09-22 实测踩到（本清单原来缺第 5 条）**：压缩时最容易犯的**不是「删规则」**，
> 而是「**把细节写成一句指针、却忘了把细节搬过去**」——
> 索引里写「五个假通过坑 见 **§38**」，而 §38 里其实只有别的内容，**这五个坑一个字都没有**。
> 第 2 条 `grep "§38"` 命中了、看着全过，细节却真的丢了。
> ⇒ **每写一个「见 §N」，都必须回读 §N 确认它真的讲这件事。**

### 机械复核基座：`scripts/zero_loss_check.py`

手工 grep 容易漏掉最该守的东西 —— **否定式硬约束**
（`绝不 / 不许 / 不能 / 只能 / 唯一 / 缺一不可`）。
这类句子一旦被压掉或压反，读者会照着**错的规则**去干，比丢一条普通说明严重得多
（实测：「`三处缺一不可`」被压成「`三处缺一`」= **语义正好反了**）。

```bash
python scripts/zero_loss_check.py \
  --old <重构前副本> --index MEMORY.md --ref REFERENCE-<项目>.md
```

它从「重构前副本」抽出每条的**硬约束指纹**，再到「新索引 + 参考资料」里找落点，分三档输出：
`✓ exact / 剥情态`、`~ 砍尾（需人工复核）`、`✗ 丢失`。
**判读**：`✗` 必须为 0；`~` 逐条人眼确认「语义在、只是措辞变了」。

> ⚠️ **写这类脚本自身有三个坑**（2026-09-22 实测，每一个都会让「零丢失」变成**假绿**）：
> ① **别在归一化时剥括号** —— 压缩常把细节挪进括号里（`（唯一写入口，不许裸调）`），
>   剥了就把「命中」判成「丢失」（实测一口气**误报 6 条**）。
> ② **`range(0, len(c) - 3)` 在 `len(c)==3` 时是空循环** ⇒ 全长一次都不试 ⇒ 假「丢失」。
>   ⇒ 上界写 `max(1, len(c) - 3)`。
> ③ **别把「脚本说命中」当成零丢失** —— 匹配只会越调越宽。
>   宽松的匹配必须**单独列出来给人复核**，不能混进 `✓` 里一起报「全过」。
> ④ ★★ **参考资料里逐字保留了重构前原文 ⇒ 所有 `✓ REFERENCE` 命中都是恒真的**（2026-09-24 实测踩到）：
>   压缩时习惯把旧正文整段塞进 `REFERENCE-*.md` 的 `## §0 重构前原文` 当保险 —— 结果是脚本拿旧指纹
>   去「新索引 + 参考资料」里找，**那份旧正文自己就在参考资料里** ⇒ 必然全 `✓`，看着「零丢失」。
>   ⇒ 一旦做了这种「原文留档」，**只看 `✓ index` 一列**，`✓ REFERENCE` 一律**当噪声**；
>   再**人工逐条过一遍索引**：「这条祈使句还在不在索引里？不在的话，它有没有 `§N` 指针兜住？」
>   （2026-09-24 实测：脚本报「直接命中 13 · 丢失 1」，那 1 条是 `**` 加粗被切开的分词假象，
>   而 13 条里真正有意义的只有落在 `index` 上的 4 条。）

## ★★ 并发写：同一份记忆可能被另一个会话同时改（2026-10-01 实测）

工作区记忆**可能同时被另一条并行会话写**。实测：我读完 MEMORY.md 之后 **49 秒**，对方又写了一次。
两个后果，都会让「整理」变成事故：

1. **你抄的锚点会失配** —— 实测基于 16:48:05 版本准备的 35 条替换，在对方 16:48:54 那次写入之后
   **有 8 条 `count == 0`**（它把那几行重排并压缩了）。**你手里的"原文"已经过期了。**
2. **对方可能自己就把限额处理掉了** —— 实测对方把 **3129 字符自己压到 2976**。
   ⇒ **动手前先看 mtime + 重新量一次字符数**，也许根本轮不到你压。

**必守三条**

- **压缩前重新 `Read` 一次**，绝不用几分钟前读到的内容当锚点（本轮就是这么翻车的）。
- **逐条 `count == 1` 校验，任一条不满足就整体不写盘**。
  本轮正是这条**挡住了把 8 条失配的替换硬写进去** —— 否则会按错锚点把文件改坏。
- **只改自己的段落**，别碰对方新写的节（本轮跳过了对方刚写的「品牌权限 / 文案提示词」整节）。

```js
// 固定件：pairs 从 JSON 文件读（别内联在 JS 里，见下）
const crlf = s.includes('\r\n');
let bad = 0;
pairs.forEach(([o, n0], i) => {
  const n = crlf ? n0.split('\n').join('\r\n') : n0;
  if (s.split(o).length - 1 !== 1) { console.log('FAIL #' + i + ': ' + o.slice(0, 40)); bad++; return; }
  s = s.replace(o, n);
});
if (bad) process.exit(1);        // ← 有不匹配就不写盘；上一轮备份到别处，别原地备份
fs.writeFileSync(P, s, 'utf8');
```

> ★ **替换对写成 JSON 文件，不要内联在 JS 字符串里**：记忆里满是 Windows 路径（`D:\work\...`），
> 在 JS 单引号串里 `\w` / `\d` 会被**静默吃掉**变成 `w` / `d`，锚点再也匹配不上。
> JSON 里写 `\\` 是显式的、不会踩；反引号在 JSON 里也不用转义。

> ★ **压缩的目标是「留出余量」，不是「刚好不超」**：本轮压到 2991/3000（只余 9 字符），
> 任何一方下一次写入立刻再次超限。**压到明显低于上限**（留 5% 以上）才算完。

## 收口：把记忆当代码提交

记忆通常有两份，别只改一份：

- 工作区（注入源）：`<workspace>/.workbuddy/memory/{YYYY-MM-DD.md, MEMORY.md, REFERENCE-*.md, TODO-*.md}`
- 代码仓库副本：`<repo>/.workbuddy/memory/...`

```bash
cp <workspace>/.workbuddy/memory/{MEMORY.md,REFERENCE-*.md,<今天的日志>.md,TODO-*.md} <repo>/.workbuddy/memory/
cd <repo> && git add -A && git status --porcelain    # 只应出现这几个文件
```

- **日志是 append-only**：`Write` 会覆盖，用「临时文件 + Python `open(...,'a')` 追加」，
  并打印 `before -> after (+N chars)` 当作证据。

> ★★ **防重复写的判据不能只看「小节标题在不在」**（2026-10-03 实测踩到）。
> 我给「视频抽帧」这一节写了个防重复守卫 `assert '第十一轮' not in old` —— 而当日日志里**早就有一条同名小节**
> （凌晨写的另一轮「文案改成看图写」）⇒ 守卫误判「已写过」，脚本 assert 退出，**这一节一个字都没落盘**；
> 我因为「脚本跑过了」而误以为写完了，直到几小时后翻日志才发现正文里 `抽帧` 命中 0 次。
> **对策（两条都要）**：
> ① 守卫查**只属于本节的关键词**（`frame.js` / `videoFrames` / 具体数字），不要拿可能撞车的标题当判据；
> ② 写盘后**回读并断言关键词命中**，而不是只看「脚本没报错」。
> ⇒ 记完日志**回读一眼正文**（`grep -c <本节专有词>` ≥ 1）才算完；标题撞车在本项目是常态（编号更是重灾区）。
- 提交前**密钥自检**要看**命中行**而不是只数个数：
  `git diff --cached | grep -n "service_role"` ——
  命中「`service_role` 在 `secrets.json.serviceKey`」这类**说明文字**是正常的，
  真出事的是**密钥值本身**（长 JWT 串）。别看到计数 > 0 就慌，也别因为「是文字」就跳过不看。
- 推送若 `github.com:443` 连不上而 `api.github.com` 通 → 用技能 `git-push-via-github-api` 的 API 路径
  （**push 完必须紧跟 sync**，并且**手工补写三级引用** `refs/remotes/origin/main`，
  否则 `git status -sb` 会显示 `[gone]`）。

## 收尾自检清单

- [ ] 量了体积（bytes + chars），并说明降幅
- [ ] 索引第一行有「完整版 = §N」指针
- [ ] 参考资料新增了完整版那一节，且当轮新规则两头都有
- [ ] 逐条反查过 ★/★★ 规则关键词，命中数 ≥ 1
- [ ] ★ 每个「见 §N」都回读过 §N，确认那一节**真的在讲这件事**（防指针悬空）
- [ ] 跑过 `scripts/zero_loss_check.py`：`✗` = 0，`~` 已逐条人工复核（**别把宽松匹配当全过**）
- [ ] 日志用追加（append-only）而不是覆盖
- [ ] ★ 日志**回读过正文**：本节的**专有关键词**（文件名/配置名/数字）命中 ≥ 1 —— 标题会撞车，别只信守卫
- [ ] 两份副本已同步；密钥自检看过**命中行**
- [ ] 提交信息里写清「字节降幅 + 规则一条没丢 + 新增哪几条」，别只写「更新记忆」
