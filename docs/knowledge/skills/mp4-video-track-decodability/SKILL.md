# 判定 mp4 视频轨「目标 App 解不解得开」（纯字节，不调 ffmpeg）

## 核心判断

**扩展名和编码四字码都不足以判定能不能解码。**

真正的判据是**视频轨的 profile 与位深**。最典型的事故：

- 文件是 `.mp4`、容器正常、编码四字码 `hvc1` 也在目标 App 的**白名单里** —— 但它其实是
  **HEVC Main 10（10-bit）**，目标 App 只解 **8-bit** ⇒ 上传后**全黑封面**，相册里**一直转圈**，
  或直接变成 **0 秒视频**。
- 同一批素材里 **8-bit 的正常、10-bit 的黑** —— 差别只在位深，肉眼和扩展名都看不出来。

⇒ 结论：**必须进容器读视频轨的 profile / 位深**，并且把「认不出」与「读不到位深」这两种
不确定状态**分开处理**（见下）。

## 一、从字节里取编码四字码与参数集

MP4 是 box 树：`moov → trak → mdia → minf → stbl → stsd`。
`stsd` 的结构：`4B 版本+flags`、`4B entry_count`，然后每个 entry 是
`4B size` + **`4B format（四字码）`** + ……

★ **偏移要拿准**（这里最容易差 4 字节）：entry 的四字码在 **box 起点 + 20**，
等价地说 = **`'stsd'` 这四个字母的位置 + 16**。
推荐按后者实现（先扫出 `'stsd'` 的下标，再读 `下标+16` 起的 4 字节）——
这样写成字符串搜索、不依赖你从哪个字节开始切片。

推导（box 从 0 起算）：`size(4) | type 'stsd'(4) | version+flags(4) | entry_count(4) | entry_size(4) | format(4)`
⇒ 四字码在 **20**；而 `'stsd'` 在第 4 字节 ⇒ **4 + 16 = 20** ✓。
⚠️ 别写成「从 box 内容（第 8 字节）起算 +16」—— 那是 24，会读到 entry 的 `size` 而不是 `format`。

拿到四字码后，**同一条 track 的样本描述里就带着参数集 box**：

| 编码 | 参数集 box | 位深 / profile 怎么读 |
|---|---|---|
| HEVC（`hvc1` / `hev1`） | `hvcC` | `hvcC内容[1] & 0x1f` = `general_profile_idc`（**Main 10 = 2**）；<br>`hvcC内容[17] & 0x07` = `bitDepthLumaMinus8`（**Main 10 ⇒ 2**） |
| AVC（`avc1` / `avc3`） | `avcC` | `avcC内容[1]` = `profile_idc`；**≥110 = High 10 及以上**<br>（110 = High 10、122 = High 4:2:2、244 = High 4:4:4） |

★★ **一定要读两个来源再下结论**：四字码只说「是什么编码」，**位深在参数集里**。
只看四字码就会把 10-bit 的 `hvc1` 当成合格放行 —— 这正是本技能要防的那个坑。

★ 建议把它实现成**纯函数**（输入一个 buffer，输出 `{codec, profileIdc, profileName, bitDepth,
bitDepthKnown, tenBit, why}`），这样能直接在单测里手搓 box 喂进去走全分支，不必真造视频。

## 二、三种「不确定」要分开，取舍不一样

| 情形 | 处理 | 为什么 |
|---|---|---|
| **认不出编码**（四字码不在白名单 / 是 `vp09`、`av01` 这类） | **fail-closed：拦** | 认不出就说明没验证过；放过去大概率是黑格 |
| **编码认识，但读不到位深**（`hvcC` 缺失 / box 结构异常） | **fail-open：放行** | 宁可漏一个，也绝不误杀一个本来能播的文件（用户的底线：不误杀） |
| **明确算出 10-bit** | **拦 + 自动转码** | 有确定证据，且修复动作明确 |

★ 只把**确定**判成「不合格」；**不确定**一律不拦 —— 但要把「没读到」这件事如实写进报告/日志，
别假装「已确认合格」。

## 三、接入合规/发布链路时的三条硬要求

1. **别在扫描时调 ffmpeg**：扫描要遍历成百上千个文件，`ffmpeg -i` 每个都要起进程（慢、可能没装）。
   字节解析是毫秒级的，且**不依赖外部二进制**。
2. **「格式不对」与「编码不可解」的**计数与修复动作**绝不能合并**：
   前者是「转 MP4」（换容器），后者是「转码 H.264 8-bit」（重编码）。合并了用户就不知道该怎么办。
   报表里各占一列、各点一次名。
3. **面向人的文案要写清「症状 + 原因 + 该怎么办」**。实测好用的措辞：
   > 视频轨是 `10-bit HEVC (Main 10)`，目标 App 解不开（相册里会是黑格 + 一直转圈，发出去就是黑封面）
   修复动作写 `转码 H.264（8-bit）`；没有可用转码器时写 `需手动转码（程序里没找到 ffmpeg）`，
   **别假装已经处理了**。

★ 顺带：如果转封装器（remux，只换容器不重编码）存在，**合格判据要进位深** ——
否则 10-bit 源会走「转封装」，产出的还是 10-bit，问题原样留着。正确行为是
**转封装不合格 ⇒ 自动落到转码**。

## 四、回归怎么写（少一条都可能是假通过）

用**手搓 box** 喂纯函数，覆盖全分支：

- `stsdOnly(codec)`：只造出四字码；
- `hvcC(profileIdc, bitDepthMinus8)`、`avcC(profileIdc)`：造参数集；
- 逐条断言每个分支，**包括**：
  - HEVC Main 10 ⇒ 判不合格；
  - **★★ 反向对照：`hvc1` 但 8-bit ⇒ 必须放行**（没有这条，「一律拦 hvc1」也能全绿）；
  - 读不到 `hvcC` ⇒ 放行（fail-open）；
  - 陌生编码（如 `vp09`）⇒ 拦（fail-closed）；
  - H.264 High 10（profile 110）⇒ 拦；H.264 High（100）⇒ 放行。
- **真造样本 + 用 ffmpeg 的原话对照**：`ffmpeg -i x.mp4` 的输出里会写
  `hevc (Main 10)` / `yuv420p10le` 或 `h264 (High)` / `yuv420p`。
  把 ffmpeg 自己打的字与**你的纯函数算出来的结果**逐字对一遍 —— 这才叫「判据正确」，
  而不是「我的实现和我自己写的期望一致」。
- 端到端那条要走**真实链路**（造一个 `.mp4` 容器 + 10-bit HEVC，喂进扫描/合规，断言
  状态 = 待处理、原因里含 `10-bit`、计数进了**新那一类**而不是「格式不对」那一类），
  并断言修复后**真解析产物**为 8-bit H.264。

## 五、常见误判与坑

- ★ **「`hvc1` 在我们白名单里」≠「合格」**：白名单通常按四字码列，而 10-bit 与 8-bit 是**同一个四字码**。
- ★ **拿扩展名判**：`.mp4` 是容器，容器里可以是任何编码、任何位深。
- ★ **拿「别的播放器能播」当证据**：桌面播放器/ffmpeg 什么都能解；目标 App 是**硬解**，能力窄得多。
- ★ **`find`/批量命令的退出码当成功**：与本节无关但同源 —— 判定「处理干净了没有」一律**回读实际状态**。
- ★ 读 `stsd` 时**别假设只有一个入口**：一个 `moov` 里可能有多处 `stsd`（音频轨也会有一个，
  里面是 `mp4a`）。⇒ 把你扫到的四字码**全部收集**，再用**视频编码白名单**挑出视频轨
  （`codes.find(c => WHITELIST.has(c))`，白名单为空 ⇒ 报「认不出视频轨编码」），
  别拿第一个 `stsd` 就当成视频轨。
