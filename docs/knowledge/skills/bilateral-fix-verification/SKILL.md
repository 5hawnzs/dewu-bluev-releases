# 双向修复验证（改前必须红，改后必须绿）

## 核心判断

**「回归全绿」不能证明修复有效** —— 既有断言很可能压根没覆盖你改的那条路径。
正确的证明方式是**双向**：把修复**改回坏版**跑一次（必须红），再还原跑一次（必须绿）。
两次都拿到可复算的数字，才算数。

没有"改前红"这一步，你的"改后绿"什么都说明不了。

## 标准流程

### 1. 先想清楚「我改掉了哪一条判断」

修复通常就是**一行**（或两句）在起作用。把它写下来 —— 那就是破坏点。
如果说不清是哪一行，说明还没定位到根因，先别做验证。

### 2. 写一个定点破坏工具（不是手工改）

必须有三个子命令 `break` / `restore` / `status`，并满足：

- **改前先备份** 到 `<file>.fixbak`，`restore` 时原样还原（不依赖 git，避免把无关改动一起搅进来）
- ★★★ **`restore()` 里绝对、绝对不许写 `git checkout -- <file>`（或 `git restore` / `git stash`）**（2026-10-04 血泪实测）：
  这条命令还原的是 **HEAD**，而**你这一轮的修复恰恰还没提交** —— 于是「还原」会把
  **几分钟前刚写完的全部在制品连同坏版一起抹掉**。实测一次性丢失两个服务文件（adb.js/publisher.js）
  的整轮修复（含新增 `ensureApp`、服务自愈、正则修复），且**没有任何 .fixbak 之外的备份可救**，只能逐段重敲。
  ⇒ 正确写法：**跑前把「当前工作区」整个备份到临时目录**（`cp <file> <tmpdir>/<file>.prebreak`），
  `restore` 用 **`cp` 从临时目录拷回**；破坏脚本一律**禁 `git checkout`**。
  ★ 判据：如果 `restore` 命令里出现了 `git`，那就是错的，改掉它。
  ★ 顺带：`git stash` 也一样危险 —— 它把工作区改动**移走**，别人（并行的另一路会话）一 `pop` 就串味了。
- **锚点唯一性校验**：`countOf(src, needle) !== 1` 就**拒绝修改**并打印实际次数。
  只替换第一处、或锚点不唯一 = 改错了地方，而工具仍会返回成功 → 静默假通过
- ★ **跨行锚点先解决 CRLF**：Windows 上的源码常是 `\r\n`，而锚点字符串里写的是 `\n`
  ⇒ `count` 恒为 **0**，报「锚点找不到」（看起来像「工具坏了」，其实是行尾不匹配）。
  ⇒ 锚点**优先取单行**；必须跨行时加一层兜底：原文匹配 0 次且锚点含换行 ⇒
  把锚点的 `\n` 换成 `\r\n` 再试一次。（2026-10-01 实测：6 个破坏项里只有唯一那个跨行的失败。）
- ★★ **单行锚点也会「不唯一」——因为是子串，不是整行**（2026-10-02 实测）：
  锚点 `  if (cancelled && …)` 在文件里有 3 处，其中两处的行首是 `    if` / `        if` ——
  **它们都包含 `  if (` 这个子串**。⇒ `countOf` 报 3、工具中止（这次是好事，说明校验起作用了）。
  ⇒ 单行锚点要带**行首锚定**，别只靠缩进看着不同：
  ```js
  // 别用：needle = "  if (cancelled && cancelled()) throw new Error('已取消');"
  // 用行首锚定 + 精确缩进（`^` 只匹配真正的行首）
  const re = new RegExp('^  if \\(cancelled && cancelled\\(\\)\\) throw new Error\\(\'已取消\'\\);', 'm');
  ```
- ★★ **正则锚点别用 `$` 收尾**（同上，2026-10-02 实测）：踩坑文件是 **CRLF**，
  `$`（默认匹配 `\n` **之前**的位置）与语句末尾的 `;` 之间**还夹着一个 `\r`** ⇒
  `;\s*$` 之外，`;$` 的命中数**恒为 0**，又变成「锚点找不到」。
  ⇒ 要么去掉 `$`（只靠 `^` + 精确缩进就能唯一），要么写成 `;\s*$`。**报 0 次时先按这条排查。**
- ★★ **锚点 `count` 恒为 0、但你确信文本明明一样 ⇒ 先查「读文件时有没有 `newline=''`」**（2026-10-03 实测）：
  脚本里已经老老实实写了 `needle.replace('\n', '\r\n')` 去适配 CRLF，结果仍然是 0 次 ——
  因为 `s = open(p).read()` 在**读取时**就把 `\r\n` 规范化成 `\n` 了，`s` 里根本没有 `\r\n`，
  而 needle 却被换成了 `\r\n`。**适配必须做在「同一侧」**：两端都 `newline=''`，或两端都不适配。
  ★ 这条同时是「写回把整个文件变成 LF」的元凶（见下面那条）—— 一次踩中两个后果：
  先报「锚点找不到」，改了适配之后又悄悄把文件的换行符换掉。
- ★ **模板字符串里的 `${…}`：三元表达式的 `}` 可能在很远的地方**（2026-10-03 实测）：
  锚点写成 `${ivNow === 0}` ⇒ 0 次；真实代码是 `${ivNow === 0` 后面**直接换行**，
  `}` 在三元表达式末尾（`${cond\r\n ? 'a' : 'b'}`）。⇒ 锚点取到 `${ivNow === 0` 为止即可，
  **别凭印象补 `}`**。报 0 次时把「锚点往后 30 个字符的实际文本」打出来对一眼，比盯着锚点猜快得多。
- ★ **先全部校验、再动磁盘**：`apply()` 要把所有替换项**都验证通过之后**才 write。
  改一半就落盘会留下一个「半坏」的中间态，比不改还难排查
- ★★ **预览/试跑开关的「缺省值」必须跟随命令行，不能是硬编码的 `False`**（2026-10-03 实测）：
  写下 `def patch(path, label, anchor, repl, dry_run=False)`，然后 17 个调用点**全都忘了传** ⇒
  `--dry` 跑起来照样**一路落盘**。当时 17/17 锚点唯一 + 回读断言全过，结果没坏，
  但**「预演」这一步已经等于没做**（最该拦住错误的那道闸门是空的）。
  ⇒ 一律写成 `dry_run = DRY if dry_run is None else dry_run`（缺省跟随命令行），
  **不靠调用点自觉**。同一原则适用于 `--check` / `--force` / `--no-write` 这类开关。
- **备份已存在时拒绝再次 break**（否则会把坏版当原版备份，永久损坏）
- `restore` 结尾**扫一遍 `[BREAK]` 标记**，确认一个都没残留
- ★★ **读写必须用二进制 / `newline=''`，否则还原 md5 对不上会让你误判**：
  Python 默认 `open(p,'r')` 会把 `\r\n` **通用换行**成 `\n`，`write(s, newline='')` 再写回就
  把**整个文件的行尾换成了 LF**。于是「还原后 md5 与最初不一致」——
  内容其实等价（git 归一后无差异），但你会以为「还原失败」或「隔壁会话又改了」，
  然后去查一个不存在的 bug。2026-10-02 实测：`copywriter.js` 同一份干净源码，
  两次 `status` 报出 `f0ab0745…` 与 `1cadbd64…` 两个 md5，就是这么来的。
  ⇒ 破坏工具一律用 `open(p, 'rb')` / `open(p, 'wb')`，或两端都显式 `newline=''` 并保证同源。
  ⇒ 另外：**md5 只能证明「与备份一致」，不能证明「与最初的干净源码一致」**——
  要证明后者，必须跟 git 比（`git diff -- <file>` 为空）。

参考实现：`D:\work\e2e\fix-break.js`（2026-10-01 得物蓝V 项目）。

### 3. 关键坑：运行时覆盖 ≠ 改前版

**最省事的做法（在测试里改回旧配置）经常不等价**，会造出一个"根本没坏"的坏版，于是永远不红。

真实踩过的例子：

```js
// 改后版 init
sharp.cache({ memory: 64, files: 0 });

// 以为这样就能模拟改前版 ↓ —— 错！
sharp.cache({ memory: 64 });   // 只覆盖 memory；files/items 沿用「当前值」，仍是 0 → 没坏
```

`sharp.cache({...})` 这类 API 是**部分覆盖**语义。必须显式给全：
`sharp.cache({ memory: 64, files: 20, items: 100 })`，或者干脆做**源码级破坏**。

⇒ 造完坏版先自问：**我到底改掉了哪一条判断？** 再用一次实验证明"坏版真的坏"。

### 3.1 假通过坑：一处缺陷有**多条防线**时，只拆一条会全绿

同一处缺陷常常被**两条独立防线**同时兜住。只拆一条，另一条照样拦住 ⇒ **断言全绿**，
而你会得出「破坏成功但断言没红 ⇒ 这条断言是摆设」的**反向结论**。

真实例子（2026-10-01）：`dump()` 会拿上一屏冒充当前屏，靠两条防线拦住 ——
① 抓前 `rm -f` 远端文件；② 检查 dump 是否真的回了 `dumped to`。

| 破坏 | adbtest 结果 |
| --- | --- |
| 只拆 ① | **只红 1 条**（顺序断言），核心那条「返回值必须是 null」**仍是绿的** |
| 只拆 ② | 也不红核心那条 |
| **① + ② 一起拆** | **红 6 条**，含「返回上一屏残留 XML」 |

⇒ **判据：破坏工具明明打印了「已破坏 X」，测试却全绿 ⇒ 先怀疑「还有另一条防线」，而不是「断言没在查东西」。**
逐条排除，直到某条断言变红，才算证明它有效。

⇒ 工具要支持**一次破坏多项**：`break P6 P9`（给 `break` 加一个编号列表参数即可）。
写坏版组合时在代码/注释里注明**哪几项属于同一处缺陷**，免得下次又只拆一条。

### 3.2 更危险的坑：脚本自己崩 ⇒ 还原没跑到，坏版被留在源码里

`check` / `verify` 这类一键流程通常是「逐个破坏 → 跑测试 → **最后统一 `restore()`**」。
只要中途任何一步抛异常，**`restore()` 就永远不会执行** —— 磁盘上留下**全部的坏版**，
而人只看到脚本报错退出，很可能转头去干别的了。

（2026-10-01 实测：B6 用跨行锚点去匹配 CRLF 文件 ⇒ `count==0` 直接 throw ⇒
**B1~B5 五个坏版全留在源码里**，直到下一次跑验证才发现 `status` 全是「已破坏」。）

⇒ 四道护栏，缺一不可：

1. `apply()` **先把所有替换全部校验通过，再动磁盘**（别改一半）；
2. 循环体包 `try { ... } finally { restore(); }` —— 崩了也必须还原；
   ★★ **但「汇总/报告要用的变量」必须声明在 `try` 外面**：写成 `try { const base = {}; … }`、
     而 `finally` 里的汇总表又去读 `base` ⇒ `ReferenceError` **崩在收尾那一步**（2026-10-05 实测）。
     这次没伤到源码（还原已经跑完），但**整张汇总表没打出来**，证据文件缺了最关键的一段，
     而且退出码变 1、看起来像「还原失败」。⇒ **判据：`finally` 里只许做「还原 + 打印已经拿到的结果」，
     凡是要打印的东西，其变量一律在 `try` 之前 `let x = null;` 先声明好。**
3. **每次跑完独立复核**：`grep -rn "BREAK " src/` 与 `ls *.bak` 必须为空。
   **别信脚本自己打印的「已还原」** —— 它可能根本没跑到那一行。
4. ★ **让「还原」本身变成可断言的证据，而不是一句自述**：`restore()` 之后拿内存里留着的
   原始字符串做**逐字节比对** —— `fs.readFileSync(f,'utf8') === orig`，把结果打成
   `源码逐字节还原 ✔/✘`；同时把「`*.bak` 无残留」也写成脚本里的一条硬断言，让 `exit` 码
   跟着「破坏变红 ✔ / 还原全绿 ✔ / 逐字节还原 ✔」三条一起走。
   这与第 3 条不矛盾：**自述不可信，断言可信** —— 第 3 条防的是「脚本撒谎」，第 4 条
   防的是「脚本没说、人也忘了手动扫」。参考实现 `D:\work\e2e\relbreak.js`（把这三条结论
   直接打进输出，跑一次就能看清）。

### 3.3 「累计破坏」：逐条验证时没先还原 ⇒ 上一条的效果混进这一条

`check` 的朴素写法是「`for` 每一项：`apply` → 跑测试 → 记 FAIL 数……最后统一 `restore`」。
这样 **B2 数出来的 FAIL 里含着 B1 的破坏** —— 你以为在量 B2，其实量的是「B1+B2」，
于是很自然会得出「这条断言在查别的东西」这种**错误结论**。

（2026-10-01 实测：B8 本该只红 **1** 条，因为 B7 的破坏还留在盘上，红了 **3** 条。）

⇒ 修法：循环体里**每条破坏之前先 `restore(true)`**（加个静默参数），保证**每条都从干净源码开始**。
修后逐条数字才可信（实测 B7→2 / B8→1 / B9→1 / B10→3 / B11→1 / B12→1，各自干净）。

```js
for (const t of list) {
  restore(true);      // ★ 关键：每条都从干净源码起步，否则变成「累计破坏」
  apply(t);
  const r = runTests(t.verify);
  report(t.name, r.fail);
}
restore(true);
```

⇒ **判据：破坏工具报「已破坏 X」，却红了「明显不相关」的断言 ⇒ 先怀疑上一条没还原**，
别急着下「这条断言在查别的东西」的结论。

与 §3.2 是同一件事的两面：**§3.2 是「崩了所以没还原」，§3.3 是「没崩但也没还原」**。
两者的后果一样（盘上留着不该留的坏版），所以护栏也一样 ——
**每次跑完都要独立复核 `grep -rn "BREAK " src/` 与 `*.bak` 为空**。

### 3.4 最隐蔽的一种：**测试替身（桩）比真实依赖宽松 ⇒ 它把缺陷「销毁」了**

定点破坏能证明「断言有效」，但它证明不了「**源码里的缺陷在没被破坏时也会被抓住**」。
如果测试注入的替身**接受任何参数**，它消费参数的方式就和真实依赖不一样，
于是「参数顺序 / 参数类型写错」这类缺陷在测试里**永远不会显形**。

（2026-10-02 得物蓝V 实测：`updater.js` 把 `setTimeout` 的 `(fn, ms)` 写成了 `(ms, fn)` ——
生产环境直接抛 `ERR_INVALID_ARG_TYPE`（未捕获），后果是「界面显示自动更新已启用、
实际启动自检一次都没跑过」；而测试注入的桩是 **`setTimer: () => {}`（空函数照单全收）**，
**65 项断言全绿**。桩把证据销毁了。）

⇒ 两条护栏：

1. 替身要**按真实签名校验**：参数类型不对 / 顺序不对时，**记录下来并让断言红**，而不是默默接受；
2. 光验「返回值 / 状态」不够，要**真跑一遍被排上的回调**（行为级断言）——
   签名对、回调体是空的，也一样白搭。

**判据：只要测试里出现 `() => {}`、`jest.fn()`、`vi.fn()` 这类"万能"替身，就问一句 ——
「真实依赖会不会因为参数不对而报错？这个桩会不会把那个错吃掉？」**
（修法示例：`const timers = []; const spyTimer = (fn, ms) => { timers.push({ fn, ms }); return 0; };`，
然后断言 `typeof t.fn === 'function' && t.ms === EXPECTED`，再调一次 `t.fn()` 看它真的干了活。）

### 3.4b ★★ 破坏脚本**自己的期望**也会写错（2026-10-05 实测，两条连中）

定点破坏跑完常出现 `PASS 7 条 / FAIL 2 条`，而这 2 条 **FAIL 是脚本的错、不是产品的错**。
两种形态（这一轮各撞一次）：

**① 期望写宽：我把「由别的防线满足的断言」也算成"该红"。**
场景 = 一个缺陷有多条独立防线。我的 D7 把主图这道闸门整块摘掉，却还把
「重扫失效 ⇒ 这一条记失败」写进"该红"清单 —— 它**不红**。查法：去坏版日志里看那条断言是
`PASS` 还是 `FAIL`（这里是 PASS），再看它的实际证据串里写的是**哪条防线**的文案
（实测是「图片已推到设备，但没能写进媒体库」＝ 推送后那道**进库确认**，与主图无关）。
⇒ 判据：**每条"该红"都必须先回答「这条断言在查的是我改坏的那句吗」**；答不上就删掉、
或换一条破坏面更精准的坏法去覆盖它。

**② 只"放水"不改产品 ⇒ 红 0 条，设计本身就是错的。**
把**测试夹具**改宽松（例如让库里回读直接跟随文件时间，抹掉「文件时间 vs 库缓存时间」的区别）
**单独打**上去，产品没变 ⇒ 一切照旧，**一条都不红**，什么都没证明。
⇒ 正确构造是**反向对照（negative control）**：**同一跑里同时**打上
「夹具放水」+「产品改坏」，判据**反过来** ——
「那几条**事实类**断言必须**仍然绿**」。仍绿 ⇒ 证明它们**正是靠夹具不宽松才立得住**
（即：夹具一旦放水，这个真机实测过的坑就会静默溜过去）。
本技能 §3.4 讲的是"桩太宽松把缺陷销毁了"；**这一条讲的是"怎么把这个销毁过程当场演示出来"**。

**③ 破坏面太广 ⇒ 红一大堆，别慌、也别数条数。**
D5（把置顶时间从 `max+2` 改成 `max-2`）让 29 条断言一起红 —— 因为置顶失败会让后面每一条
发布都失败。**「红了几条」不是判据**；判据永远只有一句：**我指的那条，红了没有。**

**④ 断言串本身写错 ⇒ 报一条与产品无关的 FAIL（2026-10-05 v1.0.15 发版实测，两条各撞一次）。**
这类不是"期望写宽/写窄"，而是**我连要搜的那个字符串都抄错了**。两种：
- **参数被自己的分隔符切坏**：`node tools/verifypack.js --need "file=sub"` 是**按最后一个 `=` 切**的
  （`s.lastIndexOf('=')`）。我写 `--need 'src/renderer/index.html=data-admin="1"'`
  ⇒ 切成 file=`…html=data-admin`、sub=`"1"` ⇒ 报「文件读不到 / FAIL」。
  ⇒ **值里带分隔符时，换一个不含分隔符的子串**（改用 `data-admin`），或先读工具源码确认切法。
- **抄的是"逻辑上的写法"，源码里是"转义后的写法"**：断言「`uimap.js` 含 `[A-Za-z0-9_.]+:[A-Za-z0-9_.]+/`」
  ⇒ **假红**，因为源码里那个 `/` 是**转义的 `\/`**（`/^[A-Za-z0-9_.]+:[A-Za-z0-9_.]+\/[A-Za-z0-9_.]+$/`）。
  ⇒ 要搜正则字面量时，**照抄源码里转义后的那一串**（或搜不带特殊字符的锚点）。

★★ 统一判据：**断言出红时，先证明「这条断言串本身对」，再怀疑产品**。
证明方法很便宜 —— 把那个子串拿去 `grep` 一遍被查文件：`grep -c "<子串>" <文件>` 是 0
而人眼明明看得见，就是断言串写错了。**否则你会去"修"一个根本不存在的问题**（这条与 §3.4b①②③
是同一个家族：红/绿都要先问「这条断言在查的到底是什么」）。

### 3.5 ★★ 不能改源码时怎么破坏：**「内存破坏 + 抠函数跑」**（并发工作区专用）

**什么时候用**：同一个仓库/工作区有**另一路会话（另一个人、另一个 AI）正在改同一个文件**。
此时「改源码 → 跑 → 还原」是**危险动作** —— 还原那一下会把对方的改动一起抹掉（哪怕只有几秒窗口）。
另一种场景：文件是**共享的生产源码**，你不想让坏版哪怕落盘一瞬间。

**做法**：破坏不落在磁盘上，只改**内存里的源码文本**。

```js
// 1) 从源码文本里抠出函数体（用大括号配平找结尾，比按行正则稳）
function extractFn(src, name) {
  const s = src.indexOf('async function ' + name);
  let i = src.indexOf('{', s), depth = 0;
  for (; i < src.length; i++) {
    if (src[i] === '{') depth++;
    else if (src[i] === '}') { depth--; if (depth === 0) { i++; break; } }
  }
  return src.slice(s, i);
}
const imagePartsOf = new Function('path', 'imaging',
  'return (' + extractFn(src, 'imagePartsOf') + ')')(path, imaging);  // 依赖显式注入（用真的，别用桩）

// 2) 破坏只替换内存字符串 ← 磁盘文件全程不动
const d1 = new Function('path', 'imaging',
  'return (' + extractFn(src.replace('.slice(0, cfg.imageCount)', '.slice(0, 99)'), 'imagePartsOf') + ')')(path, imaging);
// 3) 末尾必须断言「仓库文件一个字节没动」
assert(fs.readFileSync(FILE, 'utf8') === src);
```

**要点 / 边界**：

- 跑破坏前先验**锚点 `count==1`**、断言「替换真的落地了」（`broken !== src`）—— 这两条和磁盘破坏法一样不能省。
- 灵敏度自检照样成立：实测拆掉张数限制 ⇒ 由 2 变 **6**；把类型过滤反过来 ⇒ 变 **0**（两条都红）。
- 抠出来的依赖要用**真实模块**（真 `sharp`/真 `imaging`），别图省事拿桩 —— 否则掉进 §3.4 的坑。
- ★ **边界**：只适用于**自包含函数**。要破坏的是**模块级结构**（`require` 链、导出、import 写法、
  文件间契约）时，抠函数跑不了 ⇒ 只能走磁盘破坏，那就**先跟另一路会话打招呼**，或改用 worktree 快照。

（2026-10-03 得物蓝V 实测：另一路会话正在改 `copywriter.js`，用此法完成
「视频不进模型 / 送图张数=2」的行为级自证 —— `11 PASS / 0 FAIL`，含 2 条破坏 + 1 条「文件未动」。）

### 3.6 ★★「套件中断」≠「没抓住」—— 破坏之后**一行 `FAIL` 都不打**的两种情况（2026-10-03 实测）

判断「这条破坏有没有被抓住」，绝大多数人（包括我的第一版脚本）是这么写的：

```python
fails = [l for l in out.split('\n') if l.startswith('FAIL')]
hit   = [l for l in fails if expect in l]
verdict = 'RED' if hit else 'GREEN(未抓住!)'   # ✗ 双向都会错
```

**这个写法有两个方向的错**，我在同一轮里两个都踩到了：

**① 改前版抛异常 ⇒ 一条 `FAIL` 都不打，被误判成「没抓住」。**
拆掉被测的守卫之后，**行为级断言自己抛了异常**（它拿不到预期的界面元素），
测试跑到那里就 `throw` 出去、被顶层 `catch` 兜住，**整个套件中断**，
前面已打印的 `FAIL` 行里**没有**我期望的那一条 ⇒ 判成 `GREEN(未抓住!)`。
结论差点写成「这批断言是假绿」——而实际上它**抓得非常准**，只是没用 `FAIL` 的形式表达。

**② 拿退出码当「中断」判据 ⇒ 把「没抓住」美化成「抓住了」。**
于是我加了一条 `aborted = (code != 0)` —— 但**有 `FAIL` 时退出码本来就不是 0**，
`aborted` 恒为真 ⇒ 那些「期望串写错、本该是 GREEN」的条目，全被贴上了 `RED-中断`。
**这是两个方向的错叠加：先用错判据把抓到的说成没抓到，再用另一个错判据把没抓到的说成抓到了。**

⇒ 正确做法三条：

1. **让断言自己把「抛异常」变成 `FAIL`**（治本）：行为级断言一律
   ```js
   let thrown = null, observed = null;
   try { observed = await 被测函数(...); } catch (e) { thrown = e; }
   ok('★ 行为级：……', !thrown && 期望的条件, thrown ? ('这一步抛异常了：' + thrown.message) : ...);
   ```
   —— 于是「拆掉守卫 → 抛异常」会**打出一条 `FAIL`**，而不是中断套件。
   （这与**用户级记忆**里那条「抠函数跑『不许抛异常』必须 `try/catch` + 断言」是同一件事，
   只是这里要作用于**调用被测函数的地方**，不只是抠函数的脚本。）
2. **「中断」的判据只能是输出特征，不能是退出码**：
   `aborted = ('ADB TEST ERROR' in out) or ('Traceback' in out) or (PASS 行数明显低于正常值)`。
3. 把「中断」**单独计一类**（`RED-中断`），并且在报告里明说「这条是中断、不是 FAIL」——
   别把两种证据强度混成一个 `RED`。

**自检**：跑完破坏后，先看**总 `PASS` 行数**有没有掉。正常 167、这次掉到 3 ⇒ 一眼就是中断，
不用去猜「是不是没抓住」。

### 3.7 ★★ 坏版**语法崩了** ≠ 「没抓住」（2026-10-04 实测）

把「破坏后没红」判成「这条断言是摆设」之前，必须先确认**坏版是一个合法的坏版**。

实测：破坏「对象字面量」时替换字符串把逗号弄丢了（变成 `{a:1  b:2}`，`b` 前面没有 `,`）⇒
`app.js` 当场语法错、渲染层整体白页 —— 于是 11 条**完全无关**的断言一起红、
`PASS` 从 199 掉到 13。判据脚本只找「期望的那条在不在 FAIL 里」，看到没有就报
「★ 全绿＝没抓住！」—— 其实那条断言**根本没机会运行**。

⇒ **破坏落地之后、跑测试之前，先做一次语法自检**：

```python
r = subprocess.run([NODE, '--check', target], capture_output=True)
if r.returncode != 0:          # 坏版造坏了 —— 单独计一类，别混进 RED / GREEN
    report(name, '坏版语法崩了')
    continue
```

**判据**（与 §3.6 同源、成因不同）：`PASS` 骤降 **且** 红的那些跟期望**毫无关系** ⇒
先怀疑「坏版不是合法的坏版」，别急着下「断言没抓住」的结论。
（§3.6 是「好版被拆后行为级断言抛异常中断套件」，本条是「破坏脚本把源码改成了非法文件」。）

### 3.8 ★★ 用例之间**互相污染** ⇒ 假红 ⇒ 把「多条防线」的结论**读反**（2026-10-04 实测）

这是 §3.1 的**镜像坑**，方向正好相反、后果一样糟。

场景：同一处缺陷被 **两处独立防线** 兜住（例：`publish.run` 与 `publish.rerun` 各调一次
`assertExcelClosed`）。你写了三个断言，用**同一个计数变量** `runCalls` 连着跑：

```js
⑦  publish.run 被拦  →  assert(runCalls === 0)
⑦b publish.rerun 被拦 →  assert(runCalls === 0)   // 复用同一个计数器
⑦c 反向对照（可写时不许拦）→ assert(runCalls === 1)
```

预期：破坏 A（拆掉 `publish.run` 那道）应**只让 ⑦ 红、⑦b 保持绿** —— 结论是「两处各有一条防线」。

实测却**多红了一条**：⑦b 也红了，报「**找不到该行**」。
根因不是代码缺陷，而是**用例耦合**：⑦ 一旦放行，被测函数返回的 `rows: []` 被
`project.patch` **写回工程状态** ⇒ 发布队列被清空 ⇒ 紧跟其后的 ⑦b 连「要重跑的那一行」都找不到。

为什么危险：它把「A 只该红 ⑦」这个**关键结论**糊掉了 —— 你会读成「拆 A 就红一片」，
既看不出每条防线各自的归属，也**无法排除**「其实只有一条防线、其余是副作用」。

⇒ **修法**：给每个子用例一个 `arm()`，跑之前把**现场整套重置** ——
被测状态（队列/数据）+ 环境开关（文件锁）+ **计数器**：

```js
const arm = (locked) => {
  runCalls = 0;                       // 计数器：否则上一条的调用会算到这一条头上
  project.patch({ ...队列与报告路径... });   // 被测状态：否则上一条把它清空了
  fs.chmodSync(file, locked ? 0o444 : 0o644); // 环境开关
};
arm(true);  const a = await jobs.run('publish.run', {});   // ⑦
arm(true);  const b = await jobs.run('publish.rerun', { seq: 1 }); // ⑦b
arm(false); const c = await jobs.run('publish.run', {});   // ⑦c
```

重置后矩阵才干净：**破坏 A ⇒ 只 ⑦ 的 3 条红（⑦b/⑦c 绿）；破坏 B ⇒ 只 ⑦b 红** ——
这才证明「两处各有一条独立防线，少一处就有一条路径溜过去」。

**判据（两条都要）**：
1. 破坏**某一条**防线时，若**不该红**的用例也红了 ⇒ 先查**用例之间有没有共享状态/计数器**，
   别急着下「这些断言都在查同一处」的结论；
2. 只要一个套件里有 ≥2 个「跑完会改全局状态」的行为级用例，**默认它们必须各自重置现场**。

### 3.8b ★★ 破坏脚本跑起来之后：**判据读哪儿** ＋ **套件必须硬超时**（2026-10-05 实测）

破坏脚本是「把源码改成坏版 → 跑 → 还原」，所以它运行期间**工作区源码本来就是坏的**。

**① 判据一律读「跑前那份字节备份」，别读工作区。**
实测踩坑：脚本跑到一半我去 `git diff` 看目标文件，看到的是**坏版正则**，差点误判成「我的修复没生效」。
⇒ 破坏脚本一启动就把 `orig = readFileSync(TARGET)` 落成 `*.prebreak` 备份 ——
   · 中途要审自己的改动 / 核对锚点唯一性 ⇒ **读那个备份**；
   · 还原也**只认这个备份**（`cp` 回去 + md5 复核），一律**禁 `git checkout`**（会抹掉未提交的在制品）。
   · 想「跳过某一轮只重跑另一轮」⇒ 给脚本加 `--only=<标签>`，别手工去改源码。

**② `execFileSync` 跑的套件**必须带 `timeout`，别裸跑。**
实测：**同一份坏版**，一次 run 只要 **289s** 正常收敛；另一次跑了 **19 分钟仍未返回**。
判「在跑」还是「卡住」：采样进程的 **CPU 时间 + 内存**（都不涨 ⇒ 阻塞，不是在算）。
⚠️ 该次阻塞的**确切原因未查明**，别编原因；只需知道**它会偶发**，用超时兜住：
```js
out = execFileSync(NODE, ['tools/xxx.js'],
  { cwd: ROOT, encoding: 'utf8', maxBuffer: 128 * 1024 * 1024, timeout: 12 * 60 * 1000 });
// catch 里要区分「断言失败」与「被超时杀掉」：e.signal || e.killed ⇒ 本轮结果不可用，别当通过
```
⇒ 卡住的处置顺序：**停进程 → 按字节备份还原（md5 复核）→ 补上超时 → 只重跑那一轮**。

### 3.8c ★★ 一个坏版**同时具备两个方向的缺陷** ⇒ 期望表要把两条都算红（2026-10-05 实测）

改回**旧版正则**这种破坏，很容易被当成「只该让正向断言红」。实测它**同时**让负向断言也红：
旧正则既**拒绝**合法值（正向该红），又**放行**假格式（负向该红）—— 因为**它本来就是一个两头都错的写法**
（这正是当初那个 bug 的两半）。
⇒ 现象：脚本报「✘ 与预测不符」，其实**是你预测漏了一半**。修法是把期望改成
`{正向: RED, 负向: RED, 端到端: RED}` 并在注释里写清「为什么负向也红」。
⇒ 反过来说：负向用例里**必须**留着「旧版会错误放行的那种值」，否则这条破坏会漏掉一半缺陷。
⇒ 边界：破坏面**广**（红一片）不叫「分辨力有问题」；判据仍然只有一句 —— **我指定的那条，红了没有**。

### 4. 断言要盯语义，不要锁内联写法

- 负向断言只看**代码行**（先剥掉注释，否则自己写的注释会一起命中）
- 断言写 `失败数 >= 1 && 残留文件数 > 0`（语义），别写 `=== 'EPERM'`（换台机器错误码可能不同）
- 抠函数跑必须 `try/catch` + 补一条「**不许抛异常**」的聚合断言：
  改前版抛 `TypeError` 时是**一条 FAIL 都不打**的，看起来"没问题"

### 4.1 ★★ 「某关键词不许出现」型断言，会被自己的防御对象搞成**必然误报**

最容易漏的一种「断言本身坏了」，症状是**你越修越红**：

- 原断言：`!/service_role/.test(源码)`（意图：不许把那个危险 key 写进代码）。
- 后来加了一个功能：**主动拦下**用户粘进来的 `service_role` key ⇒ 代码里**必须**出现这四个字：
  ```js
  if (/service_role|secret/i.test(key)) return { ok:false, error:'绝不能填进客户端' };
  ```
  ⇒ 断言从此**必然红**。而那一行**看着像漏洞，其实是防线**。

**判别口诀**：只要那个关键词**成了「被防御的对象」**，「不许出现」就不再是一个有意义的判据。
**修法不是删掉断言，而是拆成两条查语义的**：

1. **正面**：那条拦截**必须存在**（防止将来有人把拦截删了、只在注释里说"已拦下"）——
   断言锚在拦截的**实质写法**上（如 `/if \(\/service_role\|secret\/i\.test\(key\)\)/`）；
2. **负面**：全文件不许有**真正的凭据字面量**（`eyJ…` 长串 / `sb_secret_` 开头），
   而不是不许出现那个**词**。

★ 同类风险：`!/TODO/`、`!/debugger/`、`!/console\.log/` —— 一旦这些词进入「被检查/被清洗」的对象，同样必然误报。
★ 改断言时**必须留档说明为什么改**（改在源码注释里），否则下一个人会把它"修"回去。

**另一个常被忽略的同类**：断言**数个数**而不数**内容**。
`ok(字段数 === 18)` 在你故意加一列时会红——这时要改成**逐个列名对白名单**（`want.every(k => got.includes(k))`），
既容纳合法新增，又仍能抓住「偷加了一列素材路径」。**别只把 18 改成 19 就完事。**

### 4.2 ★★ 「包含某词」型断言，在**同一段文案里本来就出现两个互斥词**时必然假通过

2026-10-02 实测。被检查的那行界面文案是：

```
跟随内置  当前实际在用：https://… · 来源：跟随内置（换项目＝发新包，各台升级后自动跟随）
   ↑徽章                                 ↑说明
```

两个互斥词（`跟随内置` / `本机指定`）**同时**出现在这一行里（徽章用一次、说明用一次）。
断言写成「整段 `.includes('跟随内置')`」⇒ 把**来源那半句人为改成「本机指定」**（真·说反）之后，
**仍然 PASS**。改成「只取 `来源：` 后面那一段，且**不许出现反面的词**」之后坏版才真红。

**判别口诀**：断言要查的片段里，若**两种结果各自的词都天然会出现**，那么「包含」型断言恒真。
**修法**（二选一，能同时做更好）：

1. **截片段**：把文本切到唯一位置再比（`text.split('来源：')[1]`）；
2. **加负向**：除了「必须出现正面的词」，再加「**不许出现反面的词**」。

★ 这类属于「一处语义多条防线」的近亲：**不是断言没查东西，是它查的那个词同时属于两种结果**。
★ 并且它**只在造坏版的时候才暴露**——不做反向验证，这条断言会一直绿着骗你。

### 4.3 ★★ 降级链 / 兜底链的断言只看**返回值形状** ⇒ 假通过

2026-10-02 实测（得物发布页抓取）。被测的是一条**降级链**：
`uiautomator dump` 重试 → 关动画重试 → （**仅当传了包名**）退到 `dumpsys activity top` 备用通道。

断言写的是「没传包名 ⇒ 不许降级」：

```js
ok('没给包名时不许降级', r.ok === false && r.via === 'uiautomator', …)
```

定点破坏把 `if (pkg) { 走备用通道 }` 改成 `if (true) { 走备用通道 }` ⇒ **报红 0 条**。
原因：备用通道函数自己也会拒绝空包名（`{ok:false, why:'没给包名'}`），
于是最终**还是**落到 `ok:false` + `via:'uiautomator'` —— **返回值形状一模一样**，
但行为已经变了（白跑一次 adb、报错里多出一段备用通道的字样）。

**修法**：降级链的断言不能只看「最后返回什么」，要查**「有没有真去调那一步」**：

```js
ok('没给包名时不许降级：连 dumpsys 都不该调，报错里也不该多出备用通道的字样',
   r.ok === false && r.via === 'uiautomator'
   && !/dumpsys activity top/.test(calls())   // ★ 指令日志里不许出现那一步
   && !/dumpsys/.test(r.why || ''), …);       // ★ 报错文案里也不许多出痕迹
```

**推广到所有「A 失败才退到 B」的结构**（重试链、多源回退、多通道降级、缓存回源）：
- 断言必须同时覆盖**三条**：①该退时**真退了**（`via/used` 标记 + 指令日志里**有**那一步）；
  ②不该退时**一步都没走**（指令日志里**没有**那一步，而不只是「结果看起来一样」）；
  ③退之前那些**应尽的尝试不省略**（本例：先试过关动画）。
- 「用返回值形状判断走了哪条路」是**不可靠**的——两条路的失败结果常常长得一模一样。
- 判据落到**可观测的副作用**上：`calls.log` / 请求记录 / 分支计数器。有桩的话让桩**把调用记下来**。

★ 这与 4.1 / 4.2 同源：**断言查的那个东西，在「对」和「错」两种情况下都成立 ⇒ 恒真**。

### 5. 报告里保留两侧数字

```
| 检查点 | 改前（源码破坏） | 改后 |
| T1 等比缩放 | 转换 0 / 失败 1 / 残留 .__tmp_scale_4.jpg | 转换 1 / 失败 0 / 无残留 |
| T2 导出后 reportRow | [0,0,0,0] | [2,3,4,5] |
```

同时**保留"改后仍必须为真"的对照项**（如「真被占用仍要 busy=true + 暂存」）——
证明修复没把相邻的正常行为一起改坏。

### 6. 别忘了对照项里也要有负例

只测"新行为生效"是不够的。凡是被你这次修复**分流掉**的旧路径，都要有一条断言守着它仍然工作
（P3 修「假占用」的同时，必须有一条断言证明「真占用」还照常暂存）。

### 7. ★★ 把「我的预测」也写进脚本，并允许它报「不符」

反向验证有个容易被浪费掉的价值：**它会告诉你每条断言到底在守什么** —— 而这跟你事先想的不一定一样。

做法：给每条破坏预填一个 `expect_*`（我猜哪套会红），脚本跑完打印「符合预期 / 与预期不符」。
不符时**不要改脚本去迎合结果** —— 那等于把「预测」偷换成「事后解释」。正确动作是：

1. 把「原来猜什么 / 实测什么 / 为什么」写进报告与记忆（**猜错不丢人，把猜的当成实测才丢人**）；
2. 顺手厘清**断言分工**：如果某条断言其实同时守着别的语义，写进报告，免得下次漏测。

实测例子（2026-10-04，`_rv-badrender.py`）：B2「拒绝对象不再被识别」我猜 `uicheck` 会**全绿**
（因为它的断言写的是「壳 **or** 登录页都算有交代」），实测**多红了 1 条** ——
「壳里把原因写出来」那条也能区分「拒绝」与「缺字段」。⇒ 这条断言同时守着两个语义，值得知道。
（B1/B2 两个坏版：uicheck 201/3 与 203/1、logintest 97/4 与 98/3，还原后 204/0 与 100/1。）

      不读工作区 —— 这时候工作区源码本来就是坏版（见 §3.8b）
- [ ] ★★ 跑套件用的 `execFileSync` **带 `timeout`**（实测同一坏版一次 289s、另一次 19 分钟不返回）；

- [ ] **还原是「逐字节比对」验过的**（不是靠脚本打印一句「已还原」），且 `*.bak` 无残留也进了脚本的硬断言
- [ ] ★ **还原后与 git 比过**（`git diff -- <file>` 为空），不只是「与备份一致」——
      脚本自己的读写可能已经把行尾换掉（见 §2 的 `newline` 那条），md5 一致只证明「等于备份」

      ★ 汇总/报告要用的变量**声明在 `try` 之外**（否则崩在收尾、汇总表打不出来，见 §2 第 2 条）
- [ ] 逐条验证时**每条破坏前先 `restore` 回干净源码**（否则是「累计破坏」，FAIL 数失真）
- [ ] 坏版**真的坏了**（先单独跑一次红，确认是预期的红，不是抛异常导致的空结果）
- [ ] ★★ 破坏后若**一行 `FAIL` 都不打**，先看**总 `PASS` 行数**有没有掉 —— 那多半是**套件中断**、

- [ ] ★★ 「中断」的判据**不是退出码**（有 `FAIL` 时退出码本来就不是 0，会把「没抓住」美化成「抓住了」）
      ⇒ 只认 `ADB TEST ERROR` / `Traceback` / `PASS` 行数骤降；「中断」单独计一类，别混进 `RED`
- [ ] ★★ 行为级断言喂的是**被测代码导出的值**（`uimap.X.id`），不是测试里抄的字面量
      —— 否则「把配置里的 id 改错」它永远绿（见 §4.5）
- [ ] ★★ 补丁工具的**预览开关缺省跟随命令行**（`dry_run = DRY if dry_run is None else …`）
      —— 别让「试跑一次」变成真落盘（见 §2）
- [ ] 还原后绿
- [ ] ★★ 每条破坏都预填了「期望红 / 期望绿」，脚本会打印「符合预期 / 与预期不符」；
      不符时**如实记录**（不改脚本迎合结果），并顺手厘清那条断言其实在守什么（见 §7）
- [ ] ★ 测试里的替身（桩）**没有** `() => {}` / `jest.fn()` 这种「万能」写法 ——
      否则真实依赖会因参数不对而报的错，会被桩**吃干净**（见 §3.4）
- [ ] 关键回调 **行为级**验过（真调一次那个回调，看它是否干了本该干的事），不只看返回值/状态
- [ ] 修复**分流掉**的旧路径也有断言守着
- [ ] ★★ **断言红的时候，先问「是代码错了，还是断言过时了」**：
      若某关键词已变成「被防御的对象」（见 §4.1），断言必然误报 ⇒ 拆成「正面：拦截存在 + 负面：无凭据字面量」，并**在源码里留档说明**
- [ ] 「数个数」型断言（字段数/条目数）在**有意新增**时红 ⇒ 改成**逐个白名单对**，别只是把数字 +1
- [ ] ★★ **「包含某词」型断言**：被查片段里若**两个互斥词天然都会出现**（徽章+说明、是/否、开/关），
      断言恒真 ⇒ 先**截到唯一片段**再比，并补一条「**不许出现反面的词**」（见 §4.2）
- [ ] ★★ **降级链 / 兜底链**（A 失败才退到 B）的断言：不能只看返回的 `ok`/`via` 形状

      （该退时有、不该退时没有），外加「报错文案里不许出现那条通道的痕迹」（见 §4.3）
- [ ] 破坏脚本**多文件**时，每个文件各存一份内存干净副本，且**每个文件都逐字还原校验**（别只校验最后一个）
- [ ] UI 类断言尽量**两手都上**：**结构**（用行号比对证明元素在目标容器**之外**，比 match 一段 HTML 稳）
      ＋ **行为**（真 `click()` → 查状态 → 派发 `Escape` → 查 `hidden`）
- [ ] 报告含两侧数字
- [ ] 验「被拒绝 / 无权 / 拦截」类断言**配了正向对照**（只测负向＝假通过：别的机制会给同一个错误码）
- [ ] 宣称「幂等 / 防重 / 可重试」的地方**喂过重复请求**、看过它的**真实返回**（源码里写过的头/参数不算证据）
- [ ] 安全类「改不了 / 删不了」的验证，**表里确实有一行与过滤条件匹配的记录**（否则「0 行」是空==空）
### 4.4 ★★ 断言「查错了东西」的两种典型形态（2026-10-03 实测，定点破坏第一轮 11/14 全是这两类）

破坏脚本能让断言变红，只能证明「断言**会**失败」，不能证明「它查的是我以为的那个东西」。
下面两类是我实测里最常漏的 —— **它们和被测代码是否坏掉无关，是断言自己写歪了**：

**① 只验了「必带」，没验「来源」。**
需求是「额外话题从**品牌提示词**里抓」。我写的断言是：

```js
// ✗ 看着像在验「提示词的话题进了组合」，其实那两个必带来自别处
assert(rows.every(r => r.topics[0] === 必带A && r.topics[1] === 必带B));
```

`必带A/必带B` 来自**设置页**（`copy.requiredTopic`），跟「池子从哪来」无关。
把池子来源整段换成写死的本地池，**这条断言照样全绿**。
⇒ 修法：把它拆成「**必带**顺序对」＋「**每一行**的额外位都能在**抽取函数的结果**里找到」，
并补一条「设置页那几个词**一个都不许出现**」。这样「来源」被真正钉住（配合 §5.11 的样本量要求）。

**② 查了 `ternary` 里**走不到**的那个分支。**
断言写成 `plan.titleStyle ? 检查A : 检查B`，而 `buildPlan` **每行都会给出格式** ⇒
`titleStyle` 恒为真 ⇒ `检查B` **永远执行不到**。这种断言**不可能失败**，等于没写。
⇒ 两条出路：① 把它改成**源码级**断言（查那段拼接逻辑里真的写死了哪一句）；
② 如果只能在运行时验，就**如实标注这条断言的强度**（「只覆盖 A 分支，B 分支走不到」），别让它冒充全覆盖。

**自检口诀**：造完坏版先问「**我到底改掉了哪一条判断**」，再问
「**这条断言在改动前会不会本来就是绿的**」——
凡是「拆掉一大片逻辑它还是绿」的断言，就是查错了东西或查了不可达分支。

**顺带一条（样本量）**：验「池子 / 列表的来源」时，**采样条数必须多过池子能给的个数**，
否则滑动窗口永远绕不回开头，混进尾部的污染词**永远采不到**（详见 `multimodal-copy-audit` §5.11）。

### 4.5 ★★ 行为级断言**别用测试文件里硬编码的常量**——那样「改配置」永远抓不住（2026-10-03 实测）

我加了一组「屏幕守卫」的断言，测试里是这么写的：

```js
const DRAFT_TITLE = 'com.shizhuang.duapp:id/iv_draft_title';   // ← 测试自己写死的
const DRAFT_EXIT  = 'com.shizhuang.duapp:id/fl_publish';
...
await publisher.runStep(SERIAL, { action: 'tapId', value: DRAFT_EXIT, whenOn: DRAFT_TITLE }, ...);
```

反向验证时我把**被测代码里的常量**改错（`uimap.DEWU.draft.exitId` → 另一个 id），
结果**行为级断言照样全绿** —— 因为它用的是**测试自己的**那份常量，
被测代码里那个值它压根没读。只有「常量值相等」那条断言变红了。

**为什么危险**：这类断言给人「行为级验过了」的安全感，实际上
它验的是「引擎拿着**我给的** id 会怎么做」，**完全没验「发布器实际会拿哪个 id」**。
而真机上线用的是**配置里的** id —— 这正是最该被钉住的那个值。

⇒ 两条同时上：

1. **行为级断言要喂「被测代码自己导出的值」**，别喂测试里的字面量：
   `value: uimap.DEWU.draft.exitId, whenOn: uimap.DEWU.draft.titleId`。
   这样「配置写错」会直接让行为级变红（我改完之后，原先"没命中"的那两条破坏立刻变成真 `FAIL`）。
2. **再单独留一条**「这个值必须等于真机实测的那个 id」的断言 —— 两条防线各管一头：
   一条管「值对不对」，一条管「用的时候真读了这个值」。

**一般化**：凡是断言里出现**字符串字面量**、而该字面量在被测代码里也有一份的地方
（resource-id / 表名 / 列名 / 事件名 / 状态码），都要问一句
**「我这次验的是我抄的这份，还是它真会用的那份？」**
抄一份来验，等于把最该验的东西换成了一个常量。

### 4.6 ★★ 「把这块 UI 撤掉」时：**撤入口 ≠ 删功能**，断言两头都要钉（2026-10-04 实测）

用户说「红框里的东西对所有人隐藏，没有用」这类需求时，先分清那块 UI **背后有没有别的东西在用**：

- 只撤界面入口（DOM + 它对应的 action 处理器，处理器留着就是没人调用的死代码），
  **底层读取链一个字节都不动**。这次撤的是设置页「输出目录 / 隔离目录」两个只读框，
  但这两个值主进程还在读：`store.get('paths.output')` 出现在合规报告 / 运行日志 / 品牌统计 /
  隔离被拒素材等处。**真把读取链删了，导出报告当场报「没有配置输出目录」。**
- 断言必须**两条**，缺一不可：
  1. **页面看不见**：两个角色视角**各验一次**（只验一支，会漏掉「管理员还看得见」这种半拉子改法）；
     判据用运行时 `textContent` / `querySelector`，别只看源码删没删（真有隐藏元素就漏了）。
  2. **读取链还在**：源码级查出那些 `store.get('paths.xxx')` 的调用点仍然存在 + 默认值接线没断。
     ★ 判据要**照抄代码里真实的调用形状**（`store.get('paths.output')`）。
     凭印象写成裸串 `paths.output` 会到处命中注释；写成抄来的 `c.paths.output` 又会永远查空 ⇒ 假通过。
- 撤掉的那块**别再出现在副标题/摘要文案里**（「路径、内容校验、…」要改成「内容校验、…」）——
  界面文字得跟界面上真有的东西对得上，这条也单独写一条断言。
- 源码级负向断言别忘了剥**两种**注释：JS 的 `/* */`、`//` **以及 HTML 的 `<!-- -->`**。
  界面是模板字符串拼出来的，说明性注释就是 HTML 形式；只剥前两种时，注释里的 `cfg:path`
  会把断言误判成红（实测第一版就是这么红的：报 `cfg:path=true`，而代码里一处都没有）。

### 4.7 ★★ 「计数 + 唯一性」型断言**对「成员改名」完全失效**（2026-10-05 实测，枚举清单类）

给内置枚举 / 清单（句式骨架、模板表、档位表、错误码表…）**加一项**时，最自然的断言是
`list.length === N` ＋ `new Set(list.map(x => x.code)).size === N`。定点破坏实测它们的盲区：

- 把新加的成员 **`T15` 改名成 `TXX`** ⇒ 长度还是 15、code 也不重复，**这两条全绿**；
- 连「system 里列全了 N 种」那条也绿 —— 它写的是 `every(st => sys.includes(st.code + ' ' + st.name))`，
  改了号它**自己也跟着改**，属于「拿被测对象校被测对象」；
- 整组里唯一抓住的是「**新成员存在**」那条（`STYLES.find(st => st.code === 'T15')`）——
  而那只是因为它的断言文案里**恰好点名了 T15**。换个枚举就没有这个运气。

⇒ 三条规矩：

1. 枚举类断言必须再加一条**结构**断言：**成员编号 / 键连续**。
   `list.every((x, i) => x.code === 'T' + String(i + 1).padStart(2, '0'))`
2. **`every(...)` 只能证明「都在」，证明不了「没少」**（空数组也全过）；计数断言只防「多 / 少」，不防「改名」。
   两者**互补，不能互相替代**；再加一条「首尾成员点名」（`styleOf(0)` / `styleOf(N-1)`）才算齐。
3. 破坏清单里要给**每个新加成员**配一条**改名破坏**（不只是删除破坏）：
   删除会被计数断言抓到，**改名不会** —— 这一对正好互为对照，缺了改名那条就永远发现不了这个盲区。
