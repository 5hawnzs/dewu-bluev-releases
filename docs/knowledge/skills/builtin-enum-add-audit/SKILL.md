# 给「内置枚举 / 清单」加一项：改动面审计 + 自证

## 什么时候用

- 用户说「再加一种 / 再多一个 / 这个清单里补一条」（骨架列表、模板列表、档位、状态码、颜色映射表…）。
- 加完之后出现「**界面 / 文档还写着旧数量**」「**测试全绿但新那条就是不出现在产出里**」。
- 加完之后出现「**新旧两处指令互相打架**」（下面第 3 步）。

## 为什么不能只改那个数组

这类枚举的每一项几乎总被**三处**引用：① 定义处；② **硬写数量的文案**（UI 提示、拼给模型的提示词、
文档生成器）；③ **断言里的数量 / 首尾编号 / 逐个成员点名**。
只改 ① 的结果通常是「测试红一片」或者更糟：「**全绿但界面在骗人**」。

---

## 第 1 步：全仓搜「数量词」与「编号范围」，把耦合点列全

不要靠记忆。一张能用的搜索网（把 `N` / `T01~T0N` 换成实际的数）：

```
grep -rn "N 种\|N 个\|length === N" --include=*.js --include=*.md --include=*.html <仓库>
grep -rn "T01~T0N\|T01-T0N\|T01…T0N" <仓库>
```

分五类落表（照这个顺序最容易找全）：

| # | 类别 | 典型位置 | 容易漏的点 |
|---|---|---|---|
| 1 | 定义处 | 枚举数组本体 | — |
| 2 | **拼给模型的提示词** | `promptXxx()` 里硬写的「【N 种 …】」 | 数量词与**成员名单**常在两个地方 |
| 3 | **UI 文案** | 界面上的「N 种 …（T01~TN）· 不可编辑」 | 常常**两处**：说明段 + 表格标题 |
| 4 | **断言** | `length === N`、`styleOf(N-1)`、`styleOf(N)`、⑬ 段又钉一次 | 同一数量常被**两个不同的测试段**各钉一次 |
| 5 | **文档 / 文档生成器** | `docs/**/build.js`、README、HANDOFF | 生成器改了但**产物没重新生成** ⇒ 文档仍在骗人 |

## 第 2 步：先跑一遍「体检」，别凭眼看

把候选成员**当成数据**喂给被测系统的真判据（不是自己另发明一套）。一个够用的探针骨架：

```js
const hotwords  = require('<repo>/src/main/services/hotwords.js');
const copycheck = require('<repo>/src/main/services/copycheck.js');
// 1) 不许有 +   2) 不许写死颜色/禁用词表   3) 必须自带连接字/收尾
// 4) 行为级：代入真值后不许被 looksLikeWordPaste() 判成标签串
// 5) 长度 ≤ 该字段上限（注意：示例本身常不受上限断言约束，所以「示例超长」要自己查）
```

★ 第 4 条才是「不是凑巧写对」的真证明；前三条只是「源码里有那几个字」。

## 第 3 步：找「语义冲突」的邻近指令（这一步最容易被跳过）

新成员如果带来**新的行为**（新位置、新的个数、新的字段），去 grep 那些**硬写行为**的邻近句子：

- 实测案例：新骨架是「**两个** emoji 夹在句中」，而 `copywriter` 里两句写着
  「15 字以内，**结尾 1 个**贴合的 emoji」（看图分支一句、无图分支一句）。
  ⇒ 不同步改，模型收到的是**互相矛盾**的指令，而**所有测试照样全绿**（没有断言覆盖「指令一致性」）。
- 做法：`grep -n "<该行为的关键词>" <拼提示词的文件>`，逐条对齐；两边都改。

## 第 4 步：成员若依赖「外部资源 / 映射」，先量覆盖率再定口径

实测案例：新骨架要求「两个 emoji 的颜色＝本行颜色」。把颜色词表**逐条**过一遍映射，
发现 **26 个色名里 24 个有、只有「灰 / 浅灰」没有**（爱心与圆圈都没有灰色；灰心 `🩶` 是 Unicode 15 / 2022
才加的，老机型显示成豆腐块）。

- ⇒ 产出**两个**东西：① 覆盖率数字（写进报告，别只写结论）；② **缺口的口径**（本例：「颜色是灰 / 浅灰时别用这条，
  退回邻近的另一种写法」），并把它**写进提示词**、再给这条口径配一条断言。
- ★ 别忘了派生映射的边界：本例 `coarse()` 把 `棕 / 卡其 / 驼 / 米 / 燕麦` 都判成「橙」（HSL 色相 h<45），
  所以映射表里为**暖棕系**单独写了例外（→🤎/🟤）。**派生值合理 ≠ 人看得舒服**，要人工过一遍。

## 第 5 步：给新成员配闸门（六类，缺一不可）

1. **存在性**：新成员在、`code` 唯一 —— 但要记住它**抓不到改名**（见第 7 步）。
2. **结构连续性**：`list.every((x, i) => x.code === 'T' + String(i + 1).padStart(2, '0'))`。
3. **形状**：新成员的示例必须满足它自己的定义（如「正好两个相同 emoji」+ 在**允许清单**里）。
   数 emoji 要用**不含变体选择符 `\u{FE0F}`** 的字符类，否则 `❤️` 会被算成 2 个。
4. **不许滥用**：其余成员的示例仍满足旧约束（如「只有它才是两个 emoji」）。
5. **口径进提示词**：映射表 / 例外 / 数量词，逐条断言**拼进 system 的那段**里真的有。
6. **行为级 + 源码级两头**：拼 system 的那段（行为级）＋ 运行时真正走的那条分支所在的文件（源码级，如实标注强度）。

## 第 6 步：量化「一批能用到几种」

如果这个枚举是**按行轮换**的（`styleOf(i) = i % list.length`），先量**真实的批次大小分布**
（去读台账 / 日志），再回答「加这一项值不值」：

- 实测案例：一批篇数分布 ＝ `1×2 / 3×8 / 10×6 / 30×8` ⇒ **10 篇的批行号只到 9，看不到第 11 项起**；
  30 篇的批才会全出现。⇒ 结论是「**日常就 10 篇一批的话，加不如换**」。
- ★ 这条要**先算再答**，不要默认「加得多就更丰富」。

## 第 7 步：定点破坏自证（**必须包含「改名破坏」**）

- 备份到临时目录、跑完 `cp` 还原（**禁 `git checkout`**，会抹掉未提交的在制品）；逐条破坏前**先 restore**。
- 每个新成员至少配**三条**破坏：**删除** / **改名** / **改坏它的形状**（如删掉一个 emoji）。
- ★★ 实测盲区：`length === N` ＋ `code 唯一` **对「改名」完全失效** —— 把 `T15` 改成 `TXX`，长度没变、
  也不重复，两条例行断言**全绿**；连「system 里列全了 N 种」那条也绿（它 `every(...)` 用的是**改后的自己**）。
  只有「新成员点名」那条抓住了 —— 而那只是因为断言里恰好写了 `T15`。⇒ 这就是第 5 步第 2 条存在的理由。
- 还要给**口径 / 映射表**配破坏：删掉映射里的一行 ⇒「映射表真的拼进 system」必须红。

## 第 8 步：报告写清三件事

1. **改了哪些文件 / 多少处**（照第 1 步那张表）。
2. **前后可复算的数字**（断言条数、全量套件通过数）。
3. **没做的 + 残留**（例：文档生成器改了但产物没重新生成，因为工作树里另一路会话的回归还没收工 ——
   宁可不生成，也别把**中途数字**烤进文档；收工后一条命令补）。

## 一条并行的注意

若同一工作树里**可能有另一路会话**在改代码：先 `git status` ＋ 看关键文件 `mtime`；
自己只改**需要的**文件，别人的在制品**不要顺手改**；做全量回归时若某套件红了，
先看那套件依赖的文件的 `mtime` 是否落在**你这次跑动的时间窗内** —— 很可能是它的**中途快照**，
单独重跑那一个套件即可证伪。

## 变体：新增的是「判据 / 规则」，而不是枚举成员（2026-10-05 实测）

规则引擎（文案核对、合规校验、权限门控…）加一条判据，和加一个枚举成员**同族但多三个坑**：

1. ★★ **先搜「现无此类判据 / 尚未覆盖」这类如实声明的注释 —— 加了判据它就当场变成假话。**
   实测：`copytest` 头部写着「模型照不照做**没有程序判据**（`copycheck` 现无『emoji 颜色 ↔ 标题色词』一致性判据）」，
   而这一轮恰好补的就是它 ⇒ 不同步改，注释立刻骗人。仓库越老实，这种「自我声明」越多，**必搜**。
2. ★★ **新判据会新增告警 ⇒ 必须配「正反对照」，只测一个方向等于没测。**
   同一段输入：**该报的必须点名**（灰那件写了 💙💙 ⇒ 报）、**不该报的一条都不许报**（蓝那件写 💙💙 ⇒ 静默）。
   再加三类边界：① **本来就没法判的**（标题只有 emoji、一个色词都没有）⇒ 不报；
   ② **看着像但不是**的装饰物（🍂🔥🐻 不是颜色）⇒ 不报；③ **真实数据里的怪叫法**（电商色名「燕麦色 / 花灰色（加绒）」）
   ⇒ 先量一遍覆盖率再定口径。
3. ★★ **每条「例外」都要单独配一条定点破坏。** 例外是你为「不误杀」特意放宽的地方，最容易写反或写漏：
   实测 6 条破坏（表写胖 / 去掉灰例外 / 去掉暖棕互认 / 口径改回更窄的那个 ✓ 判据短路 / 判据改宽）
   **全部命中预设断言**。其中「把比对口径从『所有色词』改回『紧挨单品的声明色』」这条最关键 ——
   它证明的是**取舍本身**在起作用（那条更窄的口径会把 `{色}系` 当氛围词跳过 ⇒ 判据静默失效）。
4. ★ **动手前先扫一遍「新判据会不会把现有夹具打红」**：全仓 grep 新判据要识别的那类字符 / 词
   （这次是 18 个彩色 emoji），确认没有别的套件在用，再开工；有的话先改夹具口径，别等回归红一片。

判据的**设计取舍（五条例外各为什么）必须写进源码注释**，并在注释里写明「这条判据是事后核对、**拦不住**执行」
—— 否则下一个人会把「有判据」读成「已经覆盖」。级别取 `warn`（标黄）而不是 `bad`（拦发布），除非用户明确要求拦。
