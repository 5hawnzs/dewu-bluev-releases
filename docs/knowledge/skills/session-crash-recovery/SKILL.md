# 会话闪退后的内容找回

## 0. 铁律

**闪退 ≠ 数据没了。** 会话记录是**逐条落盘**的；客户端崩了，文件还在盘上。
用户说「没了」时，**不要重头再问一遍需求** —— 先去磁盘捞。

★ 但也要如实：**界面上的那条会话确实回不来了**（列表里点不开）。
捞出来的是**内容**，你要负责把它**落成工作区文件**并告诉用户路径 —— 那是他唯一能回看的东西。

---

## 1. 先认人：哪个文件是「刚崩的」，哪个是「现在这条」

路径：`~/.workbuddy/projects/<目录名>/<sessionId>.jsonl`，**一行一条 JSON**。

```bash
cd ~/.workbuddy/projects/<目录名>
ls -lat --time-style=+%m-%d\ %H:%M | head
```

- ★ **不要按文件大小挑**。实测（2026-10-03）同一目录里同时躺着 **109 MB / 15,287 行**的旧会话
  和 **170 KB** 的新会话 —— **新会话才是用户当前正在用的那条**。
  ⇒ 判活跃：**mtime 最新 + 隔 1 分钟再采一次仍在长大**。
- ★ `<目录名>` **不可逆推真实路径**（`-` 同时表示 `:` 和 `\`，且真实文件夹名本身也含 `-`）。
  要确认归属就读每行里的 **`cwd`** 字段。
- 想确认「崩在哪一刻」：看该文件**最后一条记录的时间戳**；若它停在一个
  `function_call_result` 上、后面没有 `message` ⇒ 就是**半路被砍**（不是正常收尾）。

---

## 2. 解析：三个坑（我全踩过）

| 记录 `type` | 内容 |
|---|---|
| `message` | 真对话，`role` = `user` / `assistant` |
| `reasoning` | 模型思考（`rawContent[].reasoning_text`）—— **待办/结论常藏在这里** |
| `function_call` / `function_call_result` | 工具调用与结果（正文在 `output.text`） |
| `file-history-snapshot` | 文件改动快照 |

1. **坑 1 —— 消息正文块不是 `type:'text'`**，而是 `input_text` / `output_text`，正文在 **`text`** 字段。
   只判 `b['type']=='text'` ⇒ **打印出一片空**，会让你误判「没记录」。
   正确写法：`for b in content: txt += str(b.get('text',''))`。
2. **坑 2 —— JSON 是紧凑无空格的**（`"type":"message"`）。
   用 `'"type": "message"'`（带空格）当预过滤 ⇒ **0 命中**。
3. **坑 3 —— 100 MB 别整体 `json.loads`**。只读尾巴：
   ```python
   f = open(p, 'rb'); f.seek(max(0, os.path.getsize(p) - 4_000_000))
   lines = f.read().decode('utf-8', 'ignore').split('\n')[1:]   # ★ 丢掉第 1 行（被 seek 截断）
   ```

★ Windows 沙箱：脚本**先落盘再跑**（多行/含反引号的内容别塞 `python -c`），
用 Python 全路径；产物写进工作区再 `Read`，别指望 stdout 能把长内容原样带回。

---

## 3. 最值钱的一条：`conversation_history_summary`

上下文爆掉时客户端会自动塞一条**摘要记录**（`message` / role=`user`，正文包在
`<conversation_history_summary>` 里）。它有固定小节，等于**现成的交接单**：

```
## 1. Primary Request and Intent     用户到底要什么
## 2. Key Technical Concepts         关键概念/常量
## 3. Files and Code Sections         改过哪些文件、贴了关键代码
## 4. Errors and fixes                踩过什么坑、怎么修的
## 6. All user messages               ★ 用户说过的原话（引用/追责用）
## 7. Pending Tasks                   ★ 待办
## 8. Current Work                    崩在哪一步
## 9. Optional Next Step              ★ 下一步该干嘛
```

捞法：扫全文件找含 `<conversation_history_summary>` 的 `message`，取**最后一条**，
整段导成 `.md` 再读。

---

## 4. 标准动作（照做）

1. `ls -lat` 该工作区对应的 `projects/<目录名>/` → 认出**活跃会话**与**被闪退的那个**。
2. 从闪退那个文件尾部捞两样：
   - 最后几条 `message`（谁说了什么、有没有「Interrupted by user」）；
   - **最近一条 `conversation_history_summary`**（§7 待办 / §8 当前 / §9 下一步）。
3. ★★ **跟三个来源交叉核对**再开口：
   ① 该工作区的**当日工作日志**（`.workbuddy/memory/YYYY-MM-DD.md`）；
   ② **磁盘现状**（`git status`、关键文件 mtime、配置文件内容、跑过的产物）；
   ③ 其它**并行会话**的记录（同工作区可能有别的会话也改了同一个仓库）。
   ⇒ 摘要里的「Pending Tasks」**可能已经被后续动作做掉了**，**别把已完成项当待办报给用户**。
4. **落成文件**交付：命名带「内容找回」，例如 `闪退会话-内容找回-YYYYMMDD.md`
   （摘要正文 + 闪退前最后几条消息的原文）。
5. 用户的真实诉求常常是下一句：**「还有什么待确认的，你全部列给我」**
   ⇒ 把所有来源里的「待用户拍板 / 等用户放话 / pending / 未做（如实）」**全量合并成一张清单**，
   每条写清【现状 / 卡在哪 / 需要他做什么 / 我的建议】，按「会不会卡住他现在要干的事」排序，
   并明确标出**哪些已经做完**（他被这些"已做完的待办"折腾过，最想知道这个）。
6. 之后按「会话记录太大 ⇒ 开新会话 + 先写交接单」处理，**否则下一次还会崩**。
