# adb + uiautomator UI 自动化：延迟定位与提速加固

适用：Node/Python 驱动模拟器/真机，`adb shell input tap` + `uiautomator dump` 找节点点击的自动化
（批量发布、批量采集、RPA 类）。典型症状：**「点按钮太慢」**、一条任务几十秒。

**核心心法：先量，再改；并且分清「每次都付」和「每批只付一次」。**
用户说的「点击慢」几乎总是**判断错误** —— 慢的不是点击，是点击前那次抓屏。

---

## 0. 铁律

1. **不要凭感觉优化。** 先用裸命令把一次操作拆成四类耗时，拿到数字再动手。
2. **盲点（不抓屏、按死坐标点）只对「版式绝对固定」的目标用。** 点错的后果是**静默点错**
   （挂错商品 / 少选素材），比慢严重得多。坐标会漂的屏一律保留抓屏。
3. **任何「快路径」都必须能被关掉、且关掉后断言变红。** 否则你不知道它是真快还是没生效。
4. **改了用户设备的系统设置（动画开关等）必须 `finally` 还原**，并断言「跑前跑后都是原值」。
5. **「合并成一条 shell」和「缓存」是两种不同的省法**，别混：前者省每次的往返，后者省重复的等待。

## 1. 第一步：把耗时拆开（给命令，直接抄）

在宿主侧量，不要在代码里加计时器猜：

```bash
export ABC="<path>/adb"
# 纯往返（基线，与命令内容无关）
T0=$(date +%s%3N); $ABC -s $S shell "echo hi" >/dev/null; T1=$(date +%s%3N); echo "往返 $((T1-T0)) ms"
# 点一下
T0=$(date +%s%3N); $ABC -s $S shell "input tap 540 1000" >/dev/null; T1=$(date +%s%3N); echo "tap $((T1-T0)) ms"
# 抓屏（连打 3 次，看第 1 次和第 3 次是否一样）
for i in 1 2 3; do
  T0=$(date +%s%3N)
  $ABC -s $S shell "rm -f /sdcard/p.xml; uiautomator dump /sdcard/p.xml 2>&1"
  T1=$(date +%s%3N); echo "dump#$i $((T1-T0)) ms"
done
# 不等 idle 的备用抓取
T0=$(date +%s%3N); $ABC -s $S shell "dumpsys activity top" >/dev/null; T1=$(date +%s%3N); echo "dumpsys $((T1-T0)) ms"
```

**实测基准（MuMu 12 / Android 12 / 1080×1920，仅作量级参照）**

| 动作 | 耗时 |
|---|---|
| `input tap x y` | **138–146 ms** |
| 纯 `adb shell` 往返 | 135 ms |
| `dumpsys activity top` / `dumpsys window \| grep mCurrentFocus` | 160 / 140 ms |
| 普通页 `uiautomator dump` 本体 | **2036 ms** |
| 整个「rm + dump + cat」一条 shell | ≈ 2240 ms |
| **持续动画页裸 dump** | **11230 / 11136 / 11127 ms，三次全 `could not get idle state`** |
| 同一张屏**关掉三个系统动画**后 | **2036 ms** |

⇒ **抓屏比点击贵 15 倍**。结论先摆出来：优化方向是「少抓屏 / 合并抓屏 / 同一个坑只踩一次」，
不是「把 tap 调快」。

## 2. 三种省法（按收益从大到小）

### 2.1 「每批只付一次」—— 收益最大，最容易漏

`uiautomator` 在**永不 idle 的屏**上会先白等一次 idle 超时（实测 ~11 s）才失败。
如果这个屏在每个任务里都会经过，那就是 **11 s × 任务数**。

做法：给抓屏函数加一个 `preferAnimOff` 快路径（已知这屏不会 idle ⇒ 直接关动画抓），
再由**批次上下文**按「这一步 / 这一屏」的稳定键记住它：

```
批次 ctx 里放一个 cache（如 ctx.animOffSteps = {}）
键用**步骤名**（定位表里写死的），不要用填充过数据的 value（每条内容都不一样，缓存永不命中）
第 1 条：默认路径 → 抓到后把这一步记进 cache，并在日志里说清
第 2 条起：命中 cache → 直接走快路径
```

实测：同一张相册页 **13462 ms → 2396 ms（每条省 11.07 s）**；
同一个步骤在一次运行里出现两次：**13824 ms → 3085 ms**。

**两个必须注意的点**
- 缓存必须挂在**批次**对象上。挂在模块级全局变量上会跨批次泄漏（用户改了定位表却还走旧判断）；
  每次 `run()` 新建即可，**不要落盘**。
- 关动画后**必须 `finally` 还原**（读原值 → 写 0 → 抓 → 写回原值），并加断言「跑前跑后都是 `1 1 1`」。

### 2.2 合并往返 —— 省的是每次的固定开销

一次 `adb shell` 往返约 120–180 ms，**与命令内容无关**。所以：

- **抓屏**：`rm -f X; uiautomator dump X 2>&1; echo <标记>; cat X 2>&1`
  合成一条 shell，用标记切分「dump 的返回」和「文件内容」。
  3 次往返 → 1 次。失败判据别改：标记**前半段**里有 `dumped to` 才算 dump 成功。
  ⚠️ `uiautomator dump --compressed` 实测**更慢**，别用。
- **多点点击**：`input tap a b; sleep 0.25; input tap c d; ...` 合成一条 shell。
  `sleep` 要放**设备端**（小数秒可用），不要放宿主侧 JS —— 放宿主侧等于每次都多一次往返。
  实测 3 击：分三条 ~380 ms → 合一条 **127 ms**。
- **只有 1 个点时不要加 sleep**（白等 250 ms 也是成本）。

### 2.3 复用同一次抓屏

如果一个薄/判断步骤（例如「当前这一屏对不对」）刚抓过屏，紧接着的点击步可以**直接复用那份结构**，
不要再抓第二次（省 ~2.2 s）。中间不能有任何动作，否则结构就不新鲜了。

### 2.4 给「裸 dump」套 `timeout` 上限 —— 把**第一次**的白等从 11.5s 砍到 4s

2.1 的缓存只省「第 2 条起」。**第 1 次撞上永不 idle 的屏照样要白等一次 idle 超时（实测 ~11.5 s）**，
而这一屏可能只在这一步出现一次 —— 缓存救不了它。

做法：宿主侧给裸 dump 套设备自带的 `timeout`（Android 6+ toybox 都有；先验一句
`adb shell "timeout 2 sleep 5; echo \$?"` → 应回 `124`）：

```bash
rm -f /sdcard/p.xml; timeout 4 uiautomator dump /sdcard/p.xml 2>&1; echo <标记>; cat /sdcard/p.xml 2>&1
```

超时被杀 ⇒ sh **一个字都不打印** ⇒ 与「页面永不 idle」**同症状** ⇒ 照旧走原有回退链
（关动画 → dumpsys）。实测把 11.5 s 压到 4 s（健康页裸 dump 是 2.06 s，`4` 留了约 2× 余量）。
**上限值怎么定**：取「健康页裸 dump 耗时 × 2」，别贴着健康值（贴着会把只是稍慢的正常页也切掉）。

**两个坑（都真踩过）**
- ★★ **设备上没有 `timeout` 时**，sh 打印 `not found`、命令**根本不执行**。若把它当普通失败，
  下一步会退到 **dumpsys 备用通道 —— 那条没有文字** ⇒ 按 `text` 找的步骤**静默全失效**。
  正确做法：识别 `not found` ⇒ **去掉上限原样再抓一次**，老设备行为与改之前一字不差。
- ★ **逃生通道（关动画那条路）不要加上限**：它本来就是给「慢页面」用的，
  加上限会把「只是慢、但能正常抓」的页面误杀。

## 3. 盲点（`tapXY`）—— 高风险，必须有稳定性证据

**先给结论：不要因为「坐标已经摸清楚了」就大面积改盲点。**
实测到的漂移（同盘同一 App）：

| 目标 | 漂移 |
|---|---|
| 相册页页签 | y **276 ↔ 140** |
| 相册页网格 | y **359 ↔ 204 ↔ 240** |
| 编辑页标题框 | y **308（图文）/ 444（视频）** |
| 首页「发布新动态」 | 随上方内容变（网络驱动页面） |

安全用法：
- 只对**全局固定**的目标用（如 App 底部 tab 栏），并且要**用 dump 取真实 bounds 中心**核对一次
  （例：`tab_user` `[810,1819][1080,1920]` → 中心 `945,1869`）。
- 图文/视频两套分开的定位表，可以各自写死自己那套的坐标（`etTitle` 308 / 444 就属于这种）。
- **导入期**就要挡住空坐标/解析不出的坐标，否则会点到屏幕左上角。
- 想更保险：配一个「屏幕守卫」（按当前这一屏的 resource-id 判断这一步该不该执行）。

### 3.1 两个取坐标的坑（实测踩过）

- ★★ **`dumpsys activity top` 里的坐标是「相对父容器」的，不是屏幕绝对坐标。**
  看到 `flNextStep 891,0-1080,98` 很容易当成「屏幕右上角」—— 实际那只是父容器里的偏移，
  真机**绝对** bounds 是 `[891,1794][1080,1892]`（右下角）。差点据此把坐标写错。
  ⇒ **要绝对坐标就先把三个系统动画关掉（写成 0）再跑 `uiautomator dump`** ——
  动画一关，本来永不 idle 的屏也能 idle，拿到的 `bounds` 就是绝对坐标；抓完记得还原。
- ★★ **同一个 resource-id 可能只是「整格里的一个小角」。**
  相册页的 `flThumbSelect` 看着像整格，实测只有 **88×88**、位于缩略图**右上角** ——
  它就是**那个选择圆点**（`ivThumbSelect` 是它内部 35×35 的小圆）。
  点它的中心 `(166,359)` 才对；点缩略图正中通常是「打开预览」而不是「选中」。
  ⇒ 拿到 bounds 后**先对着截图核一眼**，再算中心。
- ★ 顺带：**选中之后才进 accessibility 树的节点**（示例：相册页的「下一步」`flNextStep`）
  在选中前的 dump 里**根本不存在**。别拿「选中前 dump 不到」当成「这一步写错了」。

### 3.2 ★★ 改成盲点会**连那份「天然等待」一起省掉**（实测 0/2 的坑）

- `tapId` 每步都要先 `uiautomator dump`（~2.1s）才点 ⇒ **点击之间天然隔着 ~2.1s**，
  顺手把屏间转场等掉了。`tapXY` 是**立即点** ⇒ 上一次点击的转场还没结束就点下一下。
- 后果：那一下被当成「**转场中的空点**」或被系统合成**一次双击**。
- 症状很阴：**报错落在后面好几步**（"找不到 `etTitle`"），离真因很远。
- 实测（得物视频，1080×1920）：相册下一步 → 剪辑页下一步 → 封面页跳过，三步连点 ⇒
  **一条还停在剪辑页（两下全丢）、另一条只过了一屏**；逐屏手动点（每步隔 ≥1s）则 100% 通过。
- **对策**：改盲点后，**只要下一步落在「新的一屏」上，就必须补固定等待**。
  最省事的做法是在配置层插一步 `{action:'wait', value:1200}`（不改源码）。
  - 有**屏幕守卫**（`whenOn`）的那一步**不用补** —— 守卫本来就要 dump 一次，那 2.1s 就是等待。
  - 等待值用「手动点一次、看屏幕多久变」量出来（本例转场 <1s，取 1200ms 留余量）。
- ★★ **改盲点前，先用真机确认「这一步点完真的到下一屏」**。别假设「连点两下 = 过两屏」：
  得物**封面页**点右边「下一步」进的是**又一屏「编辑封面」**（还得再点一下），
  点左边「跳过」才直达编辑页。同一坐标连点两下根本过不去。
  ⇒ 把「目标屏」当场 dump 出来核一次，是唯一可靠办法。

### 3.3 ★★★ 「有具体坐标却老是点偏」第一根因：**坐标空间（coordinate space）**

（与「肉眼估坐标」并列的两层根因之一；实测于 MuMu 12 / Android 12）

- `input tap x y` 吃的是**当前前台应用方向下的设备像素**。同一台机**两种坐标系会并存**：
  - 得物（竖屏锁定）：`init=1080x1920 … cur=1080x1920`
  - MuMu 桌面（横屏）：`cur=1920x1080`；同刻 `screencap` 的 PNG 与 dump 的 `bounds` **同步变 1920x1080**。
- ★★★ **`wm size` 报的是「自然方向」尺寸**（`Physical size: 1080x1920`），**不随旋转变** ⇒
  拿它去校验坐标会**判反**（把对的判成错的、错的判成对的）。
  正确来源 = **`dumpsys window displays` 里的 `cur=`**（`init=` 是自然方向，`cur=` 才是当前坐标系）。
- ★★★ **`input tap` 对越界坐标不报错**：实测 `input tap 945 1869` 在 1920x1080 上
  **rc=0、什么都不点** ⇒ 坐标系不对 = **全程静默点偏、日志零报错**。
  ⇒ **必须主动校验，不能等报错**。
- ★ 坐标系跟**前台应用**走，**不是**设备级旋转开关：实测 `settings put user_rotation 0` 之后
  `cur=` 仍可能是 1920x1080。
- **两层守卫（推荐都装）**
  1. **表级**：抓定位表时把当时坐标系戳进表（`{screen:{w,h}}`）；发布时读当下 `cur=`
     与之比对，尺寸不符（含 **w/h 互换**的"转了个向"）⇒ **直接抛错**，别点。
  2. **逐点**（最后一道）：每次 `tapXY` 前把 `(x,y)` 与当前坐标系比，越界即抛错；
     坐标系**读不到时不拦**（返回"可判定=false"），**不猜**。
- ★ 两条防线**相互独立**：定点破坏「只拆逐点调用点」时，表级仍能拦住 —— 反之亦然
  （证明时两条各测一次）。
- **取坐标的助手**（把「肉眼估」这件事彻底删掉）：写一个只读脚本，
  输入「元素查询词」→ 输出**设备像素中心** + 可粘贴的 `{"action":"tapXY","value":"x,y"}`，
  并顺带打印当前坐标系/前台/边界自洽性。**dump 的 `bounds` 本来就是设备像素，
  `input tap` 也吃设备像素 ⇒ 中间不需要任何换算**（我的旧错法：截屏肉眼估 + 猜一个 1.8 倍缩放，
  把 y 算成 235，真值 423）。

## 4. 每个提速都要有「三件套」

| 件 | 内容 | 反例（假绿） |
|---|---|---|
| **可复算断言** | 数**命令行的条数 / dump 的次数**，不要只断言 `ok` | 只看 `ok===true` ⇒ 慢路径也过 |
| **反向对照** | 配一条「老路径下应该是 2 条 / 4 次」的对照 | 两边都取空 ⇒ `空==空` 假通过 |
| **定点破坏** | 把快路径关掉（`if (false && …)`），断言必须**变红** | 只看退出码 ⇒ 套件中断也算「没抓住」 |

定点破坏的纪律（详见技能 `bilateral-fix-verification`）：**每条破坏从干净源码起**、
`try/finally` 兜还原、跑完复核 MD5、判据是「**那一条断言行变成 FAIL**」。

**负向断言也要有**：例如「页面本来就会 idle ⇒ 不许往缓存里塞」——
塞错了的后果是以后每一步都无端关掉用户设备的动画。

## 5. 四个必踩的假绿坑

1. **点击成功的函数返回 `undefined`**（只有「跳过」才返回 `{skipped}`）⇒ 断言里写 `!r.skipped` 会抛异常，
   **整段断言一条都不打**，只看有没有 FAIL 的人会误判成全绿。
   写法：`!(r && r.skipped)`；并且断言块整体 `try/catch`，把「抛异常」也算 FAIL。
2. **夹具把输出重定向当成文件名**：真机上 `cmd 2>&1` 的重定向**不属于命令本身**。
   一旦上游把「抓屏 + 回传」合并成一条 shell，不剥重定向的夹具会去 `cat 2>&1`，
   **整条链路全部认不出来**（实测一次挂 35 条断言）。夹具要剥 `2>&1` / `>/dev/null`，并支持 `echo`。
3. **补丁脚本 LF、源码 CRLF** ⇒ 跨行锚点 `count=0`。
   一律「读入归一成 LF 匹配锚点、写回按该文件原风格转」，落盘后回读复核 `CRLF>0 且 LF=0`。
4. ★★★ **「现象 / 夹具判据 / 修复代码 / 回归断言」四者互为出处 ⇒ 整套可靠性 = 0。**
   （实测教训，代价是**改坏了真正发出去的内容**）真机报了一个错 → 我在**新写的夹具**里编了一条
   判据去复现它 → 照这条判据写「修法」→ 夹具变绿 → 断言又照修法写 → 全绿收工。
   四样东西其实是同一个幻觉的四个副本，互相"证明"。真实后果不是「没修好」，
   而是**静默改坏了数据**（把反斜杠写进了正文）。
   ⇒ 三条硬规则：① 判据只能来自**被测系统的逐条实验**（例：真机跑 12 组输入，确认行首 `#`
   **根本不会炸**）；② **夹具里不许出现我没在真机上见过的判据**；③ 关键修复的行为级断言要能
   **独立**证明「设备真正收到了什么」——例：夹具按 **sh 双引号语义**解码 `--es msg "…"` 后记账，
   断言「**收到的串逐字符 == 源文**」，任何人往内容里塞反斜杠都会当场变红。
   ★ 注意「没测到」（坑 1~3）和「**测反了**」（本坑）不是一回事，后者更贵。

另：**函数定义在哪个文件要先确认**（例：`screenGuard` 在 publisher 里而不是 adb 里）——
锚点放错文件会 `count=0`；落盘前用 `count==1` 的闸门拦一道。
