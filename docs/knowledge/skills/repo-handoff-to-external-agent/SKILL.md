# 交接给外部编码代理：先分类，再补齐 git 之外的部分

## 何时用

- 用户说「我要让 Codex / Claude Code / 别人 接你的班」，问**需要给他什么**。
- 项目长期在一个 AI 会话里演进，规则、技能、历史文档长在**仓库之外**（客户端的私有目录里），
  接手方 `git clone` 之后「代码能跑，但什么规矩都不知道」。
- 要把项目迁到**另一台机器**或**换一个 AI 工具**继续做。

## 0. 一句话原则

> **接手方能拿到的东西，只等于「仓库里的」+「你明确交到他手上的」。**
> 你的记忆、技能、历史文档如果只躺在客户端私有目录里，**交接时等于不存在。**

所以交接动作 = ①**分类**（哪在 git 里、哪不在）→ ②**把知识搬进 git** → ③**把搬不进去的列成清单**。

---

## 1. 第一步：分类（三条命令就能定性）

```bash
cd <repo>
git remote -v                       # 远端是哪、私有还是公开
git rev-parse HEAD                  # 本地 HEAD
git ls-remote origin refs/heads/main  # ★ 远端真实状态（唯一硬证据）
git status --short                  # 工作树是否干净
git ls-files | awk -F/ '{print $1}' | sort | uniq -c | sort -rn   # 仓库实际收了什么
```

然后把项目里的资产按**三类**过一遍（下面这张表直接照抄进交接单）：

| 类别 | 典型内容 | 结论 |
| --- | --- | --- |
| **git 里全都有** | 源码、测试、给 AI 的入口文档、历史交接文档 | clone 完就能开工 |
| **git 外，但本机已就位** | 凭据文件（已被 `.gitignore`）、模拟器/设备、SDK、`node_modules`、SSH key | **同机运行 = 不用转移**；换机才要另给 |
| **git 外，二进制/原件** | 已发布的安装包、归档、大 zip、截图、逐次运行的取证件 | 按需索取，**故意不进 git** |

★ 第二类是**最容易漏答**的：用户问「我得给他什么」，正确答案常常是「**只要他在这台机器上跑，就只缺一次 `npm install`**」。

---

## 2. 第二步：把仓库之外的知识收进 git

这些内容原本在客户端私有目录，要在仓库里给它们一个家（示例：`docs/knowledge/`）。

### 收哪些

| 类别 | 去哪找（WorkBuddy 环境） |
| --- | --- |
| 项目规则全文 / 记忆索引 | `<工作区>/.workbuddy/memory/REFERENCE-*.md`、`MEMORY.md` |
| 跨项目工作规范与用户偏好 | `~/.workbuddy/REFERENCE-通用.md`、`~/.workbuddy/MEMORY.md` |
| 技能 | `~/.workbuddy/skills/*/`（`SKILL.md` + 附带脚本） |
| 成品文档 | 工作区根目录的 `*.md` / `*.html` / `*.diff` / `*.sql` / `*.json`（交付报告、SOP、定位表…） |
| 工作日志 | `<工作区>/.workbuddy/memory/YYYY-MM-DD.md`（原始流水，标注「别整读」） |
| 已部署站点源码 | 站点目录（★ **剔掉里面的下载目录/安装包**） |

### ★★ 入库前的三道检查（缺一条都可能出事）

1. **确认它不会被打进产品包**
   读构建配置里的白名单，例如 Electron：
   ```bash
   node -e "const p=require('./package.json');console.log(p.build.files)"
   ```
   本案是 `["src/**/*","package.json", …]` ⇒ `docs/**` **不进包**，安全。
   ★ 若白名单是通配 `**/*`，内部规则会被打进 exe **外发给终端用户** —— 这种必须先改白名单或换目录。
2. **扫凭据字面量**（在**复制之前**扫源目录，复制之后再扫一遍目标目录）
   ```bash
   grep -rilE "(eyJ[A-Za-z0-9_-]{30,}|AKID[A-Za-z0-9]{12,}|sb_secret_|sk-[A-Za-z0-9]{24,}|postgres(ql)?://[^ ]*:[^ ]*@|-----BEGIN [A-Z ]*PRIVATE KEY)" <dir>
   ```
   命中后**逐条判死**，不要一把删也不要一把放：
   - 占位符/示例（`AKIDxxxxxxxx…`、`<你的key>`）⇒ 安全。
   - 看起来是真的 JWT ⇒ **解它的载荷判权限**，别猜：
     ```bash
     p=$(echo "$tok" | cut -d. -f2); pad=$(( (4 - ${#p} % 4) % 4 ))
     printf '%s' "$p$(printf '=%.0s' $(seq 1 $pad))" | tr '_-' '/+' | base64 -d
     ```
     看到 `"role":"anon"` 且它本就随公开前端发布过 ⇒ 可接受；`service_role` / secret ⇒ **停手**。
3. **剔垃圾**：`__pycache__` / `*.pyc` / `*.bak*`。
   ★ 坑：`find -type d -name __pycache__ -prune -exec rm -rf {} +` **实测没删掉**（顺序/`-prune` 组合不对）；
   直接按路径 `rm -rf <path>` 才干净。用 `find <dir> \( -name __pycache__ -o -name '*.pyc' -o -name '*.bak*' \) | wc -l` 复查到 0。

### 幂等导出脚本（可重跑）

把上面整套写成脚本放工作区根（**别放仓库里**），重跑即可刷新快照。要点：
`mkdir -p` 各子目录 → `cp` 各类资产 → `find` 清垃圾 → 末尾打印 `du -sh` 与文件数当证据。
★ 脚本里若删自己刚建的目录，用**显式路径**而不是通配；不要在个人目录上跑 `rm -rf`。

## 3. 第三步：写入口文件（决定接手方能不能自己走起来）

### 3.1 认准「那个工具会自动读的文件」

| 工具 | 自动读的入口 |
| --- | --- |
| **OpenAI Codex** | 仓库根的 **`AGENTS.md`** |
| Claude Code | `CLAUDE.md` |
| 通用 | `README.md` + 一份 `docs/HANDOFF-<工具>.md` |

★ 入口文件是**每轮都会被注入上下文**的，所以它要**短**：只放「不遵守就出事」的祈使句 + 指向详细文档的指针。
详细的规则、技能、历史文档放 `docs/knowledge/`，**别堆进入口文件**。

### 3.2 一页纸交接单 `docs/HANDOFF-<工具>.md` 的结构

```markdown
# 交接给 <工具>
## 0. 结论先说：git 里已有什么、还缺什么      ← 上面 §1 的三类表
## 1. 粘给我的第一条消息                       ← 下面 §3.3，paste-ready
## 2. git 里已有的东西（clone 即得）           ← 逐目录 + 文件数
## 3. git 之外、必须「在这台机器上存在」的东西  ← 逐条可核 + 「挡不挡开工」
## 4. 当前状态快照（HEAD/版本/回归/公网/产物）  ← 全给实测值
## 5. 验收标准（这是标准，不是建议）
## 6. 已知遗留（明知未修，别当新发现）          ← ★ 不写这条，接手方会把老问题当新 bug 查
## 7. 要发布时读哪份 SOP
```

### 3.3 「第一条消息」要素（缺一条接手方就会踩坑）

- **在哪干活**：绝对路径 + 「这个目录不许改名/移动」（若有绝对路径依赖必须说）。
- **读什么、什么顺序**：入口文件 → 详细交接文档的指定小节 → 知识库索引（并明说「**别整读**」）。
- **三条最贵的硬约束**：这类约束是「用真实事故换来的」，不写接手方必然重犯。
  本项目实例：① 有并发会话在改同一棵树 ⇒ `app.js`/`store.js` 只许局部替换；
  ② 每改一处跑回归，且 **绝不设某个环境变量**（回归里有一条断言断言的正是「它没设」，设了会 FAIL 并挂住不退出）；
  ③ 中文注释、取不到就写「取不到」、**不许造假成功**。
- **验收门槛**：「全绿 ≠ 通过；必须能回答『我改掉了哪条判断、哪条断言会因此变红』」。
- ★ **提醒数字会过时**：「文档里的断言数/体积/耗时**每次实测重取**」——
  否则接手方会照抄一个过期数字当基线。

## 4. 第四步：提交、推送、取证

```bash
git config core.quotepath false        # ★ 不加这条，中文文件名在一堆输出里会显示成八进制转义，看不清都加了什么
git add <明确的路径>                    # 不要 git add -A / git commit -a
git diff --cached --name-only | wc -l
git diff --cached --name-only | grep -iE "(\.env|node_modules/|\.exe$|secret)" || echo "✔ 无危险项"   # ★ 入库前最后一道
git commit -F <消息文件>                # ★ 消息文件路径要给 Windows 形式：E:/x/y.txt
git push origin main
echo "local : $(git rev-parse HEAD)"; echo "remote: $(git ls-remote origin refs/heads/main | cut -f1)"   # ★ 两者必须一致
```

★ **`git status` 干净 + `git log` 有提交，都证明不了「推上去了」** —— 唯一硬证据是 `ls-remote` 与 `HEAD` 相等。
★ 提交后**核对文件没被换行符处理搞坏**：`git show HEAD:<path> | wc -l` 与源文件行数比对
（`LF will be replaced by CRLF` 那一屏警告是**正常的**，不是错误）。

---

## 5. ★★ 最后一条，最容易忘：知识库是**快照**，会过期

搬进仓库的规则/技能/文档，是**导出那一刻**的副本；客户端那边的「活文档」还在继续长。
**规则一改，仓库里的快照就是错的 —— 接手方会按旧规则干活。**

⇒ ① 在知识库 `README.md` 顶部显式写明「**这是快照，导出时间 <日期>，活文档在 <路径>**」；
　 ② 在项目记忆里留一条「**改完活文档要重新导出**」的规则 + 导出脚本路径。

---

## 6. 常见坑速查

| 现象 | 原因 | 对策 |
| --- | --- | --- |
| `git commit -F /e/x/y.txt` → `could not read log file` | Git Bash 的 `/e/…` 传给 Windows 版 git 不认 | 用 `E:/x/y.txt` |
| 中文文件名在一堆输出里是乱码/转义 | `core.quotepath` 默认 true | `git config core.quotepath false` |
| 满屏 `LF will be replaced by CRLF` | `core.autocrlf=true` | 正常；用 `git show … \| wc -l` 核对 |
| `find … -prune -exec rm -rf {} +` 没删掉目录 | 表达式顺序问题 | 直接 `rm -rf <显式路径>`，再 `find … \| wc -l` 复查 0 |
| 接手方说「文档不全」 | 知识资产本就在仓库之外 | 回到 §2，先分类再搬 |
| 内部规则出现在安装包里 | 构建白名单是通配 | 先读 `build.files`，把它排除在外 |

## 7. 交付时的三句话（直接给用户）

1. **git 里已有什么**：代码 + 测试 + 入口文档 + 知识库（规则/技能/历史文档/日志）—— clone 一次就够。
2. **git 之外只剩三样**：① 本机环境（依赖/模拟器/真机 App）；② 凭据文件（已 gitignore，同机 = 不用转移，**绝不许贴出来**）；③ 二进制原件（安装包/归档/取证件，按需索取）。
3. **粘这段话给他**：把 `docs/HANDOFF-<工具>.md` §1 的第一条消息给用户，让他直接复制粘贴。

## 8. 换机（「如果换设备让他跑呢？」）：多出来的只有「搬钥匙」

同机交接只缺一次依赖安装；**换机要多搬几份「不能走 git」的文件**，并在新机**重置机器专属配置**。
用户从「同机交接」追问到这个问题时，先给一句判别，再给 runbook：

> **同机 = 只缺一次 `npm install`；换机 = 多出一件「搬钥匙」的活，而钥匙不能走 git。**

### 8.1 先判「目标机是什么系统 / 拿它干什么」

| 目标 | 前提 |
| --- | --- |
| 要跑真实链路（连设备/相机/硬件） | 目标机必须与**产品形态同平台**（例：产品只打 Windows 安装包、仓库里的 vendor 二进制是 `.exe` ⇒ 目标机就得是 Windows x64） |
| 只改代码、不连设备 | 换平台可行，但要**整体替换**平台相关件：原生 addon（如 `sharp`）、平台二进制（adb/ffmpeg 之类）、打包目标 |
| ★ 注意 | 有些 npm 脚本是**强制取某平台版**的（如 `--os=win32`）—— 在别的平台上跑它会把**对的版本顶掉** |

★ 让工程放在**同一个绝对路径**，能省掉一整类「读不到数据」的怪问题。

### 8.2 通道分类（这张表本身就是交付物）

| 东西 | 通道 |
| --- | --- |
| 源码 / 测试 / 文档 / 知识库 | `git clone` |
| **已经在 git 里的二进制**（`vendor/` 之类） | `git clone`（★ 别再去原机拷一遍，容易拷到旧版） |
| **运行时配置**（含密钥 + **机器实测出来的数据**） | 只能单独搬（加密包/U 盘/内网），**绝不许走 git** |
| **凭据文件**（口令哈希、`.env`、SSH 私钥） | 同上 |
| 设备 / 模拟器 / 登录态 / 驱动 | 新机自装 |
| 已发布产物 / 归档 / 大 zip / 取证件 | 按需，二进制，故意不进 git |

★ 一句话给用户：**「这三份文件加起来 ≈ 项目的全部钥匙；一旦进 git，即使之后删掉也留在历史里，只能轮换密钥。」**

### 8.3 ★★ 别假设「配置能导出」；没有就**给它做一个**

先查有没有内置的导出功能，**再看它导的到底是什么**。
实测教训：界面上确实有「导出配置 / 导入配置」，但读源码发现它**只导出云端协作三个字段**
（`exportConfig()` 返回 `url / anonKey / org`），**不含模型密钥、不含机器实测出来的 UI 定位表**
⇒ **看见按钮不算证据，要读它的实现。**

确认「没有」之后，**不要停在「那只能整份拷 / 在新机重填」** —— 写一个搬运工具
（本案：`tools/config-portable.js`，`inspect / export / import / selftest` 四个子命令）。
核心设计就一条：**把配置分成三个桶**。

| 桶 | 判据 | 处理 |
| --- | --- | --- |
| 可搬运 | 业务配置 + **机器实测出来的数据**（UI 定位表、坐标、设备清单、阈值、词库） | 原样带走 |
| 必须重置 | 机器专属：绝对路径、机器标识、机器名、窗口位置、可执行文件路径 | **显式写空值**（配置多是「深合并、只覆盖不删键」⇒ 置空也必须显式写） |
| 密钥 | 按**叶子键名**正则匹配（`apikey`/`secret`/`token`/`password`…） | **默认剔除**，`--with-secrets` 才带 |

工具的硬要求（每条都有理由）：

- **`import` 默认只预演**，`--yes` 才写盘，且**先备份**目标文件（`*.bak-before-<用途>-<时间戳>`）。
- **导入侧不抹本机已有的密钥**：包里标为「已剔除」的路径，本机若已有值则保留本机值。
- **正则不许写裸 `key`** —— 会把公开的 `anonKey`（publishable key，靠 RLS 收口）误当密钥抹掉。
- **自带往返自测**（临时目录，**不碰真配置**）：喂假配置 → 导出 → 导入 → 断言「该空的空了、该留的留着」。
  ★ 本案首跑就**真红了一条**（路径工具函数对**顶层键**返回 `undefined` ⇒ 那两个顶层键没被置空）
  —— 自己写的工具，必须有能立刻抓到这类错的用例；**首跑全绿反而要怀疑断言在放水**。
- **别塞进回归套件的硬编码数组**：套件表若是手写数组，加进去会**改变基线断言数**、让已发出的验证结论失效；
  维护型脚本与它并列即可（本案 17 套 1622 项的基线因此保持不动）。
- 交付时给出**「旧机导出 → 新机导入」两行命令**，并写明「导入前把 App 关掉」——配置常是启动读进内存、
  之后整份写回，开着导很容易被内存旧值刷掉。

### 8.4 ★★ 搬运行时配置前，先找出「机器专属」的那几处

直接照搬配置文件最常见的坑，**都要在文档里写明怎么重置**：

1. **机器标识**：若代码是「有就复用、没有才生成」（`let id = cfg.machineId || ''; if (!id) { id = gen(); save(id) }`），
   照搬 ⇒ **两台机器共用一个 id**，服务端把两台当成一台（统计、上报全乱）。
   ⇒ 新机上把该字段**置空**，让它重新生成；顺手确认机器名（常见是取 `os.hostname()`）。
2. **绝对路径**：配置里的目录是原机的绝对路径（常带用户名/盘符），换机后**静默失效**（不报错，就是读不到）。
   ⇒ 新机必须重选；且**先验证原值本身是否还有效** —— 本案原机那个源目录早就被删了，「沿用原值」纯属自欺。
3. **★ 游标 / 水位线 / 缓存**（最容易漏）：同步或上报状态文件里的 `offset` / `uploaded` / `lastSyncAt`
   —— 照搬 ⇒ 新机**接着原机的位置往下推，可能漏推一截且不报错**。
   ⇒ 这类文件**删掉让它自己重建**；同理：设备/安装标识（`.updaterId`）、本地缓存（`pool.json`）。
4. **账号库**：能直接登录的东西（口令哈希）按密钥对待；★ 若产品有「首次启动读种子文件 → 立刻删除」的机制
   （例：`auth.seed.json`，环境变量优先），**那比搬哈希更安全**，优先写进文档；
   两者都不给 ⇒ 产品会建出厂账号，也要写明默认口令。
   ★★ **别只看「哈希」，还要看里面有没有「记住登录 / 会话」字段**：本案 `auth.json` 里 `remember` 有值
   ⇒ 照搬等于把**已登录态**一起搬过去（N 天免密）——这是它比「一串哈希」更该按密钥对待的原因。
   ★ 顺手核一下「**出厂口令还在不在用**」：本案账号里 `mustChange: true`，而源码里只有「改过口令」才会置 false
   ⇒ 说明**口令至今仍是出厂默认值**，这既是「其实没必要搬账号文件」的理由，也是一条该报给用户的风险。


### 8.5 ★★ 把「开关类字段」也列进验收清单

配置里常有关掉/打开真实行为的开关（干跑 / 模拟 / 调试 / mock）。**照搬之后行为会跟着过去**，
而使用者以为自己在真跑。⇒ 在验收清单里**逐条点名确认**（本案：`publish.mock` 原机是 `true` = 干跑）。

### 8.6 换机验收（照做才算交接成功）

```bash
git rev-parse HEAD; git ls-remote origin refs/heads/main   # 两条一致 = 代码到位（唯一硬证据）
npm install && <原生/平台依赖的安装脚本>
node tools/<配置搬运工具>.js selftest                        # 先证工具本身没坏（不碰真配置）
node tools/<配置搬运工具>.js import <包>                      # 预演；看清它打算写什么
node tools/<配置搬运工具>.js import <包> --yes                # 真写（App 关着跑）
node tools/run-all.js                                      # 全绿
npx electron .                                             # 起界面、版本号对
```
+ 运行时配置逐条勾：**密钥在不在、机器实测数据在不在、路径对不对、机器标识是不是新生成的、开关是不是想要的状态**。
+ ★ 顺手确认**没照搬**那几类：同步游标文件（删掉重建）、设备/安装标识、本地缓存。
+ 设备类：`adb devices` 能列设备、输入法/驱动装好。
+ 收尾：**旧机上撤销不再需要的访问授权**（部署公钥/账号），清理传输用的中转文件（压缩包别留在下载目录/网盘）。
+ ★ 提醒对方：知识库是**快照**，里面的数字每次实测重取。

## 9. ★★ 二次交付：交接包已经做过一遍时，**先复核，别直接转交**

用户过几天又来说「我要交接了」——**你手里已经有一个交接包，但它可能已经错了**。
实测（同一项目，3 天后二次交付）：文档里 3 条事实已过期，且**没人会主动发现**：

| 类型 | 文档写的 | 实测 | 为什么危险 |
| --- | --- | --- | --- |
| **状态类** | 「本机已装副本仍是 1.0.13」 | 实际已升到 **1.0.15** | 交接文档本身就是权威 ⇒ 接手方照它判断「用户还在旧版、要不要催升级」 |
| **数字类** | 「150 文件 / 28 技能」 | **151 / 29** | 数字最容易腐烂（导出脚本改过、技能新增过） |
| **目录描述** | 「dist 里恰好 1 个 exe」 | 1 个 exe ＋ `win-unpacked/` ＋ yml | 读起来像「目录是干净的」 |

**复核清单（照做，每条留实测值）**：
1. `git rev-parse HEAD` **与** `git ls-remote origin refs/heads/main` 两值相等 ＋ `status --short` 干净。
2. **快照 vs 活文档**逐份 `md5sum`（或 `wc -c`）——**一致才叫没过期**；不一致 ⇒ 重跑导出脚本。
3. `find <工作区根> -maxdepth 1 -newermt "<导出时刻>"` —— 导出之后有没有新的交付文档/规则。
4. 文档里**每个可核数字**逐条实测。★ 「已装副本版本」别信文档，取**三重独立证据**：
   注册表 `Uninstall` 的 `DisplayVersion` ＋ `resources/app.asar` 内的 `package.json.version`
   ＋ `resources/<随包资源>/*` 的 md5。
   ★★ **两条实测被推翻的老做法**（2026-10-08 踩到）：
   - `grep -a -o '"version":"1\.0\.[0-9]*"' app.asar` **返回空**（asar 的头部/索引布局让这条匹配不上）
     ⇒ 用 `@electron/asar` 的 `extractFile(asar,'package.json')` 读，稳。同理**文件清单**要用
     `listPackage()`，别靠 grep。
   - **安装目录文件 `mtime` 不能当证据**：NSIS 会保留**源文件**时间戳 —— 本案 `app.asar` 的 mtime
     是**打包那一刻**，比真正安装的时刻早 13 分钟。只看 mtime 会推出「这是构建残骸」的错误结论。
   - ★ **安装路径可能根本不在 `%LOCALAPPDATA%\Programs`**（本案在 `D:\bluevbeta\<产品名>\`）。
     定位靠全盘找 `-name app.asar` / `-iname "*<产品名>*.exe"`，**别只查默认目录然后报「没装」**。
5. ★ **`git ls-remote` 会间歇性失败**（实测 `github.com:443` 报 `Connection was reset` /
   `Could not connect`，同一仓库几分钟前刚推成功过）⇒ 改走 **GitHub API 作为等价硬证据**：
   `GET /repos/<o>/<r>`（看 `private` / `default_branch`）+ `/git/ref/heads/main`（sha）
   ＋ `/commits/main`。凭据取 `~/.git-credentials` 里那条 PAT。
   ★ 但要在报告里**写清用的是哪条通道**，别把 API 的成功说成 ls-remote 的成功。
6. 对外通道 `curl` 一下发布的 `latest.yml` / `beta.yml`，版本与体积对不对得上。
7. **维护工具当场自测一次**（如 `selftest`）——「文档说它能用」≠ 它现在还能用。

⇒ 复核结果写成一页纸：**对得上的也列**（用户才知道你真核过），对不上的标 `❌` 给处置建议。
**不擅自改仓库文档后直接推送**——改文档要连带重新导出快照 + 提交，先问。
★ 一句话：**「交接包存在」≠「交接包是对的」。** 交接是一次性动作，交付物却是会腐烂的资产。

## 10. ★★ 接手方的工具本身没装 / 装不了（实测踩到）

§1 的三类分类只管**项目资产**，还漏一类：**接手方要用的那个工具（Codex / Claude CLI / IDE 插件）
在这台机器上到底存不存在、装不装得上。**

### 10.1 先查「装没装」（五处都查，缺一处就会误报）

```bash
command -v codex                                     # PATH
ls -d ~/.codex                                       # 官方配置目录
ls "$(npm root -g)" | grep -i codex                  # npm 全局
ls ~/.vscode/extensions ~/.cursor/extensions 2>/dev/null | grep -iE "codex|openai"   # IDE 扩展
reg query "HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall" /s /f "codex"   # 已装程序
```

★★ **查不到 ≠ 不存在**：装在 **WSL**、**别的 Windows 用户**、**便携解压目录**时上面全查不到。
⇒ 汇报必须带这句「我的查法有盲区」，否则就是在拿一个不成立的结论骗人。

★★ **桌面版 Codex 的指纹（2026-10-08 实测）**：`~/.codex/` 里有
`.desktop-created`、`.codex-global-state.json`、`auth.json`、`config.toml`、`skills/`、`plugins/`、
`installation_id`、`memories_1.sqlite`…；程序在 `%LOCALAPPDATA%\Codex\`，
CLI 在 `%LOCALAPPDATA%\OpenAI\Codex\bin\<hash>\codex.exe`。
⇒ ★ **PATH 里没有 `codex` 命令是正常的**（桌面版不挂 PATH）——**别据 `command -v codex` 空就报「没装」**。
进程名：`codex.exe` / `codex-windows-sandbox-service.exe` / `codex-computer-use-swift.exe`。
`config.toml` 里 `[windows] sandbox = "unelevated"` 等是它自己的沙箱设置，与项目无关。
★ **它在 `~/.codex/skills/` 也有一套技能**，但**它自动读的仓库入口是根目录的 `AGENTS.md`** —— 交接重点放那里。
★ 判断「装没装」时**先看 `~/.codex` 的 mtime**：本案 11:2x 那次复核报「没装」是对的（目录 11:23 才被创建），
   **16:xx 之后再报「没装」就错了** ⇒ 这类结论**有时效性**，二次交付必须重查。

### 10.2 再定「走哪条路」——**云端版与本地版的前提完全不同**

| | 本地（CLI / 桌面 App / IDE 扩展） | 云端（Codex Cloud，网页派活） |
| --- | --- | --- |
| 要 GitHub 吗 | **不要** | **必须要**（云端容器只拉 GitHub 仓库） |
| 看得见本机吗 | ✅ 全部 | ❌ 只有仓库里的 |
| 本机设备 / 模拟器 / 私密文件 | ✅ | ❌ |

★★ **远端在 gitee / 自建 Git / 内网的仓库，云端那条路直接走不通** ⇒
交接单开头就要写明「只能用装在这台机器上的本地版」。对这类项目反倒是好事：
发布链路依赖本机 adb + 模拟器 + 真机，云端本来就干不了。

### 10.3 ★ 装得上吗：本机可能**没有独立 Node**

AI 客户端（WorkBuddy 之类）把 Node 放在**自己的沙箱运行时目录**并挂进 PATH。
于是 `node`/`npm` 看着能用，但：**系统里没有** `C:\Program Files\nodejs`（用户自己的终端未必有 node）；
且在这套运行时里 `npm i -g <tool>` 会**装进客户端沙箱目录**，可能被清理 / 升级覆盖。

⇒ 给三条路（按稳妥排序），**别自己动手装**（改全局环境属外部动作，先问）：
1. `winget` / 官网装**独立 Node LTS**（注意工具的最低版本要求）→ 新终端 → `npm i -g <tool>`；
2. **官方独立二进制**（GitHub Releases 解压即用，不依赖 Node）；
3. 塞进客户端沙箱运行时 —— **不推荐**，写明理由。

★ 交接单里带「装完怎么验证」：`<tool> --version`（＋登录命令，如 `codex auth login`），
再 `cd <仓库>` 把第一条消息贴进去。
