# 跨项目工作偏好（用户级）

> 由多轮协作归纳出的硬要求，与具体项目无关；**项目专属规则写进各自项目的记忆**。
> 完整版（理由/实测数字）= `~/.workbuddy/REFERENCE-通用.md`。

## 诚实性（最高优先级）
- **绝不写假值**：取不到就说「取不到」/填 `—`；**未知 ≠ 0**。
- 认不出的东西不得当成「已确认不满足」。**不编造、不美化、不把猜测写成事实。**
- 汇报失败/降级要**明说**（例：「未迁移，功能已置灰」）；不许让界面骗人，也不许让结论骗人。

## 速度与准确度
- 「最快最准」= **快 = 减少无效耗时；准 = 不误杀本来有效的东西**（宁多花开销也绝不误杀；「为显快而丢数据」一律拒绝并说明）。

## 改动的证据标准
- 说「修好了」之前必须有**可复算的实测数字**（前后对比），不能只有推理。
- 测试要**双向**：喂「改前」的版本必须红，否则证明不了断言在查东西。
- ★ **反向验证的「假通过」坑**（全绿 ≠ 断言有效；**已记到 ⑮＋⑯⑰⑱**）：★⑮ **现象/夹具判据/修复/断言四者互为出处 ⇒ 可靠性=0**（2026-10-04 实测：照自己发明的夹具判据去"修"，把反斜杠写进了发出去的正文）⇒ 判据只能来自被测系统的逐条实验，**夹具里不许出现我没在真机上见过的判据**；① 备份顺序写反 ⇒ **必须先造坏版**再跑到红
  ② 环境变量选错 ③ 改前版抛异常 ⇒ **一条 FAIL 不打**（抠函数跑须 `try/catch` +「不许抛异常」断言）
  ④ 坏版只**追加**、没**替换**关键那句 ⑤ 定点破坏**锚点不唯一**（先过 `count==1`）
  ⑥ **一处缺陷多条防线 ⇒ 只拆一条假绿**（拆齐为止）⑦ **比较型断言两边取空 ⇒ 空==空 假通过**。
  ⇒ 造坏版后先自问「我改掉了哪条判断」。细节（含 ⑧⑨⑩）见 `REFERENCE-通用.md`。
- ★★ **破坏脚本「自己写的期望」也会错**：把「由**别的防线**满足的断言」当"该红" ⇒ 报**假 FAIL**（诊断：去坏版日志看那条是 PASS 还是 FAIL、证据串来自哪条防线）；**只「夹具放水」不改产品 ⇒ 红 0 条**、白做 ⇒ 必须**同一跑叠上「产品改坏」、判据反过来**（反向对照）；破坏面广会红一堆，**只看「我指的那条红没红」**。见技能 `bilateral-fix-verification` §3.4b。
- ★★★ **`restore()` 绝不等于 `git checkout -- <file>`**（会把**未提交的在制品**整片抹回 HEAD；实测丢过两个服务文件的全部当轮修复）⇒ 正确写法 = **跑前备份到临时目录、跑完 `cp` 还原**；破坏脚本一律**禁 `git checkout`**。
- ★ **自证新坑**：脚本崩在半路会把**坏版留在源码里** ⇒ `apply` 先全校验后落盘 + `check` 用 `try/finally` 兜还原；**逐条破坏前先 `restore` 回干净源码**（不还原 =「累计破坏」）；**跨行锚点遇 CRLF 匹配 0 次**；**断言数别凭记忆、每次实测**。
- 断言盯**语义**；**负向断言只看代码行**（先 `codeOnly()`，注释会一起命中）。
- 「源码里有这行字」≠「它真解决了问题」⇒ 关键修复做**行为级验证**（把真实代码块抠出来跑）。
- ★★ 验「幂等/防重」要喂**重复请求**看返回什么；**验「被拒绝」要配正向对照**（否则只测负向＝假通过）。已记到 ⑬⑭。
- 维护「通用测试基座」：把 `codeOnly()`/`count==1`/`try-catch` 做成**固定件**；**抽取清单别手工维护**（必然掉队 ⇒ 缺依赖 ⇒ **静默失效、整组假绿**）⇒ **自动求依赖闭包**；只把「**必须由测试控制**」的桩留在 `DENY` 白名单里。

## 记忆文件（上限是硬约束）
- ★★ **被自动注入的 MEMORY.md 是「上下文」，不是归档**：**超限即静默截断**。实测上限 —— **用户级 ≤ 4,000 字符/session**；**工作区级 `<工作区根>/.workbuddy/memory/MEMORY.md` ≤ 3,000 字符/session**。⇒ 索引只留「不遵守就出事」的祈使句 + `§N` 指针，**理由/常量/路径挪进 REFERENCE**；每写「见 §N」都要**回读 §N** 确认。见技能 `agent-memory-hygiene`。
- ★★ **记忆有两套，别写错地方**：**工作区级**（自动注入源）vs **项目级**（跟着代码走、可进仓库）⇒ 改一份必须同时改另一份。

## 会话与任务存储（客户端机制）
- **任务（todo）按会话隔离**（`~/.workbuddy/tasks/<sessionId>/`）⇒「队列里任务不见了」**先查磁盘**。
- **对话消息会丢** ⇒ 重要交办**落地成工作区文件**；用户说「消息不显示」时先列「我实际收到哪几条」核对。
- ★★ **「越用越卡、一卡消息就没了」= 会话记录文件太大**（`projects/<项目>/<sessionId>.jsonl`）⇒ 卡住瞬间消息写入被中断。**诊断** = 按大小排序 `projects/*.jsonl`；**对策 = 开新会话**（换工作区不管用），但先写**交接单**。
- ★ **报「卡」先分流**：① 量**资源** ② 量**读文件耗时**（实测 I/O 不是瓶颈）③ 问清「**卡在哪一步**」。见技能 `workbuddy-slowness-triage`。
- ★★ **界面「点不动 / 自动卡退」= 渲染进程崩溃 ⇒ 直奔 `~/.workbuddy/logs/Crash-Log/`，别量资源**：实测 23 条 `renderer_crash: reason=killed exitCode=1`（**去重 21 次** ⇒ **条数≠次数**）、无 OOM ⇒ **客户端缺陷、本机修不了**；必查 `logs/update/*.log` 的 `Update blocked by install dir guard`（**下完 100% 也装不上**）。
- ★ **清 `traces/`+旧 `logs/` 只回收磁盘，别当「提速」交付**。
- ★★ **给官方报缺陷走「设置 → 帮助与反馈 → 意见反馈」**（唯一内置通道）：正文框**仅 300 字符**、可传图 ≤10MB、「上传日志」**默认已勾** ⇒ **长内容渲染成 PNG 走图片通道**。见技能 `workbuddy-crash-report-submit`。
- ★★ **「整机卡机」但 CPU/内存/磁盘全宽松** ⇒ 查 Windows 事件日志 `ID 1000/1002` 找**周期性崩溃循环**（同一程序 24h 崩 N 次且**间隔恒定**）；内存吃紧看 **`PagesPerSec` + 页面文件用量**（§A）。
- ★★ **定时任务「合并」必补覆盖率**：`next_run = 完成时刻 + 55 分钟` ⇒ 合并后**实际间隔翻倍、覆盖率腰斩**；**合并前就要讲清**并让用户在「拉长单次 / 留 2 条错开 / 改常驻进程」里选（§B）。
- ★ **会话「消失」多半是列表被刷屏**（抽**首条 user 消息**当标题）；说「XX 不见了」**先按工作空间归类**。★★ **「看不见的并行会话」= 同盘其他工作区文件夹**（列表**按工作区过滤**）；定位按 **mtime 倒序 + 隔 1 分钟复采**，**别按文件大小排**。
- ★★ **`projects/<目录名>` 不可逆推工作区真实路径**（`-` 同时表示 `:` 和 `\`）⇒ 读 jsonl 每行的 **`cwd`**；**推不出来 ≠ 目录不存在，绝不写成结论**。
- ★ **接续/迁移前先 `git status` + 看关键文件 mtime**；**推没推都要有远端证据**（`git ls-remote origin`）；**交接 5 步**见 `REFERENCE-通用.md`。
- ★★ **「卡在等确认 / 结果收不到」都有现成开关**：结果推手机 = 定时任务 `push_to_wechat`；远程批准 = 多端协同（开「允许移动端连接此设备」+「允许锁屏运行」）。详见 §手机侧。

## 环境
- Windows 沙箱的命令/路径/编码坑见技能 `win-sandbox-scripting`。要点：**每次 Bash 都是新 shell** ⇒ PATH 必须**在同一条命令里** `export`；`timeout` 写 `/usr/bin/timeout`；Node/Python 用**全路径**。
- ★ **同一文件的多个 Edit 必须串行**（并行发只剩最后一个生效，且 Edit 仍返回成功）⇒ 改完立刻读文件 / 跑测试验证。
- ★ 脚本一律**先落盘再跑**（`python -c` 的反引号会被 bash 吃掉）；**任何反斜杆**（含注释/docstring）都踩 unicode 转义坑 ⇒ 用 `r'''`。
