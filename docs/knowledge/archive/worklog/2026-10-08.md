### ④ 为什么日志里会出现 `fetch failed · ENOTFOUND …`（2026-10-08 四类实测）
- 机制：Node 的 `fetch` 在 DNS/TCP 层失败时只给 `TypeError: fetch failed`，真原因在 **`e.cause`**（undici 可能再嵌一层，故 `describeErr` 往下扒 ≤3 层）。**前半＝Node 给的，后半＝我们补的**。
- `ENOTFOUND` = libc `getaddrinfo` 的「域名查不到 IP」⇒ **请求根本没发出去**，与云端无关。
- 出现两次（`ENOTFOUND … getaddrinfo ENOTFOUND host`）是 `code + message` 拼接所致，非重复 bug。
- 实测四类（同一 Node，真跑）：
  | 故障 | e.message | e.cause.code | describeErr 输出 |
  |---|---|---|---|
  | 域名不存在 | fetch failed | ENOTFOUND | fetch failed · ENOTFOUND getaddrinfo ENOTFOUND host |
  | 高位端口无监听 | fetch failed | ECONNREFUSED | fetch failed · ECONNREFUSED connect ECONNREFUSED ip:port |
  | 端口 9（undici 黑名单） | fetch failed | (无) / msg=`bad port` | fetch failed · bad port |
  | 3s 超时 | The operation was aborted due to timeout | 无 cause（e.name=TimeoutError） | 同 message |
- ★ 教训：想测「连接被拒」**不能用 127.0.0.1:9**（undici 把 1/7/9… 列进 blocked ports，报 `bad port` 而非 ECONNREFUSED）⇒ 用**高位无监听端口**（实测 58999）。
- 与本文档上一条「我演示误插 2 条」的关系：那条 ENOTFOUND 演示里的域名 `no-such-host-…invalid` 是**我编的**（`.invalid` 永不可解析）⇒ 必然 ENOTFOUND，**不是你机器的真实故障记录**。
- 真机 ENOTFOUND 的**推断**来源（未单独实测）：TUN/fake-IP 下解析由 `FlClashCore` 提供，进程不在/重启/切节点空窗 ⇒ 无人应答。**实测到的**只有：fake-IP 解析到 `28.0.0.x`、代理在时 GET 24/24＋POST 12/12 全绿。
- 本次链路状态：只读 GET（带 anon apikey）= **HTTP 200 / 1425ms** ⇒ 此刻代理是活的。
