## ★★ 查实一个会反复踩的沙箱坑：**大目录删不掉（safe-delete fail-closed）**

现象：`electron-builder` 打回默认 `dist/` 时**整个打包中断** ——
`remove D:\...\dist\win-unpacked\chrome_100_percent.pak: Access is denied`。

**一开始的两个猜想都是错的**，别再用：
- ❌「有实例在跑占用了文件」—— 查过，**没有进程**；
- ❌「沙箱不许动 D 盘上的文件」—— 同一个路径上 **Python 改名 / 删除单个文件都成功**。

**真正原因**（Python 直接把沙箱日志带出来了）：
沙箱把删除**重定向到回收站**，这棵目录树（约 220 MB / 19 文件）回收站放不下 ⇒
`SHFileOperationW 失败: 0x78 = ERROR_CANCELLED` ⇒ 沙箱 **fail-closed，宁可不删**。

| 谁去删 | 报什么 |
|---|---|
| Python `shutil.rmtree` | 异常的 message 是空的，但沙箱日志吐 `[safe-delete][SAFE_DELETE_FAIL_CLOSED] … SHFileOperationW 失败: 0x78` |
| coreutils `mv <目录> <新名>` | `Permission denied` |
| PowerShell `Remove-Item -Recurse -Force` | **无输出、退出码 0，目录原封不动**（最坑：看着像成功） |
| `app-builder.exe`（electron-builder 内部） | `Access is denied` ⇒ 打包中断 |

**判据（一秒分流）**：先确认无进程占用；再试删目录里一个无关**小文件** ——
**小文件能删、整棵目录删不掉 ⇒ 就是这条**。
**对策**：**别清旧目录，直接换输出目录**（`-c.directories.output=<新目录>`，再把 exe/blockmap/latest.yml 搬回约定位置）。
已写进技能 `win-sandbox-scripting` §3.0（并更正了那一节原文「报错可忽略」的说法）与工作区 `发版流程SOP.md` 第 3 条。

## 架构咨询：转网页版 vs 继续做 App（用户提出，我出判断，**未拍板**）

用户场景：50 款 × 150 篇 = **7500 条**发得物穿搭精选，素材已按款分好，多人协作。
用户四个判断：①网页更方便 ②app 收不到别人日志（web 靠 supabase 能）③app 接 supabase 有风险 ④app 发布比 web 慢。

**我的结论（交付 `得物蓝V-网页版vsapp-架构判断.md`）**：

- ★★ **不是二选一。发布核心只能跑本机** —— 浏览器沙箱**无法启动/调用本机进程** ⇒ 调不动 `adb.exe`、驱动不了 MuMu。这是死结。
  ⇒ **「纯网页版发布器」不存在**。唯一「纯网页」路线＝服务器模拟器农场（素材上传 + N 账号集中一机一 IP ⇒ 得物风控风险升高），除非 24h 无人值守，不划算。
- ★★ **推荐＝本机执行端（保留现有 App，做薄）+ 云端协作台（新增网页 + Supabase）**；
  两条链路：浏览器↔执行端走 `127.0.0.1` WebSocket（**必须配对码授权**，否则任意网页都能控本机模拟器）；两边↔Supabase（浏览器 anon+RLS／执行端**机器令牌**）。
- ★★ **纠正一条归因**：「收不到别人日志」**不是 App 形态的锅，是台账=本机 jsonl 这个数据层设计**（`HANDOFF.md:407-408` 白纸黑字：跨机汇总只能靠共享盘）。换云→现有 App 一样能实时收。
- ★★ **纠正一条误判（重要）**：发布耗时 **93% 是在等人为间隔**（`publisher.js` 文件头注释原话「2.5 小时里 93% 是在等间隔」；`store.js:60 intervalSec: 60`）⇒ **换网页一秒都不会快**。
  速度只由**并行设备数**决定：7500 条 ≈ 单机 125h / 5 台 25h / 10 台 12.5h / 20 台 6.3h。
- ★★ **Supabase 风险的正确解法**＝anon key + RLS（浏览器原生用法）；红线只有一条：**任何客户端都不许内置 `service_role`**。
- ★★ **不要重写发布核心**（`adb.js`/`uimap.js`/`publisher.js`，有 768 项断言在守）—— 重写＝把踩过的坑再踩一遍；执行端只「做薄 + 加对外接口」。
- 落地顺序：阶段0 先**实测**一条发布真实耗时（未实测，已在文档 §7 诚实标注）→ 阶段1 **只读看板**（性价比最高，不动发布核心）→ 阶段2 派活+实时日志+权限上云 → 阶段3 收口。
