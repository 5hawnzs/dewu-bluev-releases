按 [PRD](https://c325414b53f748618ec865de0d865c08.app.workbuddy.host/#prd) 与原型页实现的 Electron 桌面应用，
面向 **Windows 10/11 x64**，把「素材整理 → 合规检查 → 文案生成 → 货号颜色校验 → 发布单 → 模拟器发布」六段流水线做成一个人当天能跑完的工具。

```bat
npm install            :: 首次，会拉 Electron（国内可先 set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/）
npm start              :: 本机运行（macOS/Linux 也能跑，用于开发自测）

:: 在任意平台打出 Windows 包（会先把 win32 预编译的 sharp 取下来，再交给 electron-builder）
npm run dist:win
```

## 模块实现说明

> 以下规则已按 8/12 那场真机演示录屏（15:44，118 帧关键帧 OCR）对齐到现有工具的实际口径。
> **交接与真机口径见 [`docs/HANDOFF.md`](docs/HANDOFF.md)**：里面有真机界面文案原文、判定口径、命名样例、
> 发布日志原文、差异总表、待办与回归要求；逐帧 OCR 证据见 `docs/video-ocr-118frames.txt`。

1. **素材整理** — 先秒级出「待整理清单」（只读元数据），再后台建扁平副本。
   扁平名用连接符（默认 `_`）把原层级路径接起来（真机：`8124MT_UWG450159+灰色+达人昵称_1`）；
   **原素材完全不动** —— 不改名、不移动，只建副本（`flatten.touchOriginal` 可切回「改名加时间戳」）。
2. **合规检查** — 判断与处理分离：扫描出报告后只处理有问题的那批。规则对齐真机：
   图片**必须 JPG**、**≥1764 像素²（约 42×42）**、边长 **150~1500**、超限**自动等比缩放**（`autoScale`）、超 10MB 二分压缩；
   视频**必须 `.mp4`**（`.mov`/`.m4v` 等会**自动转成 mp4**，见「依赖状态」）且 <600 秒，超时**只标红不裁剪**（裁剪会改变内容，可能被判非原创）；
   垃圾文件隔离到 `_rejected` 而非删除。另外支持真机的**「检查父目录」**：选一个父目录，里面每个子文件夹独立出报告并分组展示。
3. **文案生成** — 本地先定死每篇的标题格式（F01–F10 轮换）/ 叙事视角 / 话题组合（代码保证去重），模型只填空；并发按**路数均分**（不是「15 条/批」切批，避免尾批拖慢）；结构化输出容错解析（markdown 代码块、中文标点、多余逗号），单条重试不整批失败。未配置模型时用本地模板填空，流程一致。

   **人设提示词按品牌走**（2026-10-01 新增）：送进模型的 system 由两段拼成 —— **前段是品牌自己的「文案生成提示词」**（人设、口吻、卖点），**后段是程序追加的输出约束**（JSON 字段名 `title`/`body`、字数与极限词要求）。
   顺序不能反：后段是解析器依赖的硬约束，被品牌模板覆盖掉会导致整批 `JSON.parse` 失败，而现象看着像「模型不听话」。
   **没配提示词的品牌会被拦下**（拦在任务实例化之前，不写台账），不会拿别的品牌的口吻顶替，也不会静默回落到内置默认人设。
   入口是「文案生成 → 提示词配置」按钮弹出的弹窗（品牌名 / 两段提示词 / 是否启用 / 本次选用），详见下方「按品牌的文案提示词」一节。
4. **货号颜色校验** — 两种取色来源：本地商品池（CSV/TSV/JSON 导入）或**接口查询**（`verify.mode=api`，自带 endpoint + SKU APIKey）。
   判定文案对齐真机：「颜色匹配」/「**单色货号，颜色可空**」/「**多色货号须指定颜色（共 N 色：…）**」/「**货号 xxx 未查到颜色信息，请核对**」。
   额外用图片实际提出的主色反查目录里填的色名（目录写「冠军白」但图是黑的会被抓出来）。
   ★ **2026-10-02 起：颜色校验不是发布流程的必需项** —— 只有「**多色货号没填颜色**」会拦住发布；
   「商品池/接口查不到货号」和「颜色不匹配 / 主色不符」**都只告警、照常发布**（结论列里写清原因）。
   没校验过、或颜色填错了，发布端按你填的**货号**在「关联好物」里搜出结果后**默认选第一件商品**发出去。
   出厂**一条示例货号都没有**（空池），必须自己导入商品池或配接口 —— 以前那 5 条假货号已删。
   > 录屏里出现的 `dw.shike.tech/sku-color` 只是**别人的示例后台**，本工具不访问、不抓取它；要用它的导出表，按 CSV/JSON 导入即可。
5. **发布单** — exceljs 导出 26 列，校验未通过的整行标红；结果先追加写 `publish-log.jsonl`，
   一批结束再合并回写 Excel。**回写时若 Excel 被 WPS 占用，整批结果写入 `pending-results.json` 暂存，下次运行先补写再继续**
   （真机日志原话：「Excel 仍被占用，暂存保留，下次再试」）。
6. **模拟器发布** — 60–120 秒随机间隔（可配），失败可单独重跑。

   **两条通道，状态在界面上一眼可见**（发布页顶部会显示「真实设备通道 / 模拟通道」）：

   | | 真实通道（adb） | 模拟通道（mock） |
   | --- | --- | --- |
   | 触发条件 | 找得到 `adb`（**程序内置**，或系统 PATH 里；「设置 → 高级设置 → adb 路径」填了就以你填的为准）、设备在线、得物包名识别到、uiautomator 可用 | 上述任一不满足 |
   | 做什么 | 推图到 `/sdcard/DCIM/Camera` + 触发媒体扫描 → `uiautomator dump` 抓界面 → 按定位表点击/输入 | 只跑流程：节奏、重试、jsonl 追加、Excel 回写 |
   | 失败 | 报真原因（找不到节点会列出当前可见文本）+ 自动存失败截图 | 随机失败，仅用于演练 |

   **真实通道必须先配 UI 定位表**：先把模拟器**停在得物发布页** —— 得物 App 首页**右上角那个相机图标**
   （`com.shizhuang.duapp:id/ivCamera`，**没有文字**）点进去就是，页面是
   `media.publish.activity.TotalPublishProcessActivity`，首屏是**选素材的相册**（顶部有 全部/照片/视频 三个页签）。
   → 「设置 → 高级设置 → 抓取页面结构」会 dump **当前这一屏** → 输出目录 `dumps/uiMap-<时间>.json`
   （按关键词猜的一套候选步骤，含 `${title}` `${body}` `${topic1..5}` `${sku}` 占位符）→ 改对后「导入 UI 定位表」。
   没配就点发布会**直接报错而不是报成功**。
   ★ 抓之前程序会先读「你现在停在哪一屏」并显示出来：停在**别的 App** 上会被拦下（那时抓出来的是桌面，表毫无意义）；
   停在得物但**不是发布页**只告警 —— 「填标题」「搜货号」这些后续屏本来也可能要抓。

   中文标题/正文依赖设备装了 [ADBKeyboard](https://github.com/senzhk/ADBKeyBoard)（走 `ADB_INPUT_TEXT` 广播）；
   没装的话自检会明确提示，输入会失败而不是静默发空文案。

   另外三项也按真机对齐：
   - **设备管理（一个设备 = 一个账号）**：多台模拟器列表（每个模拟器对应一个账号，名字自己起，如「主号」「小号」）。★ **点「扫描设备」会把 adb 现在认到的设备直接列出来**（含还没加进来的），点那一行的「**加入并使用**」即可 —— 你不用知道那串设备名是什么，也不用自己抄序列号；手动添加 / 删除 / 选用仍在（手动填序列号收进了折叠区）；
   - **固定间隔 + 倒计时**：默认 60 秒，等待时显示「`按 60 秒间隔，57s 后执行`」，而不是静默等待；
   - **单条耗时与失败恢复**：每条记 `耗时 65.2s` 写进日志/表格；失败自动存截图并执行**回退**（返回键 + `uiMap.recover` 里配的「删除卡片」等动作），避免下一条起点被残留界面污染。
7. **多批次任务 · 报告导出 · 失败恢复动作**（对齐真机的任务列表 / 导出报告 / 重导出日志）：
   - **多批次并行**：任务实例化（每个 job 独立 id / 取消令牌 / 进度 / 日志标签），`copy.generate` 是批次级 ——
     点「选择素材目录并启动任务」，一个目录就是一个批次，可同时「处理中」；批次名形如 `7月第六批(已安排)_20260812_151245`。
     产物各写 `输出目录/batches/<批次>/copy.json`，互不覆盖。文案生成页与模拟器发布页都有「运行中的批次」表格：
     批次名 · 进度 · 已用时 · **查看详情**（按批次筛出该批次这一步的日志）/ **取消任务** / **全部取消**。
     取消是「当前步骤结束后停下」，不丢已产出的结果；被取消的任务统一报「任务已取消」，不会拿别的报错冒充。
   - **导出报告**（合规页）：`合规报告_<时间戳>.xlsx`（`汇总` 按子文件夹 + `明细` 全量）+ 同名 `.csv`（带 BOM），导出后自动定位文件。
   - **重导出日志**（发布页）：把 `publish-log.jsonl` 按批次导成可读的 `发布日志_<批次>_<时间戳>.log` 与 `.csv`，
     行格式对齐真机：`[V] 行 2 [图文] 发布完成，已回填时间 15:34:41（耗时 65.2s）`、`[X] 行 3 失败：找不到发布按钮（耗时 61.9s）`。
   - **失败恢复动作可编辑**（「设置 → 高级设置 → 失败恢复动作」）：发布失败后要退回干净起点，否则下一条的界面会被残留页面污染。
     真机是「回退转发页」「删除卡片」这类动作，每个账号/版本都不一样，所以做成文本框可编辑（默认给一条示例，不用猜格式）。
     只认真正会被执行的 `tapText / tapId / tapDesc / wait`（返回键回退时本来就会先按，不用写）；
     写错 action、value 为空、wait 不是毫秒数，都会**报错并列出可用值**，不静默跳过 —— 跳过等于「以为回退了，其实没有」。
   - **导入「AI 内容报告」**（发布单页「导入 AI 内容报告」）：真机那条流水线的中间产物 —— 26 列 xlsx，
     `素材路径 / 素材来源 / 标题 / 文案 / 内容类型 / 好物1~9_货号+颜色`。按**列名**识别（列顺序无关，
     他们的报告和我们导出的发布单都能吃）；素材路径是**绝对路径**（如 `D:\你的素材目录\20260901`），
     表里没写就追问一次「这一批的素材目录」。**一个叶子文件夹 = 一条内容**，行数与叶子数不等会直接报错并说明，
     绝不猜着配；标题/文案空着由本地生成；发布结果回写报告的 **B 实际执行时间 / C 执行结果**两列
     （被 WPS 占用就整批暂存、下次导入或发布时先补写）。

## 视频发布（当前卡点，2026-10-01 实测定性）

**先说结论**：代码链路是通的，但**今天在真实设备上发不出视频** —— 卡住的地方不是「坐标还没量」，
而是 ★ **推上去的视频进不了手机的相册**（于是得物的「选素材」页里根本没东西可选）。
**点击本身是好的** —— 复测已经证实（见下）。

**为什么视频和图片不是「差不多」**（对着这条认知纠正一下）：

| | 图片 | 视频 |
| --- | --- | --- |
| 界面 | 发布页一套 `steps` | **完全是另一套界面** ⇒ `uiMap.videoSteps` 要单独抓，图文那套套不上（没配就当场失败，不硬套） |
| 推素材 | 推到 `DCIM/Camera` 就能用（系统自己的后台扫描会收进去） | ★ **推完进不了相册** —— 三条扫描路径实测全断，只有重启模拟器有效（见下表） |
| 点选素材 | 能点 ✓（实测：点一行里的格子 → 进入预览页、出现「下一步」） | **也能点 ✓**（实测：点 `(87,255)` → 截图 md5 确实变了）—— **所以卡点不在这** |
| 节奏 | 60s 间隔 | 90s 间隔（推得久 + 等索引） |
| 封面 | 无 | 用**得物默认推荐**的（不点封面区、不上传封面图）—— 这一步本身**不是**卡点 |

**真正的卡点：推上去的视频进不了相册**（实测 MuMu 12 / Android 12，900×1600）

| 办法 | 实测结果 |
| --- | --- |
| `MEDIA_MOUNTED` 广播 | ✗ `SecurityException` —— 它已是**受保护广播**，shell 用户（uid=2000）**发不出去** |
| `MEDIA_SCANNER_SCAN_FILE` 广播 | ✗ 返回 `Broadcast completed: result=0`（看着像成功），但**等 20 秒后媒体库里仍然查不到** —— 不是慢，是**没有接收者** |
| `content insert` 直写媒体库 | ✗ 静默失败 —— shell 不在 `media_rw` 组 |
| **重启模拟器** | ✓ **唯一确认有效**：重启后 `bluev_t.mp4` 出现在媒体库（`_id=68`） |

所以代码里 `adb.mediaScan()` 那两条广播在这台设备上**都不生效**（保留着：换设备/系统版本可能仍有效）。

> ★ **更正一条旧结论**：以前记的是「相册缩略图块 adb 点不动（9 种注入方式截图 md5 一字不差）」——
> **不成立**。2026-10-01 复测：视频进媒体库后，缩略图在 **(87,255)**、174×174、上面带播放图标和 `0:03`，
> 点它之后**截图 md5 确实变了**（`dc968252…` → `9cc3bc28…`）。
> 以前"怎么点都没反应"是因为**相册里根本没有素材**（点在空白处），
> 而且 `(88,358)` 是**图片布局**的坐标 —— 发布页有**两种布局**，写死一个坐标必然点空。

**已经就绪的部分**：推视频、媒体库轮询、`videoSteps` 机制、`videoNote`、图文/视频分辨率的语义判定
（报告「内容类型」列为准；两边都有又没标就判「校验未通过」，**绝不猜着发**）、节奏参数 —— 这些都做完并有断言守着。
缺的只有「在真实设备上把素材选中」那一下。

**出路**（都还没验证，按可行性排序）：

1. ★ **发布前自动重启一次模拟器**（让系统重扫相册）—— 已知唯一确定有效，代价是几十秒；

### 文案提示词（2026-10-01 新增）

原先「设置 → 内容与校验」里有 `copy.promptWrite` / `copy.promptFilter` 两个全局输入框，它们
**从来没被任何代码读过** —— 填了不生效。这就是「点了提示词配置看不懂」的根源：界面在骗人。

现在改成按品牌各配一份，而且**真的进模型**：

- **入口**：「文案生成」页的「提示词配置」按钮，或「设置 → 内容与校验」里那个按钮 —— 点开是个弹窗（不是跳页）。
- **弹窗列表里**：每个品牌一行（品牌名 / 启用状态 / 配没配 / 摘要），右侧**三个按钮**：
  **「配置」**（进去改提示词）、**「选择」**（本次用它 —— 只改内存里的当前品牌，**不落盘**，重启回到默认）、
  **「默认选择」**（写进 `config.json` 的 `copy.defaultBrandId`，以后每次打开都是它）。
  行里的「本次」「默认」两个小标就是当前状态。
  > 这两个按钮**必须不是同一件事**：点「选择」不写配置、点「默认选择」才写。回归里专门有断言盯着 ——
  > 把「选择」也做成落盘的，断言会红。
- **点「配置」进去**编辑：**品牌名**、**文案生成提示词**、**筛选排序提示词**、**是否启用该品牌**、**本次选用**。
- **拼装顺序**：品牌模板放在 system 的**开头**（角色、调性、写什么）；JSON 字段名、标题字数上限这些
  **解析器依赖的硬约束由程序追加在后面**，不用写进模板 —— 漏写一句就会让整批 `JSON.parse` 失败，
  而现象看起来像「模型不听话」。
- **没配就拦下**：拦两道 —— `jobs.run` 在任务实例化之前拦（不写台账），`copywriter.generate` 里再兜一道
  （防有人直接 require 模块调用）。没有品牌归属的场合（免登录自检 / 测试直调）不套这一层。
- ⚠️ 如实说：「筛选排序提示词」**当前版本还没接进任何流程**（工具里没有素材筛选 / 排序这一步），
  只是先按品牌存着。弹窗里也这么标着 —— 别以为配了就有效果。
- 单条提示词上限 **4000 字**（粘贴超长内容会截断而不是整条保存失败）；`\r\n` 会归一成 `\n`。

## 应用更新（自动更新 · 正式版 / 测试版两条通道）

装好的**安装版**（`…-x64-win.exe`）启动约 20 秒后会自己查一次更新源。发现新版本会告诉你，但
**不会自己下载、更不会自己重启** —— 这两步都要你在「设置 → 应用更新」里点。

| 项 | 说明 |
| --- | --- |
| 更新源 | 腾讯云 COS 的**桶根目录**（地址在 `package.json` 的 `build.publish`，**编译进包**） |
| 通道 | **正式版 / 测试版两条，共用同一个安装包**。通道名只决定读源上哪个清单文件：正式版读 `latest.yml`、测试版读 `beta.yml` |
| 怎么切 | 「设置 → 应用更新 → 更新通道」点一下，**不用重装**（源地址不变，只是换个文件名去读）。偏好存在 `config.json` 的 `update.channel`，重启后仍然生效 |
| 谁能切 | ★ **只有管理员**。普通成员在设置页**看不到任何「测试版」字样**（连那句说明都不显示），直接调 `update:set-channel('beta')` 也会被主进程拦下。更要紧的一条：管理员切到测试版之后，**换普通成员登录会自动收回并落盘** —— 否则那个人会一直收测试包，而他连那个按钮都看不见，没法自救 |
| 检查时机 | 启动后约 20 秒自检**一次**（不是定时轮询），以及手动点「检查更新」 |
| 下载 | **手动**。包有 108.7 MB（1.0.3 实测 113982650 B），不替用户决定占带宽 |
| 安装 | **手动**；而且**有任务在跑时会拦住** —— 重启会把跑一半的发布掐断，且没有回滚 |
| 不支持的情况 | **开发模式**（`npm start`）不检查；**如果哪天又产出便携版，它也装不了**（每次启动自解压到临时目录，没法就地替换）。这些情况「应用更新」一栏会**如实写不可用**，不摆点了没反应的按钮 |
| 更新日志 | **默认关闭**，设置页一键开（偏好存 `config.json` 的 `update.log`）。开着时会把 electron-updater **自己的日志**一并收进 `%APPDATA%\…\logs\update.log`。★ 为什么值得开：这条链上最坑的失败是**静默**的 —— 差分下载失败会**悄悄退回全量**（进度条照样走完，只是慢），而那条 error 只从 updater 的 logger 出来（原先把 `up.logger` 写死 `null`，等于把它一起吞了）。日志里只有版本号、通道名与字节数，**不含**素材/品牌/SKU；超过 2 MB 自动轮转为 `.1`，不会无限长大 |
| 换源地址的代价 | 地址编译进包 ⇒ 改了等于所有已装客户端全部失联，只能重发一次包。★ **但切通道不受影响** —— 通道名不是地址 |

> ★★ **「换源地址」和「切通道」是两件事，别混**：
> 源地址编译在 `resources/app-update.yml` 里，运行时**改不了也不许改**（electron-updater 官方就不给 `setFeedURL`）；
> 而**通道名**只决定「读哪个清单文件」，electron-updater 有公开的 `set channel()` 支持运行时改。
> ⇒ 测试版是**显式 opt-in**：正式版用户读的一直是 `latest.yml`，不会被测试包波及 ——
> 换句话说，**正式版通道里永远不会出现测试版的版本号**。唯一能让它出现的，是有人手滑用正式通道发了
> 一个预发布版本（`1.0.1-beta.1`）—— 这一种现在被 `channelMismatch` 闸门拦住了（见下面的「发版流程」）。
>
> ★ **关于降级**（从测试版切回正式版会用到）：正式版的版本号本来就更小，所以
> 「测试版 → 正式版」那一次会**允许降级**（否则切了也回不去）；反过来**不允许** ——
> 平时一直开着降级的话，源上被人放个旧包，正式版用户就会被**悄悄降下去**。

### 发版流程（打包机上）

```bash
# 1) 先改 package.json 的 version
#    不涨版本号会「同名覆盖」，而且 electron-updater 按版本号比较，客户端会直接判「没有新版本」
#    测试版的版本号建议带预发布段，例如 1.0.1-beta.1 —— 这样「换成正式版 1.0.1」算升级而不是降级
# 2) 发正式版：
npm run dist:release
#    发测试版（同一个包，只是把清单传成 beta.yml）：
npm run dist:release:beta
```

`dist:release` = 打包（`dist:win`）+ 上传（`release:stable`）；`dist:release:beta` = 打包 + `release:beta`。
上传的东西是 electron-builder **不会代传**的那三样：安装包 exe、清单文件、`.blockmap`
（generic 提供者必须自己上传，漏了就是「包打了但客户端永远收不到」）。

**两条通道的文件放在同一个目录**，只有清单文件的名字不同：正式版 `latest.yml`、测试版 `beta.yml`。

#### 老包怎么清（发得多了源上会堆一堆 88 MB）

产物名字里带版本号，所以**每次发版天然新增一个约 88 MB 的文件**；上传脚本只有「上传」能力、
桶上也没有生命周期规则 ⇒ 老包只增不减（实测 4 个 exe 合计 343 MB）。

```bash
npm run release:prune          # 只看：要删哪些、腾多少（**默认就是 dry-run，一个字节都不删**）
npm run release:prune:apply    # 确认名单没问题后再真删
npm run release:prune -- --keep-more=2   # 每条通道多留几个历史版本
```

保留策略：每条通道各留「**当前版本 + 1 个可回滚的历史版本**」（`--keep-more=N` 可调），
`latest.yml` / `beta.yml` 与认不出名字的对象**永远保留**。

★ **故意不做「同名覆盖」**（那个人人都会先想到的方案）：正式通道允许降级 ——
用户从测试版切回正式版靠它、出事回退也靠它，老包被覆盖就**回不去**了；
而且「哪次更新对应哪个包」这条审计线索也会一起消失。

★ 三条 **fail-closed** 闸门（源上状态不明时宁可什么都不动，也不误删）：
① 读不到 `latest.yml` ⇒ **一个字节都不删**；
② 比当前版本**还新**的包（多半是「包传上去了、清单没传成」）⇒ 保留，先查清楚；
③ 认不出版本号的对象 ⇒ 一律保留。
另外版本号解析**故意做得窄**（只认 `…-<版本>-x64-win.exe` 这个形状）——
通杀型 semver 正则会以为 `1.0.1-x64-win.exe` 的版本是 `1.0.1-x64`（`x64` 本身是个合法的预发布段），
读错版本的后果是**删错包**，所以宁可认不出来。删完还会逐个 HEAD 复核「保留名单里的包一个都没少」。

> ⚠️ 发版脚本的 `--channel` **两种写法都支持**（`--channel beta` 与 `--channel=beta`）。
> 这一条有专门的断言守着 —— 只认空格写法的话，`--channel=beta` 会被**静默**忽略、退回 `stable`，
> 等于把**测试版包推给所有正式用户**。

客户端按自己的通道去读对应的那份 —— 所以正式版和测试版可以**同时存在**，互不干扰。

**源上当前状态**（2026-10-02 从公网实测）：正式版 `latest.yml` = **`1.0.3`**、测试版 `beta.yml` = **`1.0.1-beta.2`**。
`1.0.3` 相对 `1.0.2` 的变化：登录页**窗口＝卡片**（去掉卡片外面那圈底色 —— 就是反馈了三次的「黑边框 / 色块」，并治好白底白字）、**视频复用图文定位表**（不用再单独抓视频页）、删掉 `connect()` 的假序列号兜底；

### 装完之后怎么验收（这一步只能在你的机器上做）

★ **为什么打包机上做不了**：打包机只有 `dist/win-unpacked/` 这个**绿色解包目录**，
自动更新只对**装出来的安装版**生效（解包目录跑起来判定就是「未打包」，更新面板会如实写不可用）。
所以「真的能更新」这件事，必须在**装过一次的机器**上验。

```bash
# ① 在打包机上把当前版本发到源上（桶为空时尤其要做，否则客户端点检查更新是 404）
npm run dist:release            # 正式版；dist 已有包时也可只跑 npm run release:stable

# ② 在验收机上装一次，双击刚生成的安装包
#    dist\得物蓝V素材发布工具-1.0.0-x64-win.exe
#    安装器是「按用户安装 + 可改目录」，不需要管理员；卸载不删 %APPDATA% 里的数据

# ③ 打开应用 → 设置 → 应用更新，应当看到：
#    当前版本 1.0.0 · 通道「正式版」 · 状态「未检查」

# ④ 回打包机，改 package.json 的 version 成 1.0.1，再发一次
npm run dist:release

# ⑤ 回验收机，点「检查更新」→ 出现「有新版本 1.0.1」→ 点「下载更新」→ 进度条走完
#    → 点「立即安装并重启」→ 重启后「当前版本」应当真的变成 1.0.1
```

判据就一条：**重启后「当前版本」这个数字真的变了**。数字没变 = 这条链没通，
按顺序查三处：`dist/win-unpacked/resources/app-update.yml` 的 `url`、源上 `latest.yml` 里的 `path`、
以及应用里「应用更新」栏给出的**具体报错文案**（这一栏不会只显示「已是最新」了事）。

> - ⚠️ **版本号不涨 = 什么都没发生**。electron-updater 是按版本号比较的，源上放个同版本号的新包，
>   客户端只会判「没有新版本」——这是最容易把人骗过去的一种假成功。
> - ⚠️ **别拿解包目录（`win-unpacked\*.exe`）当验收对象**，它永远说「不可用」。
> - ℹ️ 验收测试版那条通道：验收机上先点「更新通道 → 测试版」，再按上面 ④⑤ 走，只是第 ④ 步改成
>   `npm run dist:release:beta`（版本号建议写成 `1.0.1-beta.1`）。

## 依赖状态

- 图片引擎：优先 `sharp`（支持 HEIC、libvips 多核）；原生模块加载失败时自动降级为纯 JS 引擎（`jpeg-js` + `pngjs`），降级状态显示在「设置 → 外部依赖」。sharp 是 N-API 预编译包，**不需要 electron-rebuild**。
- 视频时长：纯 JS 解析 MP4/MOV 的 `moov → mvhd`，不需要 ffmpeg。
- **视频转 MP4（2026-10-02 起：ffmpeg 随包内置）** —— 得物**只收 mp4**，所以 `.mov` / `.m4v` / `.avi` / `.webm` / `.mkv`
  会被**自动转成 `.mp4`**。转换服务在 `src/main/services/video.js`，策略是**先无损转封装、再转码兜底**：
  先用 `-c copy` 只换容器（H.264/HEVC 这类 mp4 放得下的编码，**秒级完成、画质零损失**）；
  容器/编码放不下（如 ProRes）才用 `libx264 + aac` **转码**。转完会**解析产物**核对
  （ftyp 品牌属于 mp4 家族、`moov` 可读、视频轨编码在白名单里）—— 不合格就**如实报错**，绝不假装转好了。
  合规检查（`src/main/services/compliance.js`）判完这么处理：

  | 情况 | 判定 | 会被自动处理吗 |
  | --- | --- | --- |
  | `.mp4` 且 ≤ 600 秒 | 合格 | — |
  | 不是 `.mp4`（`.mov`/`.m4v`/`.avi`/`.webm`/`.mkv` 等） | 「转 MP4」，`status: todo` | **会**。`fix()` 真的转，转完改名成 `.mp4` |
  | 不是 `.mp4` **且找不到 ffmpeg** | 「需手动转 MP4」，`status: manual` | **不会**。只提示（正常装了本程序不会走到这里） |
  | 时长读不出来（moov 缺失 / 编码不支持） | 「人工确认」 | **不会** |
  | > 600 秒 | 「只标红不裁剪」（裁剪会改变内容） | **不会**（转成 mp4 也过不了，所以不去白转一次） |

  ★ 注意这个**顺序**：先判时长、再决定转不转 —— 已经超上限的片子不会被白转一遍。
  ★ 与**图片**一样，视频现在也会在 `fix()` 里真的动手了（`todo` 才处理，`manual` 一律不碰）。

  **ffmpeg 从哪来**（与 adb 同一套三段解析）：① 「设置 → 外部依赖 → ffmpeg 路径」**你手填**的完整路径
  （填了且文件在就用它）→ ② **程序内置**那份（`vendor/ffmpeg/ffmpeg.exe`，打包后在 `resources/ffmpeg/`）→
  ③ 系统 `PATH` 里的 `ffmpeg`。内置那份是 **GPL-3.0** 静态构建（`ffmpeg-static` b6.1.1 = ffmpeg 6.1.1-essentials），
  许可全文随包（`vendor/ffmpeg/LICENSE.txt`）；来源、字节数、md5 都记在 `vendor/README.md`，`uicheck` 会逐项互校。
  > ⚠️ **GPL 的边界**：只在自己公司内部装机使用没问题；**若要分发给客户/外部方**，请换成 LGPL 共享构建
  > （`vendor/README.md` §3 给了具体做法）。
  > ★ 具体到本仓库：`1.0.1` 正式版**不含** ffmpeg（只内置 adb + 中文输入法）；**`1.0.2` 起正式版开始含它（`1.0.3` 同样含）** —— 推送前要确认这份包的分发范围（内部装机 OK；要发给客户/外部方就换 LGPL 共享构建）。
- 发布单：`exceljs`。
- 模拟器驱动：**adb 已接入**（真实通道走 `src/main/services/adb.js`：推素材 + 媒体扫描 + `uiautomator dump` 解析 + 坐标点击/中文广播输入）；检测到设备走设备通道，否则走模拟通道，节奏与重试逻辑一致。
  **uiautomator2 尚未接入** —— 它仍是备选，但**理由变了**：以前以为是「相册缩略图块 adb 点不动」，
  2026-10-01 复测已推翻（点击是好的）。现在的真卡点是**素材进不了相册**，而 uiautomator2 **解决不了它** ——
  真要往下走，优先考虑「发布前重启一次模拟器」（详见「视频发布」一节）。
- **adb 从哪来（2026-10-01 起：随包内置）**：三段解析，优先级从高到低 ——
  ① 「设置 → 高级设置 → adb 路径」**你手填**的完整路径（填了且文件在就用它，程序**不会**拿内置的偷偷替掉）；
  ② **程序内置**的那份（`vendor/adb/` → 打包后 `resources/adb/adb.exe`，见 `vendor/README.md`）；
  ③ 系统 `PATH` 上的 `adb`（老用户既有的装法，不会被内置版本打断）。
  ⇒ **新同事装上就能用，不用自己去模拟器安装目录里翻 `adb.exe`**。留空这一格 = 自动（优先内置）。
  填了一个**不存在**的路径时会自动退回内置那份，并在检查结果里**明说**「你填的那个不存在」。
  自检的「技术详情」里会回显**现在用的是哪一个、是哪来的**。
  ★ **实测（2026-10-01）**：内置的官方 adb（`1.0.41 / 37.0.1-15733141`）与机器上已有的
  adb（MuMu 自带 `36.0.0-13206524`）**不会互相重启 adb 服务**，也不会抢设备连接。
  ★ **自检结果看着不对时，先看两件事**：① 「技术详情」里 `adb 路径` 那一行的**来源**；
  ② 「设备」那一栏的 serial 对不对
  （模拟器的网络桥接地址如 `127.0.0.1:16385` 和 adb 侧真正认到的 `emulator-5554` **经常不是同一个**，
  填错就每一项都失败，看着像设备坏了。serial 不对时自检会直接把「应该选哪个」写给你）。
