# 得物蓝V 素材发布工具 · Windows 桌面版

按 [PRD](https://c325414b53f748618ec865de0d865c08.app.workbuddy.host/#prd) 与原型页实现的 Electron 桌面应用，
面向 **Windows 10/11 x64**，把「素材整理 → 合规检查 → 文案生成 → 货号颜色校验 → 发布单 → 模拟器发布」六段流水线做成一个人当天能跑完的工具。

## 快速开始

```bat
npm install            :: 首次，会拉 Electron（国内可先 set ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/）
npm start              :: 本机运行（macOS/Linux 也能跑，用于开发自测）

:: 在任意平台打出 Windows 包（会先把 win32 预编译的 sharp 取下来，再交给 electron-builder）
npm run dist:win
```

已产出（`dist/`，本机实测交叉打包成功）：
- `得物蓝V素材发布工具-1.0.0-x64-win.exe` — NSIS 安装版（可改安装目录、建桌面/开始菜单快捷方式、卸载保留数据）

> **2026-10-01 起只产出安装版**：原先还有一个 `-便携版.exe`（免安装绿色版），已按「只保留正式版/测试版两条通道」
> 的要求从构建里去掉了（`build.win.target` 只剩 `nsis`）。★ 注意「便携版」是**打包格式**，和「正式版/测试版」
> 这两条**发布通道**不是一回事 —— 通道决定应用从哪里取更新，格式只决定你怎么装。
> `src/main/updater.js` 里那条「便携版不支持自动更新」的判断**保留着**（成本为零，用来兜住早期装过便携版的人）。

`dist/` 里现在**只会有一个 exe**（含 **win32-x64 版 sharp + libvips DLL**，在 `resources/app.asar.unpacked/node_modules/@img/sharp-win32-x64/lib/`），
所以 Windows 上 HEIC 转 JPG 可用，用户不需要装任何东西；macOS / Linux 版本的二进制已在打包时剔除。

> 交叉打包只验证了「能产出、结构正确」；**请务必在一台真实 Windows 上装一次再发出去**，
> 重点验：窗口按钮/拖动、HEIC 转换、长路径、以及卸载后 `%APPDATA%` 里的数据是否保留。

## 模块实现说明

> 以下规则已按 8/12 那场真机演示录屏（15:44，118 帧关键帧 OCR）对齐到现有工具的实际口径。
> **交接与真机口径见 [`docs/HANDOFF.md`](docs/HANDOFF.md)**：里面有真机界面文案原文、判定口径、命名样例、
> 发布日志原文、差异总表、待办与回归要求；逐帧 OCR 证据见 `docs/video-ocr-118frames.txt`。

1. **素材整理** — 先秒级出「待整理清单」（只读元数据），再后台建扁平副本。
   扁平名用连接符（默认 `_`）把原层级路径接起来（真机：`8124MT_UWG450159+灰色+达人昵称_1`）；
   **原素材完全不动** —— 不改名、不移动，只建副本（`flatten.touchOriginal` 可切回「改名加时间戳」）。
2. **合规检查** — 判断与处理分离：扫描出报告后只处理有问题的那批。规则对齐真机：
   图片**必须 JPG**、**≥1764 像素²（约 42×42）**、边长 **150~1500**、超限**自动等比缩放**（`autoScale`）、超 10MB 二分压缩；
   视频**按扩展名判 `.mp4`** 且 <600 秒，超时**只标红不裁剪**（裁剪会改变内容，可能被判非原创）；
   垃圾文件隔离到 `_rejected` 而非删除。另外支持真机的**「检查父目录」**：选一个父目录，里面每个子文件夹独立出报告并分组展示。
3. **文案生成** — 本地先定死每篇的标题格式（F01–F10 轮换）/ 叙事视角 / 话题组合（代码保证去重），模型只填空；并发按**路数均分**（不是「15 条/批」切批，避免尾批拖慢）；结构化输出容错解析（markdown 代码块、中文标点、多余逗号），单条重试不整批失败。未配置模型时用本地模板填空，流程一致。

   **人设提示词按品牌走**（2026-10-01 新增）：送进模型的 system 由两段拼成 —— **前段是品牌自己的「文案生成提示词」**（人设、口吻、卖点），**后段是程序追加的输出约束**（JSON 字段名 `title`/`body`、字数与极限词要求）。
   顺序不能反：后段是解析器依赖的硬约束，被品牌模板覆盖掉会导致整批 `JSON.parse` 失败，而现象看着像「模型不听话」。
   **没配提示词的品牌会被拦下**（拦在任务实例化之前，不写台账），不会拿别的品牌的口吻顶替，也不会静默回落到内置默认人设。
   入口是「文案生成 → 提示词配置」按钮弹出的弹窗（品牌名 / 两段提示词 / 是否启用 / 本次选用），详见下方「按品牌的文案提示词」一节。
4. **货号颜色校验** — 两种取色来源：本地商品池（CSV/TSV/JSON 导入）或**接口查询**（`verify.mode=api`，自带 endpoint + SKU APIKey）。
   判定文案对齐真机：「颜色匹配」/「**单色货号，颜色可空**」/「**多色货号须指定颜色（共 N 色：…）**」/「**货号 xxx 未查到颜色信息，请核对**」，
   且**接口查不到的货号仅告警不阻断**。额外用图片实际提出的主色反查目录里填的色名（目录写「冠军白」但图是黑的会被抓出来）。
   > 录屏里出现的 `dw.shike.tech/sku-color` 只是**别人的示例后台**，本工具不访问、不抓取它；要用它的导出表，按 CSV/JSON 导入即可。
5. **发布单** — exceljs 导出 26 列，校验未通过的整行标红；结果先追加写 `publish-log.jsonl`，
   一批结束再合并回写 Excel。**回写时若 Excel 被 WPS 占用，整批结果写入 `pending-results.json` 暂存，下次运行先补写再继续**
   （真机日志原话：「Excel 仍被占用，暂存保留，下次再试」）。
6. **模拟器发布** — 60–120 秒随机间隔（可配），失败可单独重跑。

   **两条通道，状态在界面上一眼可见**（发布页顶部会显示「真实设备通道 / 模拟通道」）：

   | | 真实通道（adb） | 模拟通道（mock） |
   | --- | --- | --- |
   | 触发条件 | `adb` 在 PATH、设备在线、得物包名识别到、uiautomator 可用 | 上述任一不满足 |
   | 做什么 | 推图到 `/sdcard/DCIM/Camera` + 触发媒体扫描 → `uiautomator dump` 抓界面 → 按定位表点击/输入 | 只跑流程：节奏、重试、jsonl 追加、Excel 回写 |
   | 失败 | 报真原因（找不到节点会列出当前可见文本）+ 自动存失败截图 | 随机失败，仅用于演练 |

   **真实通道必须先配 UI 定位表**：发布页「抓取页面结构」会 dump 当前界面 → 输出目录 `dumps/uiMap-<时间>.json`
   （按关键词猜的一套候选步骤，含 `${title}` `${body}` `${topic1..5}` `${sku}` 占位符）→ 改对后「导入 UI 定位表」。
   没配就点发布会**直接报错而不是报成功**。

   中文标题/正文依赖设备装了 [ADBKeyboard](https://github.com/senzhk/ADBKeyBoard)（走 `ADB_INPUT_TEXT` 广播）；
   没装的话自检会明确提示，输入会失败而不是静默发空文案。

   另外三项也按真机对齐：
   - **设备管理（一个设备 = 一个账号）**：多台雷电模拟器列表（`UR视频号 / UR女人号 / 斯凯奇穿搭 …`），可添加、删除、检测在线、选用；
   - **固定间隔 + 倒计时**：默认 60 秒，等待时显示「`按 60 秒间隔，57s 后执行`」，而不是静默等待；
   - **单条耗时与失败恢复**：每条记 `耗时 65.2s` 写进日志/表格；失败自动存截图并执行**回退**（返回键 + `uiMap.recover` 里配的「删除卡片」等动作），避免下一条起点被残留界面污染。
7. **多批次任务 · 报告导出 · 失败恢复动作**（对齐真机的任务列表 / 导出报告 / 重导出日志）：
   - **多批次并行**：任务实例化（每个 job 独立 id / 取消令牌 / 进度 / 日志标签），`copy.generate` 是批次级 ——
     点「选择素材目录并启动任务」，一个目录就是一个批次，可同时「处理中」；批次名形如 `7月第六批(已安排)_20260812_151245`。
     产物各写 `输出目录/batches/<批次>/copy.json`，互不覆盖。文案生成页与模拟器发布页都有「运行中的批次」表格：
     批次名 · 进度 · 已用时 · **查看详情**（按批次筛出该批次这一步的日志）/ **取消任务** / **全部取消**。
     取消是「当前步骤结束后停下」，不丢已产出的结果；被取消的任务统一报「任务已取消」，不会拿别的报错冒充。
   - **导出报告**（合规页）：`合规报告_<时间戳>.xlsx`（`汇总` 按子文件夹 + `明细` 全量）+ 同名 `.csv`（带 BOM），导出后自动定位文件。
   - **重导出日志**（发布页）：把 `publish-log.jsonl` 按批次导成可读的 `发布日志_<批次>_<时间戳>.log` 与 `.csv`，
     行格式对齐真机：`[V] 行 2 [图文] 发布完成，已回填时间 15:34:41（耗时 65.2s）`、`[X] 行 3 失败：找不到发布按钮（耗时 61.9s）`。
   - **失败恢复动作可编辑**（发布页「失败恢复动作」）：发布失败后要退回干净起点，否则下一条的界面会被残留页面污染。
     真机是「回退转发页」「删除卡片」这类动作，每个账号/版本都不一样，所以做成文本框可编辑（默认给一条示例，不用猜格式）。
     只认真正会被执行的 `tapText / tapId / tapDesc / wait`（返回键回退时本来就会先按，不用写）；
     写错 action、value 为空、wait 不是毫秒数，都会**报错并列出可用值**，不静默跳过 —— 跳过等于「以为回退了，其实没有」。
   - **导入「AI 内容报告」**（发布单页「导入 AI 内容报告」）：真机那条流水线的中间产物 —— 26 列 xlsx，
     `素材路径 / 素材来源 / 标题 / 文案 / 内容类型 / 好物1~9_货号+颜色`。按**列名**识别（列顺序无关，
     他们的报告和我们导出的发布单都能吃）；素材路径是**绝对路径**（如 `D:\卡宾\20260901`），
     表里没写就追问一次「这一批的素材目录」。**一个叶子文件夹 = 一条内容**，行数与叶子数不等会直接报错并说明，
     绝不猜着配；标题/文案空着由本地生成；发布结果回写报告的 **B 实际执行时间 / C 执行结果**两列
     （被 WPS 占用就整批暂存、下次导入或发布时先补写）。

## 登录与账号（默认开启）

打开就要求登录：没登录时界面被登录页盖住，**所有业务通道（读写配置、跑任务、选目录、开文件）在主进程侧都会被拦**，
不是「前端藏起来」那种假登录。

| 项 | 说明 |
| --- | --- |
| 账号库 | `%APPDATA%\dewu-bluev-publisher\auth.json`，和 `config.json` 分开存，不会被「设置 → 保存」覆盖 |
| 口令 | `crypto.scrypt` + 每账号随机盐，只存哈希，不存明文 |
| 出厂管理员 | `admin` / `BlueV@2026`（登录页会提示，进去后建议立刻改掉） |
| 记住登录 | 勾了写进 `auth.json`，7 天内免输入；不勾则关掉工具就要重新登录 |
| 防爆破 | 同一账号连错 6 次锁定 5 分钟（进程内计数，重启清零） |
| 权限 | 管理员能建/停用/删/重置其他账号，并给每个账号**分配品牌**；普通成员只能改自己的密码、只能用被分配到的品牌 |

### 发出去之前换成你自己的管理员

三选一，优先级从高到低：

1. 环境变量：`BLUEV_ADMIN_USER` / `BLUEV_ADMIN_PASS`（要在启动工具之前设好）
2. **推荐**：在 `%APPDATA%\dewu-bluev-publisher\` 放一个 `auth.seed.json`
   ```json
   { "username": "boss", "password": "Boss@8888" }
   ```
   首次启动会用它建管理员并**立即删除这个文件**（明文口令不留盘）
3. 什么都不做 → 用出厂 `admin / BlueV@2026`，登录后到「设置 → 账号与安全」改

要临时免登录开发：`BLUEV_NO_LOGIN=1 npm start`。

登录门有回归守护（改动这块之前先跑）：`./node_modules/.bin/electron tools/logintest.js` —— 59 项断言，
覆盖「未登录时业务通道在主进程侧就被拦」（不是前端藏起来）、口令只存 scrypt 哈希、记住登录重启免密、
普通成员看不到账号列表、停用后不能登录、不能停用/删自己、连错 6 次锁定 5 分钟。

> 加了登录之后 **需要重新打一次包**（`npm run dist:win`），旧安装包里没有这个功能。
> 卸载重装不会丢账号（NSIS `deleteAppDataOnUninstall=false`）。

## 品牌权限与按品牌统计（2026-10-01 新增）

品牌多、要分人管，所以品牌不是「一个全局设置」，而是**按账号分配的权限**。

| 项 | 说明 |
| --- | --- |
| 品牌存哪 | `config.json` 里的 `brands: [{id, name, enabled, promptWrite, promptFilter}]`；账号上存的是 **id 列表**（`auth.json` 的 `user.brands`）——**改品牌名不会把已分配的权限弄丢** |
| 谁能管品牌 | 只有管理员能增 / 删 / 改 / 停用（「设置 → 品牌管理」）；普通成员连注册表都改不了 |
| 管理员 | 默认可以用**全部启用中的品牌**，也能看到全部品牌的统计 |
| 普通成员 | 只能用被分配到的品牌；在「设置 → 账号管理」里逐个账号勾选 |
| 只分到 1 个品牌 | 自动选中，不必每次手动选（发布时不会漏标品牌） |
| 分到多个品牌 | **不替你挑** —— 没选就拦下并列出可选项（挑错了归属就是错的） |
| 产出类任务 | 文案生成 / 报告导入 / 发布单导出 / 发布 / 重跑 **必须有品牌归属** |
| 老记录 | 没有品牌的历史记录算「**未标品牌**」，品牌已被删除的算「**已删除的品牌**」；两者**各占一行、绝不并进任何品牌**，也绝不丢 |
| 统计维度 | 新增第 8 个页签「品牌统计」：各品牌的条数 / 成功失败 / 按天频次条 / 执行人，跨品牌汇总，执行人汇总；可切 7 / 30 / 90 天 |
| 执行日志 | 落盘到 `输出目录/run-log.jsonl`（原来 `logbus` 只在内存里留 500 条、重启即失，所以另存一份）；**故意不做自动轮转** |
| 导出 | 「导出统计」出 xlsx，4 个表：品牌汇总 / 按天频次 / 品牌×执行人 / 执行日志 |
| 文案提示词 | **按品牌各配一份**（不再是全局一个）。点「文案生成 → 提示词配置」弹出的弹窗里改：品牌名 / 两段提示词 / 是否启用 / 本次选用 |
| 没配提示词 | 跑「文案生成」**直接拦下**，不拿别的品牌的口吻顶替；拦在任务实例化之前，台账里不会留下没跑成的假记录 |
| 谁能改提示词 | 管理员、以及**拿到该品牌的成员**都能改（写文案的是运营，不该每次都找管理员）；但品牌名 / 启用 / 删除仍只归管理员 |

> ⚠️ **本机权限不是安全边界。** `auth.json` / `config.json` 就在本机 `%APPDATA%` 下，
> 能进这台机器的人可以直接改它们。这套权限的实际作用是**防误操作 + 让统计能对账**，
> 不是防内部的恶意越权；真要隔离得上服务端（当前没有服务端）。

### 文案提示词（2026-10-01 新增）

原先「设置 → 内容与校验」里有 `copy.promptWrite` / `copy.promptFilter` 两个全局输入框，它们
**从来没被任何代码读过** —— 填了不生效。这就是「点了提示词配置看不懂」的根源：界面在骗人。

现在改成按品牌各配一份，而且**真的进模型**：

- **入口**：「文案生成」页的「提示词配置」按钮，或「设置 → 文案提示词」——点开是个弹窗（不是跳页）。
- **弹窗里**：每个品牌一行（品牌名 / 启用状态 / 配没配 / 摘要），点进去编辑四样：
  **品牌名**、**文案生成提示词**、**筛选排序提示词**、**是否启用该品牌**、**本次选用**。
- **拼装顺序**：品牌模板放在 system 的**开头**（角色、调性、写什么）；JSON 字段名、标题字数上限这些
  **解析器依赖的硬约束由程序追加在后面**，不用写进模板 —— 漏写一句就会让整批 `JSON.parse` 失败，
  而现象看起来像「模型不听话」。
- **没配就拦下**：拦两道 —— `jobs.run` 在任务实例化之前拦（不写台账），`copywriter.generate` 里再兜一道
  （防有人直接 require 模块调用）。没有品牌归属的场合（免登录自检 / 测试直调）不套这一层。
- ⚠️ 如实说：「筛选排序提示词」**当前版本还没接进任何流程**（工具里没有素材筛选 / 排序这一步），
  只是先按品牌存着。弹窗里也这么标着 —— 别以为配了就有效果。
- 单条提示词上限 **4000 字**（粘贴超长内容会截断而不是整条保存失败）；`\r\n` 会归一成 `\n`。

## 应用更新（自动更新 · 正式版 / 测试版两条通道）

装好的**安装版**（`…-x64-win.exe`）启动约 20 秒后会自己查一次更新源。发现新版本会告诉你，但
**不会自己下载、更不会自己重启** —— 这两步都要你在「设置 → 应用更新」里点。

| 项 | 说明 |
| --- | --- |
| 更新源 | 腾讯云 COS 的**桶根目录**（地址在 `package.json` 的 `build.publish`，**编译进包**） |
| 通道 | **正式版 / 测试版两条，共用同一个安装包**。通道名只决定读源上哪个清单文件：正式版读 `latest.yml`、测试版读 `beta.yml` |
| 怎么切 | 「设置 → 应用更新 → 更新通道」点一下，**不用重装**（源地址不变，只是换个文件名去读）。偏好存在 `config.json` 的 `update.channel`，重启后仍然生效 |
| 检查时机 | 启动后约 20 秒自检**一次**（不是定时轮询），以及手动点「检查更新」 |
| 下载 | **手动**。包有 85 MB（实测 89,151,294 B），不替用户决定占带宽 |
| 安装 | **手动**；而且**有任务在跑时会拦住** —— 重启会把跑一半的发布掐断，且没有回滚 |
| 不支持的情况 | **开发模式**（`npm start`）不检查；**如果哪天又产出便携版，它也装不了**（每次启动自解压到临时目录，没法就地替换）。这些情况「应用更新」一栏会**如实写不可用**，不摆点了没反应的按钮 |
| 换源地址的代价 | 地址编译进包 ⇒ 改了等于所有已装客户端全部失联，只能重发一次包。★ **但切通道不受影响** —— 通道名不是地址 |

> ★★ **「换源地址」和「切通道」是两件事，别混**：
> 源地址编译在 `resources/app-update.yml` 里，运行时**改不了也不许改**（electron-updater 官方就不给 `setFeedURL`）；
> 而**通道名**只决定「读哪个清单文件」，electron-updater 有公开的 `set channel()` 支持运行时改。
> ⇒ 测试版是**显式 opt-in**：正式版用户读的一直是 `latest.yml`，不会被测试包波及。
>
> ★ **关于降级**（从测试版切回正式版会用到）：正式版的版本号本来就更小，所以
> 「测试版 → 正式版」那一次会**允许降级**（否则切了也回不去）；反过来**不允许** ——
> 平时一直开着降级的话，源上被人放个旧包，正式版用户就会被**悄悄降下去**。

### 发版流程（打包机上）

```bash
# 1) 先改 package.json 的 version
#    不涨版本号会「同名覆盖」，而且 electron-updater 按版本号比较，客户端会直接判「没有新版本」
#    测试版的版本号建议带预发布段，例如 1.0.1-beta.1 —— 这样「换成正式版 1.0.1」算升级而不是降级
# 2) 发正式版：
npm run dist:release
#    发测试版（同一个包，只是把清单传成 beta.yml）：
npm run dist:release:beta
```

`dist:release` = 打包（`dist:win`）+ 上传（`release:stable`）；`dist:release:beta` = 打包 + `release:beta`。
上传的东西是 electron-builder **不会代传**的那三样：安装包 exe、清单文件、`.blockmap`
（generic 提供者必须自己上传，漏了就是「包打了但客户端永远收不到」）。

**两条通道的文件放在同一个目录**，只有清单文件的名字不同：正式版 `latest.yml`、测试版 `beta.yml`。
客户端按自己的通道去读对应的那份 —— 所以正式版和测试版可以**同时存在**，互不干扰。

凭据**不进仓库**，放打包机上的 `.env`（已在 `.gitignore`；`node_modules/` 外、仓库根或 `tools/` 下都认）：

```
COS_SECRET_ID=…
COS_SECRET_KEY=…
COS_BUCKET=dewu-bluev-release-1499238579
COS_REGION=ap-guangzhou
# COS_DOMAIN 可选，不填就按 https://<bucket>.cos.<region>.myqcloud.com 拼
```

只看要传什么、不真传：`node tools/upload-release.js --channel stable --dry-run`（换 `beta` 看测试版）。

```
通道      stable
版本      1.0.0（package.json 1.0.0）
目标      https://dewu-bluev-release-1499238579.cos.ap-guangzhou.myqcloud.com
要传的文件：
  安装包    得物蓝V素材发布工具-1.0.0-x64-win.exe   85.0 MB
  版本清单  latest.yml   388 B
  增量块图  得物蓝V素材发布工具-1.0.0-x64-win.exe.blockmap   91.3 KB

--dry-run：什么都没传。
```

（`--channel beta` 时最后一行变成 `版本清单  beta.yml`，其余一样 —— **两条通道都在桶根，不是两个子目录**。）

上传脚本会挡住三种「传了等于出事」：**dist 里的版本号和 package.json 对不上**（说明 dist 是旧包）、
**源上已经是同一个版本号**（要覆盖得显式加 `--force`）、**要传的比源上还低**（往回发；
已升级的客户端收不到，而且正式版通道允许降级会把用户真的降下去）。它**只传安装版**，便携版连列都不会列进去。

### 怎么确认「源地址配对了」（实测过，不用猜）

打完包去这两个地方看一眼，对上就是对的 —— 地址写错的话，应用只会一直说「已是最新」，
**不会报错**，所以这一眼必须看：

```bash
cat dist/win-unpacked/resources/app-update.yml      # 编译进包、在 asar 外，electron-updater 只认它
cat dist/latest.yml                                 # 客户端按这里的 path 去下载，对不上就是 404
```

`app-update.yml` 长这样（**2026-10-01 实测生成**，注意 `url` 是**桶根**、`channel` 是正式版的默认值）：

```yaml
provider: generic
url: https://dewu-bluev-release-1499238579.cos.ap-guangzhou.myqcloud.com/
channel: latest
updaterCacheDirName: dewu-bluev-publisher-updater
```

> - ⚠️ **别把「便携版」理解成第三个版本**：它是打包格式，和「正式版/测试版」这两条发布通道不是一回事。
>   2026-10-01 起构建里已不再产出便携版（`build.win.target` 只剩 `nsis`），`dist/` 只会有一个 exe。
> - ℹ️ 测试版通道**已经接通**（不再只是"脚本摆着"）：`npm run dist:release:beta` 会把清单传成
>   `beta.yml`，用户在「设置 → 应用更新」里点「测试版」就会去读它。`app-update.yml` 里的
>   `channel: latest` 只是默认值 —— 用户选了测试版之后，运行时会把 channel 覆盖成 `beta`。

### 装完之后怎么验收（这一步只能在你的机器上做）

★ **为什么打包机上做不了**：打包机只有 `dist/win-unpacked/` 这个**绿色解包目录**，
自动更新只对**装出来的安装版**生效（解包目录跑起来判定就是「未打包」，更新面板会如实写不可用）。
所以「真的能更新」这件事，必须在**装过一次的机器**上验。

```bash
# ① 在打包机上把当前版本发到源上（桶为空时尤其要做，否则客户端点检查更新是 404）
npm run dist:release            # 正式版；dist 已有包时也可只跑 npm run release:stable

# ② 在验收机上装一次，双击刚生成的安装包
#    dist\得物蓝V素材发布工具-1.0.0-x64-win.exe
#    安装器是「按用户安装 + 可改目录」，不需要管理员；卸载不删 %APPDATA% 里的数据

# ③ 打开应用 → 设置 → 应用更新，应当看到：
#    当前版本 1.0.0 · 通道「正式版」 · 状态「未检查」

# ④ 回打包机，改 package.json 的 version 成 1.0.1，再发一次
npm run dist:release

# ⑤ 回验收机，点「检查更新」→ 出现「有新版本 1.0.1」→ 点「下载更新」→ 进度条走完
#    → 点「立即安装并重启」→ 重启后「当前版本」应当真的变成 1.0.1
```

判据就一条：**重启后「当前版本」这个数字真的变了**。数字没变 = 这条链没通，
按顺序查三处：`dist/win-unpacked/resources/app-update.yml` 的 `url`、源上 `latest.yml` 里的 `path`、
以及应用里「应用更新」栏给出的**具体报错文案**（这一栏不会只显示「已是最新」了事）。

> - ⚠️ **版本号不涨 = 什么都没发生**。electron-updater 是按版本号比较的，源上放个同版本号的新包，
>   客户端只会判「没有新版本」——这是最容易把人骗过去的一种假成功。
> - ⚠️ **别拿解包目录（`win-unpacked\*.exe`）当验收对象**，它永远说「不可用」。
> - ℹ️ 验收测试版那条通道：验收机上先点「更新通道 → 测试版」，再按上面 ④⑤ 走，只是第 ④ 步改成
>   `npm run dist:release:beta`（版本号建议写成 `1.0.1-beta.1`）。
